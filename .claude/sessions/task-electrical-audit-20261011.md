## 一、架构合理性评估

### 1.1 系统分层

**当前架构**（校赛验证通过）：
```
视觉子系统（MaixCAM）
    ↓ UART
树莓派控制链（Python）
    ↓ UART2（115200）
STM32固件层（协议网关 + 运动控制）
    ↓ PWM/STEP/DIR
执行器（舵机/步进电机/挡板）
```

**合理性**：✅ **基本合理**
- 视觉与运动解耦（MaixCAM独立识别）
- 树莓派做协议翻译+显示+日志（发挥Linux优势）
- STM32做实时控制（100µs级响应）

**不足**：
- 树莓派与STM32间**无心跳机制**（35秒在飞钟是Pi单边超时，STM32不知道）
- 协议命令字有冲突（0x20同时用于`BARRIER_READY`和调参命令）

### 1.2 方案B的职责划分

**电控职责边界**（清晰）：
- ✅ 运动规划（步进轨迹、加速度控制）
- ✅ 协议编解码（12字节`ITEM_TASK`）
- ✅ 安全保护（位置失效门、15秒窗、堵转检测缺失）
- ✅ 硬件驱动（GPIO/PWM/UART/TIM）

**不承担**（合理）：
- 视觉识别（MaixCAM负责）
- 件高标定（视觉侧负责，电控只执行）
- 机械设计（机械组负责）

### 1.3 可维护性

**优点**：
- 代码模块化好（`ec_app` / `ec_protocol_gateway` / `ec_axis_driver` / `ec_motion_plan`分离）
- 单元测试覆盖关键路径（`test_control_flow_guard.py`）
- 有完整接口契约（`interface-contract.md` V0.9）

**问题**：
- ⚠️ 主机测试与固件版本不匹配（39a72b45修复"对齐单轴架构"，说明曾经不一致）
- ⚠️ 死代码未及时清理（PB10迁移失败后，整条链还在）
- ⚠️ `.ioc`与代码长期不同步（定时炸弹）

### 1.4 扩展性

**已预留接口**：
- ✅ ToF传感器接口（Pi侧GPIO/I2C）
- ✅ TMC2209 UART接口（PA9/PA10空闲）
- ✅ 夹爪改造（舵机脉宽可重新标定）

**不足**：
- ⚠️ 无编码器接口预留（若要加闭环步进需改固件）
- ⚠️ 无限位开关接口（若要加硬件限位需改引脚分配）

**首版缺陷**（已修复但未验证）：
```c
// 首版：进FAULT_LOCK就失效 → 上电POST故障也失效 → 永久拒绝运动
if (t->state == EC_STATE_FAULT_LOCK) {
    position_valid = false;  // ← 过严
}
```

**改后逻辑**（`ec_app.c:291-295`）：
```c
// 只有"上一状态是EXECUTING"或"轴正在MOVING/GRIPPING"才失效
if ((last_app_state == EC_STATE_EXECUTING) ||
    (ec_axis_driver_state() == EC_AXIS_STATE_MOVING) ||
    (ec_axis_driver_state() == EC_AXIS_STATE_GRIPPING)) {
    position_valid = false;
}
```

**仍存在的边界条件**：
- ⚠️ `WAIT_DISPLAY_ACK`期间超时：运动已完成、轴已停稳，但`last_app_state`可能仍是`EXECUTING` → 误判位置失效
- ✅ 恢复路径：断电 → 手推回HOME → 上电（与"上电位置=原点"纪律一致）

**建议改进**：
```c
// 收紧判据：只在轴真正运动时失效
ec_axis_state_t ax_state = ec_axis_driver_state();
if ((ax_state == EC_AXIS_STATE_MOVING || ax_state == EC_AXIS_STATE_GRIPPING) &&
    t->state == EC_STATE_FAULT_LOCK) {
    position_valid = false;
}
```

## 四、性能优化建议

### 4.1 15秒窗口余量

**真实值**：**0.93~1.0秒**（不是文档说的1.2~1.8秒）

**证据**：
- `15秒预算分析-DSH-2026-09-19.md:161-173`实测：
  - MOTION_DONE时刻：12.9s
  - DISPLAY_ACK发出：+1.163s
  - **整轮窗口用量**：14.06s
  - **真实余量**：15.0 - 14.06 = **0.94s**

**关键发现**：
- ❌ 窗口检查覆盖`WAIT_DISPLAY_ACK`状态（`ec_app.c:445-449`）
- ❌ `MOTION_DONE`不关窗（`:518-525`注释原文"deliberately does NOT clear"）
- ❌ 要等第一帧有效`DISPLAY_ACK`才关窗

**风险**：
- 若采纳"降频到4000Hz保守"方案 → 整轮15.26s → **必然超时**

**优化路径**（按顺序）：
1. 主频168MHz（已改待烧） → 开方耗时降至约1µs
2. 巡航5000→6250Hz（整除档ARR=15） → 单件降至约10.4s
3. 加速率10000→20000Hz/s
4. 同向逼近（先走目标−3mm再正向走3mm） → 消除回程差

**验收标准**：
- 单件<11s
- 24件连跑余量>5s

### 4.2 运动速度

**当前**：
- 巡航：5000Hz（已验证不丢步）
- 加速率：10000Hz/s
- 单件：约13s

**瓶颈**：
- 开方耗时：16MHz下10.5µs，占100µs预算的10%
- 回程差：1~2.5mm/次换向 × 6次 = 6~15mm/件

**提速方案**：
- ✅ 主频168MHz → 开方降至约1µs → 省约9.5µs/步 × 数千步 → **省约0.5~1s**
- ✅ 巡航6250Hz → 省约**2.6s**
- ✅ 加速20000Hz/s → 省约**0.9s**

### 4.3 协议超时

**15秒窗**：
- ✅ 滚动失活窗（正确理解赛规）
- ✅ 运动期间续命（每当X/Y移动完成）
- ⚠️ 进展续命已开启（`progress_source_enabled=true`），但文档说"待HIL-PROGRESS-001验证"

**35秒在飞钟**：
- ⚠️ Pi侧单边超时，STM32不知道
- ⚠️ 若STM32真静默20秒 → 屏幕停20秒 → 可能违反15秒规则

#### 🔴-4 位置失效门首版过严（已改但未验证）

**问题描述**：
- 首版：进`FAULT_LOCK`就失效 → 上电阶段POST故障也失效 → 永久拒绝运动
- 实测：`ITEM_TASK`后50ms直接报`POSITION_UNREACHABLE` → Pi侧"result arrived in wrong state"
- 已改为：只有"上一状态是EXECUTING"或"轴正在MOVING/GRIPPING"才失效（`ec_app.c:291-295`）

**影响范围**：
- 首版会导致一上电就无法工作
- 现版语义正确，但未上电验证

**仍存在的边界条件**：
- ⚠️ `WAIT_DISPLAY_ACK`期间超时：运动已完成、轴已停稳，但`last_app_state`可能仍是`EXECUTING` → **误判位置失效**

**建议改进**：
```c
// 收紧判据：只在轴真正运动时失效
ec_axis_state_t ax_state = ec_axis_driver_state();
if ((ax_state == EC_AXIS_STATE_MOVING || ax_state == EC_AXIS_STATE_GRIPPING) &&
    t->state == EC_STATE_FAULT_LOCK) {
    position_valid = false;
}
```

**验证方法**：
- 正常工况：POST成功 → 首件运动正常
- 故障工况：运动中急停 → 位置失效 → 拒绝后续运动 → 断电复位 → 恢复
