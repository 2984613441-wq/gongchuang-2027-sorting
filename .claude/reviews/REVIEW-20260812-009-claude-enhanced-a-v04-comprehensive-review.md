## 7. P1发现（增强可信度和完整性）

### P1-001：缺少跨层集成测试

**事实**：
- 协议层输出`DisplayAckReceived`事件
- 状态机消费`DisplayAckReceived`事件
- 两层分别测试通过
- 但无端到端测试验证：协议解码→上下文验证→状态机消费的完整路径

**推断**：
- 当前测试可能存在"各层独立正确，集成错接"的风险
- 特别是`DisplayAckReceived.crc_match`的语义：
  - 协议层通过`DisplayAckContextValidator.to_domain_event()`生成
  - 状态机在`_display_ack()`中检查`event.crc_match`
  - 但无测试验证这两层的接口契约

**证据**：
- 状态机测试直接构造`DisplayAckReceived`（state_machine测试文件未找到协议层调用）
- 协议测试验证`DisplayAckContextValidator`（protocol测试文件未调用状态机）
- 缺少`协议→状态机→fake HAL`的端到端测试

**建议**：
补充集成测试，验证：
1. 合法`DISPLAY_ACK`帧 → 协议解码 → 上下文验证 → `DisplayAckReceived(crc_match=True)` → 状态机消费 → 放行下一件
2. CRC错误帧 → 协议拒绝 → 状态机不消费
3. 目标序号错误 → 上下文验证拒绝 → 状态机不放行
4. 重复ACK → 状态机重发缓存响应

**风险等级**：中等（测试覆盖缺口，但职责边界清晰）

---

### P1-002：无界去重缓存未设计容量和淘汰策略

**事实**：
- 状态机维护`accepted_tasks: dict[tuple[int, int], ItemTaskReceived]`（core.py:145）
- 状态机维护`consumed_display_acks: set[tuple[int, int]]`（core.py:146）
- 两个容器均无界，理论上可无限增长
- `ManualReset`时会清空（core.py:319-320）

**推断**：
- 主机测试中容器大小可控
- 真实STM32固件中：
  - 单轮可能处理数十个任务
  - 内存有限（STM32F407典型SRAM 192KB）
  - 需要固定容量和淘汰策略

**证据**：
- TASK-003第12节已记录："`accepted_tasks`在主机骨架中仍无界；正式固件前需冻结容量、淘汰和跨轮策略"
- REVIEW-008也标记为"待确认与阻塞"

**建议**：
正式STM32固件前，必须设计：
1. 容量上限（如64或128个任务）
2. 淘汰策略（FIFO、LRU或固定窗口）
3. 容量耗尽时的行为（拒绝新任务或覆盖最旧记录）
4. 跨轮清空的时机（新轮开始时自动清空）

**风险等级**：中等（主机测试不受影响，但阻塞实机长时间运行）

---

### P1-003：掉电恢复未设计

**事实**：
- V0.4规则明确："只有经验证的新轮次初始化同时清零；重连、重传、超时、通信恢复和同轮单节点重启不得自行清零"（接口契约V0.4第6.1节第6条）
- 当前Python实现未包含持久化或恢复逻辑
- 掉电后：
  - `success_count`会丢失
  - `accepted_tasks`和`consumed_display_acks`会丢失
  - 无法证明两端上下文一致

**推断**：
- 主机测试假设无掉电
- 真实比赛中，掉电/重启可能发生
- 如无持久化，重启后无法安全续跑

**证据**：
- 接口契约V0.4第6.1节第6条明确要求："若任一节点不能证明其轮次与计数上下文和另一端一致，禁止继续接件并进入待人工恢复状态"
- 当前代码无持久化实现

**建议**：
正式STM32固件和树莓派代码前，必须设计：
1. 哪些状态需要持久化（task_id、success_count、去重记录）
2. 持久化位置（STM32的FLASH、树莓派的文件系统）
3. 恢复时的一致性检查（跨节点握手验证）
4. 无法恢复时的安全行为（进入FAULT_LOCK，等待人工复位）

**风险等级**：中等（主机测试不受影响，但阻塞实机可靠性）

### P2-003：状态机不保存期望`target_seq`

**事实**：
- 状态机在`VALIDATE_TASK`接受任务后，保存`active_task: ItemTaskReceived`
- `_display_ack()`中检查`event.task_id != self.context.active_task.task_id`（core.py:291）
- 但未显式检查`event.target_seq`是否匹配`active_task.target`

**推断**：
- 当前实现依赖上游`DisplayAckContextValidator`已经验证`target_seq`
- 如果上游验证失败，`event.crc_match`为False，状态机会拒绝（core.py:290）
- 但状态机层自身无独立的`target_seq`期望字段

**证据**：
- `ItemTaskReceived`包含`target: str`（core.py:69），但`target`是字符串，非结构化字段
- `DisplayAckReceived`包含`target_seq: int`（protocol/types.py:54-58）
- 跨层映射依赖协议层正确解析

**建议**：
增强跨层集成测试（见P1-001），验证：
1. 协议层正确解析`target_seq`
2. 上下文验证器正确比较`target_seq`
3. 状态机正确检查`crc_match`

或者，状态机显式保存期望`target_seq`：
```python
active_task_target_seq: int | None = None
```

**风险等级**：低（职责边界清晰，但跨层测试缺失）
