# 生产路径主机复现（Codex，2026-09-18）

## 1. 结论先行

对指定输入 `HOME=(0,0)`、`PICK=(12.5,5.4) mm`、`PLACE=(5.0,5.0) mm`、`target_seq=4`，当前生产规划器和执行器在主机侧 HAL 模型中**不会在运动过程中 fault**：8 个程序步全部完成，`fault_step=NONE`，轴结果为 `EC_AXIS_RESULT_OK`，并各发送 1 次 `MOTION_DONE` 和 `ITEM_RESULT`。主机原始输出为：

```text
END elapsed=3463 ms state=10 axis_state=3 axis_result=0 progress=8 updates=2864 motion_done=1 item_result=1
PRODUCTION_INPUT_RESULT completed_steps=8 fault_step=NONE axis_result=EC_AXIS_RESULT_OK motion_done=1
PASS (host HAL model; no hardware claim)
```

原始输出：`docs/reports/motion-completion-20260918/production_input.log`。测试断言对应 `电控/firmware/stm32f407_m144z/tests/test_motion_completion.c:274-280`；`state=10` 是 `EC_STATE_WAIT_DISPLAY_ACK`（`电控/stm32_logic/include/ec_state_machine.h:9-22`），`axis_state=3` 是 `EC_AXIS_STATE_DONE`、`axis_result=0` 是 `EC_AXIS_RESULT_OK`（`电控/firmware/stm32f407_m144z/App/Inc/ec_axis_driver.h:78-94`）。

因此，本次精确输入下的故障**不能在当前生产运动规划/执行逻辑的主机模型中复现**。这排除了“确定性的步序列、步数、200→2000→200 Hz 速度规划或单步 move timeout 预算不足”作为现有证据支持的根因；下一步应按**硬件相关/板级集成与部署环境**排查。这里的“硬件相关”包括定时器/中断/GPIO AF/安全输入/供电复位/UART/烧录镜像一致性等软硬件交界，不等于已经证明某一个硬件元件损坏。

## 4. 逐步标称耗时与 move timeout

### 4.1 两套数值的来源不能混用

实际 counted move 启动时，无条件尝试 `ec_step_profile_plan(profile, steps, 200, 2000, 200, 5000, 5000)`；只有规划失败时才退回调用者传入的恒定频率（`电控/firmware/stm32f407_m144z/App/Src/ec_board_stm32.c:160-190`）。速度曲线用 `f²=f0²+2a·step` 计算加减速步数；短程不足以达到 2000 Hz 时自动降低峰值形成三角曲线（`电控/stm32_logic/src/ec_step_profile.c:49-151,154-178`）。TIM update ISR 每步重新装载下一步 ARR（`电控/firmware/stm32f407_m144z/App/Src/ec_board_stm32.c:484-495`）。

因此下表的“标称耗时”按 100 kHz step timer 逐步累加 `(ARR+1)` 得到，而不是按 500 Hz 恒速估计；计算实现见 `电控/firmware/stm32f407_m144z/tests/test_motion_completion.c:148-187`，100 kHz 假设来自 `电控/firmware/stm32f407_m144z/App/Src/ec_board_stm32.c:25-28`。

另一方面，**move timeout 的代码公式仍然是**：

```text
move_timeout_ms = steps * 1000 / 500 + 1000
```

公式见 `电控/firmware/stm32f407_m144z/App/Src/ec_axis_driver.c:72-78`；其中 `500` 和 `1000 ms` 分别来自 `电控/firmware/stm32f407_m144z/App/Inc/ec_axis_driver.h:38,75-76`。MOVE 启动时保存该 deadline（`电控/firmware/stm32f407_m144z/App/Src/ec_axis_driver.c:251-265`）；执行器先消费自然完成 latch，只有没有完成且达到 deadline 才报 `EC_AXIS_RESULT_TIMEOUT`（`电控/firmware/stm32f407_m144z/App/Src/ec_axis_driver.c:368-388`）。

## 5. 主机模型的最终状态

1. **是否走完 8 步：是。** `progress=8`，断言要求 `ec_axis_driver_progress()==8`（原始输出；`电控/firmware/stm32f407_m144z/tests/test_motion_completion.c:274-280`）。
2. **第几步 fault：没有运动步 fault。** 原始输出明确为 `fault_step=NONE`。
3. **result：`EC_AXIS_RESULT_OK`。** 原始输出为 `axis_result=0` / `EC_AXIS_RESULT_OK`，枚举映射见 `电控/firmware/stm32f407_m144z/App/Inc/ec_axis_driver.h:78-86`。
4. **是否发 MOTION_DONE：是，1 次。** 原始输出为 `motion_done=1`，随后真实应用路径在轴状态 DONE 时注入 `MOTION_DONE` 和成功的 item result（`电控/firmware/stm32f407_m144z/App/Src/ec_app.c:491-529`）。

测试在运动完成后故意不提供 `DISPLAY_ACK`，所以它随后在**运动起点后的 15.000 s**进入 `FAULT_LOCK`：

```text
WATCHDOG no DISPLAY_ACK: WAIT_DISPLAY_ACK at 14999 ms, FAULT_LOCK at 15000 ms
```

这是 `test_motion_completion.c:287-297` 明确验证的 15 s watchdog 行为，对应生产代码的 15000 ms 条件（`电控/firmware/stm32f407_m144z/App/Src/ec_app.c:544-564`）。它发生在已经发出 `MOTION_DONE` 之后，因而**不是**实机所述“受理后 5 秒内 FAULT_LOCK 且从不发 MOTION_DONE”的同一个故障。

## 6. 主机通过、实机仍 fault 的差异清单

| 主机模型未覆盖项 | 代码/测试证据 | 如何造成“主机通过、实机 fault” |
|---|---|---|
| TIM update 中断延迟、合并或丢失 | 主机精确按 ARR 逐次调用 `ec_step_port_on_timer_period`（`test_motion_completion.c:84-118`）；生产计数每次 ISR 只减 1，并在归零时发布 completion latch（`ec_board_stm32.c:484-506`）。 | 硬件 PWM 可以已经让机构运动，但若 update IRQ 未被逐脉冲可靠处理，软件计数/latch 会落后或不产生；执行器到 deadline 后报 `EC_AXIS_RESULT_TIMEOUT` 并进入轴 fault（`ec_axis_driver.c:368-388`），上层把轴 fault 转为安全锁定（`ec_app.c:530-541`）。这是“机构确实动了”与“无 MOTION_DONE”可同时成立的一条路径。 |
| 真实定时器时钟、PSC、ARR preload 和 IRQ 配置 | 模型把一个 timer tick 固定为 10 μs（`test_motion_completion.c:48-59,84-118`）；生产代码假设 step timer 为 100 kHz，并明确说明该值与系统时钟/PSC 耦合（`ec_board_stm32.c:25-28`）。 | 若真实计数时钟或 ARR 生效时机不同，运动实际耗时会偏离模型；偏慢到跨过按 500 Hz 计算的 deadline 时会报 timeout。 |
| 真实 STEP 引脚 AF/定时器通道 | 主机只有假 GPIO/假 TIM handle，不执行真实 AF 电气验证（`test_motion_completion.c:16-21,42-59`）；当前源码映射为 PB6/TIM4_CH1 和 PC6/TIM8_CH1（`Core/Src/stm32f4xx_hal_msp.c:227-263`）。 | 源码映射正确不等于已烧录镜像、初始化顺序和板上复用状态都正确。某轴 AF/通道/IRQ 配置异常时，HAL 模型仍会生成理想 update；实机则可能只部分运动、无正确 completion，最终 timeout。 |

| ESTOP、许可输入与输入噪声 | 主机把假 GPIO 输入固定为稳定值（`test_motion_completion.c:234`）；真实定时器 ISR 对原始 active-low inhibit 做无消抖快停并置 abort latch（`ec_board_stm32.c:471-480`），应用还检查 ESTOP/电源许可（`ec_app.c:451-485`）。 | 瞬态噪声、接触抖动或许可丢失可在机构已开始移动后触发 abort/紧急停机；执行器把 inhibit/abort 转为 `EC_AXIS_RESULT_ABORTED`（`ec_axis_driver.c:354-366`），上层进入 `FAULT_LOCK`。 |

## 7. 判定

**本次二选一判定：硬件相关/板级集成与部署环境，暂不支持“当前生产运动路径的软件逻辑问题”。**

判定依据如下：

1. 当前生产规划器对精确输入生成的 8 步内容、方向、步数和舵机脉宽均有字面断言，主机运行全部满足（`test_motion_completion.c:189-218`；原始输出 `PROGRAM step=0..7`）。
2. 标称总时长为 3.46064 s，每个 MOVE 的 profile 标称耗时都明显小于其独立 move timeout；计算使用生产端 200→2000→200 Hz 限幅曲线而非 500 Hz 恒速（`ec_board_stm32.c:160-190`；原始输出 `BUDGET step=0..7`）。
3. 真实应用/执行器代码在主机模型中完成 8 步、得到 `EC_AXIS_RESULT_OK`，并发送 `MOTION_DONE`；精确输出和断言见 `production_input.log`、`test_motion_completion.c:269-280`。
4. 主机唯一后续锁定是刻意不发 `DISPLAY_ACK` 后的 15 s watchdog，时间和事件顺序均与实机“5 秒内、从不发 MOTION_DONE”不同（`test_motion_completion.c:287-297`；`ec_app.c:544-564`）。
