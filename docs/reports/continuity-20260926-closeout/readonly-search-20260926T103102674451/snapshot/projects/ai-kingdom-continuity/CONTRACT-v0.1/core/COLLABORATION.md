# 五节点共享目录与协作协议草案 v0.1

## 前提

Claude、Codex、DeepSeek、Zcode、Grok 是平行节点；各自运行帝国机制，不存在替其他节点代言或裁决的常驻中心 AI。用户保留最终裁决权。跨节点协作采用文件交接和用户或外部流程转交；未读取、未执行、未获得回复，必须如实记录。共享目录是通信和证据载体，不等于让五个模型共享会话上下文、凭据或写入权限。

## 目录布局

```text
ai-kingdom/
  README.md                       # 目录导航、文件权威性、启动协议
  core/                           # 共享规则与数据契约，带版本号
    RULES.md
    GOVERNANCE.md
    COLLABORATION.md
    CAPABILITIES.md
    HANDOFF-SCHEMA.md
  projects/<project-id>/
    INDEX.md                      # 项目入口；指向当前状态和待读任务
    SHARED-UNDERSTANDING.md       # 问题定义、双方共同理解、纠正及边界
    STATE.md                      # 当前状态、已完成/未验证/下一步
    DECISIONS.md                  # 已敲定内容与出处、版本
    WORKING-NOTES.md              # 未正式固化的结论和重要讨论
    PARAMETERS.yaml              # 精确值、单位、来源、生效范围
    EVIDENCE.md                   # 验证证据、反证、未知项
    tasks/<task-id>/
      REQUEST.md                  # 任务目标、受理人、输入版本、交付条件
      responses/<node>.md         # 各节点仅写自己的回应
      RESOLUTION.md               # 用户裁决、采纳与未采纳意见
    handoffs/<handoff-id>.md       # 新对话/压缩/跨节点的恢复快照
    events.jsonl                  # 追加式事件记录；非实时消息总线
  nodes/<node>/
    START.md                      # 该节点启动入口；指向共享 core 与项目 INDEX
    ADAPTER.md                    # 路径映射、可用工具、局限和验证状态
    inbox/                        # 发给该节点的任务引用或副本
    outbox/                       # 该节点产生、待人工转交的交接
```

## 启动、恢复、交接

1. 每个节点从自己的 `nodes/<node>/START.md` 启动，先核对 `core` 的版本，再读项目 `INDEX.md`、`SHARED-UNDERSTANDING.md`、`STATE.md` 和当前任务 `REQUEST.md`。涉及决策或精确配置时按 INDEX 引用读 `DECISIONS.md`、`WORKING-NOTES.md`、`PARAMETERS.yaml`、证据。不得根据旧对话摘要推断文件已读。
2. `REQUEST.md` 应记录目标、用户授权边界、共同理解版本、来源文件及版本、接收节点、具体问题、期望输出、截止时间、敏感数据边界。发送者只写“待接收”；接收者写确认，列明实际可访问并已读取的文件、版本、缺失项。
3. 回复写到 `responses/<node>.md`，严格分 `事实及证据 / 推断 / 建议 / 尚未验证 / 对既有理解的异议`。不可把另一节点的建议写成共同决定。需要其他节点时创建请求，不能伪造其答复。
4. 每次上下文压缩、对话结束、节点切换，产出 `handoffs/<id>.md`：共同理解及用户纠正、已定和待固化事项、未决分歧、精确参数及来源、进度和证据、下一步、必读文件和版本、未完成写盘项。接收后的恢复动作先读取并回显关键理解和缺失项，再继续工作。无法直接访问文件时由用户转交，并标明读取方式。
5. 新信息先追加到事件日志或 WORKING-NOTES，再归档入正式文件。尤其用户纠正、已达成但未正式定稿的共识及参数变更，应在本轮写入；不可等到总结阶段靠记忆重构。重要决策遵循先分析、再形成方案、再执行。

## 所有权与冲突

| 路径 | 写入者 | 生效规则 |
| --- | --- | --- |
| `core/*` | 用户授权的维护者 | 审核通过并提升版本后生效；节点不得自行覆盖 |
| `nodes/<node>/*` | 对应节点 | 仅描述自身适配与产物；不得宣称共享规则更改 |
| `tasks/*/responses/<node>.md` | 对应节点 | 作为独立意见和证据，不自动成为决定 |
| `SHARED-UNDERSTANDING.md`, `DECISIONS.md`, `PARAMETERS.yaml`, `STATE.md` | 当前任务记录员可提交修改提议；最终由用户确认重要裁决 | 每次变动保留来源、时间、版本及原值；冲突未裁决时标记待裁决，不静默覆盖 |
| `events.jsonl` | 所有节点可追加 | 带 event_id、actor、time、project、type、source、payload_ref；不允许改写历史 |

共享文件多节点并写时采用单写者或原子提交：每个节点先在自身 outbox 产出补丁或提议；由当前记录员在核对基线版本后合并。若基线已经变化，停止自动合并、保留两份意见并提交用户裁决。已定共识与用户明确纠正的优先级高于节点推断，但若与新证据冲突，记录证据并请求重新裁决。不要用“最后写入者获胜”。

## 最小验收

- 五个节点各自能从 START 找到同一版本的共同理解、状态、任务和参数；缺文件时明确失败。
- 单个跨节点任务能形成 REQUEST、至少两个独立 RESPONSE、用户 RESOLUTION 和恢复快照；不得伪造未参与节点。
- 模拟用户纠正、参数改动、上下文压缩、新对话恢复，接收节点正确复述问题定义及精确值，识别冲突并不覆盖原记录。
- 证明节点实际读取：回复附已读文件版本/哈希或修改时间、读取方式及缺失项；不要把节点自报当作完整的外部运行验证。
