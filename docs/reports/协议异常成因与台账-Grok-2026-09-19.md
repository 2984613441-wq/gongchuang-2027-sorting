## G1 `NACK_ACK_NOT_APPLICABLE` 成因

实机时间线（派工书给出，未在本工作区找到原始 log 文件）：

```
18:58:25  ITEM_TASK sent: target_seq=2 class_id=2 image_id=2 落点=(20.0,20.0)mm 抓取点=(-44.0,-27.1)mm
18:58:26  inbound NACK_ACK_NOT_APPLICABLE:
18:58:26  inbound: BARRIER_READY（STM32 就绪上报）
18:58:26  BARRIER_READY = 建轮次那一发 ITEM_TASK 已被启动序列吞掉，立即重发: frame_seq=2 (26B)
18:58:26  inbound ACK_ACCEPTED:
```

后续 ACK 正常、该件完成。下面四问按代码回答。

### 1) 板子在哪条路径发 `NACK_ACK_NOT_APPLICABLE`

**唯一生产路径**：`电控/stm32_logic/src/ec_protocol_gateway.c:225-230`（`handle_display_ack`）。

```c
if (!valid) {
    emit_nack(g, EC_NACK_ACK_NOT_APPLICABLE, ack.target_seq);
    return none_transition(g);
}
```

证据：

| 项 | 位置 |
|---|---|
| 原因码宏 `0x13` | `电控/stm32_logic/include/ec_protocol.h:129` |
| `emit_nack` 本体 | `ec_protocol_gateway.c:51-57` |
| 全仓 `emit_nack(..., EC_NACK_ACK_NOT_APPLICABLE, ...)` | **仅** `:229` 一处（生产树；备份/整合包副本不算） |
| 入站分发 | `:261-270`：`ITEM_TASK`(0x21) → `handle_item_task`；`DISPLAY_ACK`(0x25) → `handle_display_ack` |
| Keil 编进板端的就是这份 | `MDK-ARM/diankongv1.0.uvprojx` `FilePath=../../../stm32_logic/src/ec_protocol_gateway.c` |
| 主机把 `0x13` 打成 `NACK_ACK_NOT_APPLICABLE` | `电控/src/electrical_control/protocol/ack_nack.py:21-25` + `rpi/gateway.py:193-228` + `run_chain.py:1254-1256` |

`handle_item_task` 能发的 NACK 只有：

- `:137-138` `EC_NACK_TASK_REJECTED`（`WAIT_TASK` 且 `success_count==255`）
- `:103-109` `EC_NACK_WRONG_ROUND` / `EC_NACK_SINGLE_TASK_ONLY`（`REJECT_NEW_TASK`）

**没有** `ITEM_TASK` → `0x13` 的路径。

`DISPLAY_ACK` 载荷必须正好 6 字节才进入内容门（`ec_protocol.c:126-132`）；12 字节的 `ITEM_TASK` 载荷即便命令被误读也不会走到 `:229`。

### 2) 触发条件（哪个状态机不允许 ACK）

**不是**状态机「当前态不许 ACK」的分支。NACK 在 `ec_sm_consume` **之前**由网关内容门发出。

四项全真才算 `valid`（`:220-223`）：

1. `ack.target_seq == g->item_target_seq`
2. `ack.render_result == EC_DISPLAY_ACK_RENDERED`（0x00）
3. `ack.display_crc32 == expected_crc`（按当前 `class_id/image_id/success_count/result_code` 算）
4. `frame->task_id == g->sm.round_id`

任一失败 → `:229` 发 `0x13`，状态不变。

状态机真正消费 `DISPLAY_ACK` 的地方是 `ec_state_machine.c:221-228`：仅当

- `state == EC_STATE_WAIT_DISPLAY_ACK`
- `EC_EVENT_DISPLAY_ACK_VALIDATED`
- `content_validated`
- 身份匹配当前件

才 `PREPARE_BARRIER | ACK_DISPLAY_CONSUMED`。

因此：**0x13 的含义是「这帧 DISPLAY_ACK 对当前闩住的件/轮次不适用」**，即使当时根本不在 `WAIT_DISPLAY_ACK`（`FAULT_LOCK` / `POWER_ON` / `HOMING` / `PREPARE_BARRIER` / `WAIT_TASK` 同样会回 0x13）。

建轮次那发 `ITEM_TASK` 自己的行为（对照，避免误判）：

| 板端状态 | `ITEM_TASK` 结果 | 发出 |
|---|---|---|
| `FAULT_LOCK` + 安全条件成立 | `ec_state_machine.c:95-104` 学 `round_id`、`POWER_ON`、`BEGIN_POST` | **不回帧**（`consume_and_emit` 无匹配分支，`:66-110`） |
| `POWER_ON` / `HOMING` / `PREPARE_BARRIER` | `:150-154` `REJECT_NEW_TASK`（无当前件） | `0x12 SINGLE_TASK_ONLY` 或 `0x14 WRONG_ROUND` |
| `WAIT_TASK` + 新身份 | `:178-184` `VALIDATE_TASK` | `ACK_ACCEPTED` |

所以 18:58:26 的 `0x13` **不能**解释成「启动序列拒绝了 ITEM_TASK」。它要求线上另有一帧已解码的 `DISPLAY_ACK`。哪一发、载荷 hex = 【证据不足】（工作区无 UART 抓包）。较可能（推断，非实锤）：`target_seq=2` 说明 Pi 侧不是本进程第一件；STM32 刚从 `FAULT_LOCK` 用本件 `ITEM_TASK` 重建轮次时，上一件的 `DISPLAY_ACK` 迟到，内容门失败。

### 3) 主机重发会不会重复建轮次 / 多跑启动序列

**不会。** NACK 与重发是两条独立路径。

| 入站 | `run_chain.py` | 动作 |
|---|---|---|
| `NACK_ACK_NOT_APPLICABLE` | `:1254-1256` `else` → `logger.warning("inbound %s: ...")` | **只打日志**，不重发、不改调度器 |
| `BARRIER_READY` | `:1219-1241` | 仅当 `_should_resend_on_barrier_ready`（`:902-925`）为真才重发 |

重发谓词：`last_task_context is not None and scheduler.state is WAIT_MOTION_DONE`。

`resend_item_task`（`outbound.py:96-116`）：

- 原样重放缓存的 **26B** `ITEM_TASK`
- **不**递增 `tx_seq`
- **不**增加 `done_items`

时序与板端对齐：

1. 第一发 `ITEM_TASK` 打在 `FAULT_LOCK` → 只建轮次（`BEGIN_POST`），identity **不进 dedup**（`:97` 清窗口后直接 `return`）。
2. POST→HOMING→挡板 → `WAIT_TASK` + `EMIT_BARRIER_READY`（`ec_state_machine.c:145-148`）。
3. 主机收到 `BARRIER_READY` 时仍是 `WAIT_MOTION_DONE` → 重发同一帧。
4. 此时板子已在 `WAIT_TASK`，重发被当成**首件新任务** → `ACK_ACCEPTED` + `VALIDATE_TASK`。这是故意的（`:914-915` 注释；`:93-94`：一进 `POWER_ON` 后，后续帧不再走 `FAULT_LOCK` 建轮次分支）。

副作用核对：

| 担心 | 结论 | 证据 |
|---|---|---|
| 重复建轮次 | 否 | 第二次到达时 state 已不是 `FAULT_LOCK` |
| 多跑一次 POST/HOMING | 否 | `BEGIN_POST` 只从 `FAULT_LOCK` 那条发出 |
| 重复运动 | 否（本条路径） | 第一发没 ACK、没 `START_MOTION`；运动只在重发被接受之后 |
| 件与件之间的 `BARRIER_READY` 误触发重发 | 设计上靠 `WAIT_MOTION_DONE` 挡住；若下一件已发出且上一件的 `BARRIER_READY` 迟到，会再灌同一缓存帧 → 板端 dedup `RESEND` 再回一次 `ACK_ACCEPTED`，不重新执行 | `:921-922`、`ec_state_machine.c:162-163` |

### 4) 要不要修 + 最小修法

**不必为这条现象改固件。** 它没有造成故障；`0x13` 按提案 E-8 对「无效 DISPLAY_ACK」显式回 NACK，符合契约。

| 方案 | 改什么 | 建议 |
|---|---|---|
| 不改 | — | **推荐**（本派工红线也禁止改固件逻辑） |
| 主机卫生 | `run_chain.py` 在 `WAIT_MOTION_DONE` 下把 `NACK_ACK_NOT_APPLICABLE` 记成「过期 DISPLAY_ACK，与本件 ITEM_TASK 无关」，避免看起来像建轮次失败 | 可选，低风险 |
| 固件卫生 | `handle_display_ack` 仅当 `g->sm.state == EC_STATE_WAIT_DISPLAY_ACK` 才发 0x13，其它态静默丢 | 可选；会改变联调可见性，需与契约 E-8 对账，**L4 若动协议语义则等用户** |

【证据不足】若要钉死 18:58:26 那一帧 0x13 的 `target_seq`/CRC/`task_id`，需要当时 UART hex。代码路径本身不依赖这份 hex。
