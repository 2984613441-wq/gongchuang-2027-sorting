# 运动完成上报排查：时间计算已纠正，实机根因待取证

日期：2026-09-18。范围：指定交付文档 §0 / 点 3；主机上的真实 C 源码执行、只读证据审查和 Keil 编译。**没有接线、上电、烧录、打开实机串口或启动整链运动。**

## 1. 结论与交付状态

**不能把本报告当作“实机根因已定案 / 固件已修复”。** 当前代码在主机 HAL 模型中完整走完三段，交给 UART 的 `MOTION_DONE`、`ITEM_RESULT` 均恰好一帧。现场故障的原始字节流、故障源、已烧录镜像身份以及单条诊断结果缺失；树莓派只读 SSH 连接超时。生产源码本轮未改，不用猜测补丁替代实测。

已能定案的源码事实：

1. **11.3 秒并非当前程序的正确预算。** 500 Hz 只是上层请求；端口实际配置固定 200→2000→200 Hz 曲线。当前规划又是 X/Y 顺序执行，原计算漏了 Y。真实源码的 ARR 理想模型为 **6.42508 秒**，每 1 ms 轮询模型为 **6.428 秒**，落在 5.0～10.6 秒区间内。因此“早于 11.3 秒就一定没有走完”不成立。
2. **连续两次 inject 没有吞掉 DONE 帧。** 第一条 inject 同步返回前已 flush；第二条随后清空网关缓冲不影响已经交给 UART 的第一帧。已有缺陷修复注释描述的是 VALIDATE_TASK 的递归重入，不是本处的顺序调用。
3. **当前计数完成发布、停止后保留、原子取走这条链在主机模型中成立。** 不是闭环机械反馈。物理堵转本身不会阻止计数归零或完成 latch 发布；必须另有电气/中断/复位/输入等证据，才能把机械故障与软件锁定联系起来。
4. **15 秒失活窗口不是同一任务受理后 5.0～10.6 秒故障的直接解释。** 当前代码在正常时间基准下精确到受理后 15000 ms 才触发。进展源默认关闭确实是长路径的独立约束，不能因此把提前故障归因给它。
5. **所提短运动实验需要修订。** 正确语法为 `MOVE X DIR0 STEPS 400 HZ 500`；当前曲线模型耗时 **0.49558 秒**，不是恒速 0.8 秒。诊断 DONE 直接由 ISR 回调写入，绕过轴驱动的 latch 消费，不能仅凭诊断成功就宣称 latch 交接无故障。

实机三选一裁定：**(a) 当前源码配置确实高于 500 Hz；但“当时已烧录板子实际步频”仍为【证据不足】。(b) 惯性停近中心、(c) 观察了后一轮，均为【证据不足】，本报告不选择其一。** 时间计算错误可确定；现场 FAULT 的唯一触发源还不能确定。这两个结论分开。

## 3. 时间矛盾的逐项核算

### 3.1 请求频率不等于端口曲线

Axis:229 使用 `EC_AXIS_MOVE_FREQUENCY_HZ`，头文件 `App/Inc/ec_axis_driver.h:38` 为 500；但 Board:174 无条件尝试：

```c
ec_step_profile_plan(profile, steps, 200U, 2000U, 200U, 5000U, 5000U)
```

只有计算失败或 reload 为 0 才在 Board:177-179 使用传入的 `frequency_hz`。Profile:81-133 对短距离生成三角曲线，**400 步也不会因为“短”而自动回退到恒速**。400 步峰值为 1428 Hz；2736 步到达 2000 Hz 巡航。所谓“短距离回退”注释不能替代代码行为。

时钟源码链：`Core/Src/main.c:166-179` 使用 HSI / DIV1；TIM4:344、TIM8:404 的 PSC 为 159；Board:25-28 的计数时钟为 100000 Hz。本轮只核对源码，没有用示波器验证板上时钟或 STEP 波形。

### 3.2 原预算漏算 Y

Plan:56-75 把每个 waypoint 拆成两个依次完成的单轴 MOVE；Plan:150-170 按 HOME→PICK→PLACE→HOME 建三段，两次舵机等待各 200 ms。当前 HOME=(0,0)，pick=(34.2,17.3)，place=(5,5)，80 步/mm。

| 腿 | 步数 | 恒定 500 Hz | 当前曲线理想 ARR 总时长 | Axis 超时线 |
|---|---:|---:|---:|---:|
| HOME→PICK X | 2736 | 5.472 s | 1.69648 s | 6.472 s |
| HOME→PICK Y | 1384 | 2.768 s | 1.02048 s | 3.768 s |
| PICK→PLACE X | 2336 | 4.672 s | 1.49648 s | 5.672 s |
| PICK→PLACE Y | 984 | 1.968 s | 0.82048 s | 2.968 s |
| PLACE→HOME X | 400 | 0.800 s | 0.49558 s | 1.800 s |
| PLACE→HOME Y | 400 | 0.800 s | 0.49558 s | 1.800 s |
| 两次夹爪 settle | — | 0.400 s | 0.40000 s | — |
| 合计 | 8240 | **16.880 s** | **6.42508 s** | 各腿分别计时 |

原 `11.3 s` 恰是 `(2736+2336+400)/500+0.4=11.344 s`，没有包含当前顺序规划的 Y 腿。若旧板镜像曾用 XY 并行，不能把旧镜像预算移植给当前源文件，必须先核对镜像身份。

原始输出（真实 Profile / Plan C 函数运行结果）：

```text
TOTAL sequential_fixed_500=16.88000 s actual_source_profile_model=6.42508 s
```

### 3.3 单段超时余量

Axis:74-78 是 `steps*1000/500+1000`；Axis:234-235 每次启动重新设置单段起点和期限。2736 步阈值 6472 ms 在恒速 500 模型里只有 1000 ms 余量，但相对当前曲线模型为约 **4775.52 ms**。不能在未测步频时以“余量小”为理由增大常量。

若真为恒定低步频，且主循环无额外迟滞，2736 步在约 `2736/6.472=422.744 Hz` 以下就会越过该期限。真实判断仍需考虑 IRQ 丢失、轮询延迟、速度曲线以及到期前是否已经发布 completion。Axis:345-358 已优先检查 completion，再检查 timeout；边界上已经锁存的完成不会被同一次 poll 误判成超时。

## 4. 完成信号、故障入口与发送顺序

### 4.1 完成发布与消费

1. 中断入口：`Core/Src/stm32f4xx_it.c:245-256` 的 TIM4 / TIM8_UP_TIM13 → `HAL_TIM_IRQHandler` → `Core/Src/main.c:771-774` → Board:444。
2. 单轴：Board:484-495 每个 update 对剩余计数减一并更新 ARR；Board:497-506 归零后先设 `counted_completed_axis`、`counted_completion_pending=1`，再停定时器、关驱动、通知诊断回调。
3. 双轴：Board:421-440 两轴分别归零后设置同一个 completion latch。当前生产规划走单轴顺序分支；此处列出双轴分支作为代码追溯。
4. Board:134-151 停计数器会清运行和计数状态，**不清完成 latch**。Board:153-157 的清事件仅在新一次启动时调用（单轴:312，双轴:361）。
5. Board:715-734 在 PRIMASK 保护下读取并清除 latch，恢复原中断屏蔽状态；一次事件只返回一次 true。安全中止单独发布 abort（Board:475-480 / :412-417），不会冒充自然完成。
6. Axis:333-337 先消费 abort；Axis:345-355 消费自然完成，增加完成计数 / 程序步索引。最后 MOVE 到 Axis:349-353 设 `DONE`；最后 servo settle 的完成分支在 Axis:361-368。

**物理堵转/丢步的回答：开环软件计数，不是编码器或限位反馈。** 正常 update 中断到达并走完计数，就会发 completion；堵转本身不在发布条件里。没有声音也不能证明位置精度。主机 HAL 模型不包含转子、负载、电气噪声和中断延迟，不能证明硬件是否丢步或中断是否可靠。

### 4.2 两帧都经过 flush

完整同步调用顺序：

```text
App:525 inject_simple(MOTION_DONE)
  -> App:90 gateway_inject [Gateway:465 清 tx_len]
  -> State:193-197 WAIT_ITEM_RESULT / EMIT_MOTION_DONE
  -> App:91 handle_transition
  -> App:318 flush_tx -> App:69 board_uart_transmit
  -> 返回 App:525
App:527 inject_item_result
  -> App:107 gateway_inject [此时才清上一帧缓冲]
  -> State:216-220 WAIT_DISPLAY_ACK / EMIT_ITEM_RESULT
  -> App:108 handle_transition -> App:318 flush_tx
```

本轮主机 UART HAL 双件保存实际编码字节，CRC 解码成功，顺序和计数都有断言：

```text
TX t=7128 cmd=22 seq=3 bytes=A5 5A 01 03 02 00 01 00 03 22 00 00 65 AE
TX t=7128 cmd=23 seq=4 bytes=A5 5A 01 03 02 00 01 00 04 23 00 03 01 00 00 24 6C
END elapsed=6428 ms state=10 axis_state=3 axis_result=0 progress=8 updates=8240 motion_done=1 item_result=1
```

`t=7128` 为模型 HAL tick；任务受理为 `t=700`，故耗时 6428 ms。state=10 为 WAIT_DISPLAY_ACK，axis_state=3 为 DONE。**这证明主机中两帧均交给 UART 调用，不证明实物 TX 引脚或 Pi 收到它们。** Board:862 丢弃 `HAL_UART_Transmit` 返回值；现场还需 HAL 返回值与 TX 原始字节，不能把主机 HAL_OK 当作实机送达保证。本轮不改发送契约、不再加一次 flush，避免重复帧。

### 4.3 提前 FAULT 的候选无法仅按时间选择

App:530-541 把所有 Axis FAULT 转成 EMERGENCY_STOP；因此只有 APP_STATE=FAULT_LOCK 不足以区分轴 TIMEOUT、ABORTED、PORT_FAIL。State:119-128 又有独立的急停、失电、deadline 入口。还需板上 axis_result、程序步索引、实际 fault_reason 和时间基准。

故障注入一次只变一个条件，其他真实 C 源码不变：

| 主机条件 | 结果 | 能证明的范围 |
|---|---|---|
| 正常 update / 完成 latch | 6.428 s、两帧各一条 | 当前源码正常路径能完成 |
| 第一腿完全没有 update 回调 | 6.472 s、TIMEOUT、两帧为零、progress=0 | 此时连后续腿都未执行，不能解释“同一件确实三段全走完” |
| 测试程序故意抢先消费最后一腿 latch | 7.732 s、TIMEOUT、两帧为零、progress=7、8240 次 update | 与“全部计数走完但上报未到”相容；**是人为注入，不是发现了生产代码中有抢消费者** |
| 正常完成后没有 DISPLAY_ACK | 14.999 s 仍 WAIT_DISPLAY_ACK；15.000 s FAULT_LOCK | 15 秒窗口行为，无法解释同一基准下的提前 FAULT |

原始输出：

```text
END elapsed=6472 ms state=0 axis_state=4 axis_result=4 progress=0 updates=0 motion_done=0 item_result=0
INJECTED: final latch consumed by test before executor
END elapsed=7732 ms state=0 axis_state=4 axis_result=4 progress=7 updates=8240 motion_done=0 item_result=0
WATCHDOG no DISPLAY_ACK: WAIT_DISPLAY_ACK at 14999 ms, FAULT_LOCK at 15000 ms
```

不能因为第二行的时间落在现场区间内就宣布“latch 丢失为真因”。当前生产调用搜索只找到 Axis:345 消费 completion，主机正常路径也未丢失；板上版本、输入与中断现场仍缺证。

## 5. 15 秒窗口：两方案比较

App:197-198 从运动开始建立窗口；App:553 判定 `>=15000`。`App/Inc/ec_app.h:16-17` 和 Keil 工程:337 均关闭 progress source，App:136-138 是硬 no-op。即使宏设 1，App:582 的 runtime gate 仍默认 false，仅改宏也不会自动续期。

| 方案 | 最小代码范围 | 收益 | 代价与本轮处理 |
|---|---|---|---|
| 放宽 15000 | App:553 一处数值 | 能延后总时长锁定 | 改变冻结的 15 秒静默语义，掩盖静默；不能解决 5～10.6 s 提前故障。本轮不采用 |
| 验证后启用 progress | Keil Define 设置 1 + 有证据的 runtime gate 启用路径 | 按已有设计滚动窗口，保留静默 15 秒判据 | 先有 HIL-PROGRESS-001；开环计数可在堵转时继续，不能自动认作机械可观察动作。本轮维持关闭 |

设计依据 `docs/design/2026-08-30-motion-time-budget.md:70-81`，先前证据边界见 `docs/reports/2026-09-18-15秒失活监控修复记录.md:9-13`。心跳、重传、MOTION_DONE 均不续期；收到有效 DISPLAY_ACK 才结束本件窗口。

### 6.2 一次操作

```text

STATUS
MOTION ARM
```

### 6.3 判据

- 当前源码模型：400 次 update，约 0.49558 s 自然完成。原始主机结果为：

```text

DIAG updates=400 last_update=0.49558 s result=DONE latch=once axis=X
```

- 若诊断结果在约 1.8 s 成 TIMEOUT：StepTest:150-151 / :291-300 的诊断期限已经到达，说明诊断自然完成回调未完成其结果交接。继续查定时器 update/IRQ/abort/执行版本，**不能独指 Board:715 的消费者**，诊断根本没调用该消费者。

## 7. 最小修复方案与本次实际改动

**生产补丁：0 行。** 已核对的两处候选（连续 inject 丢帧、计数归零不发布）在当前源码的正常路径不成立，不能添加重复 flush、伪造 DONE、增大超时或恢复 `remaining==0` 作为成功条件。

实机补丁的最小定位门槛如下，每次只改变一项：

1. 若核对发现已烧录版本缺少当前的自然完成发布 / 原子消费实现，按具体版本差异只补这一交接；必须保留 abort 优先，停止/中止不能产生成功。当前 Board:437、503、715-734 已具备，不能重复修。烧录尚未执行。
2. 若有真实 `axis_result=TIMEOUT`，先凭 ISR 次数/ARR 时间确定是哪一腿、哪个完成边界丢失；没有完成证据不能把 TIMEOUT 当 DONE。当前 6.472 / 7.732 s 的两种主机故障均能产生零帧，时间窗不足以挑选修法。
