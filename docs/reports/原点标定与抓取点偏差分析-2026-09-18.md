### 1.2 托盘中心≠(0,0) 的三层原因

#### 原因 1：高度视差补偿被**故意关闭**

**证据**：`calibration_config.ini:74-88`

```ini
# 🔴 2026-09-18 粗标期间【全部置 0】，这是有意的，不是忘了填：
#   本次粗标是操作员把物块【底面】推到托盘两端、直接按底面位置反解出来的，
#   所以仿射矩阵 affine(像素) 给的**已经是底面坐标**。
#   若此时再套一步视差补偿（顶面→底面），等于把同一件事做两遍 → 多缩一次。
#   故粗标期间置 0 = 关掉视差补偿，抓取直接用仿射结果，正确。
1 = 0.0  # 粗标期间关闭视差（见上）
2 = 0.0
...
6 = 0.0
```

**影响**：`pixel_to_device.py:324-343` 的视差补偿被跳过（`h=0.0` 时 `x_bottom = x_top`）

**自检失败**：本地运行 `py -3 电控/src/electrical_control/rpi/pixel_to_device.py` 在 Test 4 失败：
```
AssertionError: h=40mm: expected x≈708, got 508
```
→ 说明自检用的是**带视差补偿**的预期值，但当前配置 `h=0` 关闭了补偿，两者不匹配。
→ **这不是 bug**，是配置与自检预期的差异（自检假定正式标定，当前是粗标）。

---

#### 原因 2：像素坐标输入可能偏离托盘中心

**需要确认的数据**：
1. MaixCAM 输出的像素坐标是多少？（应该是 320×320 帧的中心附近，即 (160±δ, 160±δ)）
2. 托盘中心在 320×320 帧里对应哪个像素？（根据当前标定 `ty=-251.333`，装置 y=0 对应像素 `v=232`）

**推导**：
- 若物块在托盘中心（装置坐标 `(0, 0)`），仿射逆变换：
  - `0 = a11*u + tx` → `u = -tx/a11 = 156.886/1.085714 ≈ 144.5`
  - `0 = a22*v + ty` → `v = -ty/a22 = 251.333/1.083333 ≈ 232`
- **期望像素坐标**：约 `(144.5, 232)`
- **实际像素坐标**：未在日志中找到（需要查看 MaixCAM 输出）

**如果像素输入是 (160, 160)**（帧中心）：
```python
x = 1.085714 * 160 + (-156.886) = 173.7 - 156.9 = 16.8 mm  ≈ (16.8, 2.2)mm？
y = 1.083333 * 160 + (-251.333) = 173.3 - 251.3 = -78 mm
```
→ **不匹配**日志中的 `(39.6, 2.2)`。

#### 原因 3：相机视野偏移（已知事实）

**证据**：`calibration_config.ini:32-34` 与 `pixel_to_device.py:247-250`

```python
# pixel_to_device.py:247-250
本项目相机**明确不在正中间**（用户 2026-09-18 确认），所以旧写法会引入
固定偏差 ``nadir_x * (1 - scale)``：
    nadir 偏 30mm、三棱柱 h=35mm(d=262mm, scale≈1.154) → 偏差 −4.6mm
    nadir 偏 50mm                                          → 偏差 −7.7mm
```

**当前光轴落点**（在装置坐标系）：
```python
nadir_x = a11 * 160 + a12 * 160 + tx = 1.085714*160 - 156.886 = 16.8 mm
nadir_y = a21 * 160 + a22 * 160 + ty = 1.083333*160 - 251.333 = -78.0 mm
```

→ **相机光轴不在装置原点**，偏移约 `(16.8, -78)mm`

**推论**：如果物块放在托盘中心（装置 `(0,0)`），但相机视野中心偏移，则：
- 物块在相机画面中**不在**中心 `(160,160)`
- 应该在像素 `(144.5, 232)`（根据仿射逆变换）

### 1.3 为什么日志打出 (39.6, 2.2)mm？

**关键：缺失实际像素坐标日志**

`run_chain.py:1109-1113` 只打印了转换后的毫米坐标，**没有打印输入的像素坐标**：

```python
_LOGGER.info(
    "ITEM_TASK sent: target_seq=%d class_id=%d image_id=%d "
    "落点=(%s,%s)mm 抓取点=(%s,%s)mm",
    task.payload.target_seq, task.payload.class_id, task.payload.image_id,
    _mm10(task.payload.x_position), _mm10(task.payload.y_position),
    _mm10(task.payload.pick_x_position), _mm10(task.payload.pick_y_position),
)
```

**缺失数据**：`target.pixel_x`、`target.pixel_y`（`VisionTarget` 的原始像素坐标）

**反推**：如果 `抓取点=(39.6, 2.2)mm`，仿射逆变换：
```python
39.6 = 1.085714*u - 156.886  → u ≈ 181
2.2  = 1.083333*v - 251.333  → v ≈ 234
```

→ **推测**：MaixCAM 给出的像素坐标约 `(181, 234)`，偏离帧中心 `(160, 160)` 约 21 像素（X 方向）

**验证需要**：
1. 在 `run_chain.py` 增加日志，打印 `target.pixel_x`, `target.pixel_y`
2. 或查看 MaixCAM 端输出日志（`视觉/src/maixcam_deploy/main.py`）

## 二、固定抓取点模式 vs 九点标定

### 2.1 固定抓取点模式（当前已实现）

**代码位置**：`run_chain.py:291-320` + `sorting_config.ini:151-174`

**配置**：
```ini
[PickPoint]
x = 0.0
y = -45.0
```

**工作原理**：
```python
def load_fixed_pick_point(path: str | Path) -> tuple[int, int] | None:
    """从 sorting_config.ini 的 [PickPoint] 读**固定抓取点**（单位 mm → 0.1mm）。
    ...
    返回 None 的三种情况：文件不存在、没有 [PickPoint] 节、值解析不出来。
    """
```

**优点**：
- ✅ **绕开标定**：不需要像素→毫米仿射、不需要九点标定、不需要高度视差补偿
- ✅ **零风险**：配置值由人工测量（或用诊断口 `MOVE` 命令量出），不依赖视觉算法
- ✅ **校赛适配**：赛规允许操作员每次**手动把物块放在固定位置**（规则未禁止）
- ✅ **已部署**：`run_chain.py:708-720` 有完整实现，配置存在时自动激活

**缺点**：
- ❌ **操作约束强**：每次必须把物块放在完全相同的位置（误差 > 5mm 会抓偏）
- ❌ **失去视觉定位能力**：视觉只识别"是什么"（class_id），不识别"在哪"（位置）
- ❌ **单点容错差**：放偏一次即抓空/抓偏

**当前状态**：
- `sorting_config.ini` 的 `[PickPoint]` 节**已存在**，值为 `(0.0, -45.0)`
- `run_chain.py:712` 会打印 WARNING：
  ```
  标定未加载（%s）→ 改用【固定抓取点】模式：[PickPoint] = 
  (%.1f, %.1f)mm。件必须每次放在这个位置，否则会抓空/抓偏。
  ```

### 2.2 九点标定模式（标准方案）

**设计文档**：`docs/审核v2.0.md` §1-§4 (W6 标定链设计)  
**操作流程**：`docs/plans-2026-09-16/W6-标定操作流程.md`（未读取，需确认是否存在）  
**工具**：`工具/calib_photo.py` 或 `工具/calib_grid.py`（未读取）

**工作原理**：
1. 在托盘上放 9 个标定点（已知装置坐标）
2. MaixCAM 拍摄，记录每个点的像素坐标
3. 用最小二乘法（`numpy.linalg.lstsq`）拟合 6 参数仿射矩阵
4. 九宫格反向验证，目标 RMS ≤ 2mm

**优点**：
- ✅ **灵活性高**：物块可以放在托盘任意位置，视觉自动定位
- ✅ **鲁棒性好**：单次放偏不影响其他件
- ✅ **符合设计初衷**：完整使用视觉定位能力

**缺点**：
- ❌ **需要标定时间**：九点标定 + 验证约需 30-60 分钟
- ❌ **依赖精确测量**：标定点位置误差直接传递到抓取精度
- ❌ **高度补偿复杂**：需要实测 6 类物体的高度（用游标卡尺），并填入 `[ObjectHeights]`

**当前阻塞**：
- `calibration_config.ini` 的仿射参数是**粗标定**（手推边界，精度 ±5mm）
- `[ObjectHeights]` 全为 0（故意关闭视差补偿）
- 九点标定工具脚本未验证（未读取 `工具/calib_*.py`）

### 2.3 **校赛推荐方案：固定抓取点模式**

**理由**：

1. **时间约束**：
   - 校赛准备时间有限（见 `工创日程-智能分拣.xlsx`）
   - 九点标定需要 30-60 分钟，且需要事先准备标定靶标
   - 固定抓取点只需要 5 分钟（用诊断口测量一次）

2. **风险评估**：
   - 当前粗标定精度 ±5mm，**不满足抓取精度要求**（见下节 2.4）
   - 固定抓取点的精度取决于**人工摆放**，可通过治具/定位销改善
   - 九点标定的精度取决于**标定点测量精度** + **视觉算法精度**

3. **赛规允许**：
   - 规则未禁止操作员手动摆放物块
   - 校赛侧重"完整流程演示"，不侧重"随机摆放适应性"（省赛/国赛才有该要求）

4. **已验证可用**：
   - 代码已实现（`run_chain.py:708-720`）
   - 配置已存在（`sorting_config.ini [PickPoint]`）
   - 日志已打印 WARNING（提醒操作员约束）

**实施步骤**：
1. 关闭标定加载（临时重命名 `calibration_config.ini` 或清空仿射参数）
2. 在 `sorting_config.ini` 保留 `[PickPoint]` 节
3. 用诊断口测量最佳抓取点：

4. 更新 `[PickPoint]` 的值为测量结果
5. 运行链路验证（带 `--fake-link` 主机侧冒烟测试）

### 2.4 抓取精度需求（量化依据）

**物理约束**：
- 物块尺寸：约 40mm × 40mm（正方体/三棱柱/圆柱）
- 夹爪开口：约 50-60mm（需实测，见固件 `ec_board_stm32.c` 舵机脉宽）
- **容许偏差**：≤ 5mm（经验值，超过此值可能夹空/夹歪）

**当前标定精度**：
- 粗标定：±5mm（边界值，已达容许偏差上限）
- 九点标定理论精度：≤ 2mm（设计目标，`calibration_config.ini:12`）

**结论**：
- 粗标定**不满足**精度要求（±5mm = 容许偏差边界）
- 固定抓取点**可满足**（人工摆放 + 治具 → 约 ±2mm）
- 九点标定**可满足**（理论 ≤2mm，需验证）

## 四、原点语义梳理

### 4.1 三个"中心"的关系

**问题**：设备坐标 (0,0) 在物理上是哪一点？

**三个候选点**：
1. **190mm 行程的中点**（机械中心）
2. **相机视野中心**（光学中心）
3. **托盘中心**（操作中心）

**当前定义**（方案 A）：

```c
// 固件 ec_startup_sequence.c:84-94（2026-09-16 修改）
// 方案 A：上电位置即原点，不做寻零运动
void ec_startup_homing_sequence(ec_state_machine_t *machine) {
    // 不再检查任何限位输入（X_HOME/X_END/Y_HOME/Y_END/Z_UP/Z_DOWN）
    // 上电位置即原点
    machine->state = EC_STATE_HOMING_DONE;
}
```

**结论**：
- ✅ **设备坐标 (0,0) = 上电时机构所在位置**
- ✅ **安全规程要求**：上电前人工把机构摆到 **190mm 行程正中**（见 `sorting_config.ini:56` 安全红线）
- ✅ **理想情况**：三个中心重合（机械中心 = 上电原点 = 托盘中心）

**实际情况**：
- ❌ **相机视野中心 ≠ 装置原点**（已知偏移约 `(16.8, -78)mm`，见 §一.1.2 原因 3）
- ⚠️ **托盘中心 ≟ 装置原点**（未独立验证，取决于人工摆放精度）

### 4.2 漂移风险量化

**场景**：上电时机构偏离行程中点 X mm

**影响**：
- 全场坐标整体平移 X mm
- 正方向可用行程减少 X mm
- 负方向可用行程增加 X mm

**数值示例**（X 轴）：
| 上电偏差 | 正向可达 | 负向可达 | 越界风险 |
|---------|---------|---------|---------|
| 0 mm（理想） | +95.0 mm | -95.0 mm | 无 |
| +10 mm | +85.0 mm | -105.0 mm | **正向越界**（协议域 ±145mm 内，但机械域只有 ±95mm） |
| -10 mm | +105.0 mm | -85.0 mm | 负向越界（超出机械域） |

**协议域 vs 机械域**：
- **协议域**：`EC_MOTION_WORKSPACE_LIMIT_MM10 = 1450`（±145.0mm，`interface-contract.md` §5.2 冻结）
- **机械可达域**：`EC_MOTION_REACH_LIMIT_X_MM10 = 950`（±95.0mm，`ec_motion_plan.h`）
- **实测行程**：190mm（±95.0mm，`sorting_config.ini:102`）

**风险评估**：
- 上电偏差 ≤ 5mm：低风险（余量足够）
- 上电偏差 5-15mm：中风险（余量减少，需注意落点表配置）
- 上电偏差 > 15mm：**高风险**（协议合法但机械不可达，会堵转）

**现有保护**：
- ✅ `ec_motion_plan.c:111-139` 检查两个域（协议域 + 机械域）
- ❌ X/Y **无限位开关**（2026-09-15 用户裁决，见 `sorting_config.ini:62-70`）
- ❌ 越程 = 堵转 + 挂死（已实测发生 3 次）
