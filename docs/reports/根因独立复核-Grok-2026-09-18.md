## 1. 独立结论：最可能 3 条路径（已排序）

把现象拆成 **两个时钟**，不要混成一个：

| 时钟 | 含义 | 源码闭合 |
|---|---|---|
| **故障钟** | ACK 后 ≤5s 进 FAULT_LOCK，且从不发 MOTION_DONE | 生产执行器没走到 `EC_AXIS_STATE_DONE`（`ec_app.c:518-525` 才 inject `EC_EVENT_MOTION_DONE`）；FAULT 来自轴 `FAULT`→`EMERGENCY_STOP`（`ec_app.c:530-541`）或复位 |
| **复现钟** | `BARRIER_READY` 每 5.63±0.005s | 主机 `task_timeout_s=5.0`（`run_chain.py:1076,1135-1142`）在 FAULT_LOCK 下重发同一帧 → ZERO-REPLY-FIX（`ec_state_machine.c:95-103`）→ POST 50ms + HOMING 500ms（`ec_startup_sequence.c:34-36,137-138,183-185`）→ 再发 `BARRIER_READY`。5.00 + 0.55 + 数十毫秒串口/轮询 ≈ **5.55–5.63s** |

`BARRIER_READY` 周期 **不是** 故障原因，是「已经 FAULT_LOCK + 主机 5s 重传 + 启动链」的后果。`run_chain.py:902-925,1219-1225` 在每次 `BARRIER_READY` 上还会把 `last_task_sent_at` 清零，所以 5.00s 从「建轮次后那一发真正启动运动的 ITEM_TASK」起算，节拍被主机单调钟钉死，±5ms 说得通。

### 路径 A（最可能）— 计数完成闩从未置位，首腿按 `move_timeout_for(steps)` 超时

**机制（工作树）:**

1. `WAIT_TASK` 受理 ITEM_TASK → ACK（`ec_app.c:252-272` 已冲刷，符合 51ms）→ `TASK_SAFETY_VALIDATED` → `START_MOTION`。
2. 规划首步：HOME→PICK 的 **X**，`EC_MOTION_XY_ORDER_X_FIRST=1`（`ec_motion_plan.h:139-140` + `ec_motion_plan.c:60-66,151-153`）。
3. 步数：`(125 * 80) / 10 = 1000`（`ec_axis_driver.c:52`）。**不是 100。**
4. 端口实际跑梯形 `200→2000→200 Hz, 5000 Hz/s`（`ec_board_stm32.c:174,318-321`），PWM 会出脉冲 → **机构可以动**。
5. 完成条件是 ISR 里 `counted_steps_remaining--` 到 0 后置 `counted_completion_pending`（`ec_board_stm32.c:484-507`），再被 `ec_step_port_take_counted_completion` 取走（`ec_axis_driver.c:374`）。`remaining==0` 本身不够。
6. 若 UPDATE 中断没在减计数（TIM8 是 X，高级定时器；或烧录镜像仍缺 `TIM8_UP_TIM13_IRQHandler` / NVIC），remaining 冻住，PWM 停在 **profile 第一个 ARR≈200Hz**（`main.c:368-376` 自己写过这个后果）。
7. 超时线：`1000*1000/500 + 1000 = 3000ms`（`ec_axis_driver.c:74-77,263-264`）。3s 落入「5 秒内」。
8. `fault(TIMEOUT)` → `EC_AXIS_STATE_FAULT`（`ec_axis_driver.c:209-215,385-387`）→ `ec_app.c:530-541` 注入 `EMERGENCY_STOP` → `FAULT_LOCK`。`MOTION_DONE` 分支进不去。
9. 主机仍 `WAIT_MOTION_DONE`，5.0s 重传；板子已 FAULT_LOCK → ZERO-REPLY-FIX 重跑 POST/HOMING → `BARRIER_READY`。

**与主机模型的对抗结果（不是实机，但是同一份生产路径）:**

- ISR 正常：`production_input.log` 8 步走完，`elapsed=3463ms`，`cmd=22 MOTION_DONE`，`axis_result=0`。**软件超时公式在本坐标下杀不死这条程序。**
- ISR 被禁：`missing_irq.log` 首腿 TIMEOUT、`motion_done=0`、`updates=0`，但 PWM 已 `MOVE index=1`。这才是与实机同构的故障。

**行号:**  
`ec_motion_plan.c:151-153`；`ec_axis_driver.c:52,74-77,263-264,374-387,209-215`；`ec_app.c:518-541`；`ec_board_stm32.c:174,190,444-507`；`main.c:368-378,443-446`；`stm32f4xx_it.c:238-257`；`ec_state_machine.c:95-103,193-197`；`run_chain.py:1076,1135-1142,1219-1225`；`ec_startup_sequence.c:34-36,137-138,183-185`。

**一次实机实验就能区分:**  
停掉主机自动重传（杀 `run_chain` 或把 `task_timeout_s` 临时改大，本复核不改代码：用 Ctrl-C 在 ACK 之后立刻停链）。等 ≥4s，只发 ASCII `AXIS`（工作树 `ec_diag.c:424-461` 已有；若板子回 `ERR` 则烧录镜像落后于树，改发示波器）。

| `AXIS` 读数 | 判定 |
|---|---|
| `LAST_RESULT=4`（TIMEOUT），`LAST_STEP=0`，`LAST_AXIS=X`，`LAST_STEPS=1000`，`LAST_ELAPSED_MS≈LAST_TIMEOUT_MS≈3000`，`MOVES=0` | **本路径成立**（完成闩从未走过） |
| 同上但 `MOVES≥1` 且 `LAST_STEP≥1` | 超时发生在后续腿，ISR 至少走过一腿，降为「某腿实际慢于超时线」 |
| `LAST_RESULT=5/6` 或 `FAULTS=0` 且 `LAST_RESULT=0` | 否决本路径，改看 B/C |

示波器（同一实验可并行）：X=`PC6/TIM8_CH1`，Y=`PB6/TIM4_CH1`（`stm32f4xx_hal_msp.c:235,256`）。**本路径预期：X 近恒定 ~200Hz，约 3s 被掐断，Y 无脉冲。** 若已见 200→2000→200 梯形且 X 在 ~0.83s 结束，则 ISR 活着，本路径失败。

### 路径 B — 运动中途安全抑制（ESTOP_FB / ISR 快路径 abort）

**机制:**  
`ec_axis_driver.c:13` 遮罩只剩 `EC_INPUT_ESTOP_FB`。poll：`has_inhibit` → `fault(ABORTED)`（`:354-356`）。ISR 快路径：`ec_motion_inhibit_from_raw`（`ec_board_stm32.c:412,475-481`）置 abort latch，随后 `ec_axis_driver.c:362-366` 同样 `ABORTED`。`ec_app.c:530-541` 同样走急停 → FAULT_LOCK，不发 MOTION_DONE。机构可以先动再停。

周期仍由主机 5s 重传 + ZERO-REPLY-FIX 提供，所以 **不必** 要求 ESTOP 自己每 5.63s 抖一次——一次 abort 后主机循环会把 `BARRIER_READY` 打成 5.63s 节拍。若 20 次 STATUS 期间 ESTOP 仍为真，则 `INPUTS` 能当场抓住；若是毛刺，STATUS 现态可能已经干净。

**行号:** `ec_axis_driver.c:13,32-34,354-356,362-366`；`ec_board_stm32.c:412,475-481`；`ec_app.c:451-466,530-541`。

**一次实机实验就能区分:**  
同一套「ACK 后停链 + 等 4s + `AXIS` + `INPUTS`」。

| 读数 | 判定 |
|---|---|
| `LAST_RESULT=5`（ABORTED），`LAST_ELAPSED_MS < LAST_TIMEOUT_MS` | **本路径** |
| `INPUTS` 里 `ESTOP_FB` 仍置位 | 抑制源还在，用表笔看该脚是否被拉低/悬空 |
| `LAST_RESULT=4` 且 elapsed≈timeout | 否决本路径 |

不需要先假设「ESTOP 周期性误触发」。

### 路径 C — 主循环被饿死 / 复位（IWDG≈1s），RAM 诊断被清掉

**机制:**  
堵转或 TIM 中断风暴可饿死主循环。IWDG Reload=1000、÷32 → ≈1s 复位（`main.c:199-209,126-137`）。复位后 `ec_sm_init` 回到 FAULT_LOCK（`ec_state_machine.c:44-46`），生产静态量清零，**不会**发 MOTION_DONE。主机 5s 后重传 ITEM_TASK → ZERO-REPLY-FIX 再跑启动链 → `BARRIER_READY`，周期仍是 5.63s。  
`DIAG=1` 时复位应打 `BOOT SAFE HSI=...`（`ec_app.c:597-599`）。`AXIS` 快照在软件 `fault()` 时故意不被 `init()` 清（`ec_axis_driver.c:181-183,303-313`），但 **MCU 复位会清 RAM**，于是 `FAULTS=0`、`LAST_RESULT=0`。

这与「现态不在重启」不矛盾：停链之后板子停在 FAULT_LOCK，不再有 5s 重传，也就不再复位。

**行号:** `main.c:126-137,199-209`；`ec_app.c:569-600`；`ec_state_machine.c:44-46,95-103`；`run_chain.py:1135-1142`。

**一次实机实验就能区分:**  
不断开链路，只在一个 5.63s 周期内 **抓 UART 原文**（不要只看 Python 解码后的事件名）。

| 观察 | 判定 |
|---|---|
| 周期内出现 `BOOT SAFE`，且故障后 `AXIS` 的 `FAULTS=0/LAST_RESULT=0` | **本路径** |
| 全程无 BOOT，且 `FAULTS` 递增、`LAST_RESULT∈{4,5,6}` | 否决复位，回到 A/B |
| `TICK_MS` 在 STATUS 连续采样中发生回绕/跳回 0 | 支持复位 |

IWDG 本身不是 5.63s；5.63s 仍是主机重传钟。本路径解释的是 **FAULT_LOCK 的产生方式**（复位），不是复现钟。

## 3. 他们都漏掉（或没写成可证伪命题）的点

1. **5.63s 的闭合式：** `5.00`（主机）+ `0.050`（POST）+ `0.500`（HOMING_SETTLE）+ 串口/轮询开销。这是当前树上能写出的最硬数字，Claude 没写到 `run_chain.py`，Codex md 不存在。
2. **两个时钟必须拆开：** 故障钟（3s 首腿超时或 abort/复位）vs 复现钟（主机 5s + 启动链）。混在一起会把 ZERO-REPLY-FIX 误判成根因。
3. **`STATUS.STEP_*` 对生产路径零信息。** Claude 在补丁评估里提到了，但排序仍把「现态 STEP_REMAIN=0」当运动状态。一次实验应发 `AXIS`，不是再刷 20 次 STATUS。
4. **X 是 TIM8 高级定时器，Y 是 TIM4 通用定时器。** 首腿是 X。即便 `TIM4_IRQHandler` 已修好，TIM8 的 UPDATE（`TIM8_UP_TIM13_IRQn` + RCR + MOE）仍可以单独死。示波器只看 Y 会漏诊。
5. **工作树已有「丢 ISR」主机对照。** `test_motion_completion.c` 的 `missing_irq` 就是实机现象的最小同构：PWM 启动、0 次 UPDATE、TIMEOUT、无 MOTION_DONE。Claude 穷举里没引用这份对照。
6. **FAULT 原因码没进 STATUS。** 现态只能看到 `APP_STATE=FAULT_LOCK`，分不清 `EMERGENCY_STOP` / `DEADLINE_EXPIRED` / `POWER_PERMISSION_LOST`。不发 `AXIS`/`INPUTS` 之前，任何「15s 看门狗」或「掉电」都是猜测。
7. **Claude 路径 6 的 10× 步数错误** 若被后续引用，会把超时线算成 100*1000/500+1000=1200ms，整张时间表作废。
