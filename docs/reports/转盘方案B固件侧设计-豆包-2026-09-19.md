## 0. 一句话结论

转盘角度**不需要**改动已冻结的 12 字节 `ITEM_TASK`（`class_id` 本就在线上）；
固件侧用一张 `class_id → 转盘格` 的查表 + 舵机 PWM + PG7 光电回零即可。
但落地前有 **3 个必须先由用户裁决的冲突/红线**（§4、§5），其中 PB0 与 PG7 两处引脚
均有现存占用，不能默认直接复用。

## 2. 安全边界（必须明确写出）

1. **新增光电输入（PG7）绝不进入运动安全遮罩。**
   现 `EC_AXIS_SAFETY_MASK = (EC_INPUT_ESTOP_FB)`（`ec_axis_driver.c:13`，注释 `:8-12`
   说明 6 个限位已因「X/Y 不装限位、原点=上电位置」全部移除）。
   转盘零位是**定位传感器**，不是**安全输入**：
   - 它丢失/抖动 → 只能让「转盘这一步」超时/重试或报转盘专属故障；
   - **禁止**写进 `EC_AXIS_SAFETY_MASK`，禁止让 `has_inhibit()`（`ec_axis_driver.c:32-35`）
     因 PG7 拉低而 `fault(EC_AXIS_RESULT_ABORTED)`（`:354-357`）。
   - 注意 `ec_axis_driver.c:12` 要求与 `ec_demo.c / ec_servo_test.c / ec_step_test.c`
     三处遮罩保持一致——新增输入同样**不得**进这三处。

2. **落点仍过 `ec_motion_plan_build` 双域检查。**
   `ec_motion_plan_build`（`ec_motion_plan.h:182-184`）对 PICK 和 PLACE 两组坐标同时做
   工作域 `±1450` ∩ 可达域（X `±950`、Y `±975`，`ec_motion_plan.h:82-95`）交集校验，
   越界返回 false（注释 `:177-181`）。转盘方案 B 的**落料点是固定点**
   （`drop_strategy.py:88-98`），因此：
   - 该固定点必须**预先一次**通过双域检查并落在可达域内（建议同样留 ≥5mm 余量，
     见 `ec_motion_plan.h:75-77`）；
   - 转盘只换「货格对准」，**不改落点坐标**，所以转盘角度本身不产生新的越界路径。

3. **15s 失活窗口**（`ec_app.c:553` = 15000ms，不被运动进展重置，`ec_app.c:579-583`）：
   现有近落点整链已约 12.6s、余量约 2.4s（`ec_board_stm32.c:180-184`）。
   转盘若**串行**插入一次舵机动作 + settle，会直接吃掉这点余量 → 推荐把转盘转动
   放在 **PICK→PLACE 的 XY 行程期间并发执行**，而非新增一个串行 step。
   【证据不足：当前 executor 是单 step 串行状态机（`ec_axis_driver.c:251-301`），
   「转盘与 XY 并发」需要额外的并发调度设计，本文只提风险，不展开实现。】

## 3. 技术规格（设计稿，待硬件与 L4 批准）

### 3.1 转盘舵机 → PB0 / TIM3_CH3

- 引脚/定时器：PB0 = TIM3_CH3（`stm32f4xx_hal_msp.c:213`；`.ioc:107,252`；
  `CUBEMX-INTEGRATION.md:14`）。
- 复用 `HAL_TIM_PWM` 通道，脉宽控制角度（与 Z/夹爪舵机同构，PB10=TIM2_CH3 作参考，
  `ec_axis_driver.h:122-124`）。
- 脉宽→角度：**【待测】**（转盘舵机型号未给；标准舵机 500–2500us/180°，
  6 格 = 每格 60°，需现场标定每格脉宽）。
- 互斥：见 §4.1。

### 3.2 光电零位 → PG7（NPN 低有效）

- 现配置：PG7 = `X_HOME`，`GPIO_Input`、**`GPIO_NOPULL`**（`.ioc:182-186`）。
- NPN 低有效 = 遮挡时输出拉低。开集电极输出**需要上拉**：
  - 现 `NOPULL` 下，空闲态电平不确定 → **必须把 PG7 改为带上拉输入**
    （内部 `GPIO_PULLUP` 或外部上拉电阻），使「空闲=HIGH、挡片经过=LOW」可判。
  - 这是一处**CubeMX/固件配置改动**，随 L4 一并批准。
- 回零逻辑：上电/换轮 → 转盘向零位方向慢转 → 见 PG7 下降沿（或上升沿，按挡片极性）
  → 停在零位 = 格 0（0°）。

### 3.3 角度查表（class_id → 格/角度）

- 键：**`class_id`**（已在冻结 `ITEM_TASK` 的 offset 1，`interface-contract.md:161`）。
- 板内一张 6 项常量表：`{class_id → 目标格号 0..5}`，格号再映射到脉宽。
- 未知 class_id → fail-closed：不转盘、不下落、走拒识（与 Pi 侧
  `drop_strategy.py:90-96` 的「未知 box_id 返回 None 拒识」同语义）。

### 3.4 零位 + 6 标记数逻辑

- 转盘一圈 6 格；除零位挡片外，另有 6 个格标记（或靠零位 + 舵机开环定位二选一）。
- 建议流程：
  1. 先回零（§3.2）确立格 0；
  2. 按查表把舵机打到目标格脉宽；
  3. 若带 6 标记盘：计数经过的标记数 = 目标格号，作为**到位校验**（预期数 vs 实计数），
     不符则报转盘专属故障（不进急停）。
- 【证据不足】：转盘究竟是「舵机开环定位、零位只做上电回零」还是
  「标记盘闭环计数」，取决于实际机械结构——需机械组确认标记盘形式。

## 4. 引脚冲突（必须用户裁决，本文不擅断）

### 4.1 PB0 / TIM3_CH3 现 = BARRIER_PWM_1（互斥）

- 证据：`CUBEMX-INTEGRATION.md:14` `BARRIER_PWM_1=TIM3_CH3`；`.ioc:107` `PB0.Signal=S_TIM3_CH3`。
- 含义：转盘舵机与挡板 1 抢同一个 PWM 通道。
- **待裁决**：方案 B 下挡板是否还要？
  - 若**不再用挡板** → PB0 让给转盘，挡板相关代码/配置退役；
  - 若**挡板仍要** → 转盘舵机须另选空闲定时器通道（本设计不默认选脚）。
- 【证据不足】：挡板在方案 B 链路中是否仍参与时序，文档未给出，需用户/总控确认。

### 4.2 PG7 现标签 = X_HOME

- 证据：`.ioc:183` `PG7.GPIO_Label=X_HOME`，输入、NOPULL。
- 虽 X/Y 已不装限位、X_HOME 位不在安全遮罩（§2.1），但该脚在 CubeMX 仍占着 `X_HOME` 名。
- **待裁决**：把 PG7 从 `X_HOME` 重定义为转盘零位（并改上拉）。
- 联动：`ec_inputs.h:6` `EC_INPUT_X_HOME` 位仍在——若确认永不用 X 限位，应一并确认
  是否保留该定义（本文不改）。

## 5. 协议影响评估（`interface-contract.md`）

**结论：按本文 §3.3 的「固件内查表」方案，已冻结线格式不需要改。**

- `class_id` 已在 `ITEM_TASK` 线上（offset 1，1 字节，`interface-contract.md:161`）；
  角度字节（offset 6）冻结恒 `0xFF`、语义是**夹爪不旋转**（`:166`），与转盘角度无关。
- 转盘角度**不上线**，由固件用 class_id 板内查表得到 → 12 字节载荷、`data_len==12`
  硬校验（`:167`）、CRC、外层帧均不动。

**但有一处文档说明需要补（L4，请用户裁决，本文不改）：**

- `interface-contract.md:163` 明文写「**STM32 不内建『类别→篮子』查表**」。
  这是方案 A 的设计（Pi 直接发落点坐标）。方案 B 的固件内 `class_id→格` 查表
  在字面上与这句冲突——严格说它不是「类别→落点坐标」查表，而是「类别→转盘格」内部定位。
- 建议：在 §5.2 补一句说明「方案 B 的转盘格查表属 STM32 内部实现，不落在线格式上」。
  **这是文档说明性补充、非线格式变更**，但是否动 `interface-contract.md` 仍属 L4，
  本文**只标记、不修改**，等用户裁决。

> 另一备选方案（不推荐、会触发 L4）：让 Pi 把转盘角度写进 `ITEM_TASK`——
> 需改冻结的 angle 字节语义或加字节，必然不兼容，禁止默认走这条。

## 6. 与 Pi 侧对齐（`drop_strategy.py`）

现状（`drop_strategy.py`）：
- `TurntableStrategy`（`:64`）：`get_drop_point()` 对所有货格返回**同一固定点**（`:88-98`）；
  `get_angle(box_id)` 返回角度（`:100-102`）；`requires_turntable_control()=True`（`:104-105`）。
- 方案识别靠配置节：存在 `[TurntableAngles]` 即走转盘（`:123`），角度表 `box_id = angle_degrees`（`:140-150`）。

**Pi 侧还需要什么（缺口清单）：**

1. **class_id ↔ box_id 映射是最大缺口。**
   线上是 `class_id`（活跃集 `{0,2,3,4,5,6}`，`interface-contract.md:168`）；
   Pi 配置 `[TurntableAngles]` 的键是 `box_id 1..6`（`drop_strategy.py:149,152`）。
   固件查表若以 `class_id` 为键，**必须**先有一张明确的 `class_id→box_id→格` 对照表，
   否则板内表与 Pi 配置对不上。【证据不足：当前未见此对照表。】

2. **角度表双源同步。**
   Pi 的 `[TurntableAngles]` 是运行时配置；固件表是编译期常量。
   两者会漂移。需要：一份「由 Pi 配置生成固件表」的生成脚本/手工同步步骤，
   改角度时两边同步改。【待测：无现成工具。】

3. **`get_angle()` / `requires_turntable_control()` 当前无人在线消费。**
   线格式不携带角度，所以 Pi 发完固定落点后，无法从线面上确认「转盘是否转到该格」。
   - 若 Pi **不需要**确认转盘到位 → 现状即可（固件自行回零/查表/到位）；
   - 若 Pi **需要**一个「转盘就绪」信号 → 那是新增 telemetry，属协议变更 = L4。
   【待用户裁决 Pi 是否需要转盘就绪反馈。】

4. **Pi 不发角度、只发固定落点坐标**：固件收到 `ITEM_TASK` 后，用其中 `class_id`
   自己查格；Pi 的 `get_angle()` 仅用于日志/校验，需保证与固件表一致。
