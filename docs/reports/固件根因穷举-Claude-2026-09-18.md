# 固件根因穷举分析 — 5 秒内 FAULT_LOCK 且从不发 MOTION_DONE

**日期**: 2026-09-18  
**现象**: 板子受理 ITEM_TASK（ACK_ACCEPTED 51ms）后，5 秒内进入 FAULT_LOCK，且从不发 MOTION_DONE。BARRIER_READY 每 5.63±0.005s 复现一次。机构确实发生了运动（现场确认）。  
**分析范围**: STM32 固件源码（只读，不修改）  
**宏组合**: DIAG1,MOTION1,SERVO1,GROUP0,BARRIER0,PROGRESS0

---

## 📋 已验证事实

1. ✅ Pi↔STM32 链路正常（inbound BARRIER_READY → 立即重发 → ACK_ACCEPTED 仅 51ms，连续 8 周期稳定）
2. ✅ 视觉→Pi 通（ITEM_TASK sent target_seq=4 class_id=4 image_id=4 落点=(5.0,5.0)mm 抓取点=(12.5,5.4)mm）
3. ✅ 板子从不发 MOTION_DONE（约 2 分钟 0 次），链路始终 state=WAIT_MOTION_DONE
4. ✅ 板子受理后 5 秒内进 FAULT_LOCK；BARRIER_READY 每 5.63±0.005s 复现
5. ✅ 板子现态：PING→OK PONG；20 次 STATUS 全 FAULT_LOCK/ARMED=0/STEP_REMAIN=0/STEP_RESULT=0，无变化
6. ✅ 运行时生效可达域 ±95.0/±97.5mm
7. ✅ 电机在动（现场确认）

### 路径 1：轴超时（ec_axis_driver.c:385-387）

**触发条件**:  
```c
(uint32_t)(now_ms - move_started_at_ms) >= move_timeout_ms
```

**关键行号**:
- [ec_axis_driver.c:385-387](电控/firmware/stm32f407_m144z/App/Src/ec_axis_driver.c#L385-L387): 超时判定
- [ec_axis_driver.c:74-78](电控/firmware/stm32f407_m144z/App/Src/ec_axis_driver.c#L74-L78): `move_timeout_for()` 计算公式
- [ec_axis_driver.c:263-264](电控/firmware/stm32f407_m144z/App/Src/ec_axis_driver.c#L263-L264): 单轴超时线设定
- [ec_axis_driver.c:247](电控/firmware/stm32f407_m144z/App/Src/ec_axis_driver.c#L247): 双轴超时线设定（取两轴最大值）

**实机输入计算**:

输入坐标：
- PICK: (12.5, 5.4) mm = (125, 54) mm10
- PLACE: (5.0, 5.0) mm = (50, 50) mm10
- HOME: (0, 0) mm

步进参数：
- 步进比: 80 steps/mm (ec_axis_driver.h:32-33)
- 基础频率: 500 Hz (ec_axis_driver.h:38)
- 梯形加速: 200→2000→200 Hz, 加速度 5000 Hz/s (ec_board_stm32.c:174)
- 超时余量: 1000 ms (ec_axis_driver.h:76)

**各腿实际耗时与超时线**:

| 腿 | 位移 (mm) | 步数 | 理论耗时 (梯形) | 超时线 | 余量 |
|---|---|---|---|---|---|
| HOME→PICK X | 12.5 | 1000 | 3.223s | 4.223s | 1.000s |
| HOME→PICK Y | 5.4 | 432 | 1.432s | 2.432s | 1.000s |
| PICK→PLACE X | -7.5 | 600 | 2.023s | 3.023s | 1.000s |
| PICK→PLACE Y | -0.4 | 32 | 0.232s | 1.232s | 1.000s |
| PLACE→HOME X | -5.0 | 400 | 1.423s | 2.423s | 1.000s |
| PLACE→HOME Y | -5.0 | 400 | 1.423s | 2.423s | 1.000s |

**梯形耗时模型**（基于 ec_board_stm32.c:174 的固定参数）:
```
t_total = t_accel + t_cruise + t_decel
t_accel = (v_cruise - v_start) / a = (2000 - 200) / 5000 = 0.36s
t_decel = (v_cruise - v_end) / a = (2000 - 200) / 5000 = 0.36s
steps_accel = (v_start + v_cruise) / 2 * t_accel = 396 steps
steps_decel = 396 steps
steps_cruise = total_steps - 792
t_cruise = steps_cruise / 2000

对于 1000 步 (HOME→PICK X):
  steps_cruise = 1000 - 792 = 208
  t_cruise = 208 / 2000 = 0.104s
  t_total = 0.36 + 0.104 + 0.36 = 0.824s
  超时线 = (1000 * 1000 / 500) + 1000 = 3000 ms
  余量 = 3.000 - 0.824 = 2.176s （约 2.6 倍）
```

**结论**: 
- ✅ **这条路径同时解释不发 MOTION_DONE**（超时进 fault → state=FAULT → 不会发 MOTION_DONE）
- 最短腿（PICK→PLACE Y, 32步）耗时约 0.232s，超时线 1.232s，余量约 **1.0s**
- 最长腿（HOME→PICK X, 1000步）耗时约 0.824s，超时线 3.0s，余量约 **2.2s**
- **5 秒内触发意味着某条腿的实际耗时超过了其超时线**

**实机区分方法**（优先不改固件）:
1. **新增 AXIS 命令读取** `ec_axis_driver_diag_t` 快照（已准备好的补丁）:
   - `last_result == EC_AXIS_RESULT_TIMEOUT` (4) → **确认是超时**
   - `last_elapsed_ms` vs `last_timeout_ms` → 超时那一刻的真实耗时
   - `last_step_index` → 第几步超时（0-9）
   - `last_kind/last_axis/last_steps` → 超时步的类型/轴/步数

2. **示波器测量实际步进频率**（ec_board_stm32.c:174 的梯形曲线）:
   - X 轴: PC6 (TIM8_CH1)
   - Y 轴: PB6 (TIM4_CH1)
   - 预期: 200Hz 起步 → 0.36s 加速到 2000Hz → 巡航 → 0.36s 减速到 200Hz
   - 若实测频率 **低于** 梯形曲线 → 电机带载能力不足 / 驱动板限流 / 机械阻力

3. **对照组**: 台架单轴测试（`MOTION ARM` + `MOVE X DIR0 STEPS 1000 HZ 500`）
   - 若台架单轴也超时 → **固件/硬件问题**
   - 若台架单轴正常、联动超时 → **负载/机械问题**

### 路径 4：15 秒看门狗（ec_app.c:552-565）

**触发条件**:  
```c
watchdog_active == true
&& (uint32_t)(now_ms - last_observable_ms) >= 15000
→ inject EC_EVENT_DEADLINE_EXPIRED
```

**关键行号**:
- [ec_app.c:552-565](电控/firmware/stm32f407_m144z/App/Src/ec_app.c#L552-L565): 看门狗检查
- [ec_app.c:197-198](电控/firmware/stm32f407_m144z/App/Src/ec_app.c#L197-L198): 运动开始时开启看门狗
- [ec_app.c:509-510](电控/firmware/stm32f407_m144z/App/Src/ec_app.c#L509-L510): 进度令牌更新 `last_observable_ms`
- [ec_app.c:217-220](电控/firmware/stm32f407_m144z/App/Src/ec_app.c#L217-L220): DISPLAY_ACK 关闭看门狗

**为什么 5.63s ≠ 15s**:

| 现象值 | 设计值 | 比值 |
|---|---|---|
| 5.63±0.005s | 15s | **37.5%** |

**可能的解释**:

1. **实际是其它路径，5.63s 是该路径的特征周期**
   - 例如：超时线 5s + 某个固定延迟 0.63s
   - 或：端口启动重试间隔 5.63s

2. **HAL_GetTick() 时钟源错误**（可能性极低）
   - 若 SysTick 配置错误，1ms 实际可能是 2.66ms
   - 15000 * 2.66 / 1000 ≈ 40s（不符合）

3. **复位导致看门狗基准丢失**
   - 若板子在约 5.6s 时复位，`last_observable_ms` 清零
   - 但复位应该能从外部观测到（断电重启症状）

**结论**:
- ❌ **这条路径不能解释 5.63s 复现周期**
- 15s 看门狗周期与 5.63s 实测周期相差 **2.66 倍**，不能直接对应
- 若真是看门狗，需要解释为什么实际周期是 15s 的 37.5%

**实机区分方法**:
1. **新增 AXIS 命令读取**:
   - `last_result` → 若不是 TIMEOUT/ABORTED/PORT_FAIL，则可能是看门狗
   - 但看门狗触发的是 `EC_EVENT_DEADLINE_EXPIRED`，不直接调用 `fault()`

2. **检查 HAL_GetTick() 时钟**:
   ```c
   // 在 STATUS 输出加入
   printf("TICK_MS=%lu\r\n", HAL_GetTick());
   ```
   - 对比外部计时器（如 Python time.time()）
   - 若 1 秒实际是 2.66 秒 → 时钟源配置错误

### 路径 5：复位/欠压（整个 MCU 重启）

**触发条件**:
- 电源欠压（VDD < 棕色复位阈值）
- 看门狗复位（IWDG 未喂狗）
- 软件复位（NVIC_SystemReset）
- 外部 RESET 引脚拉低

**关键行号**:
- **已删除**: ec_board_stm32.c 原 :432-454 的 TIM 中断内 `NVIC_SystemReset`（2026-09-18 删除）
- [ec_app.c:569-600](电控/firmware/stm32f407_m144z/App/Src/ec_app.c#L569-L600): `ec_app_init()` — 复位后重新初始化
- main.c: `HAL_IWDG_Refresh()` — 看门狗喂狗（需查看实际位置）

**复位特征**:
- 所有静态变量清零（包括 `ec_axis_driver_diag_t`）
- 程序计数器回到 `main()` 入口
- 串口输出 `"BOOT SAFE HSI=16000000 ..."` (ec_app.c:598)

**与路径 1-4 的区分**:

| 特征 | 路径 1-4 (软件 fault) | 路径 5 (硬件复位) |
|---|---|---|
| `diag.fault_count` | 递增 | **清零** |
| `last_result` | 保留故障码 | **清零** |
| UART 输出 | 无 BOOT 消息 | **有 BOOT 消息** |
| STATUS 静态量 | 保持 | **归零** |

**结论**:
- ✅ **这条路径同时解释不发 MOTION_DONE**（复位后重新上电，之前的运动状态全部丢失）
- 5.63s 周期可能是：
  - 某个超时触发软件复位（已删除的 TIM 中断内 NVIC_SystemReset？但已删除）
  - 电源不稳定导致周期性欠压
  - 看门狗超时（IWDG 周期约 5.6s？）

**实机区分方法**:

1. **串口监听 BOOT 消息**:
   - 若每次故障后出现 `"BOOT SAFE HSI=16000000 ..."` → **确认是复位**
   - 若无 BOOT 消息 → 不是复位

2. **新增 AXIS 命令读取**:
   - 若 `fault_count == 0` → **可能是复位**（init 不清零，但复位会清）
   - 若 `fault_count > 0` → 不是复位

3. **电源监测**:
   - 示波器监测 VDD 引脚
   - 若有周期性跌落 → 电源不稳定

4. **检查 IWDG 配置**:
   - 查看 main.c 的 `MX_IWDG_Init()` 和 `HAL_IWDG_Refresh()` 位置
   - 计算 IWDG 周期是否约 5.6s
   - 若 `HAL_IWDG_Refresh()` 在主循环里，且主循环被卡住 5.6s → 看门狗复位

## 📊 已准备的观测补丁评估

**补丁内容**（ec_axis_driver.h + ec_axis_driver.c + ec_diag.c）:

新增字段（`ec_axis_driver_diag_t`）:
- `fault_count`: 累计故障次数（init 不清零）
- `last_result`: 故障码（TIMEOUT=4 / ABORTED=5 / PORT_FAIL=6）
- `last_step_index`: 故障时执行到第几步
- `last_program_length`: 故障时程序总步数
- `last_kind`: 故障步类型（MOVE/GRIPPER/Z_SERVO/...）
- `last_axis`: 故障步轴（X/Y/NONE）
- `last_steps`: 故障步步数
- `last_pulse_us`: 故障步舵机脉宽
- `last_elapsed_ms`: 该步 start → 故障的毫秒数
- `last_timeout_ms`: 该步的超时线
- `TICK_MS`: ec_step_port_now_ms() 当前时刻

新增命令: `AXIS` (ec_diag.c:424-461)

**补丁评估**:

| 字段 | 能定位的路径 | 缺失的场景 |
|---|---|---|
| `last_result` | ✅ 路径 1-3 (TIMEOUT/ABORTED/PORT_FAIL) | ❌ 路径 4-5 (看门狗/复位) |
| `last_elapsed_ms` vs `last_timeout_ms` | ✅ 路径 1 (哪一步、超了多久) | — |
| `fault_count` | ✅ 区分路径 5 (复位会清零) | — |
| `last_step_index` + `last_program_length` | ✅ 路径 6 (序列异常) | — |
| `TICK_MS` | ✅ 路径 4 (时钟源校验) | — |

**缺什么字段**:

### 补充字段 1: 状态快照（用于看门狗路径）

```c
typedef struct {
    // ... 已有字段 ...
    
    /* 运动开始时的时刻（用于验证看门狗基准） */
    uint32_t move_started_at_ms;
    
    /* 故障时的 ec_axis_state_t */
    uint8_t last_state;  // IDLE=0 / MOVING=1 / GRIPPING=2 / DONE=3 / FAULT=4
    
    /* 故障时 ec_app.c 的 watchdog_active 状态（需从 ec_app.c 暴露） */
    uint8_t watchdog_was_active;
    
    /* 故障时 ec_app.c 的 last_observable_ms（需从 ec_app.c 暴露） */
    uint32_t last_observable_at_fault;
} ec_axis_driver_diag_t;
```

**理由**: 
- 看门狗路径（路径 4）不直接调用 `fault()`，而是注入 `EC_EVENT_DEADLINE_EXPIRED`
- 当前快照只能捕获 `ec_axis_driver` 自己的故障，捕获不到 `ec_app` 层的看门狗
- 若要诊断看门狗，需要在 `ec_app.c:553-564` 的 `inject` 前也锁存快照

### 补充字段 2: 端口失败细分（用于路径 3）

```c
typedef struct {
    // ... 已有字段 ...
    
    /* 端口失败细节（仅当 last_result == PORT_FAIL 时有效） */
    uint8_t port_fail_stage;  // 0=set_direction 1=enable 2=start_counted 3=servo_start
    uint8_t port_fail_hal_status;  // HAL_StatusTypeDef: HAL_OK=0 / HAL_ERROR=1 / HAL_BUSY=2 / HAL_TIMEOUT=3
} ec_axis_driver_diag_t;
```

**理由**:
- `PORT_FAIL` 可能来自 4 个不同的端口函数（set_direction / enable / start_counted / servo_start）
- 若要定位是哪个端口函数失败，需要在 `ec_board_stm32.c` 的失败分支锁存

### 补充字段 3: 复位计数器（用于路径 5）

```c
/* 全局变量，位于 .noinit 段（复位不清零） */
__attribute__((section(".noinit"))) static uint32_t reset_count;
__attribute__((section(".noinit"))) static uint32_t last_reset_tick;

/* 在 ec_app_init() 内递增 */
void ec_app_init(void) {
    uint32_t now = HAL_GetTick();
    
    reset_count++;
    if (reset_count == 1) {
        last_reset_tick = 0;  // 首次上电
    } else {
        last_reset_tick = now;  // 记录本次复位时刻
    }
    
    // ... 其余初始化 ...
}
```

**理由**:
- `.noinit` 段在 RAM 中，复位不清零（只有断电才清）
- 若 `reset_count` 递增且周期约 5.6s → 确认是周期性复位
- 若 `reset_count == 1` 且无递增 → 不是复位

## 📝 结论

**最可能的根因**: **路径 1（轴超时）** 或 **路径 5（周期性复位）**

**一键定位方案**: 烧录带 `AXIS` 命令的固件（已准备好），复现故障后立即发送 `AXIS`，读取 `last_result`：
- `last_result == 4` → 路径 1（超时）
- `last_result == 5` → 路径 2（抑制）
- `last_result == 6` → 路径 3（端口失败）
- `fault_count == 0` → 路径 5（复位）

**补丁充分性**: 
- ✅ 路径 1-3: **充分**（`last_result` + `last_elapsed_ms` 可定案）
- ⚠️ 路径 4-5: **不充分**（需补充 `watchdog_was_active` + `.noinit` 复位计数器）
- ❌ 路径 3 细分: **不充分**（需补充 `port_fail_stage` + `port_fail_hal_status`）
