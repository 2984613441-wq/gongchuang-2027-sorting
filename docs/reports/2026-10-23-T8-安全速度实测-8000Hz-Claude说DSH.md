# 一、先说为什么原来的实测方法是错的

## 1.1 我原定的方法（Codex 证伪）

原计划："分档测 500 / 800 / 1000 / 1500 / 2000 Hz，看哪档丢步"。

**Codex 用探针发现：五个请求档位在模型里全部采用了同一个 5000 Hz 曲线峰值。**
⇒ 传入的 `HZ` 参数与实际速度**无关**，这个方法测不出任何东西。

## 1.2 根因（我读代码确认）

`ec_board_stm32.c` 的 `start_axis_counted()`：

```c
period = 0U;
if (ec_step_profile_plan(profile, steps, 200U, 5000U, 200U, 10000U, 10000U)) {
    period = ec_step_profile_reload_at(profile, 0U, EC_STEP_TIMER_HZ);
}
if (period == 0U) {
    /* Fallback: constant frequency (very short moves / degenerate params). */
    period = (EC_STEP_TIMER_HZ / frequency_hz) - 1U;
}
```

**巡航频率是硬编码的 `5000U`。** `frequency_hz`（来自 `MOVE ... HZ f`）**只在规划失败时兜底**。

源码注释原文也写着：
> ⚠️ 注意：真正生效的是**本行的 cruise 实参**，不是 `EC_AXIS_MOVE_FREQUENCY_HZ`
> —— 后者只在规划失败时兜底。改那个宏不会提速。

## 1.3 连带发现：我此前所有"耗时"测量都是假象

我写的 `move_axis_v2.py` 有 `MIN_WAIT_FACTOR = 1.15`：按**假设的 500Hz** 强制等满理论时间×1.15 才开始检查。

**⇒ 运动 1 秒就结束了，脚本却干等到 6.7 秒才看，然后报告"7.5 秒"。**
**⇒ 之前所有"7928 步用了 7.5 秒"之类的数字，全部无效。**

修正后实测：2928 步约 1 秒量级，确认机器一直跑在 **5000 Hz**，不是我原以为的 500 Hz。

# 二、为实测做的改造：`SPEED` 运行时调速

## 2.1 问题

巡航频率是编译期硬编码 ⇒ **每试一档都要改代码 + Keil 重烧**。扫 5 档就要烧 5 次。

## 2.2 方案（已实现）

| 文件 | 改动 |
|---|---|
| `App/Inc/ec_step_test.h` | `#define EC_STEP_CRUISE_HZ_DEFAULT` + `ec_step_port_set/get_cruise_hz()` 声明 |
| `App/Src/ec_board_stm32.c` | 硬编码 `5000U` → 变量 `step_cruise_hz`；新增 setter/getter |
| `App/Src/ec_diag.c` | 新增 **`SPEED <hz>`** / **`SPEED?`** 命令 |
| `tests/test_step_test.c` | 桩（保留真实校验逻辑，使边界测试有效）|
| `tests/test_diag_disabled.c` | 桩 |
| `tests/test_diag.c` | 断言 |

## 2.3 校验规则（fail-closed，失败不改原值）

```
区间       : 10 <= hz <= 10000      (EC_STEP_MIN_HZ / EC_STEP_MAX_HZ)
必须 > 200 : hz > 200               (轨迹曲线起止频率，否则 plan 直接拒绝)
采样周期   : 100000/hz >= 2         (防以后放宽上限时算出非法 reload)
```

## 2.4 语义

- **`SPEED hz`** = 轨迹曲线的**巡航上限**，下一条 MOVE 生效
- **不是最终速度**：步数不足以跑完加减速段时，曲线走"三角形"自动降峰
- **`MOVE ... HZ f`** 仍基本无效（只在规划失败时兜底）
- 掉电恢复默认值

# 三、实测方法与结果

## 3.1 方法：方框复位测试

`/home/pi/pi_square_fixed.py` —— 走 50mm（或 100mm）正方形四腿，**首尾相接，不闭合即丢步**。

**判据诚实性说明**：`STEP_RESULT=1` **只证明脉冲发完，不证明电机真的走到了**（开环、无编码器、无限位开关）。**唯一判据是物理复位**，由用户目视确认。

**另修正了一处致命陷阱**：旧 `pi_square.py` 的 Y 方向是 2026-09-18 的旧裁定（Y+ = DIR1），
而固件 `ec_motion_plan.h:62` 已在 2026-10-18 改为 `EC_MOTION_POSITIVE_Y_DIR = EC_DIRECTION_0`。
**旧脚本直接跑会把 Y 往内壁顶死堵转**（历史已发生 3 次同类事故）。

## 3.2 结果

| 设定 | 行程 | 真实峰值 | 每腿耗时 | 闭合 |
|---|---|---|---|---|
| 4000 Hz | 50mm | 4000 | 1.30 s | ✅ |
| 5000 Hz | 50mm | 5000 | 1.15 s | ✅ |
| 6000 Hz | 50mm | 6000 | 1.15 s | ✅ |
| 7000 Hz | 50mm | **~6328（封顶）** | 1.15 s | ✅ |
| **8000 Hz** | **100mm** | **8000** | **1.75 s** | **✅** |

**⇒ 全部档位方框闭合，无丢步。**

## 3.3 为什么 7000 只有 6328（重要）

4000 步行程太短。曲线加速段步数 = `(cruise² − start²) / (2·accel)`：

| 设定 | 加速段步数 | 加速+减速 | 是否够 4000 步 |
|---|---|---|---|
| 5000 | 1248 | 2496 | ✅ 够，峰值 = 5000 |
| 6000 | 1798 | 3596 | ✅ 够，峰值 = 6000 |
| **7000** | **2448** | **4896** | ❌ **不够 → 三角形降峰到 ~6328** |

**⇒ 50mm 方框在 7000 Hz 以上测不出区别，必须加长行程。**

## 3.4 8000 Hz 的强证据

100mm（8000 步）下：
- 加速段 3198 步 + 减速段 3198 步 = 6396，巡航 1604 步
- 理论耗时 = 0.78 + 0.20 + 0.78 = **1.76 s**
- **实测 1.75 s** ← **差 0.01 秒**

**⇒ 精确吻合，证明峰值确实到达 8000 Hz**（若被三角形封在 6328，耗时会是 1.23 s）。

# 五、⚠️ 未验证 / 边界

| # | 项 | 说明 |
|---|---|---|
| 1 | **10000 Hz** | **未测**。要真到峰值需 ≥9996 步（约 125mm）；从常驻位置走 125mm 方框，X 只剩 10mm 余量，**不安全**，故未做。**不得据"软件上限是 10000"就设 10000。** |
| 2 | **丢步无硬件可发现** | X/Y 不装限位开关、无编码器。若日后机械松动/电流变化，丢步会静默发生，表现为坐标基准永久失准。**建议每次大改机械后重做方框测试。** |
| 3 | **方框尺寸要匹配速度** | 想测更高速度必须加长行程，否则曲线三角形降峰，测了个假的。判据：`步数 >= 2·(cruise² − 200²)/20000`。 |
| 4 | **加速度未单独测** | 加速/减速固定 10000 Hz/s。这个值是否能提高（影响起停响应）**未评估**。 |
| 5 | **负载条件** | 本次为空载/轻载（无物块）。**满载（夹着件）时能否维持 8000 Hz 未测**，建议后续带件复测。 |
