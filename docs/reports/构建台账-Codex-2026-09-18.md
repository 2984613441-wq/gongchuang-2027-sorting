## 0. 结论先行

1. 主工作树 `电控/firmware/stm32f407_m144z/MDK-ARM` 中确有 **9 个 HEX、9 个不同 SHA-256**。全仓所有名为 `MDK-ARM` 的目录合计 **18 个物理 HEX、10 个唯一 SHA-256**：`备份/正式代码-2026-09-18` 镜像了九个同名文件，其中八个与主树同哈希，备份中的 `diankongv1.hex` 却是另一个制品（`2a5a…`），与主树当前同名文件（`cbe9…`）不同。证据见 §2.1、§2.2 的原始哈希输出。
2. **9 个主树 HEX 中，没有一个能严格称为“当前工作树源码 + 当前 uvprojx 宏组合”的产物。**最接近者是主树 `diankongv1.0/diankongv1.hex`：它是 2026-09-18 12:25 的全量重建，宏是当前 `D/M/S/G/B/P=1/1/1/0/0/0`；但构建后 `ec_axis_driver.h`、`ec_axis_driver.c`、`ec_diag.c` 又发生了字节变化。12:25 源码清单 69 项与当前相比为 66 相同、3 不同，见 `docs/reports/motion-completion-20260918/source-hashes-after.csv:2-70` 及 §4。
3. 12:25 主树 HEX 的历史输入可以精确追到已保存的 69 项哈希清单，HEX 本身也有单独哈希记录：`docs/reports/motion-completion-20260918/hex-hash.csv:1-2`。因此可以回答“`cbe955…` 是哪份源码的产物”；不能把它等同于 23:03 之后的当前源码。
4. **当前板上固件仍不能仅凭仓库和运行现象唯一识别。**固件源码中没有 `BUILD_ID`/固件哈希/源码清单标识（§6 的搜索 `RG_EXIT=1`），本轮又没有板端 flash dump 或板端报告的制品哈希。`FAULT_LOCK`、不发 `MOTION_DONE` 等现象不是唯一制品标识。缺少的决定性证据是：板端固件字节哈希（或预先嵌入且可读取的 build ID）与本台账 SHA-256 的比对。

## 6. 板上固件的可回答边界

本轮对运行源码做了以下只读搜索：

```powershell

  电控/firmware/stm32f407_m144z/Core `
  电控/stm32_logic
```

原始结果：

```text
RG_EXIT=1
```

即这些路径中没有命中可用于唯一识别制品的 build ID/哈希字段。结合本轮未做硬件读取，当前只能建立以下判定规则，不能替板上固件作唯一选择：

1. 若未来取得板端固件字节哈希，并命中 §2.1 或 §2.2 的 10 个唯一 SHA-256之一，则按 §3 回查对应宏与源码证据。
2. 若命中 `cbe955…`，其精确源码是 `source-hashes-after.csv:2-70` 的 12:25 快照，不是当前 23:03 后源码。
3. 若命中 `2a5a57…`，对应备份树 00:43 全量构建；宏可归到 `1/1/1/0/0`，精确源文件字节仍【证据不足】。
4. 若不命中这 10 个唯一哈希，则板上固件来自仓库未留存/已被覆盖的构建产物，现有台账不能继续猜。

以后要让问题在无 flash dump 情况下也可直接回答，需要在固件中嵌入不可变 build ID（至少包含 HEX SHA 或构建清单 SHA、宏组合、时间），并让诊断/二进制协议只读返回；这属于后续设计建议，本只读任务未实施。
