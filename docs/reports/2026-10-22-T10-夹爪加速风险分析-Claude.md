## 一、当前时序与瓶颈

### 1.1 夹取流程（13 步）

**`App/Inc/ec_axis_driver.h:148-162`**（已核对固件）：

```c
// 步骤定义（step 0-12，共 13 步）
[0] 待机位（625µs = STANDBY）        ← 舵机步，等待 600ms
[1] Z 下降（夹爪降到取料位）          ← 步进，200ms 到位停留
[2] （保持 STANDBY）
[3] 张开到类别宽度（800~1900µs）     ← 舵机步，等待 600ms
[4] （保持张开）
[5] 闭合（1900µs = CLOSE）           ← 舵机步，等待 600ms
[6] Z 上升（抬起物块）
[7] （保持 CLOSE）
[8] 到落料点后释放（800µs = OPEN）  ← 舵机步，等待 600ms
[9] 回待机位（625µs = STANDBY）      ← 舵机步，等待 600ms
[10] （保持 STANDBY）
[11] （保持 STANDBY）
[12] （保持 STANDBY）
```

**舵机步统计**：5 个（步骤 0/3/5/8/9），每个等待 `EC_AXIS_GRIPPER_SETTLE_MS = 600ms`

**⇒ 舵机等待总时长 = 5 × 600ms = 3000ms = 3.0 秒/件**

### 1.2 时间预算（15s 失活窗口）

**固件注释**（`ec_axis_driver.h:201-216`）：

```
单件时间分解（当前实测，主频 168MHz）：
  视觉识别         ≈ 0.50s  （MaixCAM → 树莓派）
  取料 Z 下降      ≈ 0.40s  （步进运动）
  夹取 + 舵机等待  ≈ 3.00s  （5 × 600ms）← 瓶颈
  搬运 XY 行程     ≈ 10.0s  （最远端，500Hz）
  Z 上升           ≈ 0.26s
  ─────────────────────────
  总计             ≈ 14.16s

赛规失活窗口       = 15.0s
真实余量           = 15.0 - 14.16 = 0.84s（紧张）
```

**⇒ 夹取时序（3.0s）是最大可优化项，但改动有风险。**

## 二、历史背景：为什么是 600ms

### 2.1 演变历史

| 日期 | 值 | 原因 |
|---|---|---|
| 2025 初版 | **200ms** | 初始值（经验值） |
| 2025-06 | **600ms** | 用户反馈："一件都夹不起来"（实测失败率 100%）|
| 2026-10-18 | **仍是 600ms** | 主频修正后未重新标定 |

**关键引用**（派工单 §2.5）：
> "这个 600 是当年从 200 调上来的（'一件都夹不起来'）"

### 2.2 主频修正的影响（⚠️ 关键变化）

**旧固件问题**（2026-10-18 前）：

```c
// 旧固件：主频配置错误，实际运行在 54MHz
// 延时函数：HAL_Delay(ms) 假设主频 168MHz
// 实际延时 = 600ms × (168/54) ≈ 1875ms  ← 慢了 3.125 倍！
```

**新固件修正**（2026-10-18 起）：

```c
// 主频已修正为 168MHz
// 延时函数：HAL_Delay(600) 实际等待 600ms  ← 准确
```

**⇒ 主频修正后，600ms 实际变快了 3.125 倍（从 1875ms → 600ms）**

**推论**：
- 旧固件：写 600ms，实际等 1875ms → **足够舵机合拢**
- 新固件：写 600ms，实际等 600ms → **可能不够**（未实测）
- **若旧固件能夹起来，真实需求可能是 ≈1800ms，而非 600ms**

## 三、风险边界分析

### 3.1 舵机物理限制（MG996R）

**已知参数**：

| 参数 | 值 | 来源 |
|---|---|---|
| 型号 | MG996R | 夹爪与转盘同型号 |
| 工作电压 | 4.8V~6V | 规格书 |
| 转速（4.8V） | 60° / 0.17s | 规格书 |
| 转速（6V） | 60° / 0.14s | 规格书 |
| **最大行程**（待机→闭合） | **1900−625 = 1275µs** | 固件常量 |

**角度换算**（假设 MG996R 量程 270°，us_per_90deg ≈ 655）：

```
角度 = Δpulse_us / us_per_90deg × 90°
     = 1275µs / 655 × 90°
     ≈ 175°
```

**理论合拢时间**（6V 供电）：

```
t_move = 175° / (60° / 0.14s) ≈ 175 × 0.14 / 60 ≈ 0.41s = 410ms
```

**⇒ 理论最快 ≈ 410ms（6V）/ 485ms（4.8V）**

### 3.2 实际需要更长的原因

**机械因素**：
1. **惯性 + 抖动整定**：舵机到位后需要时间稳定（典型 50~100ms）
2. **负载影响**：夹爪有机械臂 + 物块重量，转速比空载慢
3. **摩擦 + 弹簧阻力**：夹爪机构有回弹力，减慢合拢速度
4. **电压下降**：连续运动时电源电压可能低于 6V

**电控因素**：
1. **STM32 PWM 更新延迟**：写新脉宽到 TIM2 CCR 有 1~2ms 延迟
2. **舵机响应延迟**：从接收脉宽到开始转动有 ≈20ms 延迟
3. **多舵机串扰**：5 个舵机步连续执行，可能有电流争夺

**经验安全系数**：理论时间 × 1.5~2.0

```
实际需求 ≈ 410ms × 1.5~2.0 = 615~820ms
```

**⇒ 当前 600ms 可能刚好在边界，稍快就会"夹不起来"。**

### 3.3 "夹不起来"的三种失效模式

| 模式 | 现象 | 根因 |
|---|---|---|
| **M1：未合拢** | 舵机还在转动时 Z 就上升 → 物块滑落 | 等待时间 < 实际合拢时间 |
| **M2：力度不足** | 夹爪闭合但未夹紧 → 抬起时物块掉落 | 舵机未到位（PWM 占空比未稳定）|
| **M3：位置偏移** | 舵机抖动导致物块被推偏 → 下一步夹空 | 整定时间不够（到位后晃动）|

**⇒ 任何一种失效都会导致"一件都夹不起来"（用户 2025-06 原话）。**

## 五、实测方案（用户操作）

### 5.1 实测目标

**必须回答的 3 个问题**：

1. **舵机实际合拢时间是多少？**（目视 + 秒表）
2. **600ms 是否够用？**（当前固件实测，非旧固件的 1875ms）
3. **最小安全值是多少？**（二分法试探）

### 5.2 实测步骤

**步骤 1：目视测量合拢时间**

```bash
# 在树莓派上，单独测试夹爪
# 方法 1：发送 GRIPPER 命令（需要固件支持，可能没有）
# 方法 2：直接改 TIM2 CCR 寄存器（需要写测试程序）
# 方法 3：用秒表 + 手机录像（最简单）

# 操作：
1. 夹爪设置为待机位（625µs）
2. 手机录像 + 秒表同时开始
3. 切换到闭合位（1900µs）
4. 目视夹爪完全合拢并停稳
5. 秒表停止，记录时间

# 重复 3 次取平均值
```

**步骤 2：当前 600ms 是否够用**

```bash
# 实机分拣测试（6 种件各 5 个）
# 记录失效次数：
#   - 物块滑落（M1：未合拢）
#   - 抬起时掉落（M2：力度不足）
#   - 第二次夹空（M3：位置偏移）

# 判定标准：
#   失效率 = 0%     → 600ms 够用，可以缩短
#   失效率 = 1-5%   → 600ms 临界，不建议缩短
#   失效率 > 5%     → 600ms 不够，必须延长
```

**步骤 3：二分法找最小安全值**（若 600ms 够用）

```bash
# 修改固件常量：
# ec_axis_driver.h:
#   #define EC_AXIS_GRIPPER_SETTLE_MS 500U  // 先试 500ms

# 重新编译 + 烧录
# 实机测试（6 种件各 5 个）
# 记录失效率

# 若失效率 = 0%  → 继续缩短到 450ms
# 若失效率 > 0%  → 回退到 550ms（500+50），作为安全值
```

### 5.3 预期结果与决策树

```
实测合拢时间 t_actual：
  │
  ├─ t_actual ≤ 500ms
  │   → 理论上可以缩短到 500ms
  │   → 建议保留 100ms 余量 → 设置 600ms（不变）
  │   → 或激进方案：550ms（节省 50ms × 5 = 250ms/件）
  │
  ├─ 500ms < t_actual ≤ 700ms
  │   → 当前 600ms 在边界
  │   → 建议延长到 700ms（安全）
  │   → 代价：单件 +0.1s，余量从 0.84s → 0.74s
  │
  └─ t_actual > 700ms
      → 当前 600ms 严重不足
      → 必须延长到 t_actual + 100ms
      → ⚠️ 若超过 750ms，会导致单件 > 15s
```

## 六、推荐方案（分场景）

### 6.1 场景 A：实测合拢时间 ≤ 500ms（理想）

**方案 A1：保守（推荐）**

```c

```

**优点**：
- ✅ 零风险（当前已验证能用）
- ✅ 无需重新标定
- ✅ 余量 ≈0.84s，足够应对抖动

**缺点**：
- ⚠️ 未利用提速潜力（可节省 0.5s/件）

**方案 A2：激进**

```c
#define EC_AXIS_GRIPPER_SETTLE_MS  500U  // 缩短 100ms
```

**优点**：
- ✅ 单件节省 0.5s（5 × 100ms）
- ✅ 余量增加到 1.34s

**缺点**：
- 🟡 需要实测验证（失效率必须 = 0%）
- 🟡 机械磨损/电压波动可能导致后期失效

### 6.2 场景 B：实测合拢时间 500~700ms（边界）

**方案 B1：最小安全值**

```c
#define EC_AXIS_GRIPPER_SETTLE_MS  (t_actual + 100)U
// 例如：实测 580ms → 设置 680ms
```

**优点**：
- ✅ 保留 100ms 安全余量
- ✅ 不浪费时间

**缺点**：
- ⚠️ 余量可能减少（例如 680ms → 余量 0.44s）

### 6.3 场景 C：实测合拢时间 > 700ms（危险）

**⚠️ 问题严重**：当前 600ms 严重不足，会导致"夹不起来"

**方案 C1：延长等待**

```c
#define EC_AXIS_GRIPPER_SETTLE_MS  (t_actual + 150)U
// 例如：实测 750ms → 设置 900ms
```

**后果**：
- 🔴 单件时间 = 14.16 + (900−600)×5/1000 = 14.16 + 1.5 = **15.66s**
- 🔴 **超过 15s 失活窗口**，必然触发 ESTOP

**⇒ 必须同时优化其他环节（滑台速度 / XY 联动 / 视觉延迟）**

**方案 C2：分段优化（多管齐下）**

| 优化项 | 节省时间 | 可行性 |
|---|---|---|
| XY 联动（斜线） | ≈1.0s | ✅ T7 任务 |
| 提速到 800Hz | ≈3.75s | ⚠️ 需测丢步（T8 任务）|
| 视觉并行化 | ≈0.3s | 🟡 复杂（需改协议）|
| 取消部分停留 | ≈0.2s | 🟡 可能影响稳定性 |

**⇒ 若 XY 联动 + 提速成功，可以节省 ≈4.75s，抵消舵机延长的 1.5s**
