# 端到端 T3「分拣一件」可执行验收清单

日期：2026-09-18

状态：**待现场执行；本文只给清单与方案，未执行接线、上电、烧录、串口或实机运动。**

适用链路：MaixCAM → 树莓派 `run_chain.py` → STM32 → 机构 → HDMI 屏 → `DISPLAY_ACK`。

当前放行结论：**NO-GO**。板子仍在受理后约 5 秒进入 `FAULT_LOCK` 且没有实机 `MOTION_DONE`；本清单是故障解除后的验收门，不构成现在启动实机运动的授权。

## 0. 通过定义与当前基线

T3 只有在**同一次运行、同一件目标、同一条时间线**内同时满足以下条件，才可填写“通过”：

1. 树莓派打印本件 `ITEM_TASK sent`，坐标仍为安全临时落点 `(5.0,5.0)mm`；
2. STM32 回 `ACK_ACCEPTED`；首件启动可能先出现 `BARRIER_READY` 和原帧重发，这是现行启动路径的一部分；
3. STM32 依次回 `MOTION_DONE`、`ITEM_RESULT`；
4. `ITEM_RESULT` 为 SUCCESS，树莓派完成规则帧实屏渲染并发出 `DISPLAY_ACK`；
5. 当前代码应再看到 `ACK_ACK_CONSUMED`，证明 STM32 已消费 `DISPLAY_ACK`；若没有该行，本轮闭环证据不完整，不得把“Pi 已发送”写成“板端已消费”；
6. `success_count` 相对本轮基线只增加 1，且没有重复运动、重复计数或插入另一件任务；
7. 现场人员确认：物块被抓取、移动、释放到 `(5,5)mm` 临时落点附近，机构回到上电原点/行程正中，屏幕显示本件规定信息，全程无越程、堵转、碰撞、急停或 `FAULT_LOCK`。

任一项缺失、字段不匹配、跨运行拼接，均为“不通过/证据不足”，不是“部分通过”。当前已确认的实机基线止于：

```text
ITEM_TASK sent: target_seq=4 class_id=4 image_id=4 落点=(5.0,5.0)mm 抓取点=(12.5,5.4)mm
WARNING ec-chain: inbound ACK_ACCEPTED:
```

现有实机记录中尚无 `MOTION_DONE / ITEM_RESULT / DISPLAY_ACK` 完整闭环，因此本文不得被引用为“T3 已通过”。

## 1. 红线与立即停止条件

- X/Y 无限位且已有三次越程。**上电前先把机构摆在 190 mm 行程正中**：X 距两端各约 95 mm；Y 也按当前有效行程居中。不得用“软件会回零”替代人工摆中。
- 整个运动阶段必须有一人专职守急停，视线不离开机构；另一人负责日志。只有一人时不做测试。
- 链路运行时，除 `run_chain.py` 自身外，**任何进程都不得打开 `/dev/serial0`**。不得同时运行 `pi_gate_probe.py`、`pi_observe_board.py`、串口终端或第二个链路实例。
- `lightdm` 必须处于 `inactive`；否则 fb0 规则帧不能作为验收证据。
- `[DropPoints]` 的 1～6 在本轮全部保持 `5.0, 5.0`。T3 完整通过前禁止恢复远端落点。
- 物块只放托盘中央的固定位置；本轮不得在视觉已经锁定后再移动物块。
- 出现靠近机械端部、异响/堵转声、碰撞、坐标明显反向、失控、冒烟或人员判断不安全时，守急停人员立即急停；本轮判失败，禁止自动重试。
- 从 `ACK_ACCEPTED` 到闭环结束若出现 `FAULT_LOCK`，本轮立即失败。即使稍后由重传恢复，也不能把该轮算作“首次完整运动通过”。

### 3.2 树莓派只读预检

链路尚未运行时执行以下只读命令；这些命令只查设备与占用，**不会打开** `/dev/serial0`：

```bash
PREFLIGHT_LOG="/home/pi/t3-preflight-$(date +%Y%m%d-%H%M%S).log"
{
  echo '=== host ==='
  date --iso-8601=seconds
  hostname
  whoami
  echo '=== chain process ==='
  pgrep -af 'run_chai[n].py' || echo 'NO chain running (good)'
  echo '=== serial0 ==='
  ls -l /dev/serial0
  UART_DEV=$(readlink -f /dev/serial0)
  printf 'serial0 -> %s\n' "$UART_DEV"
  sudo fuser -v /dev/serial0 2>&1 || echo 'fuser: 无进程占用'
  command -v lsof >/dev/null && { lsof /dev/serial0 2>&1 || echo 'lsof: 无进程占用'; }
  echo '=== serial getty ==='
  systemctl is-active "serial-getty@$(basename "$UART_DEV").service" || true
  echo '=== lightdm ==='
  systemctl is-active lightdm || true
  echo '=== runtime config ==='
  sha256sum /home/pi/sorting_config.ini /home/pi/电控/deploy/run_chain.py
  sed -n '/^\[DropPoints\]/,/^\[/p' /home/pi/sorting_config.ini
} 2>&1 | tee "$PREFLIGHT_LOG"
```

逐项必须看到：

```text

<YYYY-MM-DDTHH:MM:SS+08:00>
<hostname>
pi
=== chain process ===
NO chain running (good)
=== serial0 ===
lrwxrwxrwx ... /dev/serial0 -> ttyS0

fuser: 无进程占用
lsof: 无进程占用

inactive
=== lightdm ===
inactive
```

通过条件：

- [ ] `pgrep` 没有任何旧 `run_chain.py` 实例（无论其参数是否含 `--config`）；
- [ ] `/dev/serial0` 实际解析为现场已确认的 `ttyS0`；
- [ ] `fuser`/`lsof` 没有 PID；缺少其中一个工具时，另一个检查必须有结果；
- [ ] `systemctl is-active serial-getty@ttyS0.service` 不是 `active`；若 serial0 实际解析到别的 tty，用其 basename 检查对应 getty；
- [ ] `systemctl is-active lightdm` 原始输出为 `inactive`；`active` 或 `failed` 均先处理，不带病进入验收；
- [ ] `/home/pi/sorting_config.ini` 是 Pi 本次实读配置，且记录了路径、时间与散列；
- [ ] 两份配置若不一致，以 `/home/pi/sorting_config.ini` 为本轮实际值，并先停止验收、查清部署来源，不临场猜用哪份。

若 lightdm 仍为 active，只执行：

```bash

systemctl is-active lightdm
```

第二行必须原样输出 `inactive` 后才能继续。

## 4. 执行步骤与逐步判据

### 步骤 1：启动唯一链路并保存原始日志

不要直接运行会删除 `/tmp/chain.log` 的便捷启动脚本；本次要保留唯一命名、不可覆盖的原始证据。使用前台命令，且只能启动一个实例：

```bash
RUN_ID="T3-$(date +%Y%m%d-%H%M%S)"
LOG="/home/pi/${RUN_ID}-chain.log"
cd /home/pi/电控
PYTHONPATH=src python3 -u deploy/run_chain.py \
  --config /home/pi/sorting_config.ini \
  --port /dev/serial0 \
  --image-dir /home/pi/images \
  --names-file /home/pi/电控/deploy/names.json \
  --frame-output fb0 \
  --font /usr/share/fonts/truetype/wqy/wqy-zenhei.ttc \
  --round-id "$RUN_ID" --round-task-id 1 --start-round \
  2>&1 | tee "$LOG"
```

把终端留在前台；不要再开任何串口工具。`RUN_ID`、`LOG` 路径和启动命令本身一起写进证据头。

期望原始输出：

```text
<ts> INFO    ec-chain: 落料策略=方案A（六固定盒）：[DropPoints] 六盒已校验齐全
<ts> INFO    ec-chain: 串口已打开: /dev/serial0 @ 115200 8N1
<ts> INFO    ec-chain: 视觉监听线程已启动: 0.0.0.0:8765
<ts> INFO    ec-chain: 链路就绪：next_task → send_item_task → 轮询入站 → 渲染 → DISPLAY_ACK
<ts> INFO    ec-chain: 空闲: state=READY success=0
```

最后一行是本轮计数基线；等待它出现后才放物块。若 10 秒内未出现，允许再等一个 10 秒日志周期，但不发送任何串口探针。

失败分流：

- `SerialException ... multiple access on port?`：串口被并发打开；本轮失败，停链后重新查 PID。不得归因于 STM32 协议。
- `字体文件不存在`、图片目录/名称表错误、`FramebufferFormatError`、fb0 打不开：显示前置失败；不进入运动。
- `[DropPoints]` 缺项/解析失败或不是安全临时值：配置失败；不进入运动。
- 一直 `state=RECOVERY_LOCK`：启动轮次门未建立；检查本次命令是否含经批准的 `--start-round`，不通过串口另发任务绕过。
- 启动后立即 `scheduler FAULT`：保存 traceback 和前后 30 行，本轮停止。

### 步骤 2：放一件并确认视觉→Pi 任务

急停员已就位后，放料员把**一件**物块放托盘中央固定点；手完全退出危险区。

本次给定目标的通过行必须逐字段相同：

```text
<ts> INFO    ec-chain: ITEM_TASK sent: target_seq=4 class_id=4 image_id=4 落点=(5.0,5.0)mm 抓取点=(12.5,5.4)mm
```

允许在此前看到附加屏幕行：

```text
<ts> INFO    ec-chain: 两段显示已上屏: 1024x600 target_seq=4 box_id=4
```

这条附加屏幕行不等于规则帧，也不等于 `DISPLAY_ACK`。

失败分流：

- 无 `ITEM_TASK sent`：查 `视觉监听线程已启动`、MaixCAM TCP/TASK_ID、固定抓取点/标定拒识日志；此时 AXIS/STATUS 不能解释视觉未派发。
- `target_seq/class_id/image_id` 任一不是 `4`：身份不匹配，本轮不验收。
- 落点不是 `(5.0,5.0)`：立即急停/终止链路，不等后续运动；配置或实际部署文件不符。
- 抓取点不是本轮预期 `(12.5,5.4)`：不批准运动；先核对视觉输入/当前抓取点来源，不用历史坐标替代。

### 步骤 3：确认 STM32 受理

首件启动时可能出现以下三行；顺序以本次时间戳为准：

```text
<ts> INFO    ec-chain: inbound: BARRIER_READY（STM32 就绪上报）
<ts> WARNING ec-chain: BARRIER_READY = 建轮次那一发 ITEM_TASK 已被启动序列吞掉，立即重发... frame_seq=<n> (<bytes>B)
<ts> WARNING ec-chain: inbound ACK_ACCEPTED:
```

通过条件：`ACK_ACCEPTED` 在同一链路进程、同一在飞任务且没有插入新 `ITEM_TASK sent` 的时间窗内出现。记录 `ITEM_TASK sent` 到 ACK 的时间差；51 ms 是已知历史事实，本轮以新日志实测值为准。

当前控制台 ACK 行**不含** `target_seq/task_id/frame_seq`。因此只能凭同一进程、无插入任务和相邻时间窗关联；不得把这条行改写成“ACK 明确携带 target_seq=4”。如需帧级身份，只能另行增强链路内日志，不能在运行中开第二个串口进程抓包。

失败分流：

- `inbound NACK_STALE_OR_ORDER:`：帧序号陈旧/错序；保存该行和前一条 ITEM_TASK。
- `inbound NACK_SINGLE_TASK_ONLY:`：板上已有未结案件；不得再发新任务。
- `inbound NACK_WRONG_ROUND:`：Pi/STM32 轮次号不一致。
- `inbound NACK_TASK_REJECTED:`：任务被拒；保留任务坐标与身份字段。
- 只有 `BARRIER_READY`，5 秒后反复 `ITEM_TASK 超时 5.0s 无应答`：受理未闭合；不得算链路通过。
- 完全无入站且链路进程仍活：先按失败收尾停掉链路，再读 STATUS；运行中禁止开探针。

### 步骤 4：确认运动完成

期望原始输出：

```text
<ts> INFO    ec-chain: inbound: MOTION_DONE accepted
```

协议层的 MOTION_DONE 是命令 `0x22`、空载荷；现行 `run_chain.py` 控制台不打印完整帧字节。没有链路内原始帧记录时，不得自行补写 CRC、frame_seq 或十六进制字节。

物理同步观察必须记录：抓取成功 → 搬运 → 释放 → 回到上电原点/正中；无越程、堵转、反向、碰撞或急停。`MOTION_DONE` 只表示运动序列完成，不等于本件成功。

失败分流：

- ACK 后进入 `FAULT_LOCK`、但没有 MOTION_DONE：立即判失败；按 §5 在链路停止后采 `STATUS + AXIS`。
- ACK 后没有 MOTION_DONE，随后 `BARRIER_READY` 继续以约 `5.63±0.005s` 重现：命中当前故障指纹，说明本件未闭环且启动序列再次出现；保留完整时间线，不把新一轮 BARRIER 当作本件完成。
- 停链后 STATUS 为 `APP_STATE=EXECUTING` 且 AXIS `STATE=1`：停链时板端仍认为在执行；结合链路中的 `ITEM_TASK 超时 5.0s 无应答` 与故障时间线判失败，不在运行中另开串口确认。
- 停链后 STATUS 为 `APP_STATE=WAIT_ITEM_RESULT` 且 AXIS `STATE=3 RESULT=0`，Pi 日志却没有 MOTION_DONE：分流到“运动完成事件 → 编码/TX → Pi 入站”区间；不要再改运动参数。
- 停链后 STATUS 为 `APP_STATE=WAIT_DISPLAY_ACK`，Pi 日志同时缺 MOTION_DONE/ITEM_RESULT：板端已越过运动/结果阶段，优先查板端 TX、串口混流和 Pi 入站记录。

### 步骤 5：确认 ITEM_RESULT 为成功

期望控制台先出现：

```text
<ts> INFO    ec-chain: inbound: ITEM_RESULT accepted
```

随后必须由显示行的 `success=N+1` 和物理结果共同证明成功。当前控制台这行本身**不打印** `result_code/basis/target_seq`，不能仅凭“accepted”声称 SUCCESS。

结果码分流（原始帧/监控若留有字段时）：

| `result_code` | 含义 | T3 处理 |
|---:|---|---|
| `0x00` | SUCCESS | 继续规则帧与 DISPLAY_ACK |
| `0x01` | DROP_FAILED | 失败；查释放/落料结果，不递增计数 |
| `0x02` | GRIP_FAILED | 失败；查抓取过程，不递增计数 |
| `0x03` | POSITION_UNREACHABLE | 失败；保存本件抓取/落点坐标，不运动重试 |
| `0x04` | SAFETY_INTERRUPT | 失败；查安全输入/急停，不递增计数 |
| `0xFF` | UNKNOWN | 失败；保留原始帧，不猜根因 |

若出现：

```text
<ts> WARNING ec-chain: 结果码非 SUCCESS（target_seq=4）：不显示「分拣成功」
```

则本轮明确失败，即便之后能发送失败结果的显示确认也不算 T3 成功。

### 步骤 6：确认规则帧上屏并发送 DISPLAY_ACK

现场人员先肉眼确认屏幕规则帧包含本件序号、名称/图片、SUCCESS 和累计数量；再核对原始行：

```text
<ts> INFO    ec-chain: 显示完成并确认: target_seq=4 name=<本件名称> success=1 → DISPLAY_ACK
```

若本轮基线不是 0，则 `success` 必须为 `基线+1`。现行控制台没有一条字面为 `DISPLAY_ACK sent` 的 INFO；上面这条才是当前真实控制台判据。

当前代码的完整闭环还必须看到：

```text
<ts> WARNING ec-chain: inbound ACK_ACK_CONSUMED:
```

这表示 STM32 已消费首次有效 `DISPLAY_ACK`。缺少该行时，证据只够证明 Pi 已发送，不够证明板端已消费；本轮按闭环证据不足处理。

失败分流：

- `ITEM_RESULT accepted` 后进程 traceback/退出，且无“显示完成并确认”：查图片缺失、字体、fb0/bpp、渲染异常；不要归咎于运动。
- 屏幕未实际刷新但日志称完成：实机显示证据失败；不得仅凭日志通过。
- 有 `inbound NACK_ACK_NOT_APPLICABLE:`：DISPLAY_ACK 的状态/身份/CRC 不适用；保存显示行与 NACK。
- 有 `inbound NACK_WRONG_ROUND:`：显示确认的轮次不匹配。
- 已发 DISPLAY_ACK 但无 ACK_CONSUMED，且板端 STATUS 停在 `WAIT_DISPLAY_ACK`：查 `target_seq`、`render_result`、内容 CRC、task_id 和 UART 入站；不得开始下一件。

### 步骤 7：确认 success_count 只递增一次并结束本轮

等待下一次 10 秒空闲日志，不再放第二件：

```text
<ts> INFO    ec-chain: 空闲: state=READY success=1
```

通过条件：启动基线 `success=0`，本件显示行 `success=1`，闭环后仍 `success=1`。没有第二条不同身份的 `ITEM_TASK sent`，没有重复抓放。

如本轮由有限任务源正常退出，还可补充：

```text
<ts> INFO    ec-chain: 本轮汇总: 派发 1 件, 成功计数 1
```

真实动态视觉源通常持续等待，不要求为了得到汇总行而异常结束进程。

失败分流：

- 仍为 `success=0`：ITEM_RESULT 非 SUCCESS 或计数未提交；本轮失败。
- 跳到 `success=2`：重复结果被计数或混入另一件；本轮失败。
- 状态不是 READY，或又出现新任务：未完成单件闭环/现场未隔离单件。
- 计数正确但物理未抓/未放/未回中或屏幕错误：仍失败；软件计数不替代实机观察。

## 5. 失败后的 STATUS / AXIS 分流（只能停链后执行）

### 5.1 安全收尾顺序

1. 若机构仍可能运动，急停员先按现场安全规程处置；不要为了取日志把手伸入危险区。
2. 终止唯一 `run_chain.py`，保留步骤 1 的 `/home/pi/T3-*-chain.log`（若现场另有 `/tmp/chain.log` 也一并保留），不要先删除或覆盖。
3. 执行 `pgrep -af 'run_chai[n].py'` 与 `fuser -v /dev/serial0`；确认没有链路 PID/占用。
4. **只有此时**才能让一个诊断进程打开串口：

```bash
OBS=/home/pi/工具/pi_observe_board.py
test -f "$OBS" || OBS=/home/pi/pi_observe_board.py
test -f "$OBS" || { echo 'pi_observe_board.py 未部署'; exit 1; }
python3 "$OBS" 12 \
  | tee "/home/pi/t3-axis-status-$(date +%Y%m%d-%H%M%S).log"
```

该脚本只发 `PING / STATUS / AXIS`，不发运动命令。需要同期输入快照时，等它退出后再顺序执行：

```bash
GATE=/home/pi/工具/pi_gate_probe.py
test -f "$GATE" || GATE=/home/pi/pi_gate_probe.py
test -f "$GATE" || { echo 'pi_gate_probe.py 未部署'; exit 1; }
python3 "$GATE" status \
  | tee "/home/pi/t3-inputs-status-$(date +%Y%m%d-%H%M%S).log"
```

期望保留完整 `INPUTS RAW=<hhhh> STABLE=<hhhh> ACTIVE=<hhhh>` 与 STATUS 行。两个诊断脚本都禁止与链路或彼此并行运行。

### 5.2 STATUS 判据

原始 STATUS 格式中必须保留完整行，不能只摘 `APP_STATE`：

```text
STATUS SAFE_LOCK=1 MOTION_TEST=1 SERVO_TEST=1 ARMED=0 MODE=0 STEP_AXIS=0 STEP_TARGET=0 STEP_REMAIN=0 STEP_RESULT=0 SERVO_ARMED=0 SERVO_ACTIVE=0 SERVO_US=0 GROUP_TEST=0 GROUP_ARMED=0 GROUP_ACTIVE=0 GROUP_XDIR=0 GROUP_YDIR=0 GROUP_SERVO_US=0 BARRIER_TEST=0 BARRIER_ARMED=0 BARRIER_ACTIVE=0 BARRIER_MASK=0 BARRIER_US=0 APP_STATE=FAULT_LOCK
```

关键解释：

- `APP_STATE=FAULT_LOCK`：只证明应用已锁定，不足以区分轴超时、轴中止、端口失败、急停、失电、deadline 或去重冲突；必须结合 AXIS。
- `APP_STATE=EXECUTING`：板端仍认为在执行；结合 AXIS `STATE/RESULT/PROGRESS`。
- `APP_STATE=WAIT_ITEM_RESULT`：板端已接受运动完成事件，正在结果阶段。
- `APP_STATE=WAIT_DISPLAY_ACK`：板端已经发出/处理到结果阶段，等待有效显示确认。
- `APP_STATE=WAIT_TASK`：板端没有当前未结案件；若 Pi 仍 `WAIT_MOTION_DONE`，两端状态已分叉。
- `SAFE_LOCK=1` 是当前 STATUS 格式里的固定字面量，不能凭它判断“刚发生故障”。
- STATUS 的 `STEP_*` 属于**诊断 MOVE 模块**，不是生产 `ITEM_TASK` 运动的 AXIS 现场。生产故障不得用 `STEP_RESULT=0` 推断“轴没动”；应看下一节 AXIS。

### 5.3 AXIS 字段与具体分流

原始格式：

```text
AXIS FAULTS=<n> TICK_MS=<n> STATE=<n> RESULT=<n> PROGRESS=<n> MOVES=<n> LAST_RESULT=<n> LAST_STEP=<n> LAST_LEN=<n> LAST_KIND=<n> LAST_AXIS=<n> LAST_STEPS=<n> LAST_PULSE_US=<n> LAST_ELAPSED_MS=<n> LAST_TIMEOUT_MS=<n>
```

枚举：

- `STATE`: `0 IDLE / 1 MOVING / 2 GRIPPING / 3 DONE / 4 FAULT`
- `RESULT`、`LAST_RESULT`: `0 OK / 1 BUSY / 2 INVALID_PARAM / 3 INHIBITED / 4 TIMEOUT / 5 ABORTED / 6 PORT_FAIL`
- `LAST_AXIS`: `0 NONE / 1 X / 2 Y / 3 Z`
- `LAST_KIND`: `0 MOVE / 1 GRIPPER / 2 Z_SERVO / 3 legacy MOVE_XY / 4 XY_INTERP / 255 无当前步`

`LAST_STEP` 是本次动态程序的 0-based 索引；零位移步骤会被省略，不能硬编码“第 N 步一定是哪一轴”。必须联合 `LAST_KIND/LAST_AXIS/LAST_STEPS/LAST_PULSE_US` 定位。`PROGRESS` 是已完成程序步骤数，不是百分比，也不是协议字段。

| STATUS + AXIS 原始字段 | 分流结论 | 下一步（本清单不执行） |
|---|---|---|
| 本轮 `FAULTS` 比基线加 1，`LAST_RESULT=4`（故障当时通常 `APP_STATE=FAULT_LOCK`） | 生产轴在 `LAST_STEP/LAST_AXIS` 超时 | 比较 `LAST_ELAPSED_MS` 与 `LAST_TIMEOUT_MS`，核对该腿的完成 latch/IRQ/实际烧录版本；不把超时改写成 DONE |
| 本轮 `FAULTS` 比基线加 1，`LAST_RESULT=5` | 生产轴被中止 | 同时保存 `INPUTS RAW/STABLE/ACTIVE` 与急停经过；区分真实安全输入与人为急停，不重试旧任务 |
| 本轮 `FAULTS` 比基线加 1，`LAST_RESULT=6` | 端口启动失败 | 查具体 `LAST_STEP/LAST_AXIS` 的端口启动返回；不先改协议或坐标 |
| 当前 `RESULT=1/2/3`，且 `FAULTS` 未增加 | 启动返回 BUSY/INVALID/INHIBITED；通常应走失败 ITEM_RESULT，而不是轴 fault 锁存 | 查本件 `ITEM_RESULT` 与启动条件；若同时出现相反的 `STATE=4` 组合，标 UNKNOWN，不自行解释 |
| `STATE=3 RESULT=0`，`APP_STATE=WAIT_ITEM_RESULT`，Pi 无 MOTION_DONE | 轴程序完成，问题在完成事件→编码/TX→Pi 入站区间 | 保存同一时间窗板端 TX/链路日志；不再调查视觉派发 |
| `APP_STATE=WAIT_DISPLAY_ACK`，Pi 缺 ITEM_RESULT | 板端已到等待显示阶段，结果上报未被 Pi 观察到 | 查 ITEM_RESULT 的 TX/解析；不要重放运动 |
| `APP_STATE=FAULT_LOCK`，AXIS `FAULTS` 未增加、`LAST_RESULT=0` | 没有证据指向轴 fault | 转查急停、动力许可、deadline、去重/轮次等非轴入口；仅凭时间不能定案 |
| `APP_STATE` 在连续 STATUS 中循环变化 | 复位/重启或重复启动序列嫌疑 | 保存整段时序和复位上下文；单个快照不足 |

`AXIS FAULTS/LAST_*` 是累计锁存快照，`ec_axis_driver_init()` 不会清除；重传恢复后当前 `STATE/RESULT` 可能已经变化，但 `LAST_*` 仍保留上一故障。必须记录测试前基线与测试后值，只有本轮增加量才能归到本轮。若没有测试前基线，写“历史或本轮来源未分离”，不能强归因。

## 6. `[DropPoints]` 恢复到 `90.0,92.0` 的门槛与步骤

### 6.1 何时才算“首次运动通过”

只有同时满足以下全部条件，才允许恢复远端落点：

- [ ] 本次使用六格全为 `(5.0,5.0)` 的配置，且实际运行日志的落点也是 `(5.0,5.0)`；
- [ ] 同一件、同一运行内完整出现 `ITEM_TASK sent → ACK_ACCEPTED → MOTION_DONE → ITEM_RESULT → 规则帧上屏并发 DISPLAY_ACK`；
- [ ] ITEM_RESULT 为 SUCCESS，`success_count` 从基线 N 恰好变为 N+1；
- [ ] 当前代码可观察 `ACK_ACK_CONSUMED`，已取得该行；缺失即说明板端消费证据不完整，不能把发送等同消费；
- [ ] 物块确实被抓、移、放，机构返回正中；屏幕内容与本件一致；
- [ ] ACK 后到闭环结束没有 `FAULT_LOCK`、急停、越程、堵转、碰撞、反向或自动恢复；
- [ ] 原始日志、现场观察、照片/视频时间戳和配置散列已归档并由第二人复核。

“电机有动作”“回到中心”“只看到 MOTION_DONE”“主机 fake-link 通过”或“故障后重传又动了”都不满足门槛。

### 6.2 恢复操作

恢复配置本身不属于本轮 T3 运动，不得趁链路运行时改。按以下顺序操作：

1. 正常结束链路，确认：

   ```bash
   pgrep -af 'run_chai[n].py' || echo 'NO chain running (good)'
   fuser -v /dev/serial0 2>&1 || echo 'fuser: 无进程占用'
   ```

2. 备份 Pi 实读文件并记录散列：

   ```bash

   sha256sum /home/pi/sorting_config.ini "/home/pi/sorting_config.ini.before-drop-restore-$stamp"
   ```

3. 用 `sudoedit /home/pi/sorting_config.ini`，只把 `[DropPoints]` 六行改为：

   ```ini
   1 = 90.0, 92.0
   2 = 90.0, 92.0
   3 = 90.0, 92.0
   4 = 90.0, 92.0
   5 = 90.0, 92.0
   6 = 90.0, 92.0
   ```

4. 只读回检，必须输出六个完全相同的元组：

   ```bash
   python3 - <<'PY'
   import configparser
   p = '/home/pi/sorting_config.ini'
   c = configparser.ConfigParser()
   ```

5. 将工作区权威副本同步为同样六行时，单独保存 diff/散列并注明部署方向；不能只改工作区却让 Pi 继续读旧文件，也不能只改 Pi 后声称仓库已同步。

7. **到这里仅能写“配置已恢复”**。`(+90,+92)` 距有效边界只余 X 5.0 mm、Y 5.5 mm，且 X/Y 无限位；它的首次实机运动必须作为下一项独立、有人守急停的验收，不能沿用本次 `(5,5)` 的 T3 通过结论。

### 7.1 三种口径必须分开
