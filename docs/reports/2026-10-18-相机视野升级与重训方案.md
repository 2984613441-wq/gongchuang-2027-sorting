## 0. 一句话结论

**识别区（184.5mm）比抓取区（190×195mm）小，是因为代码用正方形请求把相机横向视野裁掉了 44%。**
改成 16:9 后水平视野 184.5 → **328mm**，再把相机升高 ~18mm（262 → 280mm）让垂直视野从 184.5 → **197mm**，即可完整覆盖整个 XY 行程。
**托盘/相机位置不需要大改。**

## 2. 根因（两层）

### 2.1 第一层：代码用正方形请求，裁掉左右 44% 视野

`视觉/src/maixcam_deploy/stage1_color_v6_send.py:168, 579`

```python
FRAME_SIZE = 320
cam = camera.Camera(FRAME_SIZE, FRAME_SIZE, image.Format.FMT_RGB888)
                              ↑宽        ↑高  都是 320
```

MaixPy 行为（2026-10-18 实测）：**请求 1:1 时它从传感器 2560×1440 里裁出中间 1440×1440，再缩放**，不是缩小整幅图。

⇒ **水平方向只用了 1440/2560 = 56.25%，左右各丢 21.9%**。

实测证据：同一场景拍 5 种分辨率，16:9 能看到托盘外的蓝色/红色物件，320×320 完全看不到。
对比图见 `_turntable-edit/fov2/对比-谁被裁掉了.png`。

### 2.2 第二层：真实标定比我以为的小一半

**⚠️ 仓库副本 `电控/calibration_config.ini` 已过期，真值在树莓派 `/home/pi/电控/calibration_config.ini`（18.8KB）**

| 参数 | 仓库（过期） | **树莓派真值（2026-09-22 五点解）** |
|---|---|---|
| a11 | 1.085714 | **0.053288** |
| a12 | 0.0 | **−0.574107** |
| tx | −156.886 | **160.140440** |
| a21 | 0.0 | **−0.574107** |
| a22 | 1.083333 | **−0.053288** |
| ty | −251.333 | **85.341702** |
| camera_height | 262.0 | 262.0 |

**`a12`/`a21` 非零 ⇒ 图像坐标相对机械坐标旋转约 90°。**

换算真实比例：

```
mm/px = √(a11² + a12²) = √(0.053288² + 0.574107²) = 0.5766 mm/px
320×320 视野 = 320 × 0.5766 = 184.5 × 184.5 mm
传感器单像素 = 0.5766 × 320/1440 = 0.12813 mm
全传感器(2560×1440)视野 = 328.0 mm(横) × 184.5 mm(竖)
```

**轴映射（因旋转 90°）**：

| 机械轴 | 对应图像方向 | 需要的行程 | 当前视野 | 缺口 |
|---|---|---|---|---|
| **X** | **垂直 (v)** | 190 mm | 184.5 mm | **−5.5 mm** ❌ |
| **Y** | **水平 (u)** | 195 mm | 184.5 mm（1:1）<br>**328 mm（16:9）** | 1:1 缺 10.5mm ❌<br>16:9 **充足** ✅ |

## 6. 标定换算（不用重测，纯数学）

### 6.1 只换分辨率（高度保持 262mm）

320×320 → 1280×720 时，320 的正方形对应 1280 帧的**居中 720×720**（u 从 280 到 1000）。

```
u_old = (u_new − 280) / 2.25
v_old = v_new / 2.25
```

代入原仿射 `x = a11·u + a12·v + tx`，得：

```ini
# 1280×720 标定（高度 262mm）
a11 = 0.023684
a12 = -0.255159
tx  = 153.509
a21 = -0.255159
a22 = -0.023684
ty  = 156.786
```

推导：
```
a11' = a11/2.25 = 0.053288/2.25 = 0.023684
a12' = a12/2.25 = -0.574107/2.25 = -0.255159
a21' = a21/2.25 = -0.255159
a22' = a22/2.25 = -0.023684
tx' = tx − a11×280/2.25 = 160.140440 − 6.631 = 153.509
ty' = ty − a21×280/2.25 = 85.341702 + 71.444 = 156.786
```

### 6.2 同时把高度升到 280mm

mm/px 按 `280/262 = 1.0687` 等比放大：

```ini
# 1280×720 标定（高度 280mm）
a11 = 0.025311
a12 = -0.272690
tx  = 153.509      # 需重测确认
a21 = -0.272690
a22 = -0.025311
ty  = 156.786      # 需重测确认
```

> ⚠️ tx/ty 在升高度后会变（视野中心不动但比例变），**建议直接重标一次**（用户本来也要重标）。

## 9. 补光灯（WS2812）—— 已完成

### 9.1 硬件

| 项 | 内容 |
|---|---|
| 型号 | WS2812 环形灯，**16 颗**，每颗 0.3W（满载 4.8W ≈ 1.0A @5V） |
| 控制脚 | **PC0**（`LIGHT_EN`，固件 2026-09-18 就预留了，但**此前没有任何代码路径能点亮它**） |
| 接线 | PC0 ─[330Ω]→ DIN；5V 电源 → VDD（并 1000µF）；5V GND ══ STM32 GND（**必须共地**） |
| 5V 来源 | 降压模块（14.8V→5V，需 ≥1A 余量） |

### 9.2 为什么不能用普通 GPIO

WS2812 是**单总线 800kHz 协议**（T0H≈0.4µs / T1H≈0.8µs / 位周期 1.25µs，
帧间低电平 >50µs 锁存）。把 PC0 拉高**不会点亮**，必须按位发送 GRB 数据。

### 9.3 实现方案（已落地）

| 文件 | 内容 |
|---|---|
| `App/Inc/ec_light_ws2812.h` | 接口 + 白光通道标定常量 |
| `App/Src/ec_light_ws2812.c` | **DWT→CYCCNT 自校正位模拟**（不依赖编译器优化等级） |
| `ec_board_stm32.c` | `ec_board_light_set()` → 发 GRB 帧；安全态 → 发全 0 帧 |
| `ec_diag.c` | 新增 `LIGHT LV <0-255>` / `LIGHT RGB r g b` / `LIGHT?`；HELP 更新 |
| `ec_app.c` | 初始化调用 `ec_ws2812_init()` |
| `MDK-ARM/diankongv1.0.uvprojx` | 加入 `ec_light_ws2812.c` |

**为什么不用 PWM+DMA**：本工程 `main.c` 一个 DMA 通道都没配，补光灯只需低频开关，
位模拟每次关中断约 480µs 即可，改动面远小于新引入 DMA 链路。
（未来若需高频刷新再改 PWM+DMA。）

### 9.4 🔴 关键坑：`R=G=B` **不是白光**

WS2812 三色 LED 发光效率不同，红光最弱、蓝光最强。直接写 `(180,180,180)` 实测：

```
白纸 RGB = (122, 148, 226)   饱和度 S = 45.92%   蓝比红高 85%
⇒ HSV 六色窗口判据全部错位，白托盘会被当成"蓝色物体"
```

**扫描 6 组值实测白纸饱和度：**

| RGB | S | 结论 |
|---|---|---|
| (180,180,180) | 45.92% | 严重偏蓝 |
| (222,183,120) | 16.14% | 仍偏蓝 |
| (255,210,138) | 16.84% | 仍偏蓝 |
| **(255,200,90)** | **2.20%** | ✅ **选中** |
| (255,180,70) | 3.41% | 备选 |
| (255,160,60) | 6.11% | 偏 |

**⇒ 固件常量定为 `(255, 200, 90)`**，实测输出白纸 RGB=(176,171,177)、S=3.46%
（关灯基准 S=0.56%），亮度比关灯提升 18%，功率约 3.4W(0.68A)。

> ⚠️ **换灯珠批次必须重新扫这组值。** 任何用 RGB 灯做机器视觉补光的场合都适用此条。
