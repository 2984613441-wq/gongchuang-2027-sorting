### 1.1 时间模型（本次复算用的公式）

`ec_step_profile_plan` = `ec_step_profile.c:76-77`：
```
accel_steps = (cruise² - start²) / (2·a)      decel_steps = (cruise² - end²) / (2·d)
```
`ec_step_profile.c:86-135` 的三角分支；`ec_step_profile.c:200-204` 的 ARR 取整。

代入 start = end = 200 Hz、cruise = 5000 Hz、a = d = 10000 Hz/s：
```
accel_steps = (5000² - 200²) / (2×10000) = 24 960 000 / 20 000 = 1248
decel_steps = 1248            → 门槛（达完整巡航的最短腿）= 2 × 1248 = 2496 步
加速段时长 = (5000 - 200) / 10000 = 0.480 s（减速段同）
巡航段时长 = cruise_steps / 5000
```
**闭式（所有腿都 ≥ 2496 步时成立，本程序 6 条腿全部满足）**：
```
T_运动 = L × 0.96 + (S − 2496·L) / 5000        L = 运动腿数, S = 总步数
T_总   = T_运动 + 3 × 0.200(舵机) + 2.000(WAIT)
```
闭式与逐点离散复算的差 ≤ 30 ms（离散复算含 10 µs ARR 量化，是**准值**）。

## 3. 与实测 12.9 s 的对照：差在哪里

实测（`docs/交付/2026-09-19/总控汇总-三AI报告裁决-2026-09-19.md:151`）：
首帧 `ITEM_TASK` 19:24:57 → `MOTION_DONE` 19:25:09.9 ⇒ **≈12.9 s**；同时 `PROGRESS=10 STATE=3(DONE) FAULTS=0`。

| 项 | 值 |
|---|---|
| 本报告逐腿复算 | 12.8341 s |
| 实测 | ≈12.9 s |
| **残差** | **≈ +66 ms（0.5%）** |

**残差归因（逐项说明，均已在模型内或已知在模型外）**：

1. **已计入**：10 µs ARR 量化（100 kHz 时基）已包含在 12.8341 s 里 —— 把它换成连续积分仅得 12.805 s，也就是量化本身贡献了 **+29 ms**。
2. **未计入 · 主机→板子的首帧时延**：`ITEM_TASK` 帧经 USART2 115200 bps 收发 + 网关解析 + `ec_app_poll` 递进到 `EXECUTING` 才调用 `start_motion()`（`ec_app.c:185-198`）。窗口从 `start_motion()` 起算，而"首帧 ITEM_TASK"在这之前 ⇒ 这几十毫秒**不在** 12.8341 s 里，正好对上残差方向。
3. **未计入 · 主循环轮询粒度**：每步推进都靠主循环 `ec_axis_driver_poll()` 消费端口完成锁存（`ec_axis_driver.c:388-398`），主循环是 `while(1){ ec_app_poll(...); }` 无阻塞（`Core/Src/main.c:134-137`）。本程序有 10 个程序步 + 3 个 settle + 1 个 WAIT = 14 次状态推进，每次吃 0~1 个循环周期的延迟。
4. **未计入 · 串口与屏**：`MOTION_DONE` 自身要发出去才被主机记为"accepted"（帧长量级 10~20 字节 @115200 ≈ 1~2 ms）。
5. **不属于本条**：舵机 settle（3×200 ms）与 WAIT（2000 ms）**已在 12.8341 s 内**，不是残差。

**判定**：残差 66 ms 全部落在"帧收发 + 主循环粒度"的量级内，**没有发现模型与实机的结构性偏差** ⇒ 本模型可用于外推。
**证据边界**：板子侧 `AXIS` 采样间隔为 2 s（`交接-链路已跑通-2026-09-19.md:30-31`），单靠板子输出只能把 DONE 时刻定到 ±2 s；12.9 s 是**主机侧时间戳**推出来的，可信度高于板子侧采样。【证据不足】：该轮 `MOTION_DONE` 的毫秒级收发时延未单独记录。

## 4. 余量分析

### 4.1 对 MOTION_DONE
```
15.000 − 12.834 = 2.166 s   （占窗口 14.4%）
```

### 4.2 丢步会不会导致"巡航降到 4000 Hz"？
**先纠正一个前提**：**丢步本身不会让巡航频率下降**。步进频率由定时器 ARR 决定（`ec_board_stm32.c:200,510-521`），丢步只改变**实际位移**（滑台少走），频率一点不变。所以"降到 4000 Hz"只能是**人为改 `ec_board_stm32.c:200` 的 cruise 实参并重烧**。
丢步真正的危害是另一条超时路径：坐标基准永久失准（X/Y 无限位开关，`ec_motion_plan.h:68-71`）→ 后续每一件的实际路径与规划路径不一致 → 时间不可预测。这条路径【证据不足】，未实测量化。

### 4.3 四档巡航频率对照表（accel 固定 10000 Hz/s，当前坐标）

| 巡航设定 | accel_steps | 门槛 2×accel | 腿合计 | 舵机+WAIT | **MOTION_DONE** | 距 15 s | 相比 5000 Hz |
|---|---|---|---|---|---|---|---|
| **5000 Hz** | 1248 | 2496 | 10.234 | 2.600 | **12.834** | **+2.166** | — |
| 4500 Hz | 1010 | 2020 | 10.706 | 2.600 | **13.306** | +1.694 | +0.472 |
| 4000 Hz | 798 | 1596 | 11.495 | 2.600 | **14.095** | **+0.905** | +1.261 |
| 3500 Hz | 610 | 1220 | 12.653 | 2.600 | **15.253** | **−0.253 ❌** | +2.419 |

**⚠️ 100 kHz 时基的取整陷阱**（`ec_board_stm32.c:28` + `ec_step_profile.c:202`）：ARR = round(100000/f)，
- 5000 Hz → 20 tick（精确）
- 4500 Hz → 22 tick ⇒ **实际 4545 Hz**（快 1%，所以实测比闭式略短）
- 4000 Hz → 25 tick（精确）
- 3500 Hz → 29 tick ⇒ **实际 3448 Hz**（慢 1.5%，所以 15.25 s 比闭式 15.10 s 更慢）
- 6000 Hz → 17 tick ⇒ **实际 5882 Hz**（慢 2%，下面 §5 会用到）

**结论**：
- **4000 Hz 时 MOTION_DONE 仍在窗口内（+0.905 s），没有中途被砍断** ✅
- 3500 Hz 会中途被砍断 ❌
- **但是 4000 Hz 的 +0.905 s 只够 MOTION_DONE**；见下一节。

### 4.4 被忽略的真红线：窗口不在 MOTION_DONE 关闭
`ec_app.c:518-525` 发 `MOTION_DONE` 后**不关窗口**（注释明写 "deliberately does NOT clear, restart or extend"）；窗口要等第一帧有效 `DISPLAY_ACK`（`ec_app.c:218-219`），而 `WAIT_DISPLAY_ACK` 状态**仍在窗口检查范围内**（`ec_app.c:445-449`），过期即 `lock_machine`（`ec_state_machine.c:127-128`）。

实机那一轮的时间戳（`交接-链路已跑通-2026-09-19.md:42,44`）：
```
MOTION_DONE accepted   19:25:09.907
ITEM_RESULT  accepted  19:25:09.958
DISPLAY_ACK 发出        19:25:11.070   ← 之后才关窗
```
`MOTION_DONE → DISPLAY_ACK = 1.163 s`。于是那一轮的**窗口实际用量**：
```
12.9 s（到 DONE） + 1.16 s = 14.06 s     余量仅 0.94 s
```
⇒ **真正贴着红线的是这一环，不是运动本身。**

把它套到频率对照表上（DONE 之后固定加 1.163 s）：

| 巡航 | MOTION_DONE | 窗口实际用量 | 距 15 s | 结果 |
|---|---|---|---|---|
| 5000 Hz | 12.834 | **13.997** | +1.003 | ✅ 全部通过 |
| 4500 Hz | 13.306 | 14.469 | +0.531 | ✅ 勉强 |
| 4000 Hz | 14.095 | **15.258** | **−0.258 ❌** | 运动做完，但**进 FAULT_LOCK**，下一件起不来 |
| 3500 Hz | 15.253 | — | — | ❌ 运动中就被砍断 |

**所以"降频到 4000 Hz 还进不进 15 s"的答案是：**
- 只问 MOTION_DONE：**进**（14.10 s，余量 0.91 s）。
- 问整轮是否触发窗口：**不进**（15.26 s，超 0.26 s）→ 表现为"这一件做完了、但板子锁死、下一件不见 MOTION_DONE"。
- 要 4000 Hz 也安全，必须同时砍掉 ≥ 0.3 s 的固定开销（最直接：WAIT 2000 → 1500 ms，见 §6 补救顺序）。

**【证据不足】** 1.163 s 的 DISPLAY_ACK 段只来自单轮单次采样，且含主机屏写时间（`19:25:11.070 → 19:25:12.057` 约 0.99 s 的屏写另计）；换一台主机/换一次视觉耗时会长会短，未有重复采样。

## 5. 加速策略的杠杆在哪

### 5.1 巡航提频 vs 加减速提速率（accel 从 10000 起）

| 改动 | 腿合计 | 总时间 | 余量(15s) | **省了多少** |
|---|---|---|---|---|
| 基准 5000 Hz / 10000 Hz·s⁻¹ | 10.234 | 12.834 | +2.166 | — |
| accel → 15000 Hz·s⁻¹ | 9.313 | 11.913 | +3.087 | **−0.921 s** |
| accel → 20000 Hz·s⁻¹ | 8.853 | 11.453 | +3.547 | **−1.381 s** |
| cruise → 6000 Hz | 9.647 | 12.247 | +2.753 | −0.588 s |
| cruise → 7000 Hz | 9.267 | 11.867 | +3.133 | −0.967 s |
| cruise 7000 + accel 20000 | 7.263 | **9.863** | +5.137 | −2.971 s |

**哪个杠杆更大？→ 加减速更大。**
- 同样翻一档，accel 10000→15000 省 0.921 s，而 cruise 5000→6000 只省 0.588 s。
- 原因很直白：加减速率对**全部 6 条腿同时生效**（每条腿省 `2×(4800/a − 4800/10000)`），而巡航只作用于 40824 步中的巡航部分。
- **但要注意边际递减**：accel 10000→15000 省 0.92 s，15000→20000 只再省 0.46 s（因为 `accel_steps = (cruise²−start²)/(2a)`，a 越大节省越小）。
- 而 6000 Hz 另有量化损失（`ec_step_profile.c:202`）：ARR = round(100000/6000) = 17 tick ⇒ **实际只有 5882 Hz**，所以实测只省 0.588 s，比"算术应有"的 0.62 s 少 30 ms。想省得干净，**优先选能被 100 kHz 整除的档位：5000 / 6250 / 4000 / 2500 Hz**。
- `EC_STEP_MAX_HZ = 10000`（`ec_step_test.h:8`）**只限频率，不限加速度**，所以 20000 Hz·s⁻¹ 在代码层不被拦；但**扭矩/丢步风险实机未验证**（见 §6 R5）。

### 5.2 比两个杠杆都大的第三个杠杆：WAIT 2000 ms
`EC_AXIS_PICK_DWELL_MS`（`ec_axis_driver.h:138`）是**纯等待**（`ec_axis_driver.c:291-299`），一行改到 1000 ms 就**直接省 1.000 s** —— 比 accel 提到 15000 还多。代价是"肉眼确认滑台停在物块上"的时间减半（这是用户 2026-09-19 的实机要求，见 `ec_motion_plan.c:204-208`），属**用户裁决项**，不是技术项。

## 6. 风险清单（会让总时间超过 15 s 的具体场景）

> 记法：**落点 (Px, Py) mm**，抓取点取当前 (-41.8, -27.1)，HOME = (-95, -97.5)。
> 由 §1.1 闭式反解得**路径长度红线**：`T = 8.36 + (S − 14976)/5000`
> - `T = 15.0 s` ⇔ **S ≤ 48176 步 = 602.2 mm 路径**
> - `T = 14.0 s` ⇔ **S ≤ 43176 步 = 539.7 mm 路径**
> 在本抓取点下，`路径 = 385.0 mm + 2·(Px + Py)`（当 Px > −41.8 且 Py > −27.1，即托盘区），于是：
> - **`Px + Py ≤ 108.6 mm` ⇒ 不撞 15 s**
> - **`Px + Py ≤ 77.3 mm` ⇒ ≤ 14.0 s（推荐工作线）**
> 当前 (20,20)：`Px+Py = 40 mm`，余量 37.3 mm ⇒ 留 1.19 s。

| # | 场景 | 量化后果 | 等级 | 观测方法 |

## 7. 一页结论：今晚怎么判、撞了怎么救

### 7.1 判断"这轮会不会撞 15 s"要看的观测值（按重要性排序）

1. **`DISPLAY_ACK 时刻 − ITEM_TASK 时刻` ≤ 14.0 s** ← **最重要**。这才是窗口的完整用量；红线是 15.0 s，超了板子会在 DONE 之后进 FAULT_LOCK。
2. **`MOTION_DONE 时刻 − ITEM_TASK 时刻` ≤ 13.5 s**（当前 12.9 s，余量 2.17 s）。这条线**宽松得多**，只能证明"运动没被砍断"。
3. **落点 `Px + Py` ≤ 70 mm**（保守线；数学红线是 108.6 mm，工作线 77.3 mm）。看视觉输出/`ITEM_TASK` 里的落点坐标即可，不必等板子。
4. **板子 `AXIS` 输出**：`PROGRESS=10`、`STATE=3(DONE)`、`FAULTS=0`、`LAST_RESULT=0(OK)`。**`PROGRESS` 停在 3 或 5 就是被窗口砍断了**（对应第 [3]/[5] 步），不是机械故障。
5. **`TICK_MS` 单调**（无跳水）—— 排除复位。
6. **`pi_square.py` 闭合性**（装爪后必跑一次）—— 排除 R5 丢步。

### 7.2 撞了之后的最小改动补救顺序（从"零风险"到"动根因"）

| 顺序 | 动作 | 改动量 | 省时 | 风险 |
|---|---|---|---|---|
| **0** | **先改数据不改代码**：落点收回到 `Px+Py ≤ 70 mm` | 纯参数（`pi_set_droppoints.py`），不重烧 | 按距离线性，回到 (20,20) 即回到 12.83 s | 零（且能立刻验证） |
| **1** | WAIT 2000 → 1000 ms | `ec_axis_driver.h:138` 一行 | **−1.000 s** | 需用户同意（牺牲目视确认时间） |
| **2** | cruise 5000 → 6000（或 **6250**，能整除 100 kHz，无量化损失） | `ec_board_stm32.c:200` 一个实参 | −0.588 s（6250 实测 **−0.739 s**，且无取整损失） | 丢步风险↑，需 `pi_square` 复验 |
| **3** | accel 10000 → 15000 | `ec_board_stm32.c:200` 同行的两个实参 | **−0.921 s** | 同上；先 15000 再考虑 20000（边际递减） |
| **4** | 若 2+3 还不够：启用 `EC_APP_PROGRESS_SOURCE_ENABLED = 1`（`ec_app.h:16-17`），让窗口随运动进展重置 | 改宏 + **必须**先有 HIL-PROGRESS-001 证明观测量 | 根治（窗口不再是最紧约束） | 🟠 中高：现为 fail-closed 是**有意的**，未证明前不得打开 |
| **5** | 最后才考虑动 `ec_app.c:553` 的 `UINT32_C(15000)` | 一行 | 全部 | ❌ **用户已裁决不动**，仅作兜底记录 |

**注意顺序原则**：0/1 不碰运动参数、不需要重新做丢步标定；2/3 会改变电机实际运行曲线，**每改一次都必须重跑 `pi_square.py` 闭合性验证**（`ec_board_stm32.c:196-198` 明确要求 5000 Hz 需重做该验证）；4 是根治但门槛最高。**在不动 15000 的前提下，0+1+3 组合可把总时间压到 10.9 s 左右，余量 4.1 s，任何合理落点都安全。**
