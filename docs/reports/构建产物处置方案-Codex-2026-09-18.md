```powershell

$expectedCounts = [ordered]@{
    '.0'=1; '.crf'=41; '.d'=42; '.dep'=1; '.htm'=2;
    '.lnp'=1; '.map'=1; '.o'=42; '.sct'=1
}
$allowedExtensions = @($expectedCounts.Keys)
$generated = @(Get-ChildItem -LiteralPath $ObjectDir -File |
    Where-Object { $allowedExtensions -contains $_.Extension })

foreach ($extension in $expectedCounts.Keys) {
    $actual = @($generated | Where-Object Extension -eq $extension).Count

Remove-Item -LiteralPath $listing -Force
```

## 6. 让唯一活动产物一眼可辨

### 6.1 推荐的命名与目录规则

活动区永远只能存在 1 个 HEX；历史区中的目录名与文件名必须带 `DO-NOT-FLASH`。

| 场景 | 规则 | 示例 |
|---|---|---|
| 当前构建、尚未生产验收 | 固定输出基名，排在资源管理器最前；不得含 `prod` | `00_CURRENT_BUILD__NOT_RELEASE_APPROVED__diankongv1.hex` |
| 已完成规定验收并经用户批准的发布快照 | 不可变名称：UTC 时间 + 宏短码 + 源码哈希前 12 位 + HEX 哈希前 12 位 | `FLASH_APPROVED__diankongv1__20260918T042529Z__D1M1S1G0B0P0__src-a1b2c3d4e5f6__hex-cbe955003f87.hex` |
| 历史生产备份 | 必须加 `DO_NOT_FLASH`，即使原名带 `prod` | `DO_NOT_FLASH__diankongv1_prod_20260916__hex-3acf56267476.hex` |
| 专项测试 | 必须写测试类型和 `DO_NOT_FLASH` | `DO_NOT_FLASH__SERVOTEST__20260916__hex-9edb4f4318b7.hex` |

对现状的最小命名修改是：后续经批准把 `uvprojx:52` 的 `<OutputName>diankongv1.0</OutputName>` 改为无点号的 `00_CURRENT_BUILD__NOT_RELEASE_APPROVED__diankongv1`。这样可同时消除：

- `diankongv1.0` 链接文件与 `diankongv1.hex` 名称不一致；
- 文件名不含用途状态；
- 误把最新构建自动理解成 `prod`。

不建议把宏组合长期写死在活动文件名里，因为每次改宏还需人工同步输出名，反而会产生新失配。宏、时间和完整哈希应由同目录指纹文件自动记录；宏短码只用于不可变发布快照。

### 6.2 构建后台账文件

推荐自动生成 `MDK-ARM/CURRENT-BUILD.json`，至少包含：

```json
{
  "schema": 1,
  "status": "CURRENT_BUILD_NOT_RELEASE_APPROVED",
  "generated_utc": "2026-09-18T04:25:29Z",
  "project": "diankongv1.0.uvprojx",
  "target": "diankongv1.0",
  "hex_relative_path": "diankongv1.0/00_CURRENT_BUILD__NOT_RELEASE_APPROVED__diankongv1.hex",
  "hex_sha256": "<64 hex chars>",
  "macros": {
    "EC_DIAGNOSTIC_BUILD": 1,
    "EC_MOTION_TEST_BUILD": 1,
    "EC_SERVO_TEST_BUILD": 1,
    "EC_GROUP_TEST_BUILD": 0,
    "EC_BARRIER_TEST_BUILD": 0,
    "EC_APP_PROGRESS_SOURCE_ENABLED": 0
  },
  "macro_short": "D1M1S1G0B0P0",
  "source_set_sha256": "<64 hex chars>",
  "project_sha256": "<64 hex chars>",
  "dependency_file_count": 42,
  "toolchain": "ARMCC 5.06 update 7 build 960",
  "build_errors": 0,
  "build_warnings": 0,
  "hardware_validation": "NOT_PERFORMED_BY_THIS_BUILD"

```

规则：

- 烧录清单只能引用 `CURRENT-BUILD.json` 中的 `hex_relative_path`；烧录前重新计算 HEX SHA-256并比对。
- `build_errors != 0`、HEX 时间早于本次构建开始时间、依赖无法解析、宏缺失或哈希不匹配时，脚本必须失败且不得更新台账。
- `build_warnings` 如非 0，不自动写 `FLASH_APPROVED`。
- `hardware_validation` 不能由构建脚本自动写成 `PASS`；它只能保持 `NOT_PERFORMED_BY_THIS_BUILD`，实机验收由单独授权流程填写。
- 当前 `.gitignore` 忽略 `*.hex`、`*.log`、`*.uvguix.*` 和整个 `MDK-ARM/diankongv1.0/`。因此 HEX/日志本身不会获得版本控制保护；`CURRENT-BUILD.json` 放在 `MDK-ARM/` 根目录，可独立保留。本文不进行任何 Git 操作。

## 7. 自动“构建指纹”的可行性与最小改动

### 7.1 可行性结论

**可行性：高。** 当前工程已经提供生成指纹所需的全部材料：

- `uvprojx:337` 给出配置宏；
- 最新 `.dep` 中保存了实际传给 ARMCC 的 `-D` 宏，优先级高于只读工程 XML；
- 42 个 `.d` 文件列出本次实际使用的源文件和头文件；
- HEX、工程文件和依赖文件都可用 PowerShell `Get-FileHash -Algorithm SHA256` 计算哈希；
- 构建日志给出工具链、错误数、警告数；
- `uvprojx:82-90` 已存在 AfterMake 段，而且当前是 `RunUserProg2=1`、命令名为空，可在后续批准中清理并接入脚本。

### 7.2 推荐方案：外部 sidecar 指纹

最小改动仅两处，不改任何 C/H 文件：

1. 新增 `MDK-ARM/write-build-fingerprint.ps1`；
2. 修改 `diankongv1.0.uvprojx` 的 After Build/Rebuild 用户命令，调用该脚本；同时把空的已启用 User Program #2 修成真实命令或关闭后改用 #1。

脚本流程：

1. 记录调用时间并确认目标 HEX、`.dep`、42 个 `.d` 均为本次构建新产物；
2. 从 `.dep` 读取**实际编译宏**，而不是硬编码 `D1M1S1G0B0P0`；
3. 从 `.d` 收集实际源文件/头文件，逐文件算 SHA-256；
4. 以“规范化相对路径 + 制表符 + 单文件 SHA-256”排序后拼接，再算 `source_set_sha256`；外部工具链头文件若采用绝对路径，则单列在 `external_dependencies`，并记录工具链版本；
5. 计算 HEX 和 `uvprojx` 的 SHA-256；
6. 解析最新构建日志的错误/警告数；
7. 先写临时 JSON，全部校验通过后原子替换 `CURRENT-BUILD.json`；任何一步失败都保留旧台账并返回非零退出码。

建议的后构建命令形态如下；**该命令尚未验证 uVision 的工作目录，实施时应先做一次纯软件重建验证，不得直接据此烧录**：

```powershell
powershell.exe -NoProfile -ExecutionPolicy Bypass -File ".\write-build-fingerprint.ps1" -Project ".\diankongv1.0.uvprojx" -Target "diankongv1.0" -Hex ".\diankongv1.0\00_CURRENT_BUILD__NOT_RELEASE_APPROVED__diankongv1.hex" -Out ".\CURRENT-BUILD.json"
```

### 7.3 备选方案与取舍

| 方案 | 改动 | 优点 | 缺点 | 结论 |
|---|---|---|---|---|
| After Build sidecar（推荐） | 1 个 PowerShell 脚本 + 1 处 `uvprojx` 用户命令 | GUI/命令行构建后自动生成；不改固件二进制逻辑；HEX 与指纹用哈希绑定 | 需验证失败构建时 Hook 行为和工作目录 | **最小且足够** |
| 外部 `build-release.ps1` 包装 UV4 | 新增 1 个包装脚本，不改 `uvprojx` | 最容易做到“先看 UV4 退出码，再生成指纹” | 操作者直接点 GUI Build 可绕过 | 可作第二道门禁，不宜单独依赖 |
| 把 Build ID 嵌入固件 | 生成头文件 + 新增/修改 C 源码 + 查询接口 | 可从板上读取实际运行版本 | 改动更大，影响二进制，还涉及运行时读取设计 | 当前不需要，后续再评估 |

### 7.4 最小验收（仅主机/构建侧）

后续实施指纹时，至少验证：

1. 连续两次源码与宏完全相同的重建：`source_set_sha256`、宏组合相同；HEX 哈希是否相同如实记录，不预设 ARMCC 一定可复现。
2. 只改一个受编译头文件：`source_set_sha256` 必须变化。
3. 只改一个宏：`macros`、`macro_short`、`project_sha256` 必须变化。
4. 人为让构建失败：不得产生新的活动 HEX 指纹，不得把旧 HEX 误登记为新构建。
5. 活动区检查：排除 `_old-hex/` 后必须恰好 1 个 HEX。
6. `Get-FileHash` 结果必须与 `CURRENT-BUILD.json.hex_sha256` 完全一致。

这些验收只证明构建产物身份与台账一致，不证明硬件功能通过。
