### 1.3 `success_count` 取值时机对齐核查：✅ 一致（**结果时刻**）

#### 树莓派侧：结果到达后立即递增再构造 DisplayContent

**流程** (`电控/src/electrical_control/rpi/__init__.py:275-304`):

1. **ITEM_RESULT 到达** → 进入 `Scheduler.accept_item_result()`
2. **:291-295**: 调用 `self._counter.record_item_result()` — 成功时递增 `_value`
3. **:298-302**: 用**递增后**的 `self._counter.value` 构造 `DisplayContent`
4. **:303**: 状态 → `WAIT_RENDER`

**`RoundSuccessCounter.record_item_result`** (`电控/src/electrical_control/protocol/item_context.py:214-238`):

```python
def record_item_result(
    self,
    *,
    result_code: int,
    task_id: int | None = None,
    frame_seq: int | None = None,
) -> bool:
    code = _u8("result_code", result_code)
    identity = (task_id, frame_seq)
    if identity in self._recorded_results:
        if self._recorded_results[identity] != code:
            raise ResultIdentityConflict(...)
        return False  # 幂等：同一身份重复到达，不再递增
    if code != self.SUCCESS:  # self.SUCCESS = 0x00
        self._recorded_results[identity] = code
        return True  # 失败件：记录但不递增
    if self._value == 0xFF:
        raise SuccessCountOverflow(...)
    self._value += 1  # ← 成功件：先递增
    self._recorded_results[identity] = code
    return True
```

**结论**: `DisplayContent` 构造时拿到的 `success_count` 是**本件成功后的累计值**（包含本件）。

---

#### STM32 侧：ITEM_RESULT_RECORDED 事件提交后立即递增

**流程** (`电控/stm32_logic/src/ec_protocol_gateway.c:530-537`):

```c
/* P3-FIX: Increment the success count only when the state machine actually
 * committed WAIT_ITEM_RESULT -> WAIT_DISPLAY_ACK, so a duplicate or replayed
 * ITEM_RESULT is idempotent. ... */
if (event->type == EC_EVENT_ITEM_RESULT_RECORDED &&
    pre_state == EC_STATE_WAIT_ITEM_RESULT &&
    transition.state == EC_STATE_WAIT_DISPLAY_ACK &&
    event->result_code == EC_RESULT_SUCCESS) {
    if (g->success_count != UINT8_MAX) {
        ++g->success_count;  // ← 成功件：递增
    }
}
```

**时序**:
1. App 层发送 `ITEM_RESULT` 帧（`ec_app.c:529`）
2. Gateway 层收到后触发 `EC_EVENT_ITEM_RESULT_RECORDED` 事件
3. 状态机迁移 `WAIT_ITEM_RESULT → WAIT_DISPLAY_ACK`（:531-532）
4. **立即递增** `g->success_count`（:535）
5. 后续收到 `DISPLAY_ACK` 时，用**递增后**的 `g->success_count` 计算期望 CRC（:217）

**结论**: `ec_proto_display_content_crc32` 收到的 `success_count` 是**本件成功后的累计值**（包含本件）。

### 1.4 对齐结论：✅ 两侧语义完全一致

| 字段 | 树莓派来源 | STM32 来源 | 时刻 |
|------|-----------|-----------|------|
| `target_seq` | `task.payload.target_seq` | `g->item_target_seq` | ITEM_TASK 受理时 |
| `class_id` | `task.payload.class_id` | `g->item_class_id` | 同上 |
| `image_id` | `task.payload.image_id` | `g->item_image_id` | 同上 |
| `success_count` | `self._counter.value` | `g->success_count` | **ITEM_RESULT 递增后** |
| `result_code` | `result.result_code` | `g->item_result_code` | ITEM_RESULT 到达时 |

**关键点**: 两侧都是在 ITEM_RESULT **处理完成、成功计数器已递增**之后，才用该快照构造/校验 CRC。树莓派在 `accept_item_result` 返回的 `DisplayContent` 中冻结这五个字段；STM32 在 `handle_display_ack` 校验时从 `g->` 的全局快照读取同样五个字段。

**不存在时刻差**：两侧都是"结果时刻"（而非"渲染时刻"），因为渲染发生在 `accept_item_result` **之后**（树莓派 :303 → `WAIT_RENDER`，实际渲染在主循环 `_render_and_ack` 里）。

## 二、赛规显示门禁（R-D04）与固件 15 秒失活窗口的区分

### 2.1 赛规条文（R-D04）

**原文** (`docs/references/赛题原文-提取文本/27年工创.txt:378-379`):

> "超过 15 秒分拣装置**没有动作**或**没有显示本次分拣信息**，本轮比赛结束。"

**权威解读** (`docs/冲突与决策台账-2026-09-10.md:77` + `电控/资料/要求汇总.md R-R04:102,105`):

- **失活超时**，不是"单件必须 15 秒内完成"
- **"15 秒无动作"** = 机械装置停滞（无运动、无显示更新）
- **"没有显示本次分拣信息"** = DISPLAY_ACK 未完成前，不得开始下一件（门禁语义）

**代码落点**（树莓派侧）:

```python
# 电控/deploy/run_chain.py:838
intent = scheduler.accept_render_receipt(receipt)  # WAIT_RENDER → READY
# ↑ R-D04 门禁放行：DISPLAY_ACK 完成后，状态机才允许接受下一件
```

**状态机保证**: Scheduler 在 `WAIT_RENDER` 状态时，不接受新的 `ITEM_TASK`（会 fault）。

---

### 2.2 固件 15 秒失活窗口

**代码位置**: `电控/firmware/stm32f407_m144z/App/Src/ec_app.c:553-556`

```c
if ((uint32_t)(now_ms - last_observable_ms) >= UINT32_C(15000)) {
    /* Deadline: no observable forward progress for 15 seconds. */
    event.type = EC_EVENT_DEADLINE_EXPIRED;
    event.identity = node->sm.current_item;
```

**触发条件**:
- `last_observable_ms` 超过 15 秒未更新
- 更新 `last_observable_ms` 的唯一路径是 `ec_app_note_forward_progress()`（:121-139）
- **但该函数被 `#if EC_APP_PROGRESS_SOURCE_ENABLED` 包裹**（:123）
- **`EC_APP_PROGRESS_SOURCE_ENABLED` 当前为 `0`**（`ec_app.h:17`）
- → `ec_app_note_forward_progress()` 是**硬 no-op**（:117 注释明确写"hard no-op"）

**实际行为**:
- `last_observable_ms` **永远不被更新**
- 从 **APP 启动后第 15 秒**开始，每次 `ec_app_tick()` 都会触发 `DEADLINE_EXPIRED`
- 任何运动/渲染若在启动后第 15 秒之后仍未完成 → 必 `FAULT_LOCK`

**与赛规的关系**:
- **不是同一个东西**
- 赛规的"15 秒失活"是**从最后一次动作开始计时**的空转保护
- 固件的 15 秒窗口是**从 APP 启动开始计时**的绝对墙钟时限
- 固件窗口的设计意图是"运动有进展就重置"（见 `:136-138` 的 progress source 分支），但 `ENABLED=0` 使该机制失效

---

### 2.3 两者混为一谈的风险

**已识别迹象**:
1. `分工提示词-七点拆解.md:46` 把两者并列为"当前未解决阻塞 B"
2. 固件注释（`ec_motion_plan.h:122`）提到"DEADLINE_EXPIRED → FAULT_LOCK"，但未明说这是绝对时限还是失活超时

**核心差异**:

| 维度 | 赛规 R-D04（15 秒失活） | 固件 15 秒窗口（DEADLINE_EXPIRED） |
|------|----------------------|--------------------------------|
| 计时起点 | **最后一次动作** | **APP 启动后** |
| 重置条件 | 任何运动/显示更新 | `ENABLED=0` → **永不重置** |
| 触发后果 | 本轮比赛结束（裁判判定） | `FAULT_LOCK`（固件状态） |
| 代码落点 | 树莓派 Scheduler 状态机 | `ec_app.c:553` |

**实际影响**:
- 若单件运动+渲染耗时超过 15 秒，固件必 `DEADLINE_EXPIRED`
- 这**不等于**赛规的"15 秒无动作"（后者允许持续动作，只要不停滞）
- 当前配置下，固件窗口**更严**（墙钟时限 vs 失活超时）

### 3.2 `success_count` 取值时机：✅ 一致（结果时刻）

**树莓派**: `ITEM_RESULT` → `_counter.record_item_result()` 递增 → 用递增后值构造 `DisplayContent` → 渲染 → `DISPLAY_ACK`

**STM32**: `ITEM_RESULT` → `EC_EVENT_ITEM_RESULT_RECORDED` → 状态机迁移 → 递增 `g->success_count` → 收到 `DISPLAY_ACK` 时用递增后值校验

**不存在渲染时刻 vs 结果时刻的差异**: 两侧都是在递增**之后**、渲染**之前**冻结五个字段。

---

### 3.3 赛规显示门禁 vs 固件 15 秒窗口：✅ 已分清

| 项 | 赛规 R-D04 | 固件 DEADLINE_EXPIRED |
|---|-----------|---------------------|
| 语义 | 失活超时（从最后动作计时） | 绝对墙钟时限（从启动计时） |
| 代码 | 树莓派 Scheduler（R-D04 门禁在 `accept_render_receipt` 处放行） | `ec_app.c:553` |
| 当前行为 | 由 Scheduler 状态机保证（`WAIT_RENDER` 不接受新任务） | `ENABLED=0` → 失活重置失效 → 从启动后第 15 秒起必触发 |
| 是否同一个 | **否** | **否** |
