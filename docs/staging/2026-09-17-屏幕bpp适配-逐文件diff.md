## 1. 先纠正一个前提：`display_hdmi.py` 本身**不写** fb0

任务描述说"display_hdmi.py 按 32bpp 写 `/dev/fb0`"—— 实读代码后**不成立**：

| 文件 | 与 fb0 的关系 | 代码事实 |
|---|---|---|
| `电控/src/electrical_control/rpi/display_hdmi.py` | **不碰 fb0** | `HdmiDisplayRenderer.present()` 只做 `self._frame_output(frame)`，交出一张 PIL 帧；设备路径、字节序、写系统调用一个都没有 |
| `电控/deploy/run_chain.py` | **真有 fb0 写入** | `build_frame_output()` 的 `kind == "fb0"` 分支里 `open("/dev/fb0","wb").write(img.tobytes())`；`img.tobytes()` 是 RGB888（3 字节/像素），**与 bpp 无关** |
| `工具/pi_blit_png.py` | 已有正确实现 | `encode_frame()` 读 sysfs 的 bpp 并按 16/24/32 打包 —— 但它只贴图，不在主链上 |

原来的字节数算法：**`width*height*3`（写死 RGB888），不读 bpp、不看 line_length**。
1024×600 = 1,843,200 字节；16bpp 的 fb 只有 1,228,800 字节 → 实机 `[Errno 28]`。

**结论**：打包逻辑只做一处（作为公共函数放 `display_hdmi.py`），`run_chain.py` 只把回调换成它。
渲染路径行为不变：交给 `frame_output` 的仍是同一张 RGB `PIL.Image`。

## 5. 四个必答问题

### 5.1 bpp 的最佳处理位置：**一个公共函数**，放 `display_hdmi.py`

- 项目里"帧 → 屏幕字节"只发生在一处（`run_chain.build_frame_output` 的 fb0 分支）。
  每处自己处理 = 两份会各自漂移的打包代码（`工具/pi_blit_png.py` 已经是第二份，而且它的 24/32bpp 分支是错的，见 5.2）。
- 位置选 `display_hdmi.py` 而不是新建模块：这个文件就是"Pi 上屏"那一层，`run_chain.py` 已经 import 它；
  不新增包内文件、不改部署脚本的复制清单（`install.sh` / 打包清单都不用动）。
- fail-closed 落点：`read_framebuffer_format()` 读不到就抛错；`FramebufferFrameOutput` 在**构造期**
  （= run_chain 启动期）就调用它 —— 配置错的表现是"拒绝启动"，不是"跑到第一件物料才炸"。

### 5.2 16bpp 的 RGB565 字节序：**小端**（红 = 0xF800 = 内存字节 00 F8）

凭什么（两条独立证据）：

1. **实机证据（最强）**：`工具/pi_blit_png.py` 用 `out[j]=v&0xFF; out[j+1]=v>>8`（小端）打包，
   在同一台树莓派上 6 张图逐张上屏成功（2026-09-17 报告 §1 步 9）。字节序若反，画面是整体颜色错乱的花屏，肉眼可辨。
2. **机制**：fb 里存的是"CPU 字节序的像素值"，像素值由 `FBIOGET_VSCREENINFO` 的 red/green/blue offset 定义
   （RGB565 = r@bit11 / g@bit5 / b@bit0）；Pi 的 SoC 是小端，所以 0xF800 在内存里就是 `00 F8`。
3. 反例排除：全仓没有一处按大端写过 16bpp（pi_blit_png 与本次实现一致）。

**30 秒验证法（已内置 `--bars`）**：写红/绿/蓝三条竖条 ——
- 正确：左到右 红 | 绿 | 蓝
- 字节序反（相当于把 0xF800 写成 `F8 00`）：红→**深蓝**(0x00F8)、绿→**洋红红**(0xE007)、蓝→**暗绿**(0x1F00)
三条纯色一眼可辨，不用工具、不装包、不改任何配置。
（若机器上正好有 `fbset`，`fbset -i -fb /dev/fb0` 会直接打印 `endian little` 与 `rgba 5/11,6/5,5/0`，那是权威来源 —— 但别为它装包。）

### 5.3 virtual_size 与屏幕分辨率不符 / 读不到 line_length 怎么办

**line_length 读不到（本机就是这种）**：按紧凑行 `width*bpp/8` 处理，不再猜别的值。
依据：16bpp 1024×600 按紧凑行写 1,228,800 字节后实机整幅正常 ⇒ 该 fb 没有行填充。
实现会依次尝试 `line_length` → `stride` 两个 sysfs 节点，都读不到才回落；
读到 line_length 且大于一行宽度 → 按它每行补零（否则整幅斜切）；小于一行宽度 → 直接报错。

**virtual_size 与帧分辨率不符**：分两种，都不猜 ——
- 帧**比 fb 可见区大** → 直接 `FramebufferFormatError`（写下去必然错位/越界），启动期就报错；
- 帧**比 fb 可见区小** → 允许 + WARNING：真实后果是"只覆盖左上角，其余像素保持原样"，不是花屏；
  修法是让两边一致 —— 改 `config.txt` 的 `hdmi_cvt`（屏侧），或让 `--width/--height`、`SCREEN_WIDTH/HEIGHT` 与屏一致。
- `virtual_size` **读不到** → 抛错拒绝写：没有它无法确认帧放不放得下，而"放不下"正是 Errno 28 的来源。
  代码取 virtual_size 的前两个数（xres_virtual, yres_virtual）；fkms 单缓冲下它等于可见区。
  已知取舍：若某内核把 yres_virtual 报成两倍（双缓冲），本实现只告警不失败 —— 可接受的降级；
  真遇到就把 `validate_frame_size` 的比较对象换成 `FBIOGET_VSCREENINFO` 的 yres。

### 5.4 会不会影响方案 A / 方案 B 的显示行为

**不会。** 理由：

- 方案 A/B 的差异在机构与派发（转盘选格 / 六盒落点），两者都走**同一条**显示路径
  `DisplayContent → build_display_view → DisplayViewModel → HdmiDisplayRenderer`；
  本次改的是这条路径**最后一跳的像素打包**（frame_output 内部），
  渲染像素、版面、四字段、CRC、`DISPLAY_ACK` 时序全部未变
  （`present()` 的返回与 `RenderReceipt` 与改动前逐字节相同，回归测试也证明了这点）。
- 唯一可见差异：16bpp 的 fb 上从"花屏 / 写到一半就 Errno 28 崩"变成正确图像。
- 唯一新增风险：`--frame-output fb0` 多了一种**拒绝启动**的理由（读不到 bpp/virtual_size）。
  这是刻意的 fail-closed（屏黑着跑完一轮比赛的代价更大），启动命令与参数一个没变。

## 7. framebuffer_depth=32 为什么不生效（只分析，未动手）

1. 它是**旧固件（legacy / firmware-KMS）时代**的 `config.txt` 选项，由固件（start.elf）解析后决定
   mailbox 分配的 fb 深度。KMS 时代分辨率与像素格式由 **DRM/KMS 驱动（vc4）**决定，
   `framebuffer_depth` 不再参与 —— 这跟报告 §2.2 里 `hdmi_group`/`hdmi_mode`/`hdmi_cvt` 在 KMS 下被忽略
   是**同一类失效**（都是 legacy 选项）。
2. 报告里 fkms 已启用、`tvservice` 能报出 1024x600@60（说明 legacy 显示栈在工作、这个参数本该被解析），
   bpp 却仍是 16，所以更可能的原因依次是：
   - fkms 的 fbdev 兼容层是 DRM 的 fbdev 仿真生成的，格式取自 DRM primary plane
     （vc4 默认给 16bpp RGB565 的 framebuffer），与固件层的 `framebuffer_depth` 无关；
   - 参数位置/解析时机：必须在 `[all]` 段（报告说已确认在第 96 行、位置正确），
     但同一文件后段若有覆盖项（例如把 `dtoverlay=vc4-kms-v3d` 反注释、或 `[pi4]` 段）会把它顶掉；
   - 需要**同时**改 DRM 侧（`/boot/cmdline.txt` 的 `video=HDMI-A-1:1024x600@60` 之类）才生效。
3. **结论（也是本次的选择）**：不要把"屏能出图"押在这一项上。让它生效属于改系统配置（红线内明令不动手），
   而**代码按真实 bpp 打包**是同一问题的正确一侧：fb 是 16 还是 32，代码都出正确图像。
   真要试 32bpp：先确认 `/boot/config.txt` 里没有 KMS 覆盖项，再看 `/sys/class/graphics/fb0/bits_per_pixel`
   是否变成 32 —— **变之前不用动代码**（两种都支持）。
