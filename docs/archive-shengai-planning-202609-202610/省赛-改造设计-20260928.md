## 0. 一页总览：改造前后对照

| 维度 | 校赛（现在） | 省赛（本设计） | 为什么必须改 |
|---|---|---|---|
| **件数** | 6 件（一色一件） | **24 件** | 用户口径；= 6 盒 × 4 件上限 |
| **判分依据** | 颜色唯一确定货格 | **颜色 + 形状**（赛规 `:139-141`、`:262-266`） | 24 件必然出现同色不同形/同形不同色 |
| **视觉** | 纯 HSV 颜色，**不测形状** | **形状（模型/几何）+ 颜色（像素）+ 信息（二维码等）** | 形状是判分维度；校赛前提失效 |
| **相机** | 1 路（MaixCAM） | MaixCAM（俯视）+ **第二路（树莓派 CSI 官方相机，斜侧视）** | 单目解不了投影歧义；"信息印在哪面"不知道 |
| **深度** | 无（件高靠手工填 6 个数） | **MaixCAM PMOD_TOF100** | 件高、紧贴、堆叠都是判分相关 |
| **夹爪** | 单舵机联动（升降+开合同一路） | **自上而下包络爪（Z + 爪开合独立）** | "低位+张开"物理不存在 ⇒ 三棱柱崩飞；**且 24 件紧贴时水平对夹进不去** |
| **转盘** | 2 位置（845/2155µs）× 3 落点 | **360° 位置型舵机 + 1 落点 + 转盘转格** | 270° 量程到不了 180° 那格 |
| **落点表** | 3 个坐标 + 孪生硬约束 | **1 个落点**（孪生约束作废） | 转盘改为转格 |
| **运动链** | A4988 + 12V，开环无反馈 | **TMC2209 + 24V + StallGuard 闭环检测 + 同向逼近** | 已 3 次越程堵转；回程差 6~15mm/件；15s 余量仅 1.2~1.8s |
| **供电** | 12V 小电池（3~5Ah，1 小时） | **12V/≥10Ah + 舵机独立 5~6V 支路** | 欠压 ⇒ 失步 / UART 乱码 / Pi 红灯不亮 |
| **15 秒口径** | 🔍 **2026-09-28 核实后更正**：两侧代码**已经**是失活窗语义（见 §4-9），**不是**"单件 ≤15s" | 维持失活窗语义；**只改文档口径** + 补注释/命名 + 评估一处时序 | 多份文档（含旧交接）写着"单件必须 ≤15s"，会把下一个会话带错 |

## 2. 系统架构（改造后）

### 2.1 数据流

```
┌─────────────── MaixCAM（俯视主相机，独立小电脑，自带 NPU）───────────────┐
│  · 形状识别（模型转 .mud 跑在它自己的 NPU 上）                            │
│  · 颜色识别（像素法 HSV / MMCQ）                                          │
│  · PMOD_TOF100 深度（件高 / 紧贴 / 堆叠）                                 │
│  输出：每目标 {形状, 颜色, 货格号, 像素(u,v), 高度}  → TCP 172.20.10.8:8765│
└──────────────────────────────────────────────────────────────────────────┘
                                    │ TCP（只发结果，7~N 字节/目标，非图像流）
                                    ▼
┌────────────────── 树莓派（"链" + 第二路相机 + 信息读取）──────────────────┐
│  · 第二路相机（官方 CSI 模块，斜侧视）→ 读二维码/文字（低频、轻量）        │
│  · 排序（行扫描）→ 像素→装置坐标（仿射）→ +ToolOffset → 判界 → ITEM_TASK  │
│  · 收 MOTION_DONE / ITEM_RESULT → 上屏四栏 → DISPLAY_ACK                  │
│  · 转盘控制：GPIO18 经常驻 pi_pw.py 输出脉宽（360° 位置型舵机）           │
└──────────────────────────────────────────────────────────────────────────┘
                                    │ UART /dev/serial0 115200 8N1
                                    ▼
┌────────────────── STM32F407（运动 + 安全 + 失活窗）───────────────────────┐
│  · XY 龙门：TMC2209 ×2 @ 24V，StallGuard 堵转检测，80 步/mm               │
│  · 夹爪：Z 升降 + 爪开合 = 两个独立通道（自上而下包络爪）                 │
│  · 12 步程序 → 扩展（新增张爪/收拢步），槽位扩容                          │
└──────────────────────────────────────────────────────────────────────────┘
```

### 2.2 三个坐标系 + 两套相机外参

| 坐标系 | 定义 | 现状 |
|---|---|---|
| 像素系 | MaixCAM 320×320 取景 → 224 检测 | 已标（`FRAME_SIZE=320` / `DETECT_SIZE=224`） |
| 装置系 | mm；原点 = **上电位置 = 负端最里角 HOME (−95.0, −97.5)** | 已定 |
| 滑台记账系 | = 装置系 + `[ToolOffset]`；**发给 STM32 的全部是这一系** | 已定，`tx = cx`（不加不减 TO） |

**两套相机 = 两套外参**：MaixCAM 已有 6 参数仿射；**第二路相机要单独标一套**（含它与托盘的相对关系）。**换夹爪/挪相机后两套都要重标。**

## 3. 分支设计

### 3.1 视觉（形状 + 颜色 + 信息）

**三层，各用最合适的办法：**

| 维度 | 方案 | 依据 |
|---|---|---|
| **颜色** | **像素法**（现有 HSV 6 色窗口或 MMCQ）—— 便宜、稳、可解释 | `sort_plan.py` 原设计就是 `shape(YOLO) + color(像素)` |
| **形状** | ① **先用现有几何判据**（`extent/aspect/fill`，见配套子报告）快速验证；② 正式走**重训模型**（MaixCAM NPU） | 判分要求"形状必须对"；7 类 + 尖顶件超出几何判据的能力边界 |
| **信息** | ① **二维码/条形码：MaixPy 内置 `find_qrcodes()`，零训练**；② 印刷文字：限定字符集后轻量识别；③ 污渍/缺陷图形：并入模型 | 用户已定"信息要做（决赛要用）"；规则 `:52-53` |

**🔴 必须解决的一类**：**赛规显示示例里有「正四面体」，而现模型 7 类里没有它**（`视觉/models/labels_yolo5s_geom7c.txt`）。⇒ 重训时**补成第 8 类**（或明确用四棱锥顶替并做"看底面"的验证）。

**数据**：重新采（用户已定）。目标 **每类 ≥150 张**，**必须覆盖"紧贴工况"**（相邻件粘连是 24 件/9 件摆放的常态）。

### 3.2 夹爪（自上而下包络爪）

**设计约束（三条硬约束叠在一起）：**
1. **有尖顶件**（锥体/球体/正四面体）⇒ 吸顶面不可行
2. **件会紧贴**（一批 9 件时缝约 24~35mm；一批 24 件时 ≈0）⇒ **水平对夹进不去**
3. **薄壁件**存在（规则 `:53-54` 明写"包括薄壁货物"）⇒ 夹侧面可能压变形

**⇒ 方案**：**自上而下的三/四指自适应包络爪（软体 Fin Ray 或欠驱动自适应指）**，必要时**同轴加一个中心吸盘**（平顶/薄壁件优先吸）。

| 要点 | 说明 |
|---|---|
| 动作序列 | 到 PICK 上方 → **张爪** → **下降罩住** → **收拢** → 抬起 → 搬运 → 到 PLACE 上方 → 下降 → **张爪释放** → 抬起 |
| 自由度 | **Z 升降** + **爪开合** = 2 路 |
| 自适应 | 靠**形状自适应**（软指/欠驱动），不靠精确行程 ⇒ 覆盖 40mm 件到薄壁件 |
| 件高 | 下降深度取决于件高 ⇒ **用 ToF 量**（替代现在手工填的 `[ObjectHeights]`） |
| 夹持反馈 | **建议装微动开关/压力传感器**（规则 `:27` 允许）⇒ 顺手解掉"无夹持检测" |
| 不遮挡信息 | 抱侧面 ⇒ **顶面留给相机看**（因为信息可能印在顶面） |
| L4 | **新增一路 PWM = 改 I/O 映射 ⇒ L4**，须你批准 |

### 3.3 转盘（360° 位置型 + 1 落点 + 转盘转格）

| 项 | 设计 |
|---|---|
| 执行器 | **360° 位置型**舵机（脉宽 = 绝对角度） |
| 分格 | **6 格各自定位**；位置型有绝对反馈 ⇒ 理论上不需要回零，**光电开关保留作校验件** |
| 落点 | **1 个落点**（滑台固定）+ 转盘把目标格转过来 |
| 驱动 | 仍 **Pi GPIO18**，经常驻 `pi_pw.py` 写 `/home/pi/pw.txt` ⇒ **不动协议、不动固件** |
| 作废项 | `[TurntableSides]`/`[TurntablePositions]`（2 位置语义）、`[DropPoints]` 孪生约束（1↔4/2↔5/3↔6）、`工具/pi_set_droppoint3.py`、`TwoPositionTurntableStrategy` |
| 新增 | 6 格脉宽表；换 6 格策略；**每次转格时间要重新计入 15 秒窗** |

### 3.4 运动链（24V + TMC2209 + 闭环 + 同向逼近）

**顺序不能反 —— 见 §13.6 的最终推荐总序**（闭环 → 主频 → 24V → 巡航 → 加减速 → 热浸/对账）：
```
① TMC2209 StallGuard 堵转检测 + 无传感器回零（让"丢步"可被发现）  ← L4
② 提主频到 168 MHz（启用 25 MHz HSE + PLL）—— 必须同步重算 7 个定时器 PSC（§13.5）
③ 升 24V + 重标 Vref（Rs 必须实测）
④ 提巡航频率（5000 → 6250 Hz，整除档）
⑤ 提加速率（10000 → 20000 Hz/s）
⑥ 热浸 + 15 秒窗重新对账
```
> ⚠️ **更正我此前一处方向性错误**：主频**升高**后，若定时器 PSC 一个都不动，舵机 PWM 频率只会**升高**（TIM2/3 → 262.5 Hz、TIM10/11 → 525 Hz），**不是**"变成 9.5 Hz"。风险表述应为"**偏离 50 Hz 达 5.25~10.5 倍**"（子报告更正）。
**并行项**：**同向逼近**（先走到目标 −3mm 再正向走 3mm）⇒ 把回程差从"随换向变化的随机误差"变成"固定常量"。现状回程差估 **1~2.5mm/次换向 × 6 次 = 6~15mm/件**（与夹取精度同级）。
**🔴 前提**：`Core/Src/main.c` 的 `SystemClock_Config()` 疑似 **16 MHz HSI、PLL 未启用** ⇒ **必须先查清真实主频**，否则所有频率/超时结论作废。

### 3.5 供电

| 项 | 要求 | 判据 |
|---|---|---|
| 电池/电源 | **12V / ≥10Ah**（按整机峰值 60~80W × 1.5 倍余量） | 静态 **≥12.5V**；带载 **≥11.5V** 且压降 **≤0.5V** |
| Pi 供电 | 入口加 **1000µF + 0.1µF** | `vcgencmd get_throttled` 低两位 = 0（开机 dmesg 现有 `Undervoltage detected`） |

| 24V | 若提压，X/Y 驱动改 24V（**舵机仍走 5~6V**） | 单电源前提下做分区降压 |

### 4.1 🔍 「15 秒口径」核实结论（**2026-09-28 逐行核实，更正我此前的说法**）

**结论：两侧代码的语义其实都已经符合赛规，不需要"把单件≤15s改成失活窗"。** 需要改的是**文档口径**，外加 **1 处时序评估**。

| 侧 | 位置 | 实际语义 | 是否合规 |
|---|---|---|---|
| **固件** | `App/Inc/ec_app.h:16-26`、`:25-26` `EC_APP_PROGRESS_SOURCE_ENABLED 1U`；`App/Src/ec_app.c:38`（注释 "Rolling no-motion watchdog"）、`:157-181`（可观测进展续命入口）、`:266-271`（运动开始时开窗）、`:692-723`（`>=15000` → `EC_EVENT_DEADLINE_EXPIRED`） | **滚动"无动作"窗**：开窗后，**每当"X/Y 计数移动自然完成"就续命**；连续 15s 无该进展 ⇒ DEADLINE_EXPIRED。显示侧由 `DISPLAY_ACK` 关闭 | ✅ **符合**赛规"没有动作**或**没有显示" |
| **链侧（空闲钟）** | `run_chain.py:528-536` `--round-idle-timeout` 默认 **15.0s** | **只在"没有运动在飞"时走**；连续 15s 没有可派发的新件 ⇒ 干净收场。注释自述"这一段里没有运动，所以不会误判件周期" | ✅ **符合**（= 台面无件 15s 失活） |
| **链侧（在飞钟）** | `run_chain.py:537-554` `--inflight-timeout` 默认 **35.0s**（**2026-09-22 夜由 20.0 改成 35.0**） | 发了 `ITEM_TASK` 后 35s 没收到 `MOTION_DONE` ⇒ 判**板子静默**、记 FAULT、退出 1。注释明确写"运动期间机器一直在动，赛规 R-R04『超过 15 秒装置没有动作』**不成立** ⇒ 等久一点不违规" | ✅ 合规（它是**板子静默保护**，不是赛规判据） |

**⇒ 真正要做的三件事：**
1. **改文档口径**：把散布在多份文档里的"单件必须 ≤15s"统一改成"**没动作或没显示 ≥15s ⇒ 本轮结束**"（这是文档债，零风险）。
2. **补注释/命名**（可选、零风险）：在 `ec_app.c` 的 15s 处与链侧两支钟处显式写明"这是**失活窗**，不是单件时限"——因为审计发现**同一份代码里已有 4 处注释按旧口径推理**。
3. ⚠️ **评估一处时序（唯一可能要动代码的）**：`--inflight-timeout = 35.0s` **大于赛规的 15s**。若板子真静默，**裁判在 15s 就判本轮结束，而链要等 35s 才收场** —— 现场表现是"屏幕停在某一件约 35 秒"。
   - 影响：**不违规**（链是 fail-closed，期间不会多派件），只是**浪费 20 秒**；
   - 处置建议：**保持 35.0**（因为实测最慢单件 ≈20s，改小会误杀正常件），但把"板子静默"的**第一发现权交给固件侧 15s 看门狗**；同时**在日志里把 inflight 超时单独标记**，便于现场分辨"是板子挂"还是"正常慢件"。

**⇒ 对 24 件连续跑的意义**：用户口径（"夹取后没有放 / 分拣后没有显示，15s 结束"）与现行实现**一致** ⇒ **24 件的节拍设计可以按"件间隔 ~0.9s、单件 ~13s、只在真正失活时才结束"来做**，不必为"单件 15 秒"额外牺牲功能。

### 13.1 步进频率是怎么产生的（关键）

调用点：`App/Src/ec_board_stm32.c:201` → `ec_step_profile_plan(profile, steps, 200U, 5000U, 200U, 10000U, 10000U)`

| 实参 | 含义 | 值 |
|---|---|---|
| `steps` | 本腿步数 | 调用方传入 |
| `200U` | 起步频率 | 200 Hz = 2.5 mm/s |
| **`5000U`** | **巡航（峰值）频率** | **5000 Hz = 62.5 mm/s** |
| `200U` | 末步频率 | 200 Hz |
| `10000U` ×2 | 加/减速率 | 10000 Hz/s |

**Hz → ARR**：`reload = round(timer_hz / frequency) − 1`（`ec_step_profile.h:77`、`ec_step_profile.c:202-204`）
**`timer_hz` 的来源**：`ec_board_stm32.c:28` → `#define EC_STEP_TIMER_HZ UINT32_C(100000)`；而 TIM4/TIM8 的 **PSC 都是 159**（`main.c:344`/`:404`）⇒ **16 MHz ÷ 160 = 100 kHz**，**与那个宏一致**（全链路自洽；改任一端必须同步改另一端）。

**代入算例（全整除、零量化误差）**：
| 目标 | 算式 | ARR |
|---|---|---|
| 5000 Hz | `round(100000/5000)=20` | **19** |
| 200 Hz | `round(100000/200)=500`（与 `tests/test_step_profile.c:199` 的 499 断言一致） | **499** |
| **6250 Hz**（建议档） | `round(100000/6250)=16` | **15**（= 78.125 mm/s） |
| 10000 Hz（上限 `EC_STEP_MAX_HZ`） | `round(100000/10000)=10` | **9** |
| ⚠️ 6000 Hz（**不建议**） | `round=17` ⇒ 实际只有 5882 Hz ⇒ **−2% 量化误差** | 16 |

**⚠️ 一个极易踩的坑**：`ec_axis_driver.h:38` 的 `EC_AXIS_MOVE_FREQUENCY_HZ = 500` 与 `:201` 的 `5000` 是**两个不同的量**。前者只用于 ① 规划失败时的兜底恒频（`ec_board_stm32.c:206`）、② 超时判据。**真正决定巡航速度的是 `:201` 的第 4 个实参**（源码 `:192-193` 注释已写明）。
⇒ **只改 `:201` 实参即可提速，且动作超时判据会变得保守 10 倍**（无需求改）。加速段步数 = `(5000²−200²)/(2×10000) = **1248 步 = 15.6 mm**`，加速时长 **0.48 s**。

| TIM9 | APB1 | 预留 PWM（App 未被引用） | 159 | **839** | 同 TIM4（当前无人用，但应一并改，避免日后接线即踩） |
| TIM10 | APB2 | 挡板舵机 PWM 50 Hz | 15 | **167** | 168 MHz÷16÷20000 = **525 Hz** |
| TIM11 | APB2 | 挡板舵机 PWM 50 Hz | 15 | **167** | 同上 525 Hz |

**动态计算、不受影响的部分（有依据）**：
- **UART 波特率**：`stm32f4xx_hal_uart.c:3782` `pclk = HAL_RCC_GetPCLK1Freq()` ⇒ BRR 在 `HAL_UART_Init` 时按当时 PCLK 现算；且 `SystemClock_Config()`（`main.c:105`）排在 `MX_USARTx_UART_Init()`（`:124-125`）之前 ⇒ **115200 不用改**
- **SysTick / `HAL_GetTick()`**：`stm32f4xx_hal.c:256` 用 `SystemCoreClock`，而 `stm32f4xx_hal_rcc.c:719` 会在 `HAL_RCC_ClockConfig` 内先更新它、`:722` 再 `HAL_InitTick()` ⇒ **1 ms 节拍不受影响**
- **IWDG**：由 **LSI** 决定（`main.c:201-202` 注释"LSI 32kHz / 32 / 1000 = 1Hz"），LSI 已开（`:165`）⇒ 不受影响

**★ 支持提主频的硬理由**：`ec_step_profile.h:66-67` 原文 "**sqrt is ~1 us on a 168 MHz M4, negligible against the 100 us worst case**" —— **该头文件的设计假设本就以 168 MHz 为前提**。当前 16 MHz 下同一整数开方约 **10.5 µs**，占 `EC_STEP_MAX_HZ = 10000`（100 µs）预算的 **~10%**，而且**是在步进 ISR 里每拍都算**。⇒ **提频既让该假设成立，也是把上限从"5000 Hz 勉强"推到 10000 Hz 的前提。**

### 13.6 ★★ 最终推荐总序（子报告结论）

```
闭环（S8 StallGuard + S9 无传感器回零，⚠️L4）
   → 提主频到 168 MHz（含 7 个定时器 PSC 重算）
      → 24V + Vref 重标定（Rs 必须实测）
         → 提 cruise（5000 → 6250）
            → 提 accel（10000 → 20000）
               → 热浸 + 15 秒窗对账
```

**三条理由**：
1. **风险面不重叠**：提主频只改**时序**，改错立刻可见且**可回退**（改回 `SYSCLKSource=HSI` 即恢复），不引入机械/热/电流风险；升 24V 同时引入**电压、电流、发热、电源跌落、限流设定** 5 类**物理风险**。
2. **先修"算力天花板"，再谈"速度天花板"**：提频是提速的**前置条件**（`ec_step_profile.h:66` 的 1 µs 假设）；反过来先提 24V，则每拍 ISR 仍吃掉 ~10 µs，**10000 Hz 档根本无法安全启用**；且提频让"定时器重算"这件事**只做一次**。
3. **两者都排在闭环之后**：24V 提高可用转速、168 MHz 提高可用步频，**都会把系统推到"更容易丢步"的工况**，而现有固件对丢步**零可观测性**（`ec_axis_driver.c:13` 只剩 ESTOP 一个安全输入）。
