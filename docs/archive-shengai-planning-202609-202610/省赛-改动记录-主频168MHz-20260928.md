# 改动记录 · 固件主频 16 MHz → 168 MHz（2026-09-28）

> **授权**：用户 2026-09-28 明确「**你想改就改**，因为之前可能就是因为频率出现了一点问题吧，我觉得，然后导致它速度比较慢」。
> **性质**：**这是本次省赛改造的"第 0 步"** —— 它本身**不提速**，只是把被卡住的算力天花板打开（提速见 §6）。
> **状态**：代码已改、**主机侧自检已通过（exit 0）**、**未编译、未烧录、未上电**。

---

## 0. 一句话

固件原本跑在 **HSI 16 MHz + PLL 未启用**；而**项目自己的设计文档与运动规划代码都是按 168 MHz 写的**。
本次改成 **HSE 25 MHz + PLL = 168 MHz**，并**同步重算 7 个定时器的 Prescaler**。

---

## 1. 为什么这是"配置遗留"而不是"有意设计"（三条依据）

| # | 依据 | 原文 |
|---|---|---|
| **1** | **项目自己的设计文档按 168 MHz 时钟树核算** | `docs/design/stm32f407-pin-timer-allocation.md:90`：「TIM8/TIM4/TIM9 时钟按 STM32F407 时钟树核算（**APB2 定时器 168 MHz 或 APB1 定时器 84 MHz**，最终以 CubeMX 配置为准）」 |
| **2** | **运动规划代码的设计假设就是 168 MHz** | `电控/stm32_logic/include/ec_step_profile.h:66-67`：「sqrt is ~1 us on a **168 MHz M4**, negligible against the 100 us worst case」<br>⇒ 16 MHz 下同一整数开方约 **10.5 µs**，占 `EC_STEP_MAX_HZ = 10000`（100 µs 周期）预算的 **~10%**，而且**是在步进中断里每拍都算** |
| **3** | **CubeMX 工程里 PLL 本来就是配好的** | `电控/firmware/stm32f407_m144z/diankongv1.0.ioc`：`RCC.HSE_VALUE=25000000`、`RCC.VCOInputFreq_Value=1000000`、`RCC.VCOOutputFreq_Value=192000000`、`RCC.PLLCLKFreq_Value=96000000`（PLL 目标是 96 MHz），**但生成代码却是 `PLL_NONE` + `SYSCLKSOURCE_HSI`** ⇒ 高度疑似"某次改动没改回去" |

**⇒ 这也是"速度慢"的结构性原因之一**：16 MHz 下每拍步进中断要吃掉 ~10 µs，提速（提高巡航频率）没有余量。

### 附带确认的两件事（都有仓库证据）

- **板载 HSE 晶振 = 25 MHz**：`diankongv1.0.ioc` 的 `RCC.HSE_VALUE=25000000`，并被 `RCC.RTCHSEDivFreq_Value=12500000`（= 25 ÷ 2）交叉印证 ⇒ **PLLM=25 是安全的**。
- **F407 绝不能调用 `HAL_PWREx_EnableOverDrive()`**：`Drivers/CMSIS/.../stm32f407xx.h` 里 **无** `PWR_CR_ODEN/ODRDY`；而 `Drivers/STM32F4xx_HAL_Driver/Src/stm32f4xx_hal_pwr_ex.c:404` 注释原文：「This function can be used only for STM32F42xx/STM32F43xx/STM32F446xx/STM32F469xx/STM32F479xx devices.」
  ⇒ F407 跑 168 MHz **不需要** over-drive；**误调用**会等一个永不置位的 ODRDY ⇒ `HAL_TIMEOUT` ⇒ 若判空则进 `Error_Handler` **板子不启动**。（本次**没有**添加该调用。）

## 2. 改了什么（逐文件逐行）

### 2.1 `Core/Src/main.c` → `SystemClock_Config()`

| 项 | 改前 | 改后 |
|---|---|---|
| `OscillatorType` | `HSI\|LSI` | **`HSE\|LSI`**（IWDG 仍需 LSI） |
| `HSIState` | `RCC_HSI_ON` | 删除（改由 HSE 供源） |
| `HSEState` | — | **`RCC_HSE_ON`** |
| `PLL.PLLState` | **`RCC_PLL_NONE`** | **`RCC_PLL_ON`** |
| `PLL.PLLSource` | — | `RCC_PLLSOURCE_HSE` |
| `PLLM/PLLN/PLLP/PLLQ` | — | **25 / 336 / DIV2 / 7** |
| `SYSCLKSource` | **`RCC_SYSCLKSOURCE_HSI`** | **`RCC_SYSCLKSOURCE_PLLCLK`** |
| `AHBCLKDivider` | `DIV1` | `DIV1`（不变） |
| `APB1CLKDivider` | **`DIV1`** | **`RCC_HCLK_DIV4`**（42 MHz，F407 的 APB1 上限） |
| `APB2CLKDivider` | **`DIV1`** | **`RCC_HCLK_DIV2`**（84 MHz） |
| Flash 延迟 | **`FLASH_LATENCY_0`** | **`FLASH_LATENCY_5`** |

**算例（全整除）**：
```
HSE 25 MHz ÷ PLLM(25) = 1 MHz × PLLN(336) = 336 MHz(VCO) ÷ PLLP(2) = 168 MHz
HCLK  = 168 MHz      (AHB /1)
PCLK1 =  42 MHz      (APB1 /4)  → APB1 定时器钟 = 84 MHz
PCLK2 =  84 MHz      (APB2 /2)  → APB2 定时器钟 = 168 MHz
PLLQ  =  48 MHz      (未用 USB/SDIO，保守取值)
```

### 2.2 `Core/Src/main.c` → **7 个定时器的 Prescaler**（🔴 漏一个就堵转）

| 定时器 | 总线 | 用途 | 改前 | **改后** | 判据 |
|---|---|---|---|---|---|
| **TIM2** | APB1 | 舵机（夹爪/Z） | 15 | **83** | 84 MHz ÷ 84 ÷ 20000 = **50 Hz** |
| **TIM3** | APB1 | 舵机（挡板通道） | 15 | **83** | 同上 50 Hz |
| **TIM4** | APB1 | **STEP_Y** | 159 | **839** | 84 MHz ÷ 840 = **100 kHz** |
| **TIM8** | APB2 | **STEP_X** | 159 | **1679** | 168 MHz ÷ 1680 = **100 kHz** |
| **TIM9** | APB1 | 预留 PWM（当前未用） | 159 | **839** | 84 MHz ÷ 840 = 100 kHz |
| **TIM10** | APB2 | 舵机（挡板通道） | 15 | **167** | 168 MHz ÷ 168 ÷ 20000 = **50 Hz** |
| **TIM11** | APB2 | 舵机（挡板通道） | 15 | **167** | 同上 50 Hz |

**关键不变量**：TIM4/TIM8 的**计数时钟仍是 100 kHz**，与 `ec_board_stm32.c:28` 的
`#define EC_STEP_TIMER_HZ UINT32_C(100000)` **保持一致** ⇒ `reload = round(100000 / 目标频率) − 1` 的换算**不受影响**。

### 2.3 `Core/Src/system_stm32f4xx.c`

`uint32_t SystemCoreClock = 16000000;` → **`168000000`**（运行期会被 `HAL_RCC_ClockConfig` 覆盖，但保持初值一致可避免"在时钟配置前读它"的代码拿到错值）。

### 2.4 不需要改的部分（已核实依据）

| 项 | 为什么不用改 | 依据 |
|---|---|---|
| **UART 波特率 115200** | HAL 在 `HAL_UART_Init` 时按**当时**的 PCLK 现算 BRR；且 `SystemClock_Config()` 排在 `MX_USARTx_UART_Init()` **之前** | `stm32f4xx_hal_uart.c:3782` `pclk = HAL_RCC_GetPCLK1Freq();`；`main.c:105` vs `:124-125` |
| **SysTick / `HAL_GetTick()` 1 ms** | `HAL_RCC_ClockConfig` 内会先更新 `SystemCoreClock`，紧接着 `HAL_InitTick()` 用新值重算 | `stm32f4xx_hal_rcc.c:719` / `:722`；`stm32f4xx_hal.c:256` |
| **IWDG ≈1.0 s** | 由 **LSI** 决定，不依赖 SYSCLK | `main.c` 注释「LSI 32kHz / 32 / 1000 = 1Hz」；`LSIState = RCC_LSI_ON` |
| **`EC_STEP_TIMER_HZ`** | 计数时钟仍是 100 kHz（见 §2.2） | 自检脚本已验证 |
| **巡航频率 5000 Hz** | **本次刻意不动** —— 见 §5 | `ec_board_stm32.c:201` |

## 3. 主机侧自检（可复跑）

新增脚本 **`工具/check_clock_tree.py`**：解析 `main.c` 的时钟配置与 7 个定时器 PSC/Period，
反算频率并与期望值比对，同时校验 `EC_STEP_TIMER_HZ` 与 `SystemCoreClock` 一致性。

```powershell
cd C:\Users\29845\Desktop\工创赛
py -3 工具\check_clock_tree.py
```

**实测结果（exit 0）**：
```
  HSE = 25 MHz      PLL M/N/P/Q = 25/336/2/7      SYSCLK = 168 MHz
  HCLK = 168 MHz    PCLK1 = 42 MHz -> APB1 timer clk = 84 MHz
                    PCLK2 = 84 MHz -> APB2 timer clk = 168 MHz
  FLASH_LATENCY = 5 WS
  OK  TIM2  APB1 PSC=83   Period=19999      50.00 Hz    expect 50
  OK  TIM3  APB1 PSC=83   Period=19999      50.00 Hz    expect 50
  OK  TIM4  APB1 PSC=839  Period=9999   100,000.00 Hz    expect 100,000  (STEP_Y)
  OK  TIM8  APB2 PSC=1679 Period=9999   100,000.00 Hz    expect 100,000  (STEP_X)
  OK  TIM9  APB1 PSC=839  Period=9999   100,000.00 Hz    expect 100,000
  OK  TIM10 APB2 PSC=167  Period=19999      50.00 Hz    expect 50
  OK  TIM11 APB2 PSC=167  Period=19999      50.00 Hz    expect 50
  OK  EC_STEP_TIMER_HZ(100000) == TIM4 counter clock -> reload 换算成立
  OK  SystemCoreClock = 168,000,000
PASS
```

> 脚本注：**判据分两类** —— 舵机类看「PWM 输出频率」；步进类（TIM4/8/9）看「**计数时钟**」。
> 因为步进定时器的 `Period=9999` 只是初值，实际每步由 `__HAL_TIM_SET_AUTORELOAD()` 按目标频率动态改写。
> 另：脚本会**先剥掉注释**再检查 —— 否则会把本文件说明注释里"举例提到"的 `HAL_PWREx_EnableOverDrive()` 误判成真的调用了（实测踩过一次）。
