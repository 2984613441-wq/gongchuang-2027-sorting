## 零、为什么需要这份文档

**赛规（`docs/references/赛题原文-提取文本/省赛规则.txt` L262-266）：**
```
储物盒中只有【一个】货物得 2 分；
【多个颜色和形状相同】的货物放进同一个储物盒，每个货物得 5 分
将【不同颜色或者不同形状】的货物放入同一个储物盒（只要货物部分进入）为分拣错误，不得分
```

**⇒ 混装 = 整盒 0 分。**

**而「混装」会从三个地方冒出来：**

| 位置 | 怎么混的 |
|---|---|
| **MaixCAM → Pi** | `code` 编码错位 ⇒ Pi 以为是另一类 ⇒ 送错盒 |
| **Pi 的组表** | 同一 (颜色,形状) 被分配了两个盒，或两类被并进一个盒 |
| **屏幕图片** | `code → image_id` 错位 ⇒ 显示错图（合规扣分），且掩盖了真问题 |

**⇒ 所以三方对 `code` 的理解**必须逐位一致**，且**必须有自动校验**。本文 + 两个脚本就是为此。**

## 二、第一段通信：**MaixCAM → 树莓派**（TCP 8765）

### 线格式（冻结，`interface-contract §5.1`）

```
BATCH_TARGETS 载荷:
  target_count(1) + task_id(2, BE) + target[N]

每个 target (7 字节):
  id_byte(1) + confidence(1, 0-100) + X(2, BE) + Y(2, BE) + angle(1, 0xFF)
```

### 字段语义（**每一行都是硬约束**）

| 字段 | 字节 | 语义 | 约束 |
|---|---|---|---|
| `target_count` | 1 | 本帧目标数 | 0~255 |
| `task_id` | 2 | 帧序号（BE） | 两侧各自维护，不参与决策 |
| **`id_byte`** | **1** | **`code`（1~30）** | **必须 ∈ [1,30]**；`0` 或越界 ⇒ 视觉侧应**丢弃该件**而非整帧报错 |
| **`confidence`** | **1** | **`min(颜色置信度, 形状置信度)`** | 0~100；`< 50` ⇒ 下游视为**待定** |
| `X` | 2 | **中心像素 X**（BE） | **只用于去重/排序/重定位，绝不进运动** |
| `Y` | 2 | **中心像素 Y**（BE） | 同上 |
| `angle` | 1 | **必须 `0xFF`** | 夹爪不旋转；不是 0xFF ⇒ 拒收该帧 |

### 🔴 现在要改的一处（`vision_ingest.py`）

```python
# 现状（校赛旧模式）
BATCH_ID_BYTE_IS_BOX_ID = True
#   ⇒ id_byte 承载 box_id(1..6)，class_id = box_id = id_byte
#   ⇒ box_id 由视觉侧折叠颜色得到

# 要改成
BATCH_ID_BYTE_IS_BOX_ID = False
#   ⇒ id_byte 承载 code(1..30)，class_id = code
#   ⇒ box_id = 【由树莓派侧的 GroupTable 动态分配】
```

**🔴 但只改 `False` 不补映射 ⇒ `box_id = None` ⇒ `socket_vision_source._expand()` 对 None 一律拒识 ⇒ 一件都发不出去 ⇒ 15s 无动作 ⇒ 本轮结束。**

**⇒ 所以这两个改动必须**同一个 PR 上线**：**
1. `BATCH_ID_BYTE_IS_BOX_ID = False`
2. `GroupTable` 接管 `box_id` 分配

## 四、第三段通信：**树莓派 → 屏幕**（HDMI / fb0）

### `DisplayAck` / `DisplayViewModel`（4 个字段，赛规要求）

| 字段 | 内容 | 来源 |
|---|---|---|
| **序号** | **行序号**（1, 2, 3...） | Pi 侧按「出现顺序」编号 |
| **货物名称** | `display_name_of(code)` = `颜色+形状` | `shape_color_code.py` |
| **图片** | `image_id_of(code)` = `code` → `/home/pi/images/{code}.png` | `shape_color_code.py` |
| **分拣成功总数量** | 该类累计成功件数 | `GroupTable` 的 `count` |

### 🔴 赛规要求（L141-142、L269-271）

```
显示屏将显示分拣的相关信息统计：包括序号、具体的货物名称以及图片、分拣成功的总数量
正确显示…【每条信息得 2 分】，上述信息出现任何错误不得分。
超过15秒…【没有显示本次分拣信息】，本轮比赛结束。
```

**⇒ 三条硬约束：**
1. **4 个字段都要有**，缺一或错一 ⇒ 该条信息不得分
2. **每件分拣后必须显示**，没显示就分下一件 ⇒ 该件不得分（L275）
3. **15 秒没显示** ⇒ 本轮结束（L143-144）

### 屏幕布局（用户 2026-10-26 裁决）

**「序号」= 行序号**（1, 2, 3...），**不是盒号，也不是货物序号**（依据：L145-150 示例只有 2 行，序号 1=五棱柱、序号 2=正四面体）。

**⇒ 屏幕只显示「出现过的种类」，不是固定 6 行。**

**「货物名称」带颜色**（用户裁决）：
```
红色五棱柱 / 蓝色五棱柱   ← 同形状不同色时能区分
```

**⚠️ 赛规表1 的货物名称是纯形状名（五棱柱）。加颜色是为了区分同形状不同色。若评委要求严格逐字，改用 `shape_name_zh_of(code)`（返回纯形状名）。**
