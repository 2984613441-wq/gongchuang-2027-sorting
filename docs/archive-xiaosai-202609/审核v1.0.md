2.3 23.2 s 超时风险核实

来源：docs/冲突与决策台账-2026-09-10.md:217（E-20）：

motion-time-budget.md 算出 500 Hz 下 23.2 s ❌、3000 Hz 下 15.47 s ❌

核实结论：

这是单件最坏时间预算，假定 XY 从原点到对角 (-145, -145) → (+145, +145) = 410 mm

500 Hz 是 EC_AXIS_MOVE_FREQUENCY_HZ 的占位值（App/Inc/ec_axis_driver.h:17,25）

实际频率未标定 → 23.2 s 是推算值，非实测

但风险真实存在：若实际运动速度 \< 3000 Hz，单件可能触发 15 秒看门狗

与赛题的关系：赛题是\"15 秒没有动作\"（失活），不是\"单件必须 15 秒内完成\"。

→ 只要机构在动（XY 步进、Z 升降），看门狗不会触发。

→ 真风险：机构卡住/固件死循环 → 15 秒失活 → DEADLINE_EXPIRED → 本轮结束。

a\. 帧长度上限是多少？现有 payload 多长？加 4 字节会不会超？

外层帧 data_len 字段：uint16_t（2字节），最大 65535 字节 (ec_protocol.h:29)

现有 ITEM_TASK payload：8 字节

加 4 字节后：12 字节

总帧长：14（固定开销）+ 12（payload）= 26 字节

结论：✅ 完全在范围内，不会超限

b\. CRC 覆盖范围会变吗？

CRC 计算：ec_crc16_modbus(out, EC_PROTO_HEADER_LEN + frame-\>payload_len) (ec_protocol.c:56)

CRC 覆盖 header(12) + payload(N)，随 payload_len 自动调整

结论：✅ 自动适应，加字段后 CRC 会自动覆盖新字段

c\. 接收侧的解析是定长还是带长度字段？定长的话加字段会让旧固件解析错位吗？

解析流程：

ec_proto_decode() 先读外层帧 data_len (ec_protocol.c:75)

ec_proto_decode_item_task() 做严格长度检查 (ec_protocol.c:175)：

if (payload_len != EC_PROTO_ITEM_TASK_PAYLOAD_LEN) return false;

旧固件收到新帧：payload_len == 12 != 8 → 解码失败 → ✅ fail-closed（不会错误执行）

新固件收到旧帧：payload_len == 8 != 12 → 解码失败 → ✅ fail-closed

结论：✅ 不向后兼容，但 fail-closed，不会解析错位或执行错误动作

d\. 有没有版本号/字段可用来协商？还是只能硬切？

外层帧 version 字段：冻结为 0x01 (ec_protocol.h:35)

文档说明：interface-contract.md §3：\"协议版本校赛冻结为 0x01；不兼容时禁止启动\"

没有命令字级别的版本协商

结论：❌ 只能硬切（树莓派和 STM32 必须同时升级）

e\. grip_angle = 0xFF 这个字节能复用吗？复用是否也是 L4？

现在用途：固定 0xFF（夹爪不旋转）(ec_protocol.h:150)

复用可能性：

只有 1 字节，但需要 4 字节（抓取点 x/y 各 2 字节）

不够用 ❌

即使够用，复用也是 L4：

改变字段语义 = 改系统间通信协议

interface-contract.md 冻结了 \"grip_angle 恒 0xFF\"

结论：❌ 不可行（容量不足）；即使可行，仍是 L4

f\. 坐标单位确认：现有 x/y 是 0.1mm、域 ±1450。抓取点用同一套吗？

现有单位：0.1mm（即 mm10）(interface-contract.md:160)

现有域：\|value\| ≤ 1450（±145.0mm）(ec_protocol.h:149)

原点：装置中心 (interface-contract.md:161)

抓取点应该：✅ 用同一套（相同单位、相同域、相同原点）

理由：XY 机械坐标系统一，不需要两套坐标系

验证：抓取区域（托盘）和落料区域（六盒）都在±145mm范围内

2.4 request_id 实现方式

方案：复用外层帧 frame_seq ⭐ 推荐

理由：

外层帧已有 frame_seq(2)（ec_protocol.h:68）

语义匹配：\"每方独立递增\"（interface-contract.md:56）

不需要修改 BATCH_TARGETS 结构（main.py:342-368）

实现：

树莓派：

发送 REQUEST_FRESH_BATCH 时递增 frame_seq（例如 42）

记录当前 request_id = frame_seq

只接受 frame_seq == request_id 的 BATCH_TARGETS

MaixCAM：

收到 REQUEST_FRESH_BATCH(frame_seq=42)

采新图 → 推理

发送 BATCH_TARGETS 时回显同一个 frame_seq=42

与去重机制的关系：

外层帧去重：按 (task_id, frame_seq) 判定重复（interface-contract.md:268）

request_id：树莓派主动递增 frame_seq → MaixCAM 回显 → 树莓派校验

不冲突 ✅（请求-响应模式天然单调递增）

备选方案：在 BATCH_TARGETS 载荷中追加 request_id(2) 字段

优点：语义更明确

缺点：需要修改 BATCH_TARGETS 结构（又是一个协议变更）

暂不采用（优先复用现有字段）

2.5 超时与重试

参数 值 理由

单次超时 1000ms 视觉推理 \< 500ms（未测❓） + 网络RTT \< 50ms + 余量

最大重试 1 次 15秒预算紧张，最多 2 次尝试（首次+1次重试）

总超时 2000ms 1000ms × 2

超时后行为 记录\"无目标\"，跳过本件，不阻塞后续 保证不触发 15 秒红线

失败场景处理：

场景 行为 阻塞？

超时（1次） 重试 1 次（再等 1000ms） 否

超时（2次） 记录\"无目标\"，跳过本件，继续下一轮 否

响应 frame_seq 不匹配 拒绝（旧帧），不重试（等待匹配的帧或超时） 否

2.7 MaixCAM 请求期间的行为

问题：请求期间 MaixCAM 还发不发无条件帧？

设计：暂停无条件帧（REQUEST 期间）

理由：

避免树莓派收到\"旧的无条件帧\"和\"新的响应帧\"混在一起

简化树莓派的接收逻辑（只认 frame_seq 匹配的）

pending_request = None \# None 或 (frame_seq, timestamp)

while not app.need_exit():

\# 1. 检查是否有请求（通过长连接接收 REQUEST_FRESH_BATCH）

if received_request_fresh_batch():

pending_request = (request.frame_seq, time.ticks_ms())

\# 2. 采图 + 推理

frame = cam.read()

objects = detector.detect(frame, \...)

\# 3. 发送逻辑

if pending_request is not None:

\# 请求模式：发送一次（带正确 frame_seq），然后清除

send_batch_targets(objects, frame_seq=pending_request\[0\])

pending_request = None

else:

\# 无条件模式：按原来的逻辑发送

if objects or (now - \_last_heartbeat_ms \>= 500):

send_batch_targets(objects)

超时处理：

树莓派超时 → 重试或放弃

MaixCAM 的 pending_request 超过 2000ms 未清除 → 自动清除（避免卡死）

2\) 台架会不会绕过安全状态机？

会绕过生产状态机；急停只靠台架自己那一层，且停错通道。

证据：

• ec_app_poll() 无条件 ec_servo_test_poll + ec_diag_poll，不看 FAULT_LOCK / READY。

• 生产 ESTOP 在 ec_app_poll_motion()，只在 EXECUTING / WAIT_ITEM_RESULT / WAIT_DISPLAY_ACK 才跑。台架测试时通常不在这些态 → 生产 ESTOP 不参与。

• 台架自己查 EC_INPUT_ESTOP_FB（ec_servo_test.c:8-18, 93-107），急停 GPIO 仍能停这次 PWM。

• 停的是 ec_servo_port_stop() = TIM2_CH3 / PB10。Z 正式通道是 ec_servo_port_start_z() = TIM2_CH4 / PB11。

• ec_safety_port_stop_all() / inhibit_power() 只 stop PB10，不停 PB11。ec_axis_driver 的 stop_all() 两个都停；安全适配器没有。若舵机在 PB11，急停/SAFE_LOCK 停不掉 Z。

结论：台架不是生产抓取状态机，但也不是"裸脉冲、无安全"。它有 ARM 窗口 10 s、白名单、2 s 超时、ESTOP 轮询，但打的是 PB10 旧夹爪通道，不是注释里的 Z。

3\) ec_servo_test 还有两个会伤人的设计

1\. 引脚错。 命令表是 SERVO PB10 P1000...1900（ec_diag.c:53-59）。ec_servo_test_start() 调 ec_servo_port_start()（PB10）。生产取放用 EC_AXIS_STEP_Z_SERVO → ec_servo_port_start_z()（PB11，ec_axis_driver.c:251-252）。单舵机现在接哪根，方案没要求确认。接 PB11 时，台架会打空脚或打到另一路，Z 不动，操作员可能加大脉宽或改去 GROUP/DEMO。

2\. 2 秒后停 PWM。 EC_SERVO_RUN_MS = 2000。SERVO-TEST.md 写数字舵机"停 PWM 仍能保持"------那是 DS3120MG。用户本任务口径是 MG996R 模拟、无位置反馈：PWM 一停，保持力矩通常掉，带载 Z 可能下落。冻结表补记还写过 LDX-335MG 数字，和总览/本任务的 MG996R 打架，上电前必须先定型号。

白名单只有 1000/1100/1200/1300/1500/1700/1900，做不了 50 µs 首测步进。要更细只能改白名单（A 红线禁止先改）或不用这条台架。

A. \"显示完才能下一件\"门禁 ------ 结论 + 文件:行号

调度器软件门禁是堵死的：没有 RenderReceipt，Pi 不会派下一件。

协议上门禁是 STM32 等 Pi 发来的 DISPLAY_ACK，不是 Pi 等 STM32 回 ACK。

像素门禁是假的：frame_output=none / 写错 bpp / HDMI 没亮，present() 仍会 complete()，下一件照样走。

1\. 有没有「无 RenderReceipt 仍放行下一件」的路径？

调度器里没有。 next_task() 只在 READY 才派发（电控/src/electrical_control/rpi/\_\_init\_\_.py:199-201）。accept_item_result() 把状态打到 WAIT_RENDER（:303）。只有 accept_render_receipt() 才回到 READY（:306-329），且收据必须是 PendingRender.complete() 登记过的对象（:307-308，identity 用 is）。

run_chain.py 主循环在 ITEM_RESULT 之后同步调用 \_render_and_ack（:924-925）。ITEM_TASK 超时重传只在 last_task_context is not None 时发生（:867），而 ITEM_RESULT 一到就把 last_task_context = None（:906）------渲染阶段不会用超时强行推进。

ImageLoadError / 名称表 ValueError 不会被吞掉后继续：\_render_and_ack 无 try/except（:644-685），异常冒到 main() 整条链 return 1（:957-959）。这是退出，不是跳过。

唯一看起来像「跳过」的是 :656-658（task/content 为 None 就 return）。正常 ITEM_RESULT 路径里网关已经调过 accept_item_result，这两项应都在；这是防御分支，不是超时放行。

会放行、但屏幕没变的路径： present() 只要 frame_output 不抛，就会产出 PendingRender（display_hdmi.py:91-108）。none 的回调是 lambda img: None（run_chain.py:505-506）。这不是「无收据放行」，是「收据为真、像素为假」。

C. 15 秒看门狗与显示 ------ 结论

固件实现了滚动失活看门狗，覆盖显示等待。树莓派主链路没有 15s 看门狗。缺图导致不显示时，STM32 会在窗口到期后锁轮，不是永远静默；auto→none 则看门狗被假 ACK 关掉。

1\. 实现了没有？

有，在 STM32 ec_app.c，不在 run_chain.py。

• 开窗：运动启动 last_observable_ms = HAL_GetTick(); watchdog_active = true（:176-180）

• 判据：(now_ms - last_observable_ms) \>= 15000 → EC_EVENT_DEADLINE_EXPIRED（:407-418）

• 关窗：首次 EC_ACTION_ACK_DISPLAY_CONSUMED 或进入 READY（:196-206）

• MOTION_DONE 不续时（:456-460）

• 生产编译 EC_APP_PROGRESS_SOURCE_ENABLED=0，进度令牌是空操作（ec_app.h:18-20，ec_app.c:133-135）------窗口从运动开始一次性 15s，含整段 pick-place + 显示

• 状态机：DEADLINE_EXPIRED → FAULT_LOCK（ec_state_machine.c:89-90）

• 检查范围含 WAIT_DISPLAY_ACK（ec_app.c:377-382）

Pi 侧：run_chain.py 只有 5s ITEM_TASK 重传（:817）。state_machine/core.py:164-175 的 OBSERVABLE_WINDOW = 15.0 没有接到 run_chain。电控 Python 树无第二处 15s 失活实现。

2\. 覆盖显示吗？

覆盖「等 DISPLAY_ACK」这一路，不覆盖「屏幕上有没有像素」。

合法 DISPLAY_ACK 一到就关窗，不管 HDMI 亮没亮。

3\. 图片加载失败时看门狗会不会触发？

• ImageLoadError → Pi 退出、不发 DISPLAY_ACK → STM32 窗口继续 → 会触发，本轮锁死。 不是无限卡死。

• present() 卡在 fb0 写入 → 同样，STM32 到期锁轮。

• auto→none：ACK 照发，看门狗关掉，裁判屏空白，本轮继续。这是看门狗覆盖不到的洞。

另：若单件运动本身 \>15s（台账 E-20 的 23.2s 预算），看门狗在显示前就会打在运动上。那是 P11 的题，但会让「显示路」根本走不到。

\## 我认为 P3 需要注意的接口点

1\. \*\*签名保持 \`(const ec_gateway_t \*g, int16_t \*x, int16_t \*y)\`\*\*，单位 0.1mm、原点 = 装置中心（与 \`item_x/y_mm10\` 同系）→ P3 只填函数体 + 加 latch 字段，\`ec_app.c\` 一行都不用改。

\## 🔴 两个顺带发现（\*\*发现问题写出来，没顺手改\*\*）

\### ① \`VALIDATE_TASK\` + \`ITEM_RESULT_RECORDED\` = 无限递归（潜伏缺陷，我先踩到了）

\*\*我第一版\*\*按\"抓取点在 \`VALIDATE_TASK\` 也要校验\"写（因为签名改了，\`VALIDATE_TASK\` 那个调用点必须动），结果：

\`\`\`

\*\*机制\*\*（已定位）：\`ec_state_machine.c:149-180\` 的 \`else if\` 链里，\*\*\`ITEM_RESULT_RECORDED\` 在 \`VALIDATE_TASK\` 状态下没有任何分支\*\* → 状态\*\*不变\*\*、无 action。而 \`ec_app.c\` 的 \`VALIDATE_TASK\` 块在失败时调 \`ec_app_inject_item_result()\` → \`ec_app_handle_transition()\` → 又看到 \`state == VALIDATE_TASK\` → \*\*再进同一块 → 无限递归\*\*。

\*\*这不是我引入的\*\*（那段 \`else { inject(\...) }\` 早就存在），但它\*\*之前不可达\*\*：旧代码里 \`ec_motion_plan_build\` 在合法坐标下恒成功，走的是\"通过\"分支。\*\*任何让这个 else 分支变常态的改动都会触发它。\*\*

\*\*我的处理（是取舍，见分歧声明）\*\*：\`ec_app.c:243-264\` 改回\"只对落料点做可达性探针\"，并把原因写在注释里。\*\*根因（状态机缺一条 \`VALIDATE_TASK \--失败\--\> 某状态\` 的转移）属协议/状态机侧，我没动 ------ 留给 P8/用户裁决。\*\*

\### ② \`ACK(ACCEPTED)\` 被吞掉 ------ 与 P2 无关的既有缺陷

\*\*实测\*\*：喂一个合法 ITEM_TASK，整轮\*\*只发出 1 帧\*\*（boot 的 BARRIER_READY），该 ITEM_TASK 的 \*\*ACK 一帧都没有\*\*。

\*\*机制\*\*（已定位到行）：

\- \`ec_protocol_gateway.c:366\`（\`ec_gateway_feed_byte\` 入口）与 \`:437\`（\`ec_gateway_inject\` 入口）\*\*每次都 \`g-\>tx_len = 0U\`\*\*
