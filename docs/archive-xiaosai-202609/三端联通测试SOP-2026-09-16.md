### S1 ｜STM32 单端：上电 → 启动序列 → `WAIT_TASK`

**测什么**：板子活着吗？启动链路走到 `WAIT_TASK` 了吗？（这是后面一切的前提）

**前置（人工）**：按「方案 A」，**上电前把 X/Y 机构摆到装置中心**（上电位置即原点，`ec_startup_sequence.c:8-24`）。

**怎么测**（只读，不发一个字节）：

```powershell
:: 1) 先接好 USB-TTL（接法见 §4），把 START 键（PA4→GND 的按钮/杜邦线）准备好
py -3 工具\link_check_stm32.py              :: 列出 COM 口，确认是哪个
py -3 工具\link_check_stm32.py --port COM17 -t 30
:: 2) 看到「只读监听 30 秒」后立刻：给 STM32 上电（或按复位键），然后在 30 秒窗口内按一次 START
:: 若板子已经上电很久、又想重看一遍：加 --pulse-dtr（见下）或直接按板上复位键
```

**通的判据**：窗口内出现

```
[入站] A5 5A 01 03 02 00 00 00 01 20 00 00 xx xx
       cmd=BARRIER_READY(0x20) from=0x03 to=0x02 task_id=0 frame_seq=1 len=0 crc=OK(...) payload=
...
  [通] 收到 BARRIER_READY(0x20)：设备已进入 WAIT_TASK，可以接 ITEM_TASK。
```

退出码 0。

**不通的判据**：30 秒内**零字节**（打印 `[不通/未知] 一个字节都没收到`）。
注意：**零字节 ≠ 一定不在 `WAIT_TASK`**（见下）。

**怎么确认它在 `WAIT_TASK`（本任务最容易翻车的一点）**

| 办法 | 能不能用 | 说明 |
|---|---|---|
| 看 `BARRIER_READY(0x20)` | ✅ 唯一可靠的主动证据 | 它**只在状态转换那一刻发一次**；错过了就没有了 |
| 让它重发 | ❌ 做不到 | 固件没有「查询状态」的在线命令 |
| 发 ASCII `STATUS` | ❌ 编译掉了 | `EC_DIAGNOSTIC_BUILD=0`（`.uvprojx:337`），`ec_diag.c` 里整段被 `#if` 掉 |
| 等 `DEVICE_READY(0x03)` | ❌ 永远等不到 | 固件从不发它 |
| 发 `ITEM_TASK` 看 ACK | ⚠️ 可行但**会动机构** | 在 `WAIT_TASK` 会回 `ACK(0x05)`；不在就静默。用 `--send`（有二次确认） |
| **正确姿势** | ✅ | 让监听窗口**覆盖「上电 + 按 START」全过程**；错过了就复位重来（`--pulse-dtr` 或按复位键）再听一次 |

**不通时最可能的 3 个原因（按概率）**

1. **没按 START / START 没真的拉到 GND**。PA4 配的是 `GPIO_NOPULL`（`main.c:689-693`），
   是**低电平有效**输入（`ec_inputs.c:51-54` 取反），而且有 **20 ms 去抖**（`ec_inputs.c:3`）。
   悬空引脚读数随机 → 有时过、有时不过，这是最阴的一种。
2. **`ESTOP_FB`（PG13）被判为急停触发**。同样是 `NOPULL` + 低电平有效
   （`main.c:702-708`、`ec_app.c:284-294`）：PG13 **悬空或接 GND 都可能读到低** → POST/HOMING
   直接 `FAILED` → `EMERGENCY_STOP` → 回 `FAULT_LOCK`。**PG13 应当被明确拉到 3V3**。
3. **串口这一层就不通**（口选错/接线/波特率）—— 用 S2 区分。区分方法很简单：
   如果连乱码都没有，先去 S2 证明串口本身通。

**定位到具体环节**：先跑 S2 证明串口能收字节（哪怕是乱码）；收到字节才谈状态机。
若串口确实通、又确实收不到 `BARRIER_READY`，就按上面 1→2 的顺序查启动链：
① 用万用表/杜邦线确认按住 START 时 PA4 真的到 0 V 且保持 ≥100 ms；② 确认 PG13 为高。

> ⚠️ 上电后 STM32 **不会**主动发任何东西（没有心跳、没有开机横幅）。**开机安静是正常的。**

### S2 ｜PC ↔ STM32（串口 / USART2）

**测什么**：COM 口能不能打开、字节能不能进 PC。

**怎么测**：

```powershell
py -3 工具\link_check_stm32.py --port COM17 -t 20        :: 只读监听
:: 想验证「发出去会不会被受理」（⚠️ 会动机构，且要求设备已在 WAIT_TASK）：
py -3 工具\link_check_stm32.py --port COM17 --send --task-id 7 --x 100 --y 50
:: 会要求你手输 MOVE 才继续；另可用 工具\pc_item_task.py 做同一件事（它多一层 --dry-run）
py -3 工具\pc_item_task.py --port COM17 --task-id 7 --x 100 --y 50 --dry-run
```

**通的判据**（任一条即可，越靠上越强）：

- 打印 `[入站] ... crc=OK(...)`（收到任意合法帧）；
- `--send` 路径下看到 `[入站] cmd=ACK(0x05)`，并进一步 `MOTION_DONE(0x22)` / `ITEM_RESULT(0x23)`；
- `pc_item_task.py --dry-run` 的 22 字节帧与主机侧自检全绿（这只证明**PC 侧构造**没错，不证明链路）。

**不通的判据**：

- `错误: 打不开 COM17 ...` + exit 2（口不存在/被占用）；
- 打开成功但 20 秒 0 字节；
- 打印一整片 `[入站] 丢弃: ...`（乱码）或 CRC 不过。

**不通时最可能的 3 个原因（按概率）**

1. **串口被别的程序占着 / 选错口**。串口助手、Arduino IDE、`monitor_gui`、甚至上一次没退干净的
   python 进程都会占用；Windows 里一个口同时只能被一个进程打开。
   证实：报 `Access is denied`，或换一个口能打开。修：关掉占用进程；
   枚举时看 `USB-SERIAL CH340 (COMxx)` 的字样。
2. **TX/RX 没交叉 或 没共地**。PC 的 **TX→PA3**、**RX←PA2**、**GND↔GND**（§4）。
   共地缺失的典型现象是偶发乱码/CRC 错而不是完全静默。
   证实：**环回测试** —— 把 USB-TTL 的 TX 和 RX 直接短接：
   ```powershell
   py -3 -c "import serial;s=serial.Serial('COM17',115200,timeout=1);s.write(b'ping');print(s.read(4))"
   ```
   回 `b'ping'` = 模块和驱动都好，问题在接线或 STM32 侧；回 `b''` = USB-TTL/驱动/口的问题。
3. **波特率不对**。固件 `huart2` 固定 **115200 8N1**（`main.c:580-588`），这一项**不要**在测试中乱试。
   波特率不匹配的典型现象是**乱码**（不是静默）：`[入站] 丢弃: 未找到 0xA5 5A 帧头（噪声字节）`。

**⚠️ CH340 的 DTR/RTS 会复位 STM32**：很多 USB-TTL 板把 DTR 经电容接到 NRST。
`link_check_stm32.py` 打开串口后**主动把 DTR/RTS 拉低**以避免误复位；
`--pulse-dtr` 反过来利用它：**故意复位一次**，用来重看开机过程（复位后别忘了按 START）。
【未验证】你的 CH340 到底有没有 DTR→NRST 这条线 —— 看板子或直接实测：插上模块时板子会不会重启。

**🔴 互斥**：PC 直连和树莓派连接**不能同时**接在 USART2 上（见 §4.4）。

### S3 ｜树莓派单端（基于 `工具/pi_screen_check.py` 扩展）

**测什么**：能不能起来、Pillow/字体/`/dev/fb0`/串口设备名/权限。

**怎么测**（原有 5 项 + 我加的诊断命令，全部只读）：

```bash
# 原有 5 项（首选链路 venv 的解释器，那才是 run_chain 实际用的）
python3 工具/pi_screen_check.py
/opt/ec-chain/deploy/.venv/bin/python 工具/pi_screen_check.py

# —— 扩展：串口设备名 / 权限 / 占用（本 SOP 新增，只读）——
ls -l /dev/serial0 /dev/serial1 /dev/ttyAMA0 /dev/ttyUSB*  2>&1
groups | tr ' ' '\n' | grep -x dialout && echo "在 dialout 组" || echo "不在 dialout 组"
sudo fuser -v /dev/ttyAMA0 2>&1            # 谁占着串口（没有 fuser 用 sudo lsof /dev/ttyAMA0）
systemctl is-active serial-getty@ttyAMA0   # 串口控制台是否在抢（active=被占用）
grep -iE 'enable_uart|dtoverlay|vc4' /boot/firmware/config.txt /boot/config.txt 2>/dev/null
ip -4 addr show | grep -E 'inet '          # 本机 IP（S5 要用）
```

**通的判据**：

- `pi_screen_check.py` 里**与联通相关**的项：Pillow `[OK]`；
- 存在一个可用的串口设备名（`/dev/ttyAMA0` 或 `/dev/serial0`），权限组 `dialout`；
- 打印出本机 IP（例如 `172.20.10.8`），与 MaixCAM 的 `GATEWAY_HOST` 一致。

**不通的判据**：`/dev/ttyAMA0` 不存在 / 不在 `dialout` / `serial-getty` 为 `active` / Pillow FAIL。

**不通时最可能的 3 个原因**

1. **设备名不对**：树莓派上可能是 `/dev/ttyAMA0`、`/dev/serial0`、`/dev/ttyS0` 中的任意一个
   （`电控/deploy/README.md:39-41` 已写明端口名是部署配置，不写死）。
2. **串口控制台抢占**：`/dev/serial0` 默认是 login 控制台 → `serial-getty@ttyAMA0` active 时你打开它
   会收到一堆 `raspberrypi login:` 文本（表现为乱码 ASCII）。修：`sudo raspi-config` 关 shell over serial（要你批准）。
3. **权限**：当前用户不在 `dialout`。修：`sudo usermod -aG dialout $USER` 后重新登录。

> ⚠️ `pi_screen_check.py` 的 `[FAIL]` 大多来自**标定数据缺失**（字体/名称表/图片目录），
> 跟通不通无关 —— 别把它当成网络问题的证据。

### S4 ｜MaixCAM 单端（**最有价值的一条，能脱离树莓派验证**）

**测什么**：检测跑得起来吗？帧率？出目标吗？

**怎么测**：

```bash
# MaixCAM 上（先关掉 8765 通道，免得每帧 connect 超时拖慢循环）
ssh root@<MaixCAM_IP>
cd /root && ENABLE_NETWORK=0 python main.py        # 看到 [MONITOR] 监听端口 9001
```
```powershell
# PC 上
py -3 工具\link_check_maixcam.py --host <MaixCAM_IP> -t 15
```

**通的判据**：

```
  [通] TCP 连上了 9001。
  收到 7xx 行 JSON（约 50 行/秒），坏 JSON 0 行，…
  MaixCAM 自报 fps: 首=21.3 末=21.5 最高=22.0
  有目标的帧 120 / 空帧 600
  共 xxx 个检测框，类别分布: 0×n 3×n …
  置信度范围: 0.5xx ~ 0.9xx
```

即：**稳定 ≥5 行/秒 + 放一个货在镜头前时「有目标的帧」增长**。
（9001 的发送线程每 20 ms 推一次最新帧，`main.py:228-241`。）

**不通的判据**：

- `[不通] 连不上: ...`（被拒/超时）；
- 连上了但 `收到 0 行 JSON`；
- 一直 `全程 0 目标`（检测循环在跑，但没有目标）。

**不通时最可能的 3 个原因**

1. **IP 不对 / 不在同一网段**（MaixCAM 常是 `172.20.10.2`，PC 若走别的网卡就连不上）。
   证实：`ping <MaixCAM_IP>`；MaixCAM 屏幕上能看到 IP。
2. **main.py 没在跑，或 `ENABLE_MONITOR=0`**（比赛时建议关，调试时忘了开）。
   证实：MaixCAM 控制台应有 `[MONITOR] 监听端口 9001`；MaixCAM 上 `netstat -ltn | grep 9001`。
3. **模型/镜头问题**：`MODEL_PATH` 不存在（`/root/my_models/model_8766.mud`）会让进程直接崩；
   镜头没对准/光照差/`CONF_TH=0.5` 太高 → 有 JSON 流但 0 目标。

**定位方法**：有 JSON 流无目标 → 是视觉问题（不是网络）；无 JSON 流 → 是进程/网络问题。
用 `--self-test` 排除脚本自身问题。

### S5 ｜MaixCAM → 树莓派（TCP 8765）

**测什么**：MaixCAM 连得上树莓派吗？`BATCH_TARGETS` 到得了吗？格式对吗？

**怎么测**：

```bash
# 树莓派上（⚠️ 先确认没有 run_chain 在跑：8765 只能有一个监听者）
python3 工具/link_listen_8765.py -t 30
# 想让心跳也能自证，用空场景即可：MaixCAM 不出货时每 500 ms 发一帧 count=0
```
```bash
# MaixCAM 上（GATEWAY_HOST 默认是写死的 172.20.10.8，见 main.py:39）
ENABLE_NETWORK=1 GATEWAY_HOST=<树莓派IP> python main.py
```

**通的判据**：

```
正在监听 0.0.0.0:8765（Ctrl-C 结束），30 秒后自动停
>>> 客户端连接: 172.20.10.2:51xxx
[批次 1] count=0 task_id=0 len=3B
[批次 2] count=2 task_id=7 len=17B
    #1 class_id=3 conf= 87 x= 640 y= 360 angle=0xFF
```

出现 `>>> 客户端连接` + 至少一个 `[批次 N]` 且**没有 `[丢]` 行** = 通 + 格式合法。

**不通的判据**：

- `[不通] 没有任何客户端连上来`；
- 连上了但每个批次都是 `[丢] 非法批次 ...`；
- 连上后立刻断（对端 send 失败 → `[NET] send failed`）。

**不通时最可能的 3 个原因**

1. **`GATEWAY_HOST` 没设/仍是默认 `172.20.10.8`**，而树莓派 IP 已经不是它。
   脚本默认值就是那个 IP，**这正是最容易过时的一处**。
2. **树莓派没监听**：端口被占用（`run_chain` 在跑）、或本脚本没起来、或绑在了别的端口。
   证实：树莓派上 `ss -ltn | grep 8765`（应见 `LISTEN`）。
3. **不同网段/防火墙**：MaixCAM 与树莓派不在同一网段，或树莓派防火墙挡入站。
   证实：树莓派 `ping <MaixCAM_IP>`；`sudo ufw status`。
   MaixCAM 侧可用 `python -c "import socket;socket.create_connection(('<IP>',8765),2);print('ok')"` 直接验证 TCP 可达。

**定位到具体环节**：MaixCAM 控制台的 `[NET] sent 17B to 172.20.10.8:8765` 存在
但树莓派没打印任何东西 → 十有八九是 IP/端口/防火墙（走到了错误的机器）。
两边都打印了 → 网络没问题，转去看 `[丢]` 行的格式原因。

> 🔴 **端口互斥**：`run_chain.py` 和 `link_listen_8765.py` 都会 `bind 8765`，
> 同时跑第二个会 `Address already in use`（脚本会明确提示）。

### S6 ｜树莓派 → STM32（USART2）

**测什么**：串口设备名、权限、环回、能否发出/收到帧。

**怎么测**（只读优先）：

```bash
# a) 只读监听（树莓派上装 pyserial 的话最省事：pip3 install pyserial）
python3 工具/link_check_stm32.py --port /dev/ttyAMA0 -t 30
```
```bash
# b) 没装 pyserial 时，用标准库 termios 裸读（只读、不改任何东西）
python3 - <<'PY'
import os, termios, time
fd = os.open("/dev/ttyAMA0", os.O_RDONLY | os.O_NONBLOCK)
attrs = termios.tcgetattr(fd)
attrs[0] = attrs[1] = attrs[3] = 0
attrs[2] = termios.CLOCAL | termios.CREAD | termios.CS8
attrs[4] = attrs[5] = termios.B115200
termios.tcsetattr(fd, termios.TCSANOW, attrs)
t0 = time.time(); buf = b""
while time.time() - t0 < 30:
    try: buf += os.read(fd, 256)
```

## 2. 定位决策树：现象 → 最可能原因 → 怎么证实 → 怎么修

### 2.1 发了帧但什么都收不到（PC 侧或树莓派侧）

**按这个顺序走，不要跳步：**

1. **先确认「口」是好的**
   证实：环回测试（§S2 的一行命令 / §S6 的 termios 脚本）。
   修：换 USB-TTL、重装 CH340 驱动、换 USB 口（别用 USB Hub）。
2. **确认没人占着口**
   证实 Windows：报 `Access is denied`；Linux：`sudo fuser -v /dev/ttyAMA0`。
   修：关掉串口助手/monitor_gui/残留 python 进程/`serial-getty`。
3. **确认波特率一致**：两边都必须 115200 8N1。
   证实：有**乱码** = 波特率/校验位不匹配（不是静默）；完全静默 = 更像接线/状态机。
4. **确认接线交叉且共地**：TX↔RX、GND↔GND，3.3 V 逻辑。
   证实：万用表测两端 GND 是否连通；测 STM32 PA2 在发帧时有无电平跳动（有跳动=它真的在发）。
5. **确认设备状态**：不在 `WAIT_TASK` 时 `ITEM_TASK` 被**静默丢弃**（§S1）。
   证实：只读监听看有没有 `BARRIER_READY`；按 START 后重听。
   修：复位 → 按 START → 在窗口内观察。
6. **DTR 复位**：CH340 的 DTR 接了 NRST 时，一打开串口就复位 STM32（表现为永远收不到或总在重启）。
   证实：`link_check_stm32.py --pulse-dtr` 能复现一插就重启；或用示波/万用表看 NRST。
   修：把 DTR 的那条线断开（很多模块有跳线/焊盘），或打开串口后**等 3 秒**再发。

**另一个重要区分**：`ITEM_TASK` 发出去后**完全没有回帧**，还有一种可能：
目标序号/轮次被拒 → 那是回 **NACK**，不是静默。**静默 = 状态机根本没受理**。

### 2.2 PC 能收、树莓派不能收（或反过来）

| 方向 | 最可能原因 | 证实 | 修 |
|---|---|---|---|
| PC 能收，Pi 不能 | Pi 与 PC **同时接在 USART2 上**互相打架（电平互相顶） | 看接线：PA2/PA3 上是不是挂着两条线 | 断开一条（互斥，§4.4） |
| PC 能收，Pi 不能 | Pi 设备名/权限/控制台占用 | `fuser -v`、`groups`、`systemctl is-active serial-getty@ttyAMA0` | 换设备名 / 加 dialout / 关 shell over serial |
| Pi 能收，PC 不能 | PC 侧口被占/驱动/线序 | 环回测试 | 见 2.1 第 1、2 步 |
| 两边都能收但内容不同 | 一边波特率/流控不同 | 抓两边 hex 对比 | 统一 115200 8N1，关流控 |

### 2.3 MaixCAM 连不上树莓派（8765）

1. **IP 填错 / 不在同一网段**（最高频）
   证实：MaixCAM 上 `ping <树莓派IP>`；树莓派上 `ping <MaixCAM_IP>`。
   修：改 `GATEWAY_HOST=<树莓派真实IP>`（默认写死 `172.20.10.8`，`main.py:39`），重启 main.py。
2. **树莓派没监听**
   证实：`ss -ltn | grep 8765`（应 `LISTEN`）；或树莓派上跑 `link_listen_8765.py -t 10` 看有没有人来连。
   修：起监听（注意与 run_chain **互斥**）。
3. **防火墙 / 热点隔离**
   证实：`sudo ufw status`；手机热点/路由器开了 AP 隔离时同网段也互不通。
   修：关 ufw 或放行 8765；换路由器/热点。
4. **`GATEWAY_HOST` 没设成环境变量**（改了但没生效）
   证实：MaixCAM 控制台每帧打 `[NET] sent ... to <IP>:8765` 或 `[NET] send failed`。
   修：`GATEWAY_HOST=<ip> python main.py`（注意是在**启动进程时**设）。
5. **MaixCAM 侧 `ENABLE_NETWORK=0`**（我为 S4 关过，忘了改回来）—— 它**根本不发**。
   证实：MaixCAM 控制台没有 `[NET]` 行。

### 2.4 收到乱码 / 半截帧 / CRC 错

| 现象（脚本输出） | 最可能原因 | 证实 | 修 |
|---|---|---|---|
| 一整片 `未找到 A5 5A 帧头（噪声字节）` | 波特率不匹配；或对端在发 ASCII 文本 | 看 hex：能不能认出 ASCII 可读字符（`login:` = 串口控制台！） | 统一 115200；关掉串口控制台 |
| 偶见 `A5 5A` 但 `CRC does not match` | 噪声/接触不良/共地缺失/线太长 | 换短线、加共地、避开电机干扰 | 接线质量；避开电机线与串口线并行 |
| `监听结束时残留 N 字节未成帧` | 帧被截断：波特率、流控、或对端写一半被打断 | 看残留字节是不是某个合法帧的前缀 | 统一参数；对端加 `flush` |
| 收到的帧 `len=` 很离谱 | 长度字段被噪声破坏 | 看 raw hex | 同上 |
| **数据是乱码但看着像文本** | 收到了树莓派的 **login 提示**（serial console 抢口） | 直接 `cat /dev/ttyAMA0` 看是否有 `login:` | `sudo raspi-config` 关 shell over serial |
| 半截批次（8765） | TCP 分包被当成整批（正常 TCP 行为） | `link_listen_8765.py` 已按 count 自定界，正常不会报 | 若报「对端在批次中途断开」= MaixCAM 发一半崩了 |

### 2.5 屏幕黑屏

1. **没有 `/dev/fb0`**
   证实：`ls /dev/fb*`；`lsmod | grep -E 'vc4|v3d'`；`grep -i dtoverlay /boot/firmware/config.txt`。
   修：`config.txt` 加 `dtoverlay=vc4-kms-v3d`（**改系统配置，需你批准**）后重启；确认 HDMI 插在 **HDMI0**、供电 5 V/3 A。
2. **bpp 不对（花屏）**
   证实：`cat /sys/class/graphics/fb0/bits_per_pixel`。
   修：先用 `--frame-output file` 验证内容对不对，bpp 适配是**改代码**的事（不要顺手改）。
3. **没接 HDMI / 接错口**
   证实：插别的显示器/换线；`tvservice -s`（老系统）。
4. **`--frame-output auto` 静默降级 `none`**（最阴的一条）
   证实：run_chain 日志里只有一行 `--frame-output auto -> none`（`run_chain.py:481`），**没有 ERROR**。
   修：显式写 `--frame-output fb0`，让它**报错**而不是沉默。
   ⚠️ 赛题 15 秒不显示本轮信息就判负 —— 这条沉默降级是致命的。

### 4.2 PC（USB-TTL）↔ STM32

| USB-TTL | 方向 | STM32 |
|---|---|---|
| **TX** | → | **PA3（USART2_RX）** |
| **RX** | ← | **PA2（USART2_TX）** |
| **GND** | ⇄ | **GND（必须共地）** |
| 3V3 | ✗ | **不要接**（STM32 自己供电；两边都供会打架） |
| 5V | ✗ | **严禁**（会打坏 PA2/PA3） |
| DTR/RTS | ⚠️ | 若模块把 DTR 接到 NRST，会在打开串口时**复位 STM32** |

要点：**TX↔RX 交叉**、**共地**、**3.3 V 逻辑**、只接三根线。

### 4.3 树莓派 ↔ STM32

| 树莓派 GPIO | 方向 | STM32 |
|---|---|---|
| GPIO14（TXD，`/dev/ttyAMA0`） | → | **PA3（RX）** |
| GPIO15（RXD） | ← | **PA2（TX）** |
| GND（第 6 脚等） | ⇄ | GND（**必须共地**） |

出处：`电控/deploy/README.md:26-41`（树莓派与 STM32 都是 3.3 V，可直接互连；**严禁 5 V**）。

### 4.4 ⚠️ 互斥警告（会烧/会打架）

> **PC 直连和树莓派连接是互斥的**：USART2 只有一对 PA2/PA3。
> 两个发送端同时挂在一根线上 = 两个推挽输出对顶（可能损坏引脚），而且两边都会收到
> 另一方发的字节，测试结论全是错的。
> **切换时：先拔一根，再插另一根。** 同样，不要给同一个 STM32 同时插两块 USB-TTL。

### 4.5 其他

- X/Y 限位开关 **不装**（方案 A，`ec_startup_sequence.c:8-24`）：`X_HOME/X_END/Y_HOME/Y_END/Z_UP/Z_DOWN`
  这些引脚**没有代码在检查**，悬空不影响判据 —— **不要**为了让它过 POST 去接它们。
- 上电前**人工把 X/Y 摆到中心**（否则整场坐标平移）。
- 屏：micro-HDMI 接树莓派 **HDMI0**；屏 CTouch 口接 USB；供电 5 V/3 A（`电控/deploy/README.md:43-49`）。

## 5. 🔴 我猜你会踩的坑（按「踩了最亏」排序）

1. **用 `run_chain` 当联通探针** → 被图片/落点/字体三道门拦住，日志里全是数据错误，你会以为网络不通。
   **联通测试只用本 SOP 的三个脚本。**
2. **上电后直接发 `ITEM_TASK` 等回帧** → 板子还在 `FAULT_LOCK`，静默丢弃，你会去拆线。
   正确顺序：**监听 → 复位/上电 → 按 START → 看到 `BARRIER_READY` → 再发。**
3. **等 `DEVICE_READY(0x03)`** → 固件**从不发**（`ec_protocol_gateway.c:247-256`）。等它 = 永远不通。
   （`pc_item_task.py:370` 的提示文本里也提到它，那是**通用建议文本**，与当前固件实现不符。）
4. **发 `STATUS` / `PING` 等回显** → 生产构建 `EC_DIAGNOSTIC_BUILD=0`，整段 ASCII 命令被编译掉了
   （`.uvprojx:337`）。没回显**不是**故障。
5. **以为 `BARRIER_READY` 随时能再要一次** → 它是**一次性边沿**。错过就要复位重来。
6. **PC 和树莓派同时接 USART2** → 见 §4.4。
7. **CH340 的 DTR 悄悄复位 STM32** → 表现为每次一打开串口设备就重启，树莓派发的帧永远收不到。
   本脚本已默认拉低 DTR/RTS，但硬件上那条线还在。
8. **8765 端口双占用**：`run_chain` 与 `link_listen_8765.py` 只能有一个在跑。
9. **把 9002 当成 MaixCAM 的端口** → 9002 是树莓派的；MaixCAM 只有 9001。
10. **树莓派 `/dev/serial0` 默认是串口控制台** → `serial-getty` 抢口，你会收到 `login:` 文本，
    或直接 `Device or resource busy`。
11. **`--frame-output auto` 静默降级 `none`** → 屏幕黑但没有 ERROR。赛题 15 秒不显示 = 判负。
    调试期**显式写 `--frame-output fb0`**。
12. **START/ESTOP 引脚悬空** → `GPIO_NOPULL` 的输入，电平随机 → 状态机行为随机
    （有时能过、有时不能过），你会怀疑人生。**接线要显式**：START 需要真的拉到 GND，ESTOP_FB 需要明确为高。
13. **心跳帧 `count=0` 被误判**（S5）：无货时每 500 ms 一帧空批次是**正常心跳**，看到 `count=0` 不等于断连。
14. 🔴 **`task_id` 不匹配 → 「网络通但永远没任务」**：MaixCAM 的 `TASK_ID` 默认 **0**
    （`main.py:36`），而树莓派 `SocketVisionSource.ingest` 会**丢弃 task_id ≠ 本轮 round-task-id 的整批**
    （`socket_vision_source.py:142-144`）。所以即使 8765 通了、批次也解得出，
    `run_chain` 也会**一声不响地全丢**。启动 MaixCAM 时记得 `TASK_ID=<本轮任务号>`，
    并让树莓派 `--round-task-id` 与之相等。
15. **小坑**：Windows 是 `py -3`，树莓派是 `python3`（别在树莓派上打 `py -3`）；
    中文输出在 Windows 控制台可能需要先 `chcp 65001`。
