## 3. 三个关键技术发现（总控最该看这节）

### 3.1 🔴 class 5/6 系统性错位（数据级错误，已修）

**证据（旧 ONNX 内嵌元数据，权威）**
```
names = {0:'cube', 1:'cuboid', 2:'cylinder', 3:'hexagonal_prism',
         4:'pentagonal_prism', 5:'square_pyramid', 6:'triangular_prism'}
```
**而训练真值 `data.yaml` / `class.txt` 是**
```
5:'triangular_prism', 6:'square_pyramid'
```
⇒ 自动预标时模型判成 5（四棱锥）的框，在 `data.yaml` 里被当成 **triangular_prism（三棱柱）**。

**后果**：全部自动预标框里 **737 框（39%）** 的 5/6 是反的；v1 模型与已转 `.mud` 的这两类**名字互挂**（识别能力没坏，但名字错，且 labelImg 里显示的类别名与实物不符——这是用户"不知道哪个是哪个"的直接原因）。

**修复方式**（`_label_kit\fix_class56.py`）：
- 判定"继承自自动标注" = 与基线快照 `_baseline_labels_20261022` 中某框 **IoU≥0.9 且 class_id 相同**
- 仅对**继承框**做 5↔6 互换：**301 框**；用户手工新增 **342 框**、用户改过类的 **60 框** 一律不动
- 涉及 **222 个文件**，备份 `_label_kit\_fix56_backup\20261023-005919\`
- **已裁图肉眼验收**：修正后 class 5 为楔形三棱柱、class 6 为金字塔（图见 `_label_kit\_diag_class56.png`）

### 3.2 🟡 空标注图若保留会主动压低检出率

YOLO 把"有图无标注"当作**背景负样本**训练。若图里其实有物体却没标，等于教模型"这里没有东西"。
用户按规则把不要的图**删空标注**后，共 **635 张**（占 54%）→ 若保留作负样本会显著伤害召回，故按 D-2 移除。

**核查记录**（`_label_kit\_diag_empty_images.png`）：空图清晰度中位数 **44** > 有标注图中位 **32**，63.6% 的空图并不糊——说明它们不是"废片"，而是**用户主观判定的不同场景/不要的图**（其中 16 张为白托盘场景，已提示用户可从 `_trash` 单独捞回）。

### 3.3 🟡 labelImg 会整体重写 `classes.txt`（踩坑记录）

`libs\yolo_io.py:52-75`：**每次保存（含自动保存）**都会用内存里的 `label_hist` **覆盖** `<保存目录>\classes.txt`。
- 我用无类别参数启动过一次 labelImg → 它把 `classes.txt` 写成 **7 类**（丢了 `regular_tetrahedron`）→ **已还原**
- 正确用法：启动时**必须传类别文件**（`_label_kit\start_*.bat` 已保证，且每次启动自动 copy 一份干净的 `classes.txt`）

## 9. 环境坑（换机器/换会话必看）

### 9.1 沙箱禁命名管道 → 训练起不来

`multiprocessing.pool.ThreadPool` 内部 `SimpleQueue() → connection.Pipe()`，在 DSH 沙箱下抛：
```
PermissionError: [WinError 5] 拒绝访问
  multiprocessing/connection.py:575  h2 = _winapi.CreateFile(...)
```
Ultralytics 在 **扫标签缓存 / 校验图片** 时用它（`ultralytics/data/dataset.py:138`、`data/base.py:329`、`data/loaders.py:492`、`utils/downloads.py:665`）。

**解法**：`train_7c_sandbox_safe.py` —— **在导入 ultralytics 之前**把 `multiprocessing.pool.ThreadPool` 换成串行替身（逐文件校验，串行与并行结果等价，只慢几秒）。

### 9.2 PowerShell 截断管道会杀掉进程
