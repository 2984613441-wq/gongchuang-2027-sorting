## 0. 一句话

把「每轮只抓一件、每件都回初始位置」的夹取流程写成**可离线跑通、可测试**的模块：
**目标选择 → 路径规划 → 状态机 → 执行器**四层分开，硬件通信通过一个接口注入；
默认只用**离线模拟执行器**，不碰串口、不碰实物。

⚠️ **本模块没有接入 `run_chain.py`，也没有在实机上跑过。** 详见交付报告。

## 2. 跑起来

### 2.1 离线端到端示例（不碰硬件）

在仓库根目录：

```bash
python 电控/deploy/run_pick_strategy.py --config 电控/deploy/pick_strategy.demo.ini --scenario normal
```

会依次打印：参数来源清单 → 选择模式局限 → 锁定了哪一件 → 完整路径 →
化成"滑台记账坐标"的指令序列 → 逐步事件日志 → 本件记录。

Linux / 树莓派上把 `python` 换成 `python3` 即可（入口自己会把 `电控/src` 加进
`sys.path`，不依赖外部 `PYTHONPATH`）。

### 2.2 演示场景（每个场景自带预期，跑完自动核对）

```bash
python 电控/deploy/run_pick_strategy.py --scenario <场景>
```

| 场景 | 演示的问题 | 预期结束形态 |
|---|---|---|
| `normal` | 完整一件 | 出件 1 件 |
| `onray` | 落点正好在退出法线上 | 出件，且「现有 ITEM_TASK 可表达」 |
| `tie` | 两件到无壁边**距离并列** | 出件，选空爪更近的那件 |
| `unreachable-nearest` | 最近件在可抓窗口外 | **拒识本件**，不改抓更远的件 |
| `blocked` | 另一件挡在垂直退出通道上 | **拒识本件** |
| `path-fault` | 带料退出段故障 | 停机（FAULT），不松爪 |
| `timeout` | 卡住无完成反馈 | 运动超时（FAULT） |
| `camera-lost` | 相机断连 | 故障，且**不**判托盘为空 |
| `empty` | 连续空画面 | 本轮结束（ROUND_DONE） |
| `stale-frame` | 重复帧号 | 丢弃旧画面 |

退出码：`0` = 与预期一致；`1` = 与预期不符；`2` = 配置错误；`3` = `--strict` 下有未实测参数；`4` = 现有协议表达不了。

### 2.3 问"现有 ITEM_TASK 能不能表达这份计划？"

```bash
python 电控/deploy/run_pick_strategy.py --executor item_task
```

* 会把计划映射成现有 12 字节 `ITEM_TASK` 载荷并**打印十六进制**（默认 `sink=None`，**一个字节都不发**）；
* 表达不了时（需要"退出中间路径点"）直接拒发并逐条列出缺什么，退出码 4。

### 2.4 用实机配置自查

```bash
python 电控/deploy/run_pick_strategy.py --config 电控/deploy/pick_strategy.ini
python 电控/deploy/run_pick_strategy.py --config 电控/deploy/pick_strategy.ini --strict
```

第一条会因"缝隙几何未实测 + `require_gap_geometry=true`"**拒识本件**（这是刻意
的 fail-closed，符合需求四.6）；第二条直接退出码 3，因为配置里还有【待实测】项。

### 2.5 跑测试

```bash
cd 电控
python -m pytest tests/pick_strategy -q -p no:cacheprovider
```

`-p no:cacheprovider` 是为了避开本机沙箱对 `.pytest_cache` 的写限制，与测试本身无关。

## 3. 配置怎么写

### 3.1 硬规则：每行都要有来源标签

```ini
[Workspace]
x_min = -95.0      # 【固件常量】ec_motion_plan.h:94
```

标签只能是四种：

| 标签 | 含义 |
|---|---|
| `【实测】` | 已由实测、或对代码/文档的只读核对确认 |
| `【固件常量】` | 取自固件源码里的编译期常量（要带 文件:行号） |
| `【演示】` | 为跑通离线示例而假设的值 —— **不是测量结果** |
| `【待实测】` | 已知必须实测但还没有值 |

**漏标签或写错标签 → 加载直接报错、不出计划。** 这样"演示值被当成实机参数"
在机制上就不可能悄悄发生；运行时还会把所有【待实测】项列进"未核实参数"。

### 3.2 节的含义

| 节 | 内容 |
|---|---|
| `[Workspace]` | 滑台可达域（**下发坐标**，记账坐标，原点=装置中心） |
| `[Home]` | 初始位置（**记账坐标**；必须等于固件 HOME，否则计划被判"不可执行"） |
| `[Tray]` | 托盘内域、**无壁边在哪一侧**、缝隙几何是否已知、是否严格要求缝隙几何 |
| `[ToolOffset]` | 工具偏置（滑台记账坐标 = 物料坐标 + 本值） |
| `[Gripper]` | 夹爪完整外形半尺寸（含爪指全张） |
| `[Motion]` | 物料最大半尺寸、退出定位余量、空爪可否跨托盘 |
| `[Feedback]` | 每步超时、模拟器每步耗时、夹持未证实时是否继续、故障时是否保持夹持 |
| `[Vision]` | 选择模式（`center`/`contour`）、旧画面超时、判定"托盘为空"需要的连续帧数 |
| `[Drop]` | 离线演示落点（**记账坐标**，与线上同口径） |
| `[ObjectSize]` | 每个 box_id 的半尺寸（`center` 模式可选；`contour` 模式必须 1..6 全填） |
| `[Obstacle]` | 不可通行区（缝隙/障碍）：`x_min, x_max, y_min, y_max` |

### 3.3 两个坐标系，别混

* **物料坐标**（= 夹爪中心实际到达的物理位置）：托盘几何、抓取点、退出口都用它。
* **滑台记账坐标**：固件实际收到的数。**只有 PICK 会叠加 `ToolOffset`**
  （`pixel_to_device.py:461-470`），**落点不叠加**（`vision_ingest.py:226-236`
  直接把落点写进 wire offset 3-6）。

所以 `[Tray]` / `[Home]` / `[Drop]` 的口径是：

* `[Tray]`、抓取点 → **物料坐标**
* `[Home]`、`[Drop]` → **滑台记账坐标**（与线上一致）

程序内部会把 `[Home]`、`[Drop]` 换算到物料坐标再做几何，`describe()` 里两种
坐标都会打印出来（`落点：物理 … / 记账 …`）。

### 3.4 换选择模式（要不要按"轮廓距离"排）

默认 `selection_mode = center`：只用中心坐标到无壁边的距离。这是**近似**，
与真实轮廓距离差"沿法线方向的一半尺寸"（对 ≤40mm 的件最坏约 20mm）。

要改成轮廓近似：填 `[ObjectSize]`（**必须实测**）并把 `selection_mode` 改成
`contour`。缺任何一个 box_id 的尺寸都会 fail-closed 拒启动。

⚠️ 现有视觉线格式**根本不发宽高/轮廓**，所以 `contour` 模式用的是"每件实测
宽高 + 中心"的**矩形包围盒近似**，不是真轮廓。要真轮廓必须改 MaixCAM 与协议，
见交付报告。

## 4. 代码里怎么用（三个接口）

```python
from electrical_control.pick_strategy import (
    build_config, PickStrategyMachine, SimExecutor, VirtualClock,
    VisionFrame, Detection, Point,
)

config = build_config("电控/deploy/pick_strategy.demo.ini")

# 1) 执行器：离线用 SimExecutor；实机接自己的实现（实现 ExecutorPort 五个方法）
executor = SimExecutor(config)
clock = VirtualClock()

# 2) 状态机：落点用**记账坐标**的查表函数（与现有 drop_strategy 同口径）
machine = PickStrategyMachine(
    config, executor,
    drop_command_provider=lambda box_id: Point(20.0, 74.0),   # 返回 None = 无落点 → 拒识
)
machine.start()

# 3) 喂画面 / 喂反馈，时间由调用方注入
frame = VisionFrame(frame_id=1, received_at_s=clock.now,
                    detections=(Detection(1, box_id=6, class_id=6,
                                          x_mm=55.0, y_mm=30.0),))
machine.on_frame(frame, clock.now)

while machine.state not in (State.WAIT_FRAME, State.WAIT_RESULT,
                            State.WAIT_DISPLAY, State.ROUND_DONE, State.FAULT):
    machine.tick(clock.now)
    clock.advance(0.05)
```

状态机认识的入向事件（都**不**等于"运动完成"）：

| 调用 | 含义 | 会不会推进状态 |
|---|---|---|
| `on_frame(...)` | 新一帧识别结果 | 会（选目标+排计划+派第一步） |
| `on_ack_accepted(...)` | 收到 ACK | **不会**（只记录） |
| `on_item_result(code, ...)` | 本件结果确认 | 会（WAIT_RESULT→WAIT_DISPLAY） |
| `on_display_ack(...)` | 显示流程完成 | 会（WAIT_DISPLAY→WAIT_FRAME） |
| `on_grasp_outcome(bool, ...)` | 外部夹持判据（如果有传感器/视觉复核） | 在夹取步结算时用 |
| `on_camera_lost(detail, ...)` | 相机断连 | 进故障 |
| `tick(now)` | 推进时间、拉执行器反馈、查超时 | 会（按完成反馈逐步推进） |

**唯一能推进"运动步骤"的是执行器给出的 `Feedback(kind="done", ...)`。**
现有 STM32 只在整段程序跑完后发一次 `MOTION_DONE`，所以用现有链路接入时
反馈粒度是"整段"而不是"逐步"，本件记录里会写明
（`feedback_granularity`）。

### 换成实机执行器要做什么

实现 `ExecutorPort` 的五个方法：

```python
feedback_granularity() -> "per_step" | "whole_program"
execute(plan, step_index) -> None      # 下发/推进第 step_index 步
poll(now_s) -> list[Feedback]          # 把真实的 MOTION_DONE 等翻译成完成/故障
stop_and_hold() -> None                # 停止后续动作；**不得**发松爪
describe() -> str
```

⚠️ `execute`/`poll` 里**不要**把"帧被受理（ACK）"当成完成。

## 5. 常见问题

**Q1 为什么"落点"和"抓取点"坐标系不一样？**
因为现有整链就是这样：`pixel_to_device.py:461-470` 只给 PICK 叠加 `ToolOffset`，
`vision_ingest.py:226-236` 把落点原样写进 wire。这究竟是有意（落点本就是滑台
口令）还是漏叠加，**尚未定论**，见交付报告矛盾清单 C-5。

**Q2 为什么脚本"拒识本件"而不是继续等？**
按需求三.7：最近的一件如果抓不到/退不出，就停这一次动作并报原因，
**不**改抓更远的件。拒识**不是故障**，链路会继续等下一帧。

**Q3 为什么 `contour` 模式一开就报错？**
`[ObjectSize]` 没填全。程序不虚构尺寸：现有线格式连宽高都没有，
这些值只能由人实测后填入。

**Q4 故障后会不会把物料松开？**
不会。进故障只调 `stop_and_hold()`，并记下 `retained_grasp`（是否可能仍夹着），
**从不发 release**；`机器保持原状等人工处置`。

**Q5 为什么状态机不用 `time.time()`？**
时间全部由调用方注入（`VirtualClock`），这样离线可复现、测试可确定。

**Q6 能在 Windows 上跑吗？**
能。测试与示例都只做纯计算；唯一注意点：本次会话的文件沙箱**不允许** pytest
的 `tmp_path` 写系统临时目录，所以测试里的临时 ini 写在
`tests/pick_strategy/_tmp/`（该目录是测试产物，可随时删）。
