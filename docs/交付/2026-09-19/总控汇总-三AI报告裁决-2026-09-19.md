## 1. Claude 高风险 #1：ChannelState 永久 BUSY

**Claude 的机理**：`HAL_TIM_PWM_Start()` 置 ChannelState=BUSY，只有 `HAL_TIM_PWM_Stop()` 恢复 READY；
改动 A 之后第二次及后续调用不再 Stop → 永久 BUSY；若首次调用已是 BUSY，`return true` 路径不启动 PWM。

**我回源码复核 —— 机理成立，代码事实全对，但当前不触发，风险等级下调。**

证据（HAL 源码，全部亲自读过）：

- `Drivers/STM32F4xx_HAL_Driver/Src/stm32f4xx_hal_tim.c:1462-1468`
  → 非 READY 直接 `return HAL_ERROR`；随后 `TIM_CHANNEL_STATE_SET(..., BUSY)`。
- `stm32f4xx_hal_tim.c:1523` → **`__HAL_TIM_DISABLE(htim);` 关的是整个 TIM2 计数器**，
  不管别的通道还在不在用。`:1526` 只把**传入的那个通道**恢复 READY。
  → 这正是危险源：PB10(CH3) 与 PB11(CH4) 共用 TIM2，停 CH4 会把 CH3 的输出一起干掉，
  而 CH3 的状态字**留在 BUSY**。

**为什么不触发 —— 是调用顺序恰好保住了它**（这是我核出来、Claude 只是猜到的部分）：

```c
/* ec_axis_driver.c:136-142 */
static void stop_all(void)
{
    ec_step_port_stop_all();
    ec_servo_port_stop();      /* ← CH3 先被置回 READY */
    ec_servo_port_stop_z();    /* ← 再关整个 TIM2 计数器；CH3 状态已安全 */
    ec_step_port_disable_all();
}
```

`ec_servo_port_stop()`（`ec_board_stm32.c:627-631`）调 `HAL_TIM_PWM_Stop(&htim2, TIM_CHANNEL_3)`
→ CH3 回 READY；**之后**的 `ec_servo_port_stop_z()`（`:653-656`）才关计数器。
下一次 `ec_servo_port_start()` 看到 READY → 正常 `HAL_TIM_PWM_Start` → 计数器重新使能。

另外两条停通道路径也安全：`ec_safety_port_stop_all()`（`:831-836`）与
`ec_safety_port_inhibit_power()`（`:843-849`）**都只调 `ec_servo_port_stop()`，从不调 `stop_z()`**
（`:642` 的注释也写明了这一点）。

**裁决：🔴 → 🟡（潜伏，靠调用顺序保命）。建议仍修，但不必急。**

建议改法（3 行，不依赖 HAL 状态语义）：

```c
static bool servo_ch3_started = false;   /* 新增 */

/* ec_servo_port_start() 里，把 :560-562 的守卫换掉 */
if (!servo_ch3_started) {
    if (HAL_TIM_PWM_Start(&htim2, TIM_CHANNEL_3) != HAL_OK) return false;
    servo_ch3_started = true;
}
return true;

/* ec_servo_port_stop() 里补一句 */
servo_ch3_started = false;
```

**为什么值得改**：现在的安全靠"两行代码的先后顺序"，任何人重排 `stop_all()` 里的两行、
或单独调一次 `ec_servo_port_stop_z()`，夹爪就会**静默失能**（CCR 更新了但没脉冲输出），
而故障表现是"夹爪不动"，很容易误判成机械问题。用标志位把这个隐含依赖消掉。

**附带**：`ec_servo_port_start_z()`（`ec_board_stm32.c:644-651`）**没有这道守卫**，
但现在没有生产路径调它（`:640-642` 注释：只有 `ec_demo.c` 还调）。**当前不构成风险**，
仅在日后真把 Z 挪到 PB11 时才必须先补。

## 2. Claude 高风险 #2：HOME 贴边超程

**裁决：接受，🟡→🔴 视坐标而定。这条需要用户裁决，我不擅自改。**

事实链：

- `ec_motion_plan.h:131-132`：`HOME = (-950, -975)`（mm10）。
- `ec_motion_plan.h:83` / `:95`：`EC_MOTION_REACH_LIMIT_X_MM10 950` / `..._Y_MM10 975`。
  → **HOME 正好落在可达域边界上**。
- `ec_motion_plan.c:78-83` `within_limits()` 用的是**非严格** `(x <= lim) && (x >= -lim)`
  → HOME 恰好压线通过，没有任何余量。

所以只要下面任一为真，就会在**远端**顶死：
- 实际行程不足 190mm / 195mm（限位块松动、异物、机械磨损）；
- 上电时人手推到的"最里角"与固件假设的极限位置有偏差。

历史佐证：`ec_motion_plan.h:113-127` 已记录过 **3 次超程堵转并挂掉主控**。

**现状风险评估**：当前实机坐标是 `抓取点=(-41.8,-27.1)mm`、`落点=(20.0,20.0)mm`，
距 ±95mm 边界都很远 → **本轮不触发**。风险只在"取料点/落点靠近边界"时出现。

**两条可选修法（需用户拍板，因为都改变工作域）：**

| 方案 | 做法 | 代价 |
|------|------|------|
| 甲：留机械余量 | `EC_MOTION_REACH_LIMIT_X_MM10` 950→900、`Y` 975→925（各留 5mm） | 远端工作域各缩 5mm |
| 乙：主机侧夹紧 | 视觉/调度侧把 PICK、DROP 坐标硬限在 \|x\|,\|y\| ≤ 70mm | 不碰固件，但不能防人为直发坐标 |

**Claude 给的验证方法我认（可证伪）**：游标卡尺实测最里角与远端限位的实际间距；
或故意把原点偏移 5mm，再发一个贴近边界的 PICK 坐标，用尺量终点偏差。

## 5. Codex C2：7500 Hz/s vs 10000 Hz/s

**裁决：部分接受 —— 收下方法，不撤回 10000。实机已经反证 10000 是可行的。**

Codex 的顾虑（扭矩估算、丢步风险、建议先 7500）是**合理的保守立场**，
但它有一个前提被实机推翻了：Codex 说"生产参数被从 5000 改为 10000，**是否烧录未知**"。

**我用 2026-09-18 19:24 那轮实测把这个问号消掉了：**

- 该轮实测单轮 **≈12.9s**（首帧 ITEM_TASK 19:24:57 → `MOTION_DONE` 19:25:09.9），
  `PROGRESS=10`、`STATE=3(DONE)`、`FAULTS=0`。
- 若板上是 **accel 5000**：估算 13.5s + 2s 停顿 = **15.5s > 15s**
  → 必然触发 `DEADLINE_EXPIRED` 中途中止（就是 `(60,60)` 那次的死法）。**它没中止。**
- 若板上是 **accel 10000**：估算 11.1s + 2s = **13.1s**，与实测 12.9s 吻合。

**→ 板上确实是 10000，且 10 步序 + 2 秒停顿端到端跑通。**

**结论**：10000 **保留**。Codex 的丢步担忧改用**实测**兜底，而不是降速：

> 装上夹爪后，**先跑 `python3 /home/pi/pi_square.py 100`**（100mm 正方形，四条腿首尾相接，
> 不闭合即丢步），再用尺量四边。闭合 → 10000 留用；不闭合 → 退 7500 再测 → 再不行退 5000。

另外把 Codex 那句"装机限流与动态扭矩余量【证据不足】"原样保留，不粉饰。

## 6. Codex 阈值分歧：7192 / 4992 / 2496 —— 我撤回我的数

**裁决：派工书里的 7192 撤回；Codex 的 4992 是对的但基于旧参数；当前正确值是 2496。**

来龙去脉：

- 我的派工书 `docs/交付/2026-09-19/派工提示词-四AI并行.md:71` 写的是
  「已测：腿长 < 7192 步时根本到不了巡航段，此时只有加减速率是有效杠杆」。**这个 7192 我给不出出处，撤回。**
- Codex `tests/分拣链路收口-Codex-2026-09-19.md:65,81-93` 给了算法和原始输出：
  进入完整巡航所需腿长 = 2 × 加速段步数，而
  - `a=5000` → `accel=2496` → 门槛 **4992**
  - `a=7500` → `accel=1664` → 门槛 **3328**
  - `a=10000` → `accel=1248` → 门槛 **2496**
- Codex 的"当前参数对应 4992"是按 **accel 5000** 算的（那时它看到的是 5000 那一版）。
  **但固件现在是 accel 10000**（`ec_board_stm32.c:200`，已烧录并经 §5 反证）。

**→ 当前门槛是 2496 步。** 几乎所有实际腿长都远超 2496，
所以我派工书那句"只有加减速率是有效杠杆"**在 accel 10000 下同样失效**，
两处说法一起作废。感谢 Codex 把我自己的错误数抓出来。

**遗留**：Codex 提到"算法整数截断可能在三角曲线留下极短低峰平台，不应误称已到 5000Hz" ——
这条我**不反驳也不确认**，需要示波器或改 `profile_probe_codex.c` 出数据，标【待验证】。
