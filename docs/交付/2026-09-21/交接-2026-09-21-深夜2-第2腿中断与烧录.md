## 1. 🔴 核心问题（唯一拦路虎）

### 现象
整链跑一轮，**间歇性**在同一处失败（不是"第几件"的规律：两轮死在第 3 件，一轮死在第 1 件；
早上还有一轮 3 件全过）。失败时的日志签名固定为：

```
ITEM_TASK sent → BARRIER_READY（启动序列吞掉）→ 重发 → ACK_ACCEPTED
→ 5s 超时重传 → 板子回 **BARRIER_READY**（而不是 DUPLICATE）
→ 重发 → ACK_ACCEPTED → ~50ms 后 ITEM_RESULT 到达
→ Pi 在 WAIT_MOTION_DONE 收到 result ⇒ "result arrived in wrong state" ⇒ fail-closed 停机
```

**对比成功轮**：5s 超时重传时板子回 **`DUPLICATE`**（说明它正在执行，用缓存应答），最终正常发 `MOTION_DONE`。

### 指纹（两次独立复现，逐字段完全同型）
```
STATUS  APP_STATE = WAIT_DISPLAY_ACK
AXIS    STATE=1（非空闲）  FAULTS=0  PROGRESS=2  LAST_RESULT=0  LAST_* 全 0
        （MOVES 两次为 11 / 1 —— 它是**累计**计数，不是本件步数，不矛盾）
```

### 机制（由指纹锁死）
```
某条腿仍在 MOVING 时，应用就离开了执行态（EXECUTING）
  → 轴驱动**只在 EXECUTING 被 poll**（ec_app.c:500-504）
  → 没人 poll ⇒ 状态永远停在 1，不落回 0
  → 完成锁存的消费与超时判据**只在 poll() 内部**（ec_axis_driver.c:399）
  → **所以 LAST_RESULT 永远写不进去、FAULTS 永远是 0**
  → 应用停在 WAIT_DISPLAY_ACK
  → **15 秒失活窗也不触发**（实测冻结 34 分钟无超时）
  → Pi 5s 后重传 ⇒ 板子重跑 POST ⇒ BARRIER_READY
  → Pi 重发 ⇒ ACK ⇒ 迟到的 ITEM_RESULT ⇒ wrong state ⇒ fail-closed
```

### 关键推论（重要）
1. **`BARRIER_READY` 是"复现钟"，不是"故障钟"** —— ~5.5s ≈ `Pi 5.0s 重传 + POST + HOMING 500ms`。
   板子**早就故障了**，那 5.5s 只是 Pi 重传把已故障的板子重新拉起来的时间。（此结论由 Codex 提出，我采纳）
2. **Codex 建议的"按 `LAST_RESULT` 4/5/6 分流"在本形态下读不出来** —— 正因为"没人 poll"，故障码不会被写。
   读到 `0` 不是"没有故障"，而是"故障没被记录"。
3. **PROGRESS=2 + MOVES=1 ⇒ 走完第 1 条腿、第 2 条腿中断。**
4. **fix A 是对症的**（`ec_app.c:454-476`：离开那三态时若轴还在动就 `ec_axis_driver_stop()`）。
   但它**是止血不是治因** —— 它让这类故障**有机会被记录成故障码**，真因要烧完再复现一次才可能读出来。
