## 1. 🔴 最高优先级 & 最便宜的一步：先把摄像头机械锁死

**在标定之前必须做，否则标定全部白做。**

用户确认支架会动。那么：

```
① 找到摄像头支架的松动点（关节/夹块/螺丝）
② 拧死。必要时加一个定位销或用记号笔画一条防转标记线
③ 用同一物体连拍两次（两次之间不碰机器），比对像素坐标
   两次一致 ⇒ 相机真的固定住了，才开始标定
   仍不一致 ⇒ 支架还在动，回去继续锁（不要往下走）
```

判据：**同一物体、同一位姿、两次上电，像素坐标重复性 ≤ 1 px**。达不到就别标。

## 2. 相机位移之后，哪些坐标会坏、哪些不会坏（**我此前没讲清，这是关键**）

坐标链：`像素 →（pixel_to_device）→ 装置基准坐标 →（+ ToolOffset）→ 滑台坐标 = 下发目标`

| 坐标 | 依赖相机？ | 相机动了之后 |
|------|-----------|-------------|
| `[CameraCalibration]` 6 个仿射参数 | **是** | **必须重标**（这是唯一按像素定义的） |
| 抓取点（识别到的物块 → 滑台坐标） | **是**（经上面那条链） | 随仿射一起修好 |
| `[ToolOffset]`（夹爪↔相机几何偏移） | **是** | 可能变（相机动了，两者相对关系就变了） |
| **落点 ①~⑥ / HOME** | **否** | 纯滑台系常量，**与相机无关，不会因相机位移而变** |

⚠️ **因此用户「只标定落点、其他坐标就都能推出来」的说法，方向需要修正**：
落点是相机无关量，**从落点推不出相机映射**；5 次夹爪测量修的是**抓取侧**（仿射 + ToolOffset），
落点需要另外的独立确认（看料是否真的进了对的格子）。

**两条线要分开做，不要混在一次测量里。**

## 3. 五次夹爪测量的正确设计（用户提的方向是对的，这里给出可执行版）

**为什么 5 次比 2 次强**：2 次只能解**纯偏移**；5 次铺开在工作区里，可以把误差分解成
**偏移 + 尺度 + 旋转**三项。相机支架被碰过，最可能就是**转角变了**——纯偏移拟合修不了转角。

工作区（滑台系，来自 Pi `[WorkspaceLimits]`）：x∈[-95.0,85.0]，y∈[-97.5,87.5]。
可用交叠区（识别区 ∩ 夹取区）= **138 × 106.1 mm**。

```
采样点（尽量铺满交叠区，不要挤在一角）：
  ① 左下  ② 左上  ③ 中心  ④ 右下  ⑤ 右上

每个采样点的流程（沿用已闭环的方法，用户已确认可用）：
  1. 放一个实物在台面，视觉给出滑台抓取点
  2. 按公告的 Δ 走过去，**公告必须先发**
  3. 用户目视报告：横向偏多少 mm、纵向偏多少 mm（方向要说清）
  4. 记表：期望点 (x,y) | 实测偏移 (dx,dy)
  5. 回 HOME，换下一个点

记满 5 行后：
  · 若 5 点偏移基本一致(±2mm) ⇒ 纯偏移，只改 ToolOffset
  · 若偏移随位置线性增长     ⇒ 有尺度/旋转误差，须重标仿射 6 参数
  · 拟合完必须**回到①和⑤复验**，不能只信拟合（这是本项目的既定纪律）
```

**注意事项（本项目已付过学费）**：
- `ToolOffset` 是**全局常量**，不要在某个点上改完就以为修好了全部。
- 现有样本只有 2 个（黑圆柱 +4mm、(0,+4) 后居中；红三棱柱 0 偏移），
  且 `y_mm` 已从 -52.5 改到 **-48.5**。**这 5 次测量会覆盖并取代那 2 个样本。**
- 单位陷阱：`pixel_to_device()` **返回 0.1mm（mm10）**，加 `ToolOffset` 前必须 `/10`。
  （`工具/pi_side/p_look2.py` 顶部的警告就是为这个留的。）
- `p_look2.py` 已改为从 `/home/pi/电控/calibration_config.ini` 读 TO 与 WorkspaceLimits，
  不再有硬编码陈值，可以放心用它出读数。

**相关工具（都已存在，不要新写）**：
`工具/pi_calib_truth.py`（直接 import 生产类，不猜配置）、`工具/pi_set_affine.py`、

## 4. ✅ 待机张开脉宽：**我此前判断过严，重新定位后它是一个安全的小改动**

### 4.1 我在上一份交接里说"加它会复现丢轴 bug"——**那个结论只对了一半**

我当时担心的是"**在待机/idle 时**起一段舵机程序"——那确实会跑在 `EXECUTING` 之外，
重现 orphaned-axis。**但用户要的不是这个。**

用户要的是：**落料之后、回程之前**把舵机切到待机（最宽）开度。
这一步位于 **ITEM_TASK 内部、`EXECUTING` 之内**，与已有步骤同构，
**不新增状态、不新增程序入口** ⇒ 不触发丢轴条件。

### 4.2 缺陷的精确定位（已读源码核对，2026-09-22 凌晨）

生产路径是**串行版** `ec_motion_plan_build_with_open()`（`App/Src/ec_motion_plan.c`），
**不是** interp 版。**已核验**：`App/Src/ec_app.c:185` 调用的正是 `ec_motion_plan_build_with_open()`，
而全工程 **`ec_motion_plan_build_interp()` 没有任何 `ec_app.c` 调用点** ⇒ interp 是死代码/遗留
（`docs/XY插补*.md` 里仍然写着"改回去"的步骤，是过期文档）。

⚠️ **一处待核**：`ec_app.c:301` 出现 `ec_motion_plan_build(&program, place_x_mm10, place_y_mm10)`
—— 只有 3 个实参，与 `ec_motion_plan.h:285` 声明的 4 参签名**对不上**。
可能是另一处注释、另一个同名函数或旧签名残留。**动手改之前先看清 `ec_app.c:290-310`**，
别在错的函数上改（本项目上一次自伤就是这么来的：改了入口没 grep 调用方）。

```
ec_motion_plan.c:247-254   [0] 在 HOME 就把开度切成「该件类别开度」open_pulse_us
ec_motion_plan.c:258-263   XY  HOME → PICK          ← 空爪腿（此时已在类别开度）
ec_motion_plan.c:272-275   WAIT EC_AXIS_PICK_DWELL_MS(2000ms) + Z = EC_AXIS_Z_DOWN_US(闭合)
ec_motion_plan.c:279-285   XY  PICK → PLACE (Y 优先) + Z = open_pulse_us   ← 落料（释放）
ec_motion_plan.c:287-291   XY  PLACE → HOME         ← 🔴 空爪腿，舵机【停在落料用的类别开度】
```

**缺陷就在最后一行**：`PLACE → HOME` 回程腿**没有**再动舵机，于是整段回程维持的是
**落料用的类别开度**。而类别开度是**按件形不同**的：

```
ec_motion_plan.h:254-256   EC_MOTION_OPEN_US_CUBE=650 / PRISM=750 / CYLINDER=800
ec_axis_driver.h:86,120    EC_AXIS_GRIPPER_OPEN_US = 800，且 Z_UP_US = GRIPPER_OPEN_US
```

⇒ **正方体那一件（650）回程时夹爪比最宽态窄 150µs**，正是"回程拦住其他物品"的原因。
**用户的观察是对的，而且我现在能指出是哪一行。**

### 4.3 旁证：interp 版**没有**这个问题，两个版本行为不一致

`ec_motion_plan_interp.c:112-121` 的 6 步表：

```
step[0] HOME→PICK   step[1] open(800)   step[2] close
step[3] PICK→PLACE  step[4] open(800)   step[5] PLACE→HOME
```

interp 的 step[4]/[5] 用的是**固定 800**（最宽），所以 interp 回程本来就是宽的。
**串行版用类别开度，interp 版用固定 800 ⇒ 两版语义分叉**，这本身就是个该记的发现。

### 4.4 建议改法（**下一会话动手前必须先核步数预算**）

```
1) 新增宏 EC_AXIS_GRIPPER_STANDBY_US（待机/回程开度，建议 = EC_AXIS_GRIPPER_OPEN_US = 800）
2) 在 ec_motion_plan.c:285 之后、:287 的回程腿之前，追加一步：
      append_z_servo(out, &next_step, EC_AXIS_GRIPPER_STANDBY_US)
3) 保持 [0] 的"识别到件就切类别开度"不变（用户 2026-09-21 明确否决过改动）
4) 保持落料那一步 open_pulse_us 不变（这是"放进去"的动作，不能改成待机宽）
```

⚠️ **步数预算只剩 1 格，必须实测核对**：
`ec_motion_plan.c:245` 注释称"加此步后共 10 步 ≤ `EC_AXIS_PICK_PLACE_STEP_COUNT`(11)"。
再加 1 步 ⇒ **11/11，零余量**。动手前**先打印实际 `next_step` 计数**，
若已是 11 则必须改为"把 285 行那一步的开度直接写成待机宽"（但那会改掉落料动作，需用户裁决）。

⚠️ **与 15 秒死区对账**：每件多 `EC_AXIS_GRIPPER_SETTLE_MS`（200ms）。
`ec_app.c:553` 的 15000ms 失活窗口 + 本轮已实测到的 **件间空等 17 秒** 是叠加的。
**先解决件间空等 17 秒，再加这 200ms**，否则等于往已经越线的deadline上继续加压。

⚠️ 改完必须跑 `tests/test_motion_plan.c`（其中 22 处调用走老入口 `ec_motion_plan_build`，
`ec_motion_plan.c:294-303` 说行为"逐字节相同"——**这次改动会打破该保证，注释要同步改**）。

**方案（`当前进度与交接.md:1334-1353`，用户 2026-09-21 裁决原文）**：
- 6 格分两组各 3 个，**两组在转盘上相差 180°**

  ⇒ `1500 ∓ 655` = **845µs(a 侧) / 2155µs(b 侧)**，正好 180° 分离且都在行程内

- ❌ 旧方案「6 格 × 45° 排在 270° 弧上」**已作废**（「90°」的混淆就来自旧方案）

⇒ **2155µs 是算出来的（`center_us + us_per_90deg`），不是待测值。**
