## 【R6】分歧声明

### 分歧 1：方案一的互斥机制

**DSH 主张**（:35）：`pgrep -f forensic_v6_frame` 判断 → 无需改取证脚本

**我的观点**：**不同意**

**依据**：
1. 相机设备独占（见 R1）→ 两者无法共存
2. `pgrep` 轮询有竞态窗口（取证刚启动但 `pgrep` 还没查到 → 生产程序启动 → EBUSY）
3. 锁文件是更可靠的互斥机制（POSIX 标准，无竞态）

**替代方案**：
```python
# 监督脚本中（DSH 方案的改进）
import fcntl

def try_acquire_lock():
    try:
        lockfile = open('/tmp/vision_production.lock', 'w')
        fcntl.flock(lockfile.fileno(), fcntl.LOCK_EX | fcntl.LOCK_NB)
        return lockfile  # 持有锁
    except IOError:
        return None  # 锁被占用（取证在跑）

while True:
    lock = try_acquire_lock()
    if lock is None:
        time.sleep(3)  # 等待取证完成
        continue
    try:
        subprocess.run(['python3', '/root/stage1_color_v6_send.py'])
    finally:
        lock.close()  # 自动释放锁
```

**取证脚本同样需改**（在 `main()` 最开头）：
```python
lockfile = open('/tmp/vision_production.lock', 'w')
fcntl.flock(lockfile.fileno(), fcntl.LOCK_EX)  # 阻塞等待锁
# ... 取证逻辑 ...
lockfile.close()  # 结束时释放
```

**理由**：文件锁是内核级互斥，进程崩溃自动释放，比 `pgrep` 更可靠。

### 分歧 2：方案二的校验是否值得

**DSH 疑问**（:76）：启动期校验 BoxMap 一致性，值不值得加？

**我的观点**：**有条件值得**

**条件**：
1. 仅告警，不阻止启动（避免误判导致无法上电）
2. 校验逻辑必须简单（< 50 行，避免成为新的故障点）
3. 告警必须醒目（红色 + 蜂鸣 + 写日志）

**理由**：
- **值得**：配置漂移是真实风险（两份 ini 文件、多人修改、无版本控制）
- **代价小**：启动期检查一次，运行时零开销
- **收益明确**：抓配置错误比抓识别错误便宜 100 倍（前者改配置，后者要重训模型）

**不值得的情况**：
- 若校验逻辑复杂（需解析 JSON + YAML + ini）→ 维护成本 > 收益
- 若团队有严格的配置管理（Git + review）→ 不需要运行时校验

**我的建议**：**加，但简化**

