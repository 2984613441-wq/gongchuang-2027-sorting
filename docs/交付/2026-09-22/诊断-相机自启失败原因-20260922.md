## 一、四条必须排除的可能原因

### 1.1 S99vision 是否真被执行？

【结论】**很可能未被执行或被执行但立即退出**  
【证据】需现场查证  
【分档】推断  
【置信度】4/5

**判断命令**（用户执行）：
```bash
# 命令 1：检查 S99vision 存在性和权限
ssh root@172.20.10.9 "ls -la /etc/init.d/S99vision"
# 预期输出：-rwxr-xr-x ... /etc/init.d/S99vision（可执行位必须有）

# 命令 2：开机后立即检查进程
ssh root@172.20.10.9 "ps aux | grep -E 'vision_supervisor|stage1_color' | grep -v grep"
# 预期输出（若正常）：两行进程
#   root ... sh /root/vision_supervisor.sh
#   root ... python3 /root/forensic/stage1_color_v6_send.py

# 命令 3：检查日志（若 S99vision 写了日志）
ssh root@172.20.10.9 "cat /var/log/vision-sender.log 2>&1 | tail -30"
# 预期：若有 "camera open failed"，说明脚本被执行但摄像头被占用
```

**可能失败原因**：
- S99vision 缺少可执行权限（`chmod +x` 漏掉）
- Buildroot 的 `/etc/init.d/rcS` 没有正确调用 `S99*` 脚本
- S99vision 启动逻辑有误（立即退出）

**可证伪预测**：
- 若 `ps` 看不到 `vision_supervisor`，说明 S99vision 未被执行
- 若 `ps` 看到 `vision_supervisor` 但没有 `stage1_color`，说明监督器起来了但 sender 失败

### 1.2 监督器是否起来又被挂掉？

【结论】**busybox 的 setsid 行为可能不符合预期**  
【证据】需现场查证  
【分档】推断  
【置信度】3/5

**Buildroot/busybox 环境特殊性**：
1. busybox 的 `setsid` 可能不是完整实现（部分版本仅改 SID，不脱离终端）
2. S99vision 若用 `setsid sh /root/vision_supervisor.sh`，可能在 init 退出时被杀掉
3. `/etc/rc.local` 的 `sh /etc/rc.local &` 可能也有类似问题

**判断命令**（用户执行）：
```bash
# 命令 1：查看 vision_supervisor.sh 内容
ssh root@172.20.10.9 "cat /root/vision_supervisor.sh"
# 关注：是否有 `exec`、是否有死循环、sleep 时长

# 命令 2：查看 S99vision 内容
ssh root@172.20.10.9 "cat /etc/init.d/S99vision"
# 关注：start 函数的实现、是否用 setsid、是否后台运行

# 命令 3：检查进程树（PPID）
ssh root@172.20.10.9 "ps -o pid,ppid,comm | grep -E 'vision|stage1'"
# 预期：若 PPID = 1（init），说明成功脱离；若 PPID 是其他值且该父进程已退出，子进程可能被杀
```

**可能失败原因**：
- `setsid` 在 busybox 下不工作，进程被父进程退出时杀掉
- `vision_supervisor.sh` 本身有 bug（例如：死循环条件错误，立即退出）
- 后台运行语法错误（Buildroot 的 sh 可能不完全兼容 bash）

**修复建议**（若此条成立）：
```bash
# 方案 A：在 S99vision 中用 nohup 替代 setsid
nohup sh /root/vision_supervisor.sh >/dev/null 2>&1 &

# 方案 B：vision_supervisor.sh 开头加
#!/bin/sh
cd /root
exec 0</dev/null
exec 1>/var/log/vision-supervisor.log
exec 2>&1
# 然后是监督循环
```

### 1.3 launcher 或其他 app 是否仍占着摄像头？

【结论】**这是最可能的原因**  
【证据】DSH 今天的日志显示 "camera open failed"  
【分档】事实（基于已有日志）  
【置信度】5/5

**关键线索**：
- 原 `auto_start.txt` = `benchmark`，它会启动 `/maixapp/apps/benchmark/main.py auto_start`
- benchmark 程序使用 `maix.camera.Camera()`，独占摄像头
- DSH 改为 `none` 后，**不确定 MaixPy launcher 是否真的不启动任何 app**

**判断命令**（用户执行）：
```bash
# 命令 1：检查 auto_start.txt 当前内容
ssh root@172.20.10.9 "cat /maixapp/auto_start.txt"
# 预期输出：none（如果不是，说明被改回去了）

# 命令 2：查看所有 Python 进程
ssh root@172.20.10.9 "ps aux | grep python | grep -v grep"
# 关注：是否有 launcher、benchmark、或其他 maixapp

# 命令 3：查看 launcher_daemon 是否在运行
ssh root@172.20.10.9 "ps aux | grep launcher | grep -v grep"
# 若输出有 launcher_daemon，说明启动器仍在运行

# 命令 4：尝试手动启动 sender（测试摄像头占用）
ssh root@172.20.10.9 "python3 /root/forensic/stage1_color_v6_send.py 2>&1 | head -20"
# 若输出 "camera open failed"，说明摄像头被占用
# 若正常启动并输出识别结果，说明摄像头空闲
```

**可能情况**：
1. **情况 A**：`none` 不被 launcher 识别，launcher 仍启动了默认 app
2. **情况 B**：launcher 自己占用了摄像头（即使没启动具体 app）
3. **情况 C**：有其他服务（非 launcher）在使用摄像头

**修复方案**（按优先级）：

**方案 1（最激进）**：完全禁用 MaixPy launcher
```bash
# 在 MaixCAM 上执行
ssh root@172.20.10.9 "mv /maixapp/apps/launcher/launcher_daemon /maixapp/apps/launcher/launcher_daemon.disabled"
# 或者
ssh root@172.20.10.9 "chmod -x /maixapp/apps/launcher/launcher_daemon"
```

**方案 2（较温和）**：修改 launcher 配置，确保不启动任何 app
```bash
# 检查 launcher 配置文件位置（可能在 /maixapp/config/ 或 /etc/）
ssh root@172.20.10.9 "find /maixapp /etc -name '*launcher*' -o -name '*autostart*' 2>/dev/null"
# 然后编辑相关配置，明确禁用所有 app
```

**方案 3（保守）**：让 sender 延迟启动，等 launcher 释放摄像头
```bash
# 在 vision_supervisor.sh 开头加
sleep 10  # 等待 launcher 初始化完成并释放摄像头
```

### 1.4 auto_start.txt = none 是否被接受？

【结论】**MaixPy launcher 可能不识别 "none"，导致异常行为**  
【证据】需查阅 MaixPy 源码或文档  
【分档】推断  
【置信度】3/5

**判断逻辑**：
- MaixPy launcher 可能只识别具体的 app 名称（如 `benchmark`、`camera`）
- `none` 不是标准关键字，可能被当作无效值
- 可能的行为：
  - 忽略该值，启动默认 app（最坏）
  - 报错并卡住启动流程（次坏）
  - 什么都不启动（期望行为）

**判断命令**（用户执行）：
```bash
# 命令 1：查看 MaixPy 启动日志（如果有）
ssh root@172.20.10.9 "dmesg | grep -i maix"
ssh root@172.20.10.9 "cat /var/log/messages 2>&1 | grep -i launcher"

# 命令 2：尝试其他已知有效的值
# 先备份
ssh root@172.20.10.9 "cp /maixapp/auto_start.txt /maixapp/auto_start.txt.bak-none"
# 尝试空文件
ssh root@172.20.10.9 "echo '' > /maixapp/auto_start.txt"
# 或尝试注释符（若支持）
ssh root@172.20.10.9 "echo '# disabled' > /maixapp/auto_start.txt"
# 重启后观察
```

**替代方案**（若 `none` 不工作）：
```bash
# 方案 A：创建一个空的占位 app
ssh root@172.20.10.9 "mkdir -p /maixapp/apps/dummy"
ssh root@172.20.10.9 "echo 'import time; time.sleep(999999)' > /maixapp/apps/dummy/main.py"
ssh root@172.20.10.9 "echo 'dummy' > /maixapp/auto_start.txt"

# 方案 B：直接删除 auto_start.txt
ssh root@172.20.10.9 "rm /maixapp/auto_start.txt"
# ⚠️ 风险：不确定 launcher 在文件不存在时的行为
```

## 六、最坏情况与风险

### 风险 1：`none` 导致 launcher 异常

**症状**：系统启动后无响应、无法 SSH 连接

**概率**：低（2/5）

**缓解**：
- 启动时观察 HDMI 输出，看是否卡在某个阶段
- 若卡住，物理断电，插入 SD 卡到电脑，手动恢复 `auto_start.txt`

### 风险 2：禁用 launcher 导致其他功能失效

**症状**：触摸屏、GUI、或其他 MaixPy 功能不可用

**概率**：中（3/5）

**缓解**：
- 本项目不依赖触摸屏和 GUI（只用摄像头和网络）
- 若需要恢复，回滚时重新启用 launcher

### 风险 3：监督器与 launcher 抢摄像头

**症状**：sender 启动成功但立即崩溃，日志显示 "camera open failed"

**概率**：高（4/5）—— **这是最可能的现状**

**缓解**：
- 必须彻底禁用 launcher（方案 1）
- 或者让 sender 延迟启动（方案 3）

### 风险 4：busybox 环境兼容性问题

**症状**：`setsid`、`nohup` 等命令行为异常，进程被意外杀掉

**概率**：中（3/5）

**缓解**：
- 使用多种进程脱离方法（`nohup` + 重定向 + `exec 0</dev/null`）
- 在 S99vision 中直接用 `&` 后台运行，不依赖高级命令
