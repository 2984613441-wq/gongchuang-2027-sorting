## 1. 一句话任务 + 为什么现在做

**一句话任务：把 STM32 协议网关（`电控/stm32_logic/src/ec_protocol_gateway.c`）里每一条「收到帧但什么都不回」的静默丢弃路径，改成回一帧带原因码的 NACK；并把它内部那个单缓冲 `tx_buf` 改成一个小容量 TX 队列，使一次调用里产生的多帧不会互相覆盖——**前提是用户先批准原因码与契约的处理方式**（见 §3(a) 的「不动点」与 §8 待拍板项）。

### 3(b) `emit_frame` 的单缓冲改成 TX 队列

#### 容量依据（**必须按这个论证写，不许随手写大**）

先算清"一条事件最多并发几帧"：

1. **单次网关调用最多 1 帧**：`consume_and_emit`（`:66-113`）是 `if / else if` 链，`:70-110` 里只有第一个命中的分支会调 `emit_frame`；`handle_item_task` 的 NACK 分支（`:137-140`）**直接在 `:139` `return`**，后面不会再出帧。所以网关自身每次调用上界 = **1 帧**。
2. **App 层每次"喂一帧"最多重入网关 1 次**：`ec_app_handle_transition` 的流程是
   `feed_byte` 产 1 帧（`ec_app.c:281` 提前 flush）→ `:313-324` 再 `inject` 一次（`TASK_SAFETY_VALIDATED` 或 `ITEM_RESULT_RECORDED`）→ `:327` 尾部 flush。
   所以 **App 级"同一轮里待发帧"的上界 = 2**。
3. 今天这个"2"是靠 `ec_app.c:281` 的**提前 flush** 才没有丢帧，而不是靠缓冲深度。这正是 `ec_app.c:272-280` 那段注释说的「Placement is load-bearing」。
4. 改成队列之后上界不变，但**不再依赖 flush 的位置**——这才是队列表述的价值。

#### 硬性语义要求（改错就是回归）

1. **帧的字节内容一字不变**：队列只改"存在哪里"，不改 `ec_proto_encode` 的入参。`EC_PROTO_VERSION` / `EC_DEVICE_STM32` / `EC_DEVICE_PI` / `frame.task_id = (uint16_t)g->sm.round_id` / `frame.frame_seq = g->tx_seq` / `command` / `payload` 全部照旧（`ec_protocol_gateway.c:27-34`）。
2. **`frame_seq`（`tx_seq`）语义不变**：`++g->tx_seq` 仍然**只在真正新造一帧时**执行一次，且必须在 `ec_proto_encode` 之前（`:25`）。
3. **重放路径绝不递增 `tx_seq`**：`:93-101` 的 RESEND 现在直接 `memcpy` 进 `g->tx_buf`。改成队列后，它必须走一条**"把已知字节按原样入队、不碰 `tx_seq`"**的通道。这是 E-5 的冻结要求（`interface-contract.md:94`：「重复帧（同 `(task_id, frame_seq)`）→ **重发上次应答**（ACK/NACK 原样重放，**不递增发送方序号**）」）。**如果你把它接到会递增 `tx_seq` 的那个入队函数上，就是静默破坏 E-5 语义**——必须写一个专门的 `txq_push_raw()`。
