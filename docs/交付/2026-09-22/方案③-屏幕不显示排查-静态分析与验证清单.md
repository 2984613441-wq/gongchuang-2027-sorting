## 一、软件侧 vs 屏幕侧的分界

### 1.1 如何证明"链确实把帧写进了 /dev/fb0"

**证据链**：

1. **日志证据**（派工文档已提及）：
   ```
   两段显示已上屏: 1024x600 序号=N target_seq=N box_id=N
   ```
   → 说明 `TwoStageDisplay.show_recognized()` / `show_success()` 都执行到 `self._frame_output(frame)` 并返回成功

2. **代码路径**（`display_hdmi.py`）：
   - `:527` `_show()` → 调用 `self._frame_output(frame)` 
   - `:272-275` `FramebufferFrameOutput.__call__()` → 调用 `encode_frame()` 打包像素 → 打开 `/dev/fb0` 写入
   - **关键**：若打包失败（bpp 错误、尺寸超限）或写入失败（设备不存在、权限不足、ENOSPC），会抛异常并记录 ERROR
   - **用户报告**：日志有 `显示已上屏` → 说明 `write()` 没抛异常

3. **文件存在性**（待验证）：
   ```bash
   ls -l /dev/fb0
   ```
   → 应输出 `crw-rw---- 1 root video 29, 0 ...`（字符设备，主设备号 29）

4. **写入权限**（待验证）：
   ```bash
   groups pi
   ```
   → 应包含 `video` 组（`/dev/fb0` 的组权限是 `rw-`）

**分界判断**：
- ✅ **若上述全部通过** → 软件侧已成功写入 `/dev/fb0`，故障在「帧缓冲 → 屏幕」
- ❌ **若 `/dev/fb0` 不存在或无法写** → 软件侧未真正写入，需先修复 framebuffer 驱动

## 四、候选原因清单（按可能性排序）

### 4.1 被 `/dev/fb1` 占用（可能性：中）

**现象**：软件写入 `/dev/fb0` 成功，但屏幕实际渲染的是 `/dev/fb1` 的内容（空白或旧内容）。

**如何证伪**：
```bash
ls /dev/fb1
# 若不存在 → 排除此原因
fuser /dev/fb0 /dev/fb1
# 若两个都无进程占用 → 排除此原因
```

**修复**：
```bash
# 若 fb1 存在且有程序占用，停掉图形界面
sudo systemctl stop lightdm
# 或在 /boot/config.txt 里改成 max_framebuffers=1
```

---

### 4.2 bpp 打包错误（可能性：低）

**现象**：`bits_per_pixel` 实际不是 16，而是 24 或 32，导致打包后的字节数不匹配 → 屏幕花屏或黑屏。

**如何证伪**：
```bash
cat /sys/class/graphics/fb0/bits_per_pixel
# 若是 16 → 排除此原因（代码已按 16bpp 实测通过）
# 若是 24/32 → 代码支持，但需检查实际打包路径
```

**修复**：无需修复（代码 `:90` 已支持 16/24/32）

---

### 4.3 HDMI 未热插拔（可能性：中高）

**现象**：树莓派启动时屏幕未通电 / HDMI 线未插 → DRM 检测不到屏幕 → framebuffer 不更新到 HDMI 输出。

**如何证伪**：
```bash
cat /sys/class/drm/card0/card0-HDMI-A-1/status
# 若输出 connected → 排除此原因
# 若输出 disconnected → 确认此原因
```

**修复**：
- 短期：重插 HDMI 线，或重启树莓派（确保启动时屏幕已通电）
- 长期：`/boot/config.txt` 里已有 `hdmi_force_hotplug=1`（强制热插拔检测），应该无需改

---

### 4.4 字体缺失导致帧合成失败（可能性：极低）

**现象**：`/usr/share/fonts/truetype/wqy/wqy-zenhei.ttc` 不存在 → Pillow 抛 `IOError` → `_compose_recognized()` 失败 → 无帧输出。

**如何证伪**：
- 用户报告日志有 `显示已上屏` → 说明帧合成成功 → **已排除**

**修复**（若真缺失）：
```bash
sudo apt install fonts-wqy-zenhei
```

---

### 4.5 overscan 裁切（可能性：极低）

**现象**：`/boot/config.txt` 的 `disable_overscan=1` 未生效 → 屏幕边缘被裁切 → 两行文字在可见区之外。

**如何证伪**：
- `--bars` 自检若能看到三色条 → overscan 没问题
- 或直接读 `/boot/config.txt` 确认 `disable_overscan=1` 存在

**修复**：无需修复（配置已正确）

---

### 4.6 屏幕自身输入源选错（可能性：低）

**现象**：屏幕有多个输入源（HDMI1/HDMI2/VGA），当前选中的不是树莓派连接的那个。

**如何证伪**：
- 目视屏幕的 OSD 菜单（若有）→ 检查当前输入源
- 或用屏幕按键切换输入源，逐个试

**修复**：切换到正确的 HDMI 输入源

---

### 4.7 帧合成成功但未调用 `frame_output`（可能性：极低）

**现象**：`_compose_recognized()` 返回了帧，但 `_show()` 里的 `self._frame_output(frame)` 因为某种原因被跳过。

**如何证伪**：
- 代码审查 `display_hdmi.py:526-528`：
  ```python
  def _show(self, frame: "PIL.Image.Image") -> "PIL.Image.Image":
      self._frame_output(frame)
      return frame
  ```
  → 无任何条件分支，不可能跳过 → **已排除**

---

### 4.8 日志里的"显示已上屏"是假的（可能性：极低）

**现象**：日志记录点在 `frame_output()` 调用**之前**，而实际写入时抛了异常但被吞掉。

**如何证伪**：
- 需要读 `run_chain.py` 或调用 `TwoStageDisplay` 的地方，确认日志记录点在哪
- 若在 `show_recognized()` 返回**之后** → 说明 `frame_output` 确实执行成功 → **已排除**

**状态**：⏳ **待读 `deploy/run_chain.py` 确认日志记录点**

## 七、最坏情况与风险

### 7.1 最坏情况

**屏幕硬件故障**：
- DRM 检测到 `connected`，fb 写入成功，但屏幕就是不显示
- 用 `dd if=/dev/urandom of=/dev/fb0` 也看不到噪点
- → 可能是屏幕背光/驱动板故障，需要换屏

**成本**：1024×600 HDMI 屏 ≈ ¥150-250（淘宝价）

---

### 7.2 风险

**改 `/boot/config.txt` 后无法启动**：
- 若修改 `hdmi_cvt` / `dtoverlay` 等关键参数错误 → 树莓派可能无法启动图形界面
- **缓解**：改之前先备份 `/boot/config.txt`
  ```bash
  sudo cp /boot/config.txt /boot/config.txt.bak
  ```
- **回滚**：SD 卡插到电脑，挂载 `/boot` 分区，改回去

**停掉 `lightdm` 后无法恢复**：
- `sudo systemctl stop lightdm` 会关闭图形界面 → SSH 会话断开
- **缓解**：在 `tmux` / `screen` 里执行命令，或用 `nohup` 防止断线
- **回滚**：`sudo systemctl start lightdm` 恢复图形界面
