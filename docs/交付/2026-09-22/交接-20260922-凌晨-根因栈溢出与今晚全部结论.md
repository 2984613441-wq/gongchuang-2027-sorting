## 1. 🔴 根因：**栈溢出**（今晚全部故障由它一条串起来）

### 1.1 硬数字（来自当前 hex 的 Keil 链接图）

```
栈大小      Stack_Size = 0x400 = 1024 字节      startup_stm32f407xx.s:32
最深调用链  Max Depth = 1208 字节               MDK-ARM/diankongv1.0/diankongv1.htm
            ec_app_poll_motion        1184 字节 ← **运动轮询那条链**
            ec_app_poll_startup_sequence 1176
            ec_app_poll_start_button     1168
⇒ 最深链需要 1208 B，栈只有 1024 B ⇒ **溢出 184 B（18%）**
```

### 1.2 谁把栈吃掉了

`ec_axis_pick_place_t program;` 是**局部变量**，而且有两处：
```
App/Src/ec_app.c:165   ec_axis_pick_place_t program;   ← 真正下发运动计划用的
App/Src/ec_app.c:257   ec_axis_pick_place_t program;   ← 工作区校验用的
sizeof(ec_axis_step_t) = 32 B  ⇒  13 槽 × 32 = **416 B / 个**
```
**两个 416 B 的大家伙 + HAL 的深调用链 ⇒ 1024 B 的栈根本不够。**

### 1.3 机制链条：为什么表现为"放完料还往前走 / 没夹到 / 落点不对"

```
栈溢出 → 踩坏相邻 RAM → hard fault → **CPU 停住**
                                  ↓
        但 TIM4/TIM8 的 PWM 是【硬件】在跑，CPU 停了它不停
                                  ↓
        **步进脉冲继续发 ⇒ 轴沿"最后一次设定的方向"一直走**
        （最后一次设定 = PICK→PLACE 的 +Y）
                                  ↓
        ① 放完料之后它还在继续朝 +Y 往前走          ← 用户今晚报的现象
        ② 位置全错 ⇒ 后续"落点也不是固定落点"        ← 用户今晚报的现象
        ③ 永远不发 MOTION_DONE ⇒ 链无限重传          ← 日志实证
        ④ 板子 PING 完全无应答（不是复位，是挂死）    ← 实测
```
**⇒ 用户今晚报的三个现象，全部由这一个根因解释，不需要第二个 bug。**

### 1.4 与我的改动的关系（**这里我要把话说准，别甩锅也别背锅**）

* **溢出在我改之前就存在 —— 这点是确定的**：`ec_app_poll_motion` 那条 **1184 B** 的链，
  链接图给的 Call Chain 是 `ec_app_inject_simple → ec_app_handle_transition`，
  **未必经过 `ec_app_start_motion`**（也就是 `program` 局部变量所在的那个函数）。
  既然峰值链与 `program` 无关，那么 **+64 B 不是我造成的，溢出本来就在**。
* **我的 +64 B 会抬高"含 `program` 的那些链"**（`ec_axis_pick_place_t` 11→13 槽 × 32 B = +64 B/个，两处），
  但**这些链是否就是峰值链，我没有核**（要看 Keil 链接图里 `ec_app_start_motion` 自己的 Max Depth）。
  ⇒ **待核项**：重编后请把 `ec_app_start_motion` / `ec_app_validate` 的 Max Depth 也列出来对比。
* 不管归属如何，**修法是同一条**（§1.5），而且**必须先修**——它是今晚 20:06/20:20 两次失败的机制来源。

### 1.5 修法（两条，都很小；建议**两条都做**）

**① 把两个 `program` 局部改成 `static`（首选，直击要害）**
```c
/* ec_app.c:165 与 :257 各一处 */
static ec_axis_pick_place_t program;      /* 不占栈 —— 单线程 MCU，无重入 */
```
效果：单条链直接减 416 B ⇒ `ec_app_poll_motion` 1184 → ~768 B，**回到 1024 以内**。
代价：+416 B ZI（当前 ZI=4260，SRAM 128 KB，可忽略）。

**② 顺手把栈加大：`Stack_Size 0x400 → 0x800`**（`startup_stm32f407xx.s:32`，一处）
代价：+1 KB ZI，同样可忽略。这条是**兜底**，防别的链（1208 B 那条）以后冒出来。

**③ 复核手段**：改完重编，**看 Keil 链接图里所有 Max Depth 是否都 < Stack_Size**。
判据要写死：**`max(Max Depth) < Stack_Size`，且留 ≥25% 余量。**
（这一条应该进项目纪律：**任何新增局部大数组/结构体的改动，必须先看链接图的 Max Depth**。）

**⚠️ 别忘了**：改完要重编 + **重烧**，并同步 `tests/` 里的断言（容量/步数相关的已在 §4 列）。

### 🔴 §4.6 必须读懂的一条（我踩过的坑）

```
标定端（精确法 3 点）算的是：装置真实坐标 = 滑台坐标 − [ToolOffset]，当时用 TO = (-108.5, -20.5)
链的运行时口径：              滑台 = 装置 + [ToolOffset]
⇒ **改 TO 就等于把标定映射整体推偏**（现值 -15.5 ⇒ 每个取料点比标定真值偏 +5mm Y）
⇒ 我一度按"+1cm 向外"把 TO 改成 -10.5，取料点偏 +10mm ⇒ **夹爪停在件旁边合嘴、夹空**
```
**结论：`[ToolOffset]` 不是"偏移旋钮"，它是标定闭环的一半。**
若要"夹爪相对件向外偏一点"，应当**另加一个只为夹取用的偏置**（新字段/新节），**不要动 TO**。
现值 **-15.5 = 比标定真值偏 +5mm（用户要的 0.5cm）**，接手人必须知道这个偏置是"人为的"，不是标定结果。
