## 一、要解决的问题（用户现场原话 + 我们的机制分析）

**用户报告**：
- 「先夹 Y 那排，它就很容易夹到其他的东西」（**爪子刮到/碰到相邻件**）
- 「没有 Z 轴，从而导致它会刮到」
- 「两块本来就靠得很近，那也会出问题」
- 用户**要的是"动态"**：每一帧按实际摆位决定先夹哪个/怎么绕，"只要不夹到对方的就行"；
  也接受"先把挡路的那块移开、再回头夹目标件"——但**托盘/基础不能动**（只能靠 X/Y 动作）。

**我方机制分析（待你证实或推翻）**：
```
空爪去取料的走法（固件）：`ec_motion_plan.c:53-95` `append_ordered_xy()`
  · 三条腿全部"先 Y 后 X"（EC_MOTION_XY_ORDER_X_FIRST = 0；2026-09-21 用户现场裁决）
  · HOME→PICK：leg1 在 x = PARK.x = −95 的列上**先竖着**走到目标所在的 y；
                leg2 **在那一行的 y 上从 x=−95 横着扫到目标的 x**   ← 扫掠发生在这条腿
⇒ 扫掠的余量只取决于：目标件的 y 与【沿途其他件】的 y 之差
⇒ 排序"行内按 x 升序（先最靠 −X）"本来是对的：从 −95 扫过去时同排更靠 −X 的已被取走
⇒ **真正会刮的场合 = 行容差分桶把"物理上差 1~2cm"的两件算成同一排**，
   于是我在 A 的 y 上横扫时，B 离我只有 1~2cm ⇒ 爪片半宽（≈12.5mm）就贴上 ✗
   （桶越大 ⇒ 这种"并排"越多 ⇒ 越容易刮）
```

## 三、我方提出的方案（**请审它，并提出新方案**）

```
【方案 A（我倾向，纯链侧、不动协议）＝"扫掠走廊"动态避让】
每帧拿到全部件的位置后，逐件算走廊：
  取件 P 时，走廊 = "在 y = P.y 上从 x = −95 扫到 P.x"
  对每个尚未取走的 Q ≠ P：
     若 |Q.y − P.y| < 爪片半宽 + 安全余量   且   Q.x ∈ (−95, P.x]   ⇒ 判定"会刮到"
  排序不再是死规则，而是按当前帧挑一条不刮的路：
     ① 若挡路的 Q 自身走廊干净 ⇒ **先取 Q**（等价于"先把对方拿走"）
     ② 否则跳过 P，取下一件走廊干净的
     ③ 若所有件都被挡 ⇒ 取"重叠最小"的那件并**打 WARNING 日志**（不静默）
  参数：爪片半宽用 [Gripper] envelope_mm = 25.0（【待实测】）+ 一个安全余量（可配）
  每取一件本来就会重读一帧（现状满足"回到 P 再读视觉"）
【方案 B（用户提过的"先推一下再夹"）】
  用爪子把挡路件沿 X/Y 推开一小段 ⇒ 回头夹目标件。
  ⚠️ 我方判断的硬约束：**协议里没有"推/挪"这个动作**（只有取料点+落点）
     ⇒ 要落地必须新增命令或新增一条腿 ⇒ 属【改通信协议 = L4】，需用户批准 + 重烧固件
  ⚠️ 风险：被推走那块**新位置未知**（可能推出相机画面/顶到壁/叠到别的件上）⇒ 可能"永久丢失"
```
