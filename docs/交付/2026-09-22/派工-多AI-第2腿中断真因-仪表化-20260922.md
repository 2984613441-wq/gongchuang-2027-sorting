### 0.2 要查的问题（一句话）

### 0.3 现象与已确认的机制

**用户现场描述**：第 1 件正常 → 第 2 件**「卡一下」** → 之后机器**在落点区域去夹件**（夹不到）→ 继续往它"以为该去"的落点走 → **一直在循环**；机械上听不出问题。

**已确认的机制链（本节点逐个核对过代码，可复核）**：
```
① app 在轴还在走时离开 EXECUTING
      ↓
② ec_app.c:465-489（fix A）发现"轴被孤立" ⇒ ec_axis_driver_stop()
      ⇒ stop_all() + state=IDLE + step_index=0   ← 用户看到的「卡一下」
      ※ 该段注释自己写着：2026-09-21 现场实测复现「多发一帧 ITEM_TASK 触发 HOMING ⇒
        卡在 PROGRESS=2/MOVES=1/STATE=1，只能靠断电复位恢复」
      ↓
③ 回程腿 [10][11]（PLACE→HOME）根本没执行 ⇒ 机器停在半路
      ↓
④ 永无 MOTION_DONE ⇒ Pi 每 5s 重传（task_timeout_s=5.0 < 运动 12~15s，一轮 23 次）
      ↓
⑤ 重传的 ITEM_TASK 在 FAULT_LOCK 下触发【自愈】(ec_state_machine.c:95-104)：
   ec_dedup_clear_for_verified_new_round → 重学轮次 → POWER_ON → BEGIN_POST → POST → HOMING
      ↓
⑥ 自愈走完：PREPARE_BARRIER → WAIT_TASK 且 actions=EC_ACTION_EMIT_BARRIER_READY
   (ec_state_machine.c:145-149) ⇒ 【发出一帧 BARRIER_READY】
   ※ 旧交接原话：「BARRIER_READY 是"复现钟"不是"故障钟"」
      ↓
⑦ 下一件从"板子以为在 HOME"的起点按【增量】走（ec_motion_plan.c:13-17 下发的是差值，
   且 ec_motion_plan.h:181-184 自认"假定程序开始时滑台就在 HOME"）
   ⇒ 实际机器在半路 ⇒ 整体平移 ⇒ 「跑到落点区去夹 / 一直在转」
```

### 0.4 🔴 为什么现有仪表下**查不出真因**（这是本派工的存在理由）

| 仪表 | 为什么无效 |
|---|---|
| `AXIS ... LAST_RESULT/LAST_STEP/LAST_KIND/LAST_ELAPSED_MS` | 这些是**故障锁存**，只在 `ec_axis_driver` 走 `fault()` 时写入；而本路径走的是 `ec_axis_driver_stop()`（**stop 不是 fault**）⇒ **永远写入不进去**，读到 0 不是"没有故障"而是"故障没被记录" |
| `STATUS ... APP_STATE` | 只给"现在在哪个状态"，不给"为什么离开上一个状态" |
| `fault_reason`（`ec_state_machine.c` 里确实有写） | **App/ 全目录 grep `fault_reason\|EC_FAULT_` = 0 命中 ⇒ 写了从来没人读**；`ec_diag.c` 的可用命令清单（HELP/PING/LIGHT/STATUS/AXIS/INPUTS/STEP/MOVE/STOP ALL/MOTION ARM/SERVO/GROUP/BARRIER）**没有任何一条能读它** |
| `ec_axis_driver_diag()`（`ec_axis_driver.h:283-296`） | 有 11 个字段的诊断快照，但**它同样只在 `fault()` 里被填** |

**⇒ 结论：不先加仪表，"真因"在原理上不可读。** 派工里可以要求"设计仪表 + 在仪表到位前用现有可观测做排除法"。
