### 协议（两端已核对一致，不要再怀疑）
- 外层帧：`A5 5A 01 sender receiver task_id(2 BE) frame_seq(2 BE) command data_len(2 BE) payload CRC16/MODBUS(2 BE)`；`HEADER_LEN=12`
- device id：`MAIXCAM=1, PI=2, STM32=3`
- `ITEM_TASK=0x21`，**12 字节**：`[0]target_seq [1]class_id [2]image_id(==class_id) [3..4]x_mm10(int16 BE 落点) [5..6]y_mm10 [7]grip_angle(必须0xFF) [8..9]pick_x_mm10 [10..11]pick_y_mm10`
- `ACK=0x05 / NACK=0x06`，载荷 `reason + target_seq`；`ACK_REASON_ACCEPTED=0x00`
- NACK：`0x10 STALE_OR_ORDER`、`0x12 SINGLE_TASK_ONLY`、`0x14 WRONG_ROUND`、`0x15 TASK_REJECTED`
- `BARRIER_READY=0x20`、`MOTION_DONE=0x22`、`ITEM_RESULT=0x23`、`DISPLAY_ACK=0x25`

### 环境坑（踩过，别再踩）
1. PowerShell 嵌套引号过 ssh 会被搞坏 → **本地写 `.sh`/`.py` → LF 归一化 → `scp` → `ssh "bash /home/pi/x.sh"`**。
   归一化：`[IO.File]::WriteAllText($src, ([IO.File]::ReadAllText($src) -replace "`r`n","`n"), (New-Object System.Text.UTF8Encoding($false)))`
2. `pkill -f 'deploy/run_chain.py'` 写在一条 ssh 命令里会杀掉包裹它的 shell 自己 → 用转义形式 `pkill -f 'deploy/run_chain\.py'`。

4. 本地 `.py`/`.ini` 被 LF 归一化重写后文件观测缓存失效，后续 `edit` 报 "file changed since it was read" → 先重读。
5. `pi_ask_stm32.py` 会过滤掉 `STATUS` 行；要原始输出用 `pi_gate_probe.py status` 或 `pi_serial_diag.py`。
6. 读串口状态时**不要** `reset_input_buffer()`（会截断在途的约 350 字节 STATUS 行），也不要取第一条 STATUS（旧值）。被动读板子 1Hz 自由运行的 STATUS 最可靠。

## 点 4 · 串口通信健壮性

**任务**：让「树莓派 ↔ STM32」这条串口链在真实操作下不会被轻易搞死，并且出问题时有可观测证据。

**已坐实的问题**
1. **无独占**：链路在跑时，任何第二个进程打开 `/dev/serial0`，链路会以
   `serial.serialutil.SerialException: device reports readiness to read but returned no data (device disconnected or multiple access on port?)`
   崩溃退出（`serial_link_serial.py:84`）。**实机发生两次**，是我用探针读板子造成的（我自己的操作失误，不是代码审出来的）。
   → 评估：`serial.Serial(exclusive=True)` 是否可用（pyserial 3.5b0 / Linux tty `TIOCEXCL`）；加了之后第二个进程会怎样（期望：明确报「端口被占用」而不是把链路搞死）。给出改动与验证。
2. **同一 USART2 上混流**：板子 1Hz ASCII STATUS（约 340 字节，阻塞发送约 30ms）与二进制协议帧共用一根线。`PySerialLink._extract_frame()`（`serial_link_serial.py:100-130`）会把非帧字节**逐字节丢弃**，所以链路看不到任何 ASCII 诊断信息——出问题时**无人可看**。
   → 评估：是否有必要让链路把「被丢弃的 ASCII 行」记进日志（原始字节或摘要），代价与风险是什么。
3. **异常处理**：`run_chain.py` 的 `receive()` 抛异常会直接冒到 `main()` 的兜底 `except`（`run_chain.py:1251` 附近）→ 整条链退出。评估：是否应在 `PySerialLink` 或链路层做「可恢复异常 → 重开端口 → 继续」的处理，以及 fail-closed 的边界在哪（**绝不能因为重连而丢掉安全语义**）。
4. **重传策略**：链路 5 秒无应答就重传同一帧（`run_chain.py` 的超时分支），而板子端 `dedup` 会判 `DUPLICATE` 并重放缓存应答。核对这条闭环在**各种板子状态下**（EXECUTING / FAULT_LOCK / WAIT_TASK）分别会发生什么，是否存在「重传反而推进了状态」的副作用（**已实测存在**：建轮次那一发被吞后，重传会被当成全新首件而 ACK → 开始运动）。
5. **可观测性**：现在链路日志缺什么关键信息？（已补：落点/抓取点 mm 坐标。）还能补什么便宜又有用的（例如每帧入站的命令名与 task_id/frame_seq）。

**边界（不许做）**
- 不做实机运动。本点可用 `--fake-link` 主机模式 + 树莓派上的被动监听验证，**不要启动整链做运动测试**。
- 不改协议帧格式。
- 不许削弱 fail-closed：任何「自动恢复」都必须是无害的（重开端口可以，跳过校验不行）。

**验收证据**：复现「第二进程打开端口」的原命令与原始报错；改动后同一实验的原始输出；主机侧单测（`电控/tests/rpi/` 有 `test_serial_link_serial.py` 可参照扩展）实际运行输出。
