## 三、已完成的（有实机证据，不用重做）

1. **🔴 接收失聪缺陷已修复并实机验证通过。**
   旧固件 `ec_board_uart_rx_callback` 在 USART2 RX 中断里跑完整个协议流水线（含最长约 20ms 的阻塞 `HAL_UART_Transmit`），`HAL_UART_Receive_IT` 放在最后一句 → 必然 ORE → HAL 把 `RxState` 置 READY、关掉 RXNE 中断、调**从未定义的弱符号 `HAL_UART_ErrorCallback`** → 接收永久死亡。
   修法（已落地）：ISR 只做环形缓冲暂存并立刻重新 arm；处理搬到主循环 `ec_app.c` 的排空循环；新增 `HAL_UART_ErrorCallback` 转发。
   **实机验证**：700 条 PING，100% 响应，零溢出，三次存活检查全过。

2. **板子确实在正常收发与处理 ITEM_TASK，格式完全正确。** 我用探针逐帧解出来过：
   - 上电后第 1 个 `ITEM_TASK` → 建轮次，状态 `FAULT_LOCK → HOMING → WAIT_TASK`
   - `task_id` 匹配时回 `ACK(ACCEPTED)`
   - `task_id` 不匹配时回 `NACK(WRONG_ROUND=0x14)`

3. **已排除（逐行核对过，全部正确，别再查了）**：线格式、device id、网关组帧器 `ec_protocol_gateway.c:397-447`、帧解码器 `ec_protocol.c:62-94`、`POST/HOMING/PREPARE_BARRIER` 启动序列、`ec_sm_consume` 的 NULL 守卫、`ec_gateway_update_safety_state`、`consume_and_emit` 的 ACK/NACK 分发。

4. **输入位含义（别再误判）**：`ec_inputs.h` 里 `X_HOME=1<<0, X_END=1<<1, Y_HOME=1<<2, Y_END=1<<3, Z_UP=1<<4, Z_DOWN=1<<5, ESTOP_FB=1<<6, START=1<<7, MANUAL_RESET=1<<8, POWER_PERMISSION=1<<9`。实测 `ACTIVE=0x0008` = **`Y_END`（限位开关，不是安全输入）**；`ESTOP_FB` 与 `MANUAL_RESET` 都没触发，所以 `danger_area_clear=true`、`estop_released=true`。

**链路的入站读取认不出板子发来的二进制帧。**（❌ 已推翻，见上）

证据对比：

- **链路日志**（`/tmp/chain.log`，04:14 那次）：`ITEM_TASK sent: target_seq=3 class_id=6 image_id=6` 之后，**7 次全部** `WARNING ITEM_TASK 超时 5.0s 无应答，重传 frame_seq=1`，日志里**一条收到的帧都没有**。
- **同一时间同一端口，我用探针发同样的帧**：每次都收到应答，`BARRIER_READY` / `ACK` / `NACK` 全都正确解出来。

**⇒ 板子在回，链路没认出来。**

### 附加已坐实的真缺陷（缺陷 A，但先别急着改）

`consume_and_emit`（`电控/stm32_logic/src/ec_protocol_gateway.c:70-110`）对 `EC_ACTION_BEGIN_POST` **没有 ACK 分支**。而 `EC_ACTION_BEGIN_POST` 就是"ITME_TASK 建立轮次"这个动作（`ec_state_machine.c:84`）。

**实机原始帧证据：**
```
上电后第1发 ITEM_TASK task_id=1 frame_seq=1  →  [帧] BARRIER_READY  task_id=1     ← 没有 ACK
                                                  APP_STATE: FAULT_LOCK→HOMING→WAIT_TASK
第2发 完全相同的字节                          →  [帧] ACK ACCEPTED target_seq=3
                                                  APP_STATE: WAIT_TASK→EXECUTING
```

所以"建立轮次"那一下不被应答，Pi 侧会白等 5 秒并触发无意义重传。

**注意**：我上一轮曾推断"重传会被 dedup 判重 → RESEND → 缓存空 → 永久静默"，**这个机制被实机实验推翻了**（重传拿到了 ACK）。真实原因是建轮次分支在 `:79` 清了 dedup、在 `:85` 直接 `return`，**从未把该 identity 记进 dedup**，所以重传被判为全新首次接受而正常 ACK。**不要再用"死锁"那套解释。**

## 七、环境坑（我踩过，别再踩）

1. **PowerShell 嵌套引号过 ssh 会被搞坏** → 一律**本地写 `.sh`/`.py` → LF 归一化 → `scp` → `ssh "bash /home/pi/x.sh"`**。
   归一化写法：`[IO.File]::WriteAllText($src, ([IO.File]::ReadAllText($src) -replace "`r`n","`n"), (New-Object System.Text.UTF8Encoding($false)))`
2. **`pkill -f 'deploy/run_chain.py'` 写在一个 ssh 命令里会杀掉包裹它的 shell 自己** → 用转义形式 `pkill -f 'deploy/run_chain\.py'`。查进程用 `pgrep -af 'run_chai[n]'`。
3. **本地 `.py`/`.ini` 被上面那个 LF 归一化重写后，文件观测缓存失效**，后续 `edit` 会报 "file changed since it was read" → **换个新文件名**，或先重读。
4. `pi_ask_stm32.py` **会过滤掉 `STATUS` 行**，读不到 `APP_STATE`；要原始输出就用 `pi_serial_diag.py`。
5. 读串口状态时：**不要**在读取前 `reset_input_buffer()`（会截断在途的约 350 字节 STATUS 行，残半行会被误读成当前状态）；也**不要**取第一条 STATUS（那是旧值）。**被动读板子 1Hz 自由运行的 STATUS** 最可靠。
6. 板子 `STATUS` 行约 350 字节、`ec_diag_port_write` 是**阻塞发送**，约 30ms。

## 十一、板子现在的状态

`APP_STATE=FAULT_LOCK`、`ARMED=0`、`MODE=0`、`STEP_*` 全零，已发 `STOP ALL`，**无运动残留，安全**。`INPUTS RAW=03F7 ACTIVE=0008`。

**这个上电周期里 `round_id=1` 已被锁定**（`ec_state_machine.c:78` 的 `!=` 严格门槛），所以只有 `task_id=1` 会被接受。**要换别的 task_id，必须先按板上的 RESET 键**（RAM 归零 → `round_id=0`）。

⚠️ 注意：按 RESET 之前，用户"重新上电"那次板子实际**没跑起来**（8 秒 0 字节），按了 RESET 才恢复。所以**每次让用户上电后，先跑 `pi_link_check.sh` 确认板子在发 1Hz STATUS，再往下做**。
