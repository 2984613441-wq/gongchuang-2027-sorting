- 日期：2026-09-18
- 接手依据：`docs/交付/2026-09-18/接续提示词-链路入站读帧.md`
- 结论一句话：**该提示词 §四 的「唯一卡点」（Pi 侧认不出 STM32 二进制应答帧）已被实机证据推翻；真因在 STM32 状态机，且伴随一个「零诊断静默」缺陷。**

## 二、真因（两条，都有行号）

### 缺陷 1（本次卡点的真因）：`FAULT_LOCK` + 轮次号已学到 → **零应答静默**

板子上电即 `EC_STATE_FAULT_LOCK`、`round_id = 0`（`ec_state_machine.c:44-52`）。

第一发 `ITEM_TASK` 被用来「学轮次」，分支条件是
`event->round_id != machine->round_id`：

`电控/stm32_logic/src/ec_state_machine.c:76-86`

```c
if ((event->type == EC_EVENT_ITEM_TASK_ACCEPTED) &&
    event->danger_area_clear && event->estop_released &&
    (event->round_id != machine->round_id)) {
    ...
    machine->round_id = event->round_id;
    machine->state = EC_STATE_POWER_ON;
    machine->actions = EC_ACTION_BEGIN_POST;
    return snapshot(machine);
}
```

一旦**轮次号已经学到**（`round_id=1`），之后又发生任何一次故障把状态机打回
`FAULT_LOCK`（例如 `EC_EVENT_DEADLINE_EXPIRED` → `lock_machine()`，
`ec_app.c:552-556`，它**只改 state、不动 round_id**），那么：

- `round_id(1) != machine->round_id(1)` 为假 → :76 分支不成立；
- :88 的 `MANUAL_NEW_ROUND_CONFIRMED` 分支也不成立；
- 直接落到 `:98 return snapshot(machine);` —— **不改 actions、不设 tx_len**。

而 `ec_protocol_gateway.c:394` 在每收一个字节时就把 `g->tx_len = 0U`，
`consume_and_emit`（`ec_protocol_gateway.c:66-110`）里 `EC_ACTION_BEGIN_POST`
等动作**没有任何分支**，于是 tx_len 保持 0 → **一个字节都不发**。

⇒ 现象就是：板子活着（1 Hz ASCII STATUS 照发）、帧字节完全合法、**但对每一发
重传统统装死**，且链路日志里连一条 `FRAME_REJECTED` 都没有 —— 因为 `feed_frame`
压根没被调用过（`receive()` 返回 None）。

### 缺陷 2（原提示词说的「缺陷 A」，成立但只是次要代价）

建轮次那一发**不被应答**：`ec_protocol_gateway.c:66-110` 没有 `BEGIN_POST` 分支；
同时 `ec_state_machine.c:79` 清了 dedup、`:85` 直接 return，那个 identity
**从未被记进 dedup**，所以 5 秒后的重传会被当成「全新首件」而正常 ACK。
代价 = 每件白等 5 秒超时（04:13 实机复现：第 1 发只回 BARRIER_READY，
第 2 发同样字节回 ACK_ACCEPTED → 开始运动）。

## 三、实测复现（板子在环，运动零风险）

工具：`工具/pi_gate_probe.py`（收发都用链路**生产类**
`electrical_control.rpi.serial_link_serial.PySerialLink`，不是另写的解码器）。

自检（离线）：`selftest OK: [帧] ITEM_TASK task_id=1 frame_seq=42 payload=07 06 06 00 32 00 32 FF 00 00 FE 3E`

被动（只读 3 秒）：`收到 1014 字节，其中 CRC 合法二进制帧 0 条`（板子只自发 ASCII STATUS）

单发 `task_id=1`（与已锁轮次相同）：

```
[STATUS] APP_STATE=FAULT_LOCK SAFE_LOCK=1 ARMED=0 MODE=0
发 1 条 ITEM_TASK task_id=1 frame_seq=9 (26 B): a5 5a 01 02 03 00 01 00 09 21 00 0c 09 06 06 00 00 00 00 ff 00 00 00 00 2e 8a
PySerialLink 解出 0 条应答
  （板子在 4.0s 内零应答）
```

单发 `task_id=2`（与已锁轮次不同）：

```
发 1 条 ITEM_TASK task_id=2 frame_seq=9 (26 B): a5 5a 01 02 03 00 02 00 09 21 00 0c 09 06 06 00 00 00 00 ff 00 00 00 00 6a 7a
  <- [帧] BARRIER_READY  task_id=2 frame_seq=3 payload=-
PySerialLink 解出 1 条应答
[STATUS] APP_STATE=WAIT_TASK
```

**同一时刻、同一个 `PySerialLink`：轮次号相同的帧 → 零应答；轮次号不同的帧 →
BARRIER_READY 且被正确解出。** 机理与现象完全对上。

> 单发安全性的依据：`FAULT_LOCK` 下收到 ITEM_TASK 只会走 `BEGIN_POST`，而
> `ec_startup_sequence.c:84-94`（方案 A：上电位置即原点，寻零不动轴）与
> `:96-106`（挡板已取消，立即放行）**都不产生任何运动**；必须被 ACK 之后
> 才 `VALIDATE_TASK → EXECUTING → START_MOTION`。故本次只发一条，未触发运动。

## 四、本轮已落地的改动（Pi 侧，仅一处）

`电控/deploy/run_chain.py`：
- 新增 `_should_resend_on_barrier_ready()`（:902-925）；
- `BARRIER_READY` 分支（:1227 起）：若确有任务在飞（`WAIT_MOTION_DONE` +
  有 `last_task_context`），**立刻原样重发**该帧，而不是干等 5 秒超时。

理由：既然建轮次那一发必然被启动序列吞掉且零应答，那么 `BARRIER_READY` 就是
「板子刚建完轮次、可以收任务了」的信号，收到即重发能把每件白等的 5 秒消掉。
板子每完成一件也会再报一次 `BARRIER_READY`（`ec_state_machine.c:203-209`），
那时 state 已不是 `WAIT_MOTION_DONE`，不会误触发。

验证：
- `电控/tests/rpi/test_barrier_ready_resend.py`（新增，3 项，覆盖判据 + 「重发确为原样字节且不推进 tx_seq」）；
- 回归：`tests.rpi.*` 6 个模块共 **56 项全过**；
- 已同步到树莓派（md5 `6ef3fd66…` 与本地一致，Pi 上 `py_compile` 通过），
  旧版备份在 `/home/pi/电控/deploy/run_chain.py.bak-before-barrier-fix`。

**未改任何固件、未烧录、未触发运动。**

## 五、尚未修（要用户裁决 / 需要实机）

1. **缺陷 1（零应答静默）**：修它要动状态机的「安全锁逃逸条件」，属安全语义变更，
   需用户裁决走哪条：
   - (a) 保持锁定，但**至少回一帧 NACK(TASK_REJECTED)**，让 Pi 立刻知道而不是干等；
   - (b) 允许「同轮次号」也重新学轮次并重跑 POST（自愈，但会在每次重传时重跑启动序列）。
   ⚠️ 注意：若照原提示词 §五.3 的写法给 `BEGIN_POST` 补 `ACK(ACCEPTED)`，
   **会把链路锁死**——那会让 Pi 以为任务已被受理而进 `WAIT_MOTION_DONE`，
   但板子此时只是建完轮次、根本没执行该件，MOTION_DONE 永不到来。
   正确做法要么是 (b)，要么是 Pi 侧收到 `BARRIER_READY` 即重发（本轮已做）。
2. **板子当前状态**：`WAIT_TASK`、`round_id=2`（本次单发测试把它从 1 改成 2）。
   跑链路要 `--round-task-id 2`，或按板上 RESET 键回到 `round_id=0` 再用 1。
3. **首次运动测试尚未成功**，故 `电控/deploy/sorting_config.ini` 的
   `[DropPoints]` **仍是临时的 `5.0, 5.0`，尚未恢复 `90.0, 92.0`** —— 别忘了。
4. 原提示词 §九 的各项待办（Y 方向符号、`ec_step_test.c` 提前判完成、
   `[ObjectHeights]` 全 0、九点标定）本轮未动。
