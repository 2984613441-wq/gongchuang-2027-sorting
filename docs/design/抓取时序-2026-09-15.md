# 抓取时序设计 — 2026-09-15 复核

> 本文解决一个**实机必然抓空**的问题：固件把抓取点写死了，而赛题要求抓取点随机。
> 状态：**方案待用户确认**。确认前不要改代码。

## 1. 问题：抓取点与落料点的语义是反的

### 固件现状（实测）

`App/Src/ec_motion_plan.c:65-91` 编出来的 7 步：

| 步 | 动作 | 坐标 |
|---|---|---|
| 0 | `MOVE_XY HOME → PICK` | HOME 固定；**PICK 固定** |
| 1 | Z 下降（张开） | 在 PICK |
| 2 | Z 上升（闭合 = 夹住） | 在 PICK |
| 3 | `MOVE_XY PICK → PLACE` | **PLACE = 传入的 (x, y)** |
| 4 | Z 下降（张开 = 放料） | 在 PLACE |
| 5 | Z 上升（闭合 = 复位） | 在 PLACE |
| 6 | `MOVE_XY PLACE → HOME` | 回原点 |

常量（`App/Inc/ec_motion_plan.h`）：

```c
#define EC_MOTION_PICK_X_MM10 0        /* 抓取点写死 = 装置中心 */
#define EC_MOTION_PICK_Y_MM10 0
#define EC_MOTION_HOME_X_MM10 (-800)   /* -80.0mm，角落 */
#define EC_MOTION_HOME_Y_MM10 (-800)
```

传参（`App/Src/ec_app.c:150-162`）：

```c
/* Build the pick-place program from the current item's **drop coordinate** ... */
ec_gateway_item_target(&gateway, &x_mm10, &y_mm10);
ec_motion_plan_build(&program, x_mm10, y_mm10);
```

### 赛题要求

> 货物放置时的**方向和位置随机**，参赛队员**不能自行触碰**放入托盘的货物。
> 分拣时，必须将形状相同且颜色相同的货物分拣到同一个储物盒内。

### 结论

| | 固件现状 | 赛题要求 |
|---|---|---|
| **抓取点** | ❌ **固定 = (0,0)** | ✅ **随机**（视觉检测，每件不同） |
| **落料点** | ✅ 变动（ITEM_TASK 的 x/y） | ✅ **固定**（六个盒之一） |

**照现状跑**：机构跑到装置中心夹一下（那里通常没东西）→ 抓空 → 却按成功计数。
**结果是分拣数量全错。**

## 2. 正确时序（用户 2026-09-15 确认）

**前提**：
- **相机固定在装置中心**（不随 XY 移动）
- XY 靠**步数计数**定位
- 抓取点由**视觉给出**（每件不同）；落料点由 **box_id 查六盒表**得出（固定）
- **每件之间回停放位再重新拍照**（用户明确要求保留，不做"边走边看"的优化）

### 最终序列（9 步）

```
 ①  XY → HOME (角落 -80.0, -80.0)     让开视野（夹爪不在画面中心）
 ②  【视觉确认】请求并等待**一张新图** → 得到本件的
        (x_i, y_i)  = 物品机械坐标   ← 每件都不同
        box_id      = 该去的盒子      ← 由 (颜色,形状) 查对应表
 ③  XY → (x_i, y_i)                   抓取点（视觉给的）
 ④  Z → 下降（张开）
 ⑤  Z → 上升（闭合 = 夹住）
 ⑥  XY → (x_b, y_b)                   落料点（六盒表查出来的）
 ⑦  Z → 下降（张开 = 放料）
 ⑧  Z → 上升（闭合 = 复位）
 ⑨  XY → HOME                          回停放位，为下一件让开视野
     ↺ 回到 ①
```

> **① 与 ⑨ 是同一个动作**，所以是 9 步而不是 10 步 —— 循环自然闭合。

### 🔴 2026-09-15 修正：**删掉了"XY → 原点 (0,0)"这一步**

**原因（用户确认）**：

> "夹爪停在 (0,0) 时会不会正好挡住相机视野中心？**会挡着，这个是肯定的**。"

相机**固定在装置中心**，而 `(0,0)` 就是相机正下方 ——
**夹爪停到 (0,0) 会正好把要拍的地方挡住**，反而拍不了。

**所以停放位只回 HOME（角落 -80,-80），不去 (0,0)。**

> ⚠️ 这同时意味着：`EC_MOTION_PICK_X/Y_MM10 = 0` 那个"抓取点 = 装置中心"
> 的旧写法，**和相机位置撞在同一个点上** —— 这是双重错误（既抓错地方，又挡镜头）。

### 与固件现状的差异

| 差异 | 说明 |
|---|---|
| **抓取点必须是参数，不是常量** | `ec_motion_plan_build()` 要能分别接收**抓取点**和**落料点**两组坐标 |
| **要插一步"视觉确认"** | 现在固件里完全没有这一步 |
| **⑨ 回 HOME 之后要重新拍照** | 现在没有"到位 → 请求新图"的握手 |
| 步数从 7 步变成 9 步 | 多了"视觉确认"和"回到停放位"的组织性步骤 |

### ❌ 已否决的做法（用户 2026-09-15）

> "夹取完了之后放到那里之后，他再去看第二个……**他的这种精度要要求高一点点**。
> 所以说，**先别这样改**。"

即：**不做"不回停放位、直接看下一件"的优化**。
原因：机构停在落料盒附近时，画面里有夹爪/臂的遮挡与阴影，识别难度更大。

## 3. 🔴 前提阻塞：现在**做不到"请求一张新图"**

用户说："**在这之前，摄像头肯定是要先确认好第二个要抓取的物品是怎样的**"。

### 现状（实测）

`视觉/src/maixcam_deploy/main.py` 的主循环（L424-476）是**无条件的**：

```python
while not app.need_exit():
    frame = cam.read()
    objects = detector.detect(frame, ...)
    ...
    if objects:
        _send(encode_batch_targets(objects))    # 每帧都发
    display_obj.show(frame)
```

- MaixCAM **自己按节奏发**，不等树莓派要
- 树莓派的 `SocketVisionSource` **只接收**，没有"请你现在拍一张"的能力

### 后果（严重）

机构回到原点后，收到的可能是**几帧之前**的识别结果 ——
**那件货可能已经被抓走了**，或者画面里是已经搬走的位置。
→ **按旧坐标去抓 = 抓空**。

### 赛题 PDF 早就给了答案

`智能分拣装置方案与问题分析.pdf` §4「推荐协议：新请求、新图像、一次执行」：

> ① 树莓派准备处理下一件时生成 `request_id`；视觉端应使用**新采集图像**响应，
> 返回同一请求编号。无目标、推理失败也应返回明确状态。
>
> ② 只接受当前请求的有效结果。重复、过期、已完成任务和重启前会话的数据均拒绝。

**这就是时序 ③ 那一步的实现方式。**

### ✅ 已裁决 #3：**校赛不做高度补偿，拿实物直接标定**（2026-09-15）

用户原话：

> "**不用管物块的高度**，因为他校赛的时候我们这边也是**拿到准确物块**了的，
> 到时候我们就直接测试就行了。**等省赛的时候，我们需要去改一下**。"

| 阶段 | 做法 |
|---|---|
| **校赛** | ✅ **不做高度补偿**。手上就是比赛用的实物块，**直接拿实物标定托盘平面的映射**，"标出来的就是对的" —— 视差被实测吸收掉了 |
| **省赛** | 🔴 **必须回头改**。见下方挂账项 |

**为什么校赛可以这么做**：平面映射的误差来自"用托盘平面标定、却去抓有高度的顶面"。
但只要**标定和抓取用的是同一批实物、同一高度**，这个偏差就**恒定且被标定吸收**，
不会随机变化 —— 校准点位时抓偏了，手工修一下就行。
