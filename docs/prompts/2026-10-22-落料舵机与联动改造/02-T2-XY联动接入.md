# 二、为什么（用户原话）

> "我们还想 xy 轴可以一起动，不是 x 动 y 动这样的"

**现状问题**：现在搬运是"先走 X 到目标，再走 Y"，走的是直角折线。
改为联动后走**斜线**，两个效果：
1. **更快**（对角线比两段直角短）
2. **更平稳**（不用在拐角完全停住再启动）

# 五、具体步骤（按顺序做，别跳）

## 第一步：先让它**能编译**（不管功能）

1. 把 `ec_motion_plan_interp.c` 加进 `tests/CMakeLists.txt` 的某个测试目标，
   或者临时用 gcc 单独编译：
   ```powershell
   gcc -c -I App/Inc -I ../stm32_logic/include -I tests/host_stubs `
       -Wall -Wextra -Werror -pedantic App/Src/ec_motion_plan_interp.c
   ```
2. **大概率会报错**（这份文件从未编译过）。逐个修：
   - 缺 `#include`
   - 类型不匹配
   - 未使用变量（`-Werror` 会拦）
3. **修完必须零警告零错误**

> ⚠️ **不要改算法逻辑**。只修"让它能编译"的问题。
> 如果你认为算法本身有 bug，**写在报告里，不要自己改** —— 那是 Lead 和审查者判断的事。

## 第二步：确认驱动层能正确执行

读 `ec_axis_driver.c` 的这两处，确认 `EC_AXIS_STEP_XY_INTERP` 的**符号约定**：

```
L55:  /* Sign convention of EC_AXIS_STEP_XY_INTERP's signed step targets: a positive ... */
L119: } else if (s->kind == EC_AXIS_STEP_XY_INTERP) {
L282: } else if (s->kind == EC_AXIS_STEP_XY_INTERP) {
```

**必须确认**：`target_x_steps` / `target_y_steps` 传的是 **增量（signed increment）** 还是**绝对位置**。
`ec_axis_driver.h:224-225` 写的是：
```
int32_t target_x_steps;    /* XY_INTERP: signed X increment, steps */
int32_t target_y_steps;    /* XY_INTERP: signed Y increment, steps */
```
**⇒ 是增量。** 检查 `ec_motion_plan_interp.c` 里 `set_xy_interp()` 传的是不是增量，
**传错会导致走错方向或走错距离（可能撞限位）**。

## 第三步：接到应用层

在 `ec_app.c` 里，现在调用 `ec_motion_plan_build()` 的地方，
**增加一个可选走 `ec_motion_plan_build_interp()` 的路径**。

要求：
- **默认行为不变**（还是用旧的 `build()`），避免一上来就改变所有动作
- 增加一个**运行时可切的开关**（比如 `ec_app_set_use_interp(bool)`）
- 由 Lead 在 `ec_diag.c` 里加命令来切

## 第四步：给 Lead 提供命令规格

按总控 §4.2，你需要提供：

```
MOVE XY INTERP XDIR0|XDIR1 STEPS n YDIR0|YDIR1 STEPS m HZ f
  → Lead 据此在 ec_diag.c 里实现
```

并说明：
- 这个命令最终调用哪个函数
- 用了 interp 之后，**单件 cycle time 预估能省多少 ms**（如果有把握）
- 小行程（如 5mm）时会不会因为插补粒度问题丢步

# 八、你可能踩的坑

| # | 坑 |
|---|---|
| 1 | **`-Werror -pedantic` 很严** —— 未使用参数、隐式类型转换、C99 之外的东西都会报错 |
| 2 | **`EC_MOTION_XY_ORDER_X_FIRST` / `EC_MOTION_CARRY_LEG_Y_FIRST` 已存在**（`ec_motion_plan.h:261, 280`），**先看它们是不是就是你要的**，别重复造 |
