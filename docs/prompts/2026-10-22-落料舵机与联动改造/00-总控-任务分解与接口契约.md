> ## 🔴🔴【2026-10-22 DSH 更正】本节原写 `PSC=83` 是**错的**，正确是 `PSC=167`
>
> **错因**：我在下面照抄了 `main.c:221` 的原有注释「TIM9 **APB1** 预留 : 159 → 839」——
> **那条注释本身就是错的，TIM9 在 APB2 不在 APB1。**
>
> **证据**（我事后核实）：
> `Drivers/STM32F4xx_HAL_Driver/Inc/stm32f4xx_hal_rcc.h` 里
> `__HAL_RCC_TIM9_CLK_ENABLE()` → `SET_BIT(RCC->**APB2ENR**, RCC_APB2ENR_TIM9EN)`
> ⇒ **TIM9 在 APB2**，APB2 定时器时钟 = **168 MHz**（不是 APB1 的 84 MHz）。
>
> | 项 | 我原写（错） | **正确值** |
> |---|---|---|
> | 总线 | APB1 | **APB2** |
> | 定时器时钟 | 84 MHz | **168 MHz** |
> | Prescaler（要 1 MHz） | 83 | **167**（168/168 = 1 MHz） |
> | Period | 19999 | 19999（不变） |
>
> **Codex 在 T1 中发现了这个错误并用了正确值 `Prescaler = 167`，实现已核实无误。**
>
> **附带发现**：原 `Prescaler = 839` 在 168 MHz 下实际是 **200 kHz**，不是注释说的 100 kHz。
> 因为 TIM9 一直没用过，这个错误从未暴露。

**TIM9 现状**（`Core/Src/main.c:560-577`，⚠️ 原注释的总线写错了）：
```c
htim9.Init.Prescaler = 839;     // 原注释写"84MHz/840=100kHz"，实际 TIM9 在 APB2 ⇒ 168MHz/840 = 200kHz
htim9.Init.Period    = 9999;    // 200kHz/10000 = 20Hz  ← 太慢，舵机要 50Hz
// CHANNEL_1 = PE5（stm32f4xx_hal_msp.c:277 "PE5 ------> TIM9_CH1", AF3_TIM9）
```

**⇒ 必须把 TIM9 改成 50Hz**（**正确值**）：
```c
htim9.Init.Prescaler = 167;     // 168MHz/168 = 1MHz  → 分辨率 1µs（APB2！不是 84MHz）
htim9.Init.Period    = 19999;   // 1MHz/20000 = 50Hz
```
（TIM2 夹爪是 APB1、84MHz、PSC=83；**TIM9 是 APB2、168MHz、PSC=167** —— 两者数值不同，别照抄）

> ⚠️ **改 Prescaler/Period 会同步改 `htim9.Init.Period` 这个"最大值"判断**，
> barrier 那边用的是 `htim3.Init.Period`，**不冲突**；但 `ec_board_stm32.c:619`
> 有 `pulse_us > htim3.Init.Period` 的校验，**那是 htim3，不是 htim9，别误改**。

## 2.4 夹取时序：瓶颈在 5 个舵机步

**`App/Inc/ec_axis_driver.h`**：

| 常量 | 值 | 说明 |
|---|---|---|
| `EC_AXIS_GRIPPER_SETTLE_MS` | **600** | **每次**发完舵机脉宽后等这么久 |
| `EC_AXIS_SERVO_SETTLE_MS` | = 上面那个 | 别名 |
| `EC_AXIS_PICK_DWELL_MS` | 200 | 取料位停留 |
| `EC_AXIS_PICK_PLACE_STEP_COUNT` | **13** | 整个 pick-place 的步数 |

**舵机步（5 个）**：`[0]待机625` → `[3]类别张开` → `[5]闭合` → `[8]释放` → `[9]待机625`

**⇒ 5 × 600ms = 3.0 秒/件 纯等待。** 这是 R4 的主目标。

**时间预算**（`ec_axis_driver.h:201` 注释）：单件 **14.16s**，15s 失活窗口，**真实余量只剩 0.84~2.0s**。
