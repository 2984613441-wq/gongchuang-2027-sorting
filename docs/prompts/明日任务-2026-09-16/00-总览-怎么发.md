## 2. 依赖顺序（别搞反）

```
P1 (Keil 能编过) ────→ 一切实机验证的前提。**最急，先做。**
       │
P7 (引脚残留/挡板清理) ─→ 与 P1 同属"让固件干净可编"，可并行
       │                  ⚠️ 但 P7 要核实一条"取消挡板后一上电就 FAILED"的风险

P2 (抓取点语义) ─────→ 改代码；**要 P1 修好才能上机验证**
       └────────────→ P3 (协议方案B) 必须建立在 P2 的结论上
                       P3 选命令字要用 **P8 的"已用命令字表"**

P8 (协议清理) ───────→ 独立，且**是 P3 的前置输入**（命令字表）

P6 (颜色/模型) ──────→ 独立，纯调查+裁决
P10 (数据集) ────────→ 独立；**数据泄漏判定是 P6 的输入**（决定 mAP 0.865 可不可信）

P9 (配置一致性) ─────→ 独立，纯排查+修正
P11 (链路接线/看门狗) ─→ 独立，设计为主

P4 (Z 脉宽) ─────────→ 需硬件 + L4 授权
P5 (屏幕显示) ───────→ 需树莓派
```

**明天建议的开工顺序**：
`P1 + P7（并行，让固件能编）→ P8 + P10（并行，纯调查，产出 P3/P6 的输入）→ P2 → P3 → P6 → P9 → P11`，
`P4/P5` 等有硬件时做。

## 5. 铁律（每个 AI 的交付里必须体现）

1. **不要把自己的主机测试说成实机通过**
2. **执行者不做自己的复核** —— 复核者要么用不同模型，要么至少用不同会话
3. **不确定就写不确定**，宁可写"未验证"
4. **发现问题写出来，不要顺手改别的**（每个问题边界清楚，别越界）
5. **L4 红线**：I/O 映射 / 模型权重 / 机械图纸 / **系统间通信协议** / 任何上电 —— 都要用户批准
