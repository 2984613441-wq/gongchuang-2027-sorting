## 1. 输入事实（已核实，直接用，不要重新查）

### 1.1 为什么需要方案 B

- 赛题：**货物位置随机、不可触碰** → **抓取点每件不同**
- 六个盒子固定 → **落料点固定**
- 固件现状：**抓取点写死 (0,0)**、落料点是参数 → **反了**（见 `抓取时序` §1）
- **用户已选定方案 B**：`ITEM_TASK` **同时携带两组坐标**

### 1.2 为什么需要 `request_id`

- MaixCAM 的 `main.py`（`视觉/src/maixcam_deploy/main.py:424-476`）是**每帧无条件发**
- 树莓派的 `SocketVisionSource` **只能收、不能请求**
- → 机构回到停放位后，收到的可能是**几帧前**的结果，**那件货可能已经被搬走**
- → **按旧坐标去抓 = 抓空**

**PDF §4 早就给了答案**：
> ① 树莓派准备处理下一件时生成 `request_id`；视觉端应使用**新采集图像**响应，
> 返回同一请求编号。无目标、推理失败也应返回明确状态。
> ② 只接受当前请求的有效结果。重复、过期、已完成任务和重启前会话的数据均拒绝。

## 3. 你要设计的②：`request_id` 握手

### 需要设计的契约

```
树莓派                                MaixCAM
   │  「我要新的一批」─── REQUEST ──→  │
   │                                   │  ① 丢掉手上的旧结果
   │                                   │  ② 采一张【新图】
   │                                   │  ③ 推理
   │  ←── BATCH_TARGETS(req=42) ────── │  ④ 带上同一个 request_id
   │  只有 req==42 才接受               │
```

### 你必须回答

| # | 问题 |
|---|---|
| a | **走哪条链路？** 生产通道 8765 双向？还是复用 9001/9002 监控口？（**监控口是只读旁路，别把生产依赖压上去**） |
| b | **命令字放哪？** 现有命令字表里有没有空的？会不会又撞号（前车之鉴 **E-10**：`0x20` 撞 `BARRIER_READY`） |
| c | **`request_id` 放哪？** `BATCH_TARGETS` 里加字段，还是复用现有 `task_id` / `frame_seq`？<br>⚠️ 注意 `main.py` 里已经有 `TASK_ID` 和心跳帧的概念 |
| d | **超时怎么办？** 树莓派发请求后多久没结果就放弃？（赛题红线：**15 秒不动作本轮结束**） |
| e | **重试几次？** 拒绝重复/过期结果（PDF §4 ②） |
| f | **请求期间 MaixCAM 还发不发无条件帧？** 若继续发，树莓派必须**只认 req 匹配的那条** |
| g | **`.mud` 模型的推理耗时**会不会让"请求-响应"超过节拍预算？**没数据就写"未测"** |

## 4. 🔴 你必须做的风险审查

1. **这次改动会不会把"只读旁路"变成"生产依赖"？**
   （监控口 9001/9002 现在断了也不影响比赛 —— 加了握手会不会破坏这个性质？）

   **必须 fail-closed 还是可以降级？**
3. **和 E-10 的教训对照**：上次撞号是怎么发生的？这次如何**保证不再撞**？
   （建议：列一张**全部已用命令字**的表，标出空闲值）
4. **这两个改动能不能拆开上线？**
   （P2 只改抓取点语义就能让"不再抓空"吗？还是**必须有握手**才算安全？）
