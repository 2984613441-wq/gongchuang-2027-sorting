# 协议影响分析：本轮改动需要动哪些协议（2026-11-01）

> 触发：用户问"我们改动了这么多，后面协议要改啥"。
> 本文只做**协议层**影响分析（wire format / 编码口径 / 文档冻结状态），不改代码。
> 权威文档：`docs/design/interface-contract.md`（**V0.9**，外层帧 version 字节 = `0x01`）。

---

## 一、涉及的三条链路（先说清边界）

| 链路 | 报文 | 冻结状态 | 本轮是否受影响 |
|---|---|---|---|
| MaixCAM → 树莓派 | `BATCH_TARGETS`（3 字节头 + N×7 字节）| §5.1 已冻结 | **受影响（P0）** |
| 树莓派 → STM32 | `ITEM_TASK`（0x21，12 字节载荷）| §5.2 已冻结（2026-09-16 扩到 12B）| **受影响（P0/P1）** |
| STM32 → 树莓派 | `ACK/NACK`、`MOTION_DONE`、`PROGRESS` | 已冻结 | 轻微（步号语义） |
| 台架调试（UART2 diag） | `ZPOS` / `SLOT` / `DROP` / `SERVO` … | 非生产协议 | 本轮**已加** ZPOS/SLOT，无需再改 |

## 二、影响矩阵

### P0-1 `BATCH_TARGETS` 的 id 字节语义 + **颜色来源缺失**（最要紧）

现状（代码事实）：

* 线格式每目标 7 字节：`id_byte(1) + conf(1) + X(2,BE) + Y(2,BE) + angle(1)=0xFF`，**没有独立颜色字段**。
* 生产解析把 `id_byte` 当 **box_id(1..6)** 用：`rpi/vision_ingest.py:52` `BATCH_ID_BYTE_IS_BOX_ID = True`。
* 该文件自己写明：切到"形状模式"**会让每一件都出不了货**（box_id 留 None ⇒ `_expand()` 全拒识），
  必须先补 **class_id → box_id 的映射（颜色/形状联合判定）**（`vision_ingest.py:37-52`）。
* 而我们现在的主相机发送端发的是 **shape_id = class_id + 1（1..6）**，**不含颜色**
  （`_pi_tools/maixcam_scripts/yolo_v11_send.py:22,57,150`，脚本自己都打印"不是正式 code(1..30)"）。

⇒ **协议层面必须定一件事：颜色从哪来。** 两条路：

| 方案 | 做法 | wire 是否变 | 代价 |
|---|---|---|---|
| **A（推荐）** | 保持 7 字节；`id_byte` **正式定义 = shape_id(1..6)**；Pi 用**副相机 HSV 判色**得到 color ⇒ `code=(shape-1)*5+color+1` ⇒ 再映成落点/box | **不变** | Pi 侧新增映射 + "颜色判不出⇒该件待定/隔离"；副相机必须真接进链路（现在只在电脑侧 demo） |
| B | 扩 8 字节（加 color 或 code） | **变** | 两端必须同时升级；`data_len` 精确匹配 ⇒ 旧固件/Pi 会静默拒收 |

### P0-2 `ITEM_TASK.class_id` 的取值域没写清

* 文档只写 `class_id(1)`，**没规定域**（1..6 形状？1..30 code？）。
* 实现里 `ACTIVE_CLASS_IDS = frozenset({0,2,3,4,5,6})`（0-based 且**缺 1**），与"1..30 code"口径不一致。
* 本轮之后必须**冻结一种口径**并写进 interface-contract：
  * 若走方案 A：`class_id = code(1..30)`，`box_id` 由 `[BoxMap]` 查表得出；
  * 或明确定义 `class_id = shape(1..6)` + `color` 另立字段（那就变成方案 B）。

### P1-1 逐件运动参数（Z 取/放高度、夹爪开度、槽门时序）

新增硬件后，一件要被夹需要 3 组参数（Z 取件高度 / Z 放件高度 / 夹爪闭合开度），
另外槽门开合由固件 15 步程序负责。

* 现 `ITEM_TASK` 12 字节里 **没有**这些字段（只有目标序号、class_id、image_id、落点 XY、角度、抓取点 XY）。
* 两条路：

| 方案 | 做法 | wire 是否变 | 备注 |
|---|---|---|---|
| **A（推荐）** | **固件按 class_id 查表**（6 类或 30 code 各 3 个 µs），Pi 不传 | **不变** | 需固件新增参数表；现场标定后改表即可，不动协议 |
| B | `ITEM_TASK` 12 → 18/20 字节，尾部追加 `z_pick(2)+z_place(2)+grip_close(2)` | **变** | 破坏性：`data_len != 12` 会被**静默拒收**，两端必须同时升级；version 字节是否 0x02 需决策 |

### P1-2 15 步 v2 程序 ⇒ 步号语义

* 新程序 15 步（原串行 12 步 / 插补 9 步）。
* `PROGRESS`/`MOTION_DONE` 的字段宽度够（1 字节），**协议字段不用改**；
  但**任何按步号写死的断言/日志判断需要同步**（Pi 侧与测试）。

### P2 不需要改协议的（登记，防误改）

| 项 | 原因 |
|---|---|
| 五键排序 / 停稳 / 隔离度 / 落点锚点 | 全在 Pi 内部决策，不上 wire |
| 双相机 CONFIRMED/CONTRADICTED/UNPROVEN | Pi 内部闭环；除非要让 STM32 知道"隔离件"，才需新增字段/原因码 |
| 相机像素域 1280×720 | XY 字段 2 字节足够（0..65535）；只需重标定 + 配置里锁定 `frame_width/height` |
| `ZPOS` / `SLOT` 台架命令 | diag 通道，非生产协议（本轮已加） |
| 2 路补光灯 `LIGHT/LIGHT2` | diag 通道，已存在 |

## 三、推荐的最小改动路径（wire 完全不变）

```
① 冻结 BATCH_TARGETS：id_byte 正式定义为 shape_id(1..6)  ← 改文档 + Pi 侧映射
② 颜色来源：副相机判色（HSV），Pi 内部算出 code(1..30) → [BoxMap] → 落点
   颜色判不出 ⇒ 该件进"待定"（不派件），不猜
③ 逐件运动参数：固件按 class_id 查表（Z 取/放 / 夹爪开度），ITEM_TASK 保持 12 字节
④ 15 步步号：只改 Pi 侧断言/日志，协议字段不动
⑤ 文档升版：interface-contract 从 V0.9 → **V1.0**，逐条写清 ①②③ 的冻结口径
```

**代价**：wire 零变化 ⇒ 不会出现"两端必须同时升级、否则静默拒收"的事故；
**风险**：颜色判错的件会进待定（可用副相机三态判决兜住），且固件参数表要随件更新。

## 四、如果选"扩协议"（B 路线）的后果（如实列出）

1. `BATCH_TARGETS` / `ITEM_TASK` 任一处变长 ⇒ 对端 `data_len` 精确匹配会**静默拒收**，联调时极易误判为"机构坏了"（文档 §5.2 已警告过 8→12 字节那次）。
2. 外层帧 `version` 字节要不要升 `0x02`：升了则旧固件全拒；不升则版本号与实际格式不符，属于自欺。
3. 必须同时升级：MaixCAM 脚本、Pi 代码、STM32 固件三处，且**回滚要三处一起回**。
4. 好处：逐件参数可以按"现场实测"直接随件下发，不必改固件。
