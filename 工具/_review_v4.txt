1. 正确语义映射
[代码/实测证据]
P1000 = 张开
P1500 = 中位
P1900 = 闭合
现场目视：P1000/P1100 位于抬起侧，P1900 位于下压侧。
现有注释把 1100 写成“下降+张开”、把 1900 写成“上升+闭合”，与新硬件事实相反。
[推断]
在当前语义下：
动作
脉宽
上升 + 张开
P1000
下压 + 闭合
P1900
中间状态
P1500
P1100
开侧中间值，不能自动等同于完整上升
因此现有宏应改为：
/* ec_axis_driver.h: 当前脉宽定义块，约第 59-67 行，整体替换 */
#define EC_AXIS_GRIPPER_OPEN_US   UINT16_C(1000)
#define EC_AXIS_GRIPPER_CLOSE_US  UINT16_C(1900)
/* 单舵机联动：open = up，close = down */
#define EC_AXIS_Z_UP_US            EC_AXIS_GRIPPER_OPEN_US
#define EC_AXIS_Z_DOWN_US          EC_AXIS_GRIPPER_CLOSE_US
也就是：
#define EC_AXIS_Z_DOWN_US UINT16_C(1900)
#define EC_AXIS_Z_UP_US   UINT16_C(1000)
你方原有推理错误是把旧机构的“开/关—升/降”关系带到了新机构。P1100 不能因为“看起来在抬起侧”就直接作为 Z_UP_US；除非实测确认它是所需安全上限。
另外，所谓“六个定值”与列出的实际值不一致：1000、1100、1200、1300、1500、1700、1900 一共是七个。
2. 现有两次 Z 动作不成立
[代码/实测证据]
当前每个位置使用：
append_z_servo(out, &amp;next_step, EC_AXIS_Z_DOWN_US);
append_z_servo(out, &amp;next_step, EC_AXIS_Z_UP_US);
交换宏后，实际变成：
P1900：下压 + 闭合
P1000：上升 + 张开
[推断]
取料所需状态是：
上方 + 张开
↓
下降 + 张开
↓
下降 + 闭合
↓
上升 + 闭合
但当前单舵机只提供：
P1000 = 上升 + 张开
P1900 = 下降 + 闭合
缺失两个关键状态：
下降 + 张开
上升 + 闭合
所以：
在取料点执行 P1900 → P1000：会下压闭合，随后上升时张开，无法保持物体。
在放料点执行 P1900 → P1000：会下压闭合，随后上升张开，不能按“下降放下→张开”完成可靠释放。
增加更多相同的 Z down/Z up 重复，也不能增加自由度。
正确的逻辑序列应是：
UP_OPEN
→ XY_PICK
→ DOWN_OPEN
→ CLOSE_AT_PICK
→ UP_CLOSED
→ XY_PLACE
→ DOWN_CLOSED
→ OPEN_AT_PLACE
→ UP_OPEN
但 DOWN_OPEN 和 UP_CLOSED 在当前硬件定义下没有可用脉宽。因此，严格按你给出的事实，不存在可直接写入软件的正确脉冲序列。
唯一可能的软件替代方案是存在经过验证的机械锁存/凸轮机构，例如：
P1000：上升、张开
→ XY 到取料点
P1900：下压、闭合
→ 机械锁存保持闭合，停止 PWM
→ XY 到放料点
P1000：上升、张开并释放
这只是“有机械锁存且已验证”时的条件方案，不是现有事实下的默认方案。
建议先加入安全门，未完成机械验证时拒绝生成计划：
/* ec_axis_driver.h：配置区新增 */
#define EC_Z_PICK_PLACE_VALIDATED 0
/*
* 只有同时满足以下条件后才可改为 1：
* 1. 已证明单舵机机构存在可用的携物状态；
* 2. 已证明掉电不会造成危险掉落，或已有机械防坠/锁爪；
* 3. 已完成新结构的脉宽和时序标定。
*/
/* ec_motion_plan.c：ec_motion_plan_build() 中
* if (out == NULL) return false; 之后插入，约第 108-110 行 */
if (out == NULL) {
return false;
}
#if !EC_Z_PICK_PLACE_VALIDATED

* 当前单自由度联动机构无法表达：
* DOWN+OPEN 与 UP+CLOSED。
* 安全地拒绝生成“看似成功、实际不能取放”的计划。
*/

这会使现有主机测试中的“计划构造成功”断言必须改成“未验证时拒绝”。

等待时间估算：
T_wait = ceil(t99 / 20 ms) × 20 ms + 安全余量
其中：
t99：在最大负载、最低允许电压、最不利温度下，脉宽改变到机构稳定的 99% 分位时间；
20 ms：50 Hz PWM 的一个周期；
安全余量建议先取 20%～30%，再由实测修正。
若使用舵机规格书速度：
t_move ≥ |Δ角度| / 最低速度
但 PWM 到角度通常不是线性的，最终仍应以实测为准。总预算应检查：
总耗时 =
XY 运动时间
+ 舵机步骤数 × 单步等待时间
+ PWM 周期量化延迟
+ 安全余量

5. 失电掉落风险
[推断]
普通 PWM 舵机失电后通常不再提供保持扭矩。你没有提供机械自锁、刹车、配重或防坠结构证据，因此必须按“可能掉落”处理。
计划层不能真正解决突然断电问题。应至少满足：
机械上增加防坠/锁爪/自锁；
未验证防坠前保持 EC_Z_PICK_PLACE_VALIDATED == 0；
不把携物路径布置在人、树莓派或易损件上方；
急停、欠压、复位时都按“物体可能立即掉落”设计；
SERVO STOP 与“切断舵机电源”不能被误认为安全保持。
6. 其它风险
[代码/实测证据或推断]
PB10/TIM2_CH3 必须统一出现在启动、停止和急停路径；任何残留的 PB11/TIM2_CH4 都可能导致“命令发出但急停停不掉”。
ec_diag 的白名单实际列出七个脉宽，不是六个；应统一代码、注释和测试。
P1500 只是中位，不应默认当作安全高度、保持位或释放位。
append_z_servo() 目前没有位置反馈，完成只能表示“等待时间已到”，不能表示“舵机已到位”。
无 Z 限位/位置反馈时，机械端点碰撞只能靠脉宽和时间规避。
供电压降、堵转电流和舵机发热可能造成 STM32 复位或 PWM 异常。
如果增加 DOWN_OPEN、UP_CLOSED 等步骤，固定数组容量和测试中的“10 个已用步”都需要重新核对。
任何“主机测试通过”都不能证明舵机方向、夹持力、到位时间或掉电安全已通过实机验证。

🔴 核心问题：开机默认 AF7 的隐患
问题场景：ec_board_enter_safe_state() 在系统初始化、急停、错误恢复时被调用。
// ec_board_stm32.c:166-176
void ec_board_enter_safe_state(void)
{
ec_step_port_stop_all();
ec_barrier_port_stop();
ec_servo_port_stop();  // 调用 HAL_TIM_PWM_Stop(&amp;htim2, TIM_CHANNEL_3)
(void)HAL_TIM_PWM_Stop(&amp;htim2, TIM_CHANNEL_4);
ec_step_port_disable_all();
HAL_GPIO_WritePin(LIGHT_EN_GPIO_Port, LIGHT_EN_Pin, GPIO_PIN_RESET);
}
隐患链条：
上电后 → HAL_UART_MspInit(USART3) 把 PB10 配为 AF7
若系统在 首次 ec_servo_port_start() 之前 遇到急停或错误 → 调用 ec_board_enter_safe_state()
ec_servo_port_stop() 内部调用 HAL_TIM_PWM_Stop(&amp;htim2, TIM_CHANNEL_3)
但此时 PB10 仍是 AF7（USART），不是 AF1（TIM2） → PWM Stop 操作的硬件对象不存在
HAL 库内部写 TIM2_CH3 的 CCR/CCER 寄存器 → 无效操作，引脚保持 UART 高电平或不确定状态
影响评估：
轻度：PWM 未正确停止，舵机可能收到噪声脉冲（不太可能，因为 UART 模式下 TIM2 根本不连接到引脚）
中度：HAL 库内部状态机混乱（htim2.State 与实际不符）
重度（推断）：若系统假定&quot;调用了 stop 就安全了&quot;，但舵机实际未受控 → 紧急状态下舵机仍可能意外动作
二、运行时切换实现的技术评估
假设不回退，评估当前实现是否稳健。
✅ 切换顺序正确性
// ec_board_stm32.c:198-213
static void grip_pin_select(uint8_t alternate)
{
GPIO_InitTypeDef g = {0};
if (alternate == GPIO_AF7_USART3) {
(void)HAL_TIM_PWM_Stop(&amp;htim2, TIM_CHANNEL_3);   // ✅ 离开 PWM 前先停止
}
// ... 重新配置引脚
}
评估：
✅ 从 PWM → USART 时，先 HAL_TIM_PWM_Stop，避免切换瞬间 TIM2 仍在输出
⚠️ 从 USART → PWM 时，无对应的&quot;先停 UART TX&quot;操作 → 但 UART TX 在空闲时本就是高电平，影响较小
⚠️ 切换瞬间的毛刺风险
理论分析：
PWM → USART：HAL_TIM_PWM_Stop 后，引脚进入默认状态（通常是浮空或上拉）→ 重新配为 AF7 → 变为 UART TX 空闲高电平
风险：浮空期间若引脚电平不确定，舵机可能误读为短脉冲
USART → PWM：UART TX 空闲高电平 → 切为 AF1 → TIM2 启动 PWM
风险：HAL_GPIO_Init 完成到 HAL_TIM_PWM_Start 之间，引脚可能短暂保持高或浮空
实测建议：
用示波器抓 PB10 波形，观察切换瞬间是否有 宽度 &gt;20μs 的异常脉冲（舵机响应阈值）
若有毛刺，应改为：
// 先设为通用输出推挽低，再切 AF，最后启动外设
HAL_GPIO_WritePin(GPIOB, GPIO_PIN_10, GPIO_PIN_RESET);
GPIO_InitStruct.Mode = GPIO_MODE_OUTPUT_PP;
HAL_GPIO_Init(GPIOB, &amp;GPIO_InitStruct);
// 再切 AF
GPIO_InitStruct.Mode = GPIO_MODE_AF_PP;
GPIO_InitStruct.Alternate = ...;
HAL_GPIO_Init(GPIOB, &amp;GPIO_InitStruct);
🚨 启动时一次性确定模式 vs 运行时切换
当前方案的根本问题：每次调用都切换，即使 99% 的场景只用 PWM。
改进方案：

#define GRIP_MODE_PWM    0
#define GRIP_MODE_BUS    1
static uint8_t grip_mode = GRIP_MODE_PWM;  // 编译时或运行时配置
void ec_board_init_grip_mode(uint8_t mode) {
grip_mode = mode;
if (mode == GRIP_MODE_PWM) {
grip_pin_select(GPIO_AF1_TIM2);
} else {
// PB10 已在 USART3_MspInit 配为 AF7，无需再配
}
}
优势：
启动后不再切换 → 无毛刺风险
代码清晰：ec_servo_port_start() 不需检查模式
用户通过跳线或配置选择模式（不用重烧固件）

三、赛规合规判断
3.1 赛规原文
依据：27年工创.pdf P12（国赛）、规则/2026年四川省…项目II-2.pdf（省赛）
原文（推断，基于你的背景描述）：
&quot;超过 15 秒没有动作或没有显示本次分拣信息，本轮比赛结束&quot;
关键词：
&quot;没有动作&quot; = 无可观察执行器输出
&quot;没有显示&quot; = 屏幕未刷新结果
&quot;或&quot;关系：任一条件达成即触发
3.2 原意推断（标为推断）
推断 A：15 秒是&quot;失活判定窗口&quot;，不是&quot;单件完成时限&quot;
依据：赛题不说&quot;单件必须 15 秒内完成&quot;，而是&quot;15 秒没动作&quot;
含义：只要系统持续有可观察进展，就不触发
推断 B：&quot;可观察动作&quot;的赛规定义
机械级可观察：电机转动、夹爪开合、挡板移动——外部可见
不包括内部计数：脉冲发送、步数计数、内存状态——外部不可见
不包括通信心跳：UART 包、日志打印——与物理动作无关
推断 C：赛规初衷是防僵死，不是&quot;限速&quot;
场景：电机卡死、程序死锁、传感器失灵 → 15 秒无动作 → 强制结束保护设备
场景：正常慢速运动（如 30 秒缓慢移动一个长距离）→ 只要持续移动就不触发
关键区分：15 秒是&quot;静默超时&quot;，不是&quot;单件耗时上限&quot;

/* 估算单个段的梯形运动耗时（毫秒）。
* 公式：T = T_accel + T_cruise + T_decel
*      T_accel = 2 * accel_steps / (start_hz + peak_hz)
*      T_cruise = cruise_steps / peak_hz
*      T_decel  = 2 * decel_steps / (peak_hz + end_hz)
* 返回值：毫秒（向上取整）；失败返回 0。
*/
static uint32_t estimate_segment_duration_ms(uint32_t steps,
uint32_t start_hz, uint32_t cruise_hz, uint32_t end_hz,
uint32_t accel_hz_per_s, uint32_t decel_hz_per_s)
{
ec_step_profile_t profile;
uint64_t t_accel_us, t_cruise_us, t_decel_us;
uint32_t peak_hz;
if (!ec_step_profile_plan(&amp;profile, steps, start_hz, cruise_hz, end_hz,
accel_hz_per_s, decel_hz_per_s)) {
return 0U;
}
peak_hz = profile.cruise_hz;
/* 加速段平均速度 = (start_hz + peak_hz) / 2
* 时间 = 步数 / 平均速度（单位：秒） = 步数 * 2 / (start_hz + peak_hz)
* 转微秒：* 1000000 */
if ((start_hz + peak_hz) &gt; 0U) {
t_accel_us = ((uint64_t)profile.accel_steps * 2U * 1000000U) /
(uint64_t)(start_hz + peak_hz);
} else {
t_accel_us = 0U;
}
/* 巡航段：步数 / 频率（秒） * 1000000 */
if (peak_hz &gt; 0U) {
t_cruise_us = ((uint64_t)profile.cruise_steps * 1000000U) / (uint64_t)peak_hz;
} else {
t_cruise_us = 0U;
}
/* 减速段平均速度 = (peak_hz + end_hz) / 2 */
if ((peak_hz + end_hz) &gt; 0U) {
t_decel_us = ((uint64_t)profile.decel_steps * 2U * 1000000U) /
(uint64_t)(peak_hz + end_hz);
} else {
t_decel_us = 0U;
}
/* 转毫秒（向上取整） */
return (uint32_t)((t_accel_us + t_cruise_us + t_decel_us + 999U) / 1000U);
}
/* 估算完整 pick-place 程序的总耗时（毫秒）。
* 包含 XY 运动（按单轴最大步数计）+ Z 舵机动作（4 次 × 200ms）。
* 返回值：毫秒；失败返回 0。
*/
uint32_t ec_motion_plan_estimate_duration(const ec_axis_pick_place_t *program)
{
uint32_t total_ms = 0U;
uint32_t segment_ms;
uint32_t max_steps;
size_t i;
if (program == NULL) {
return 0U;
}
for (i = 0U; i &lt; program-&gt;num_steps; ++i) {
const ec_axis_program_step_t *step = &amp;program-&gt;steps[i];
if (step-&gt;type == EC_AXIS_STEP_XY_MOVE) {
/* XY 并行运动：取单轴最大步数 */
max_steps = (step-&gt;x_steps &gt; step-&gt;y_steps) ? step-&gt;x_steps : step-&gt;y_steps;
/* 使用硬编码的梯形参数（与 ec_board_stm32.c:146 一致）*/
segment_ms = estimate_segment_duration_ms(max_steps,
200U, 2000U, 200U,  /* start, cruise, end */
5000U, 5000U);      /* accel, decel */
if (segment_ms == 0U) {
return 0U; /* 规划失败 */
}
total_ms += segment_ms;
} else if (step-&gt;type == EC_AXIS_STEP_Z_MOVE) {
/* Z 舵机占位：200ms（待实测） */
total_ms += 200U;
}
}
return total_ms;
}

resolved_prefix = str(Path(prefix).resolve())

)
